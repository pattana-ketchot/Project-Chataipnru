# ตัวสำรองในเครื่องล้มทุกครั้ง — สาเหตุที่พิสูจน์ได้ และสิ่งที่แก้

วันที่ 28 ต.ค. 2569 · ฐานโค้ด: `mko-phase2` (4d7a5a5) · **ยังไม่ deploy · ไม่แก้การตั้งค่า production · ไม่เกี่ยวกับงานสวิตช์เลือกโมเดล**

ทดสอบบนเครื่อง local ทั้งหมด (HTTP จำลอง + Ollama ในเครื่อง) ไม่ยิงคำขอใส่ production ไม่แตะฐานข้อมูล production

---

## 1. สาเหตุที่พิสูจน์ได้: ตัวสำรองไม่เคยได้ยิงคำขอไป Ollama เลย

เพดานเวลารวมต่อคำขอเป็น **ค่าเดียวที่ทุกขั้นใช้ร่วมกัน** (`RAG_TIME_BUDGET_S` = 30 วินาที · `llm/connector.py`)
และเจ้าหลักมีสิทธิ์ใช้มันจนหมดเอง:

- `GeminiConnector._models_to_try()` ไล่โมเดลสำรอง และ **นอนรอให้โมเดลพ้นช่วงพัก** ได้ถึง
  `max_cooldown_wait_s` = 75 วินาที โดยมีเพดานเวลารวมเป็นตัวตัด
- ช่วงพักของเพดานต่อนาทีคือ `_MINUTE_COOLDOWN_S` = 45 วินาที ซึ่ง **มากกว่าเพดานรวม 30 วินาทีอยู่แล้ว**
  การนอนรอจึงไม่มีทางสำเร็จ มันทำได้แค่กินเวลาที่เหลือทั้งหมดแล้วโยน `LLMBudgetExceeded`
- `LLMBudgetExceeded` เป็นลูกของ `LLMConnectionError` → `_SplitConnector.chat()` ดักได้ตามปกติ
  แล้วส่งงานต่อให้โมเดลในเครื่อง
- โมเดลในเครื่องเข้า `post_json_bounded()` → `http_timeout()` → `check_budget()` ซึ่ง **โยนทิ้งทันที**
  เพราะเวลาเหลือศูนย์ และข้อผิดพลาดนี้ไม่ใช่ `httpx.TimeoutException` จึงไม่เข้าลูป retry ด้วย

ผลคือ `fallback_local_attempt` เพิ่มขึ้นหนึ่ง แล้ว `fallback_local_failed` เพิ่มขึ้นหนึ่งทันที
**โดยไม่มีไบต์ใดออกไปถึง Ollama เลย** ซึ่งตรงกับตัวนับของ production ที่ 10 ต่อ 10 พอดี

ยืนยันด้วยชุดทดสอบใหม่ `backend/tests/test_local_fallback_gets_time.py` ก่อนแก้:

```
[ตก] ตัวสำรองได้ยิงคำขอจริง — ยิงไป 0 ครั้ง · err=LLMBudgetExceeded: ... (ขั้นที่กำลังทำ: เรียกโมเดลในเครื่อง /api/chat)
[ตก] ตัวสำรองได้เวลาไปใช้มากกว่าศูนย์ — เหลือ 0.00 วินาทีตอนถูกเรียก
[ตก] นับว่าตัวสำรองตอบสำเร็จ — {'fallback_local_attempt': 1, 'fallback_local_failed': 1}
```

### ทำไมชุดทดสอบเดิมมองไม่เห็น

ตัวแทนเจ้าหลักในชุดทดสอบเดิม (`AllModelsDown` ใน `test_model_outage_n1.py`) **โยนข้อผิดพลาดทันทีโดยไม่กินเวลา**
ตัวสำรองจึงได้เพดานเวลาเต็ม 30 วินาทีไปใช้ ซึ่งไม่ใช่สิ่งที่เกิดจริง — ของจริงเจ้าหลักกินเวลาไปก่อนแล้วจึงล้ม
ชุดใหม่จึงเลียน "กินเวลาจนหมดเพดานแล้วค่อยล้ม" และตรวจว่า **มีคำขอ HTTP ออกไปจริงหรือไม่** ไม่ใช่ตรวจแค่ว่าเดินเส้นทางถูก

## 2. ข้อที่ตั้งไว้แต่ไม่ใช่สาเหตุ: `num_predict` ของด่านตรวจหลักฐาน

สมมติฐานเดิมคือ ด่านตรวจไม่ส่ง `num_predict` → ผลลัพธ์ยาวไม่จำกัด → 160 วินาที
วัดแล้ว **ไม่ใช่** — ด่านนี้เขียนผลลัพธ์สั้นมากอยู่แล้ว เพราะพรอมต์สั่งให้ตอบ JSON หนึ่งถึงสองประโยค

วัดด้วย `qwen2.5:3b` ของ Ollama ในเครื่อง พรอมต์จริงของด่านตรวจ (25 ชิ้น รูปแบบเดียวกับ `_format_chunks`)
เนื้อหาจาก `samples/web/ph_web.txt` · 7 คำถามคนละแบบ:

| | โทเคนเข้า | โทเคนออก |
|---|---|---|
| 7 คำถาม (วิชาบังคับ หน่วยกิต อาชีพ เรียนอะไร ค่าเทอม นอกเรื่อง เปรียบเทียบ) | 12,418–13,047 | **46–174** |

บังคับให้รันบน CPU (`num_gpu: 0` · ยืนยันด้วย `/api/ps` ที่รายงาน `size_vram = 0`) เพื่อให้เทียบสัดส่วนกับเซิร์ฟเวอร์ที่ไม่มีการ์ดจอได้:

| รอบ | ตัวอักษร | โทเคนเข้า | โทเคนออก | อ่านพรอมต์ | เขียนผลลัพธ์ | รวม |
|---|---|---|---|---|---|---|
| 25 ชิ้น ไม่จำกัดผลลัพธ์ | 24,120 | 12,425 | 52 | **253.5 s** | 22.4 s | 286.8 s |
| 25 ชิ้น `num_predict=160` | 24,119 | 12,536 | 52 | **252.9 s** | 23.5 s | 277.1 s |
| 6 ชิ้น `num_predict=160` | 6,351 | 3,258 | 48 | **38.6 s** | 12.3 s | 51.4 s |

อ่านได้สามข้อ:

1. เวลา **88–91% หมดไปกับการอ่านพรอมต์** ไม่ใช่การเขียนผลลัพธ์
2. `num_predict=160` **ไม่ลดเวลาเลย** (286.8 → 277.1 วินาที ซึ่งอยู่ในช่วงความผันผวนของการวัด)
   เพราะผลลัพธ์จริงยาว 52 โทเคน ไม่เคยชนเพดาน 160 อยู่แล้ว · `done_reason` เป็น `'stop'` ทุกรอบ ไม่ใช่ `'length'`
3. ตัวที่ลดเวลาได้คือ **ขนาดพรอมต์** (ลดเนื้อหา 3.8 เท่า → เร็วขึ้น 5.6 เท่า)

จึง **ไม่ใส่ `num_predict` ให้ด่านนี้** — ได้ไม่คุ้มกับความเสี่ยงที่ระบุไว้ในคำสั่งงาน (ตัดสั้นเกินแล้ว JSON พัง
→ โค้ดเดิมถือว่า "ตอบได้" → กลายเป็นด่านที่ผ่านทุกครั้งเงียบ ๆ) และเครื่องนี้มีการ์ดจอ เวลาที่วัดได้
จึงใช้เทียบ **สัดส่วน** เท่านั้น ไม่ใช่ตัวเลขของ production

## 3. สิ่งที่แก้

### `llm/connector.py` — กันเวลาไว้ให้ตัวสำรอง

เพิ่ม `_FALLBACK_RESERVE_S` (ตั้งทับได้ด้วย `RAG_FALLBACK_RESERVE_S` · ค่าตั้งต้น 10 วินาที) และ

```python
def reserve_budget(seconds: float | None = None) -> float | None:
    """กันเวลาช่วงท้ายของคำขอไว้ให้ขั้นถัดไป คืน "เวลาสิ้นสุดเดิม" ไว้ให้ผู้เรียกคืนค่าทีหลัง"""
```

- **แบ่งจากเพดานเดิม ไม่ใช่ต่อเวลาใหม่ทับ** เพดานรวมมีไว้กันคำขอที่ผู้ใช้รอเจ็ดนาที (13 ต.ค. 2569)
- กันได้มากสุด **ครึ่งหนึ่งของเวลาที่เหลือ** เพื่อไม่ให้คำขอที่เจ้าหลักตอบได้สบาย ๆ ถูกบีบจนล้มเอง
- ไม่ได้ตั้งเพดานไว้ (`None`) → ไม่ทำอะไร

### `backend/app/services/llm_client.py` — ใช้ตอนปล่อยเจ้าหลักออกวิ่ง

`_SplitConnector.chat()` และ `chat_stream()` เรียก `reserve_budget()` ก่อนเรียกเจ้าหลัก
แล้วคืนเวลาที่กันไว้ด้วย `apply_budget()` ทั้งตอนเจ้าหลักล้ม (ก่อนส่งงานให้ตัวสำรอง) และใน `finally`
(ให้ขั้นถัดไปของคำขอเดียวกันได้เพดานเต็มเหมือนเดิม)

ขั้นที่ห้ามใช้ตัวสำรองอยู่แล้ว (`allow_fallback=False` — คำตอบที่ต้องอ้างอิงเอกสาร) **ไม่กันเวลา**
เพราะไม่มีใครมารับช่วงต่อ เส้นทางคำตอบหลักจึงไม่ช้าลงเลย

## 5. จุดที่ยังไม่ยืนยัน

1. **ยังไม่ได้ทดสอบผ่าน route จริง** `test_chatweb_stream_budget.py` กับ `test_model_outage_n1.py`
   ต้องมี Postgres ซึ่ง Docker บนเครื่องนี้ไม่ได้รันอยู่ (`docker ps` ต่อ daemon ไม่ได้) ยังไม่ได้รัน
   ชุดใหม่ชดเชยด้วยการปั๊ม generator ทีละ step เอง แต่ **ไม่เท่ากับการยิงผ่าน `/api/chat-web` จริง**
2. **ไม่ได้อ่าน log ของ production** เครื่องนี้ไม่มี ssh config/กุญแจของเซิร์ฟเวอร์ สาเหตุข้อ 1 จึงยืนยันจาก
   โค้ด + ชุดทดสอบที่เลียนพฤติกรรมจริง ไม่ใช่จาก log ของคำขอที่ล้มสิบครั้งนั้นโดยตรง
   สิ่งที่ควรเห็นใน log ถ้าสาเหตุถูก: `เจ้าหลักตอบไม่ได้ (... ขั้นที่กำลังทำ: รอให้โมเดลพ้นช่วงพัก)`
   แล้วต่อด้วยความล้มเหลวของตัวสำรองใน **หลักมิลลิวินาที** ไม่ใช่หลักสิบวินาที
3. **10 วินาทีพอสำหรับขั้นไหนบ้าง — ยังไม่ได้วัดบนเซิร์ฟเวอร์** ขั้นที่พรอมต์สั้น (ตัวคัดกรองขอบเขต
   ซึ่งไม่ส่งเอกสารเข้าไปเลย · การเขียนคำถามใหม่) น่าจะจบทัน แต่ **ด่านตรวจหลักฐาน 25 ชิ้นไม่ทันแน่**
   ตามตารางข้อ 2 การแก้นี้จึงทำให้ตัวสำรอง "ได้ลองจริง" และทำให้ตัวนับเลิกโกหก แต่ไม่ได้ทำให้
   ด่านตรวจหลักฐานสำเร็จบนโมเดลในเครื่อง
4. **ผู้ใช้ยังไม่ได้คำตอบเมื่อ Gemini ล่ม และเรื่องนี้ไม่ได้แก้ในรอบนี้** เพราะเป็นพฤติกรรมที่ตั้งใจ ไม่ใช่บั๊ก:
   `chat.py` ตั้ง `allow_fallback = status != "answered"` คำตอบที่ต้องอ้างอิงเอกสารจึง **ปฏิเสธ**
   โมเดลในเครื่องและตอบด้วยข้อความ `FALLBACK_DECLINED` (ตรงกับตัวนับ `fallback_declined` = 3)
   การให้โมเดลในเครื่องเขียนคำตอบที่อ้างอิงเอกสารเป็นการเปลี่ยนนโยบายคุณภาพ ต้องให้เจ้าของงานตัดสิน
5. **คุณภาพคำตัดสินของด่านตรวจไม่ได้วัดซ้ำในรอบนี้** เพราะไม่ได้แก้ด่านนั้น (ดูข้อ 2) ถ้าจะลดจำนวนชิ้น
   ของพรอมต์ให้โมเดลในเครื่องตามข้อ 3 **ต้องวัดคุณภาพคำตัดสินซ้ำหลายรอบก่อน** ผลรันครั้งเดียวไม่พอ
