### 0.2 บั๊กที่การทดสอบกับฐานข้อมูลจริงเจอ — และชุดจำลองจับไม่ได้เลย

`create_refresh_token()` สร้าง JWT จาก `sub` · `type` · `iat` · `exp` เท่านั้น

ผู้ใช้คนเดียวกันที่เข้าสู่ระบบ **สองครั้งในวินาทีเดียว** จึงได้ token ที่เหมือนกันทุกไบต์

| ผลที่จะเกิดบน production | ความรุนแรง |
|---|---|
| `auth_sessions_token_hash_key` ชน unique constraint → เข้าสู่ระบบล้มเป็น **500** | เข้าระบบไม่ได้ตอนกดซ้ำหรือเปิดสองอุปกรณ์ |
| ถ้าไม่มี constraint: สองเซสชันใช้ token ใบเดียวกัน → **ออกจากระบบที่หนึ่งถอนอีกที่หนึ่งไปด้วย** | ความปลอดภัยของเซสชันพัง |

แก้ด้วย `"jti": secrets.token_urlsafe(16)` ใน payload — [security.py:113](../backend/app/core/security.py:113)

ล็อกไว้ด้วยข้อทดสอบสองข้อที่จะล้มถ้าใครถอด `jti` ออก — `test_เข้าสู่ระบบสองครั้งติดกันได้_token_คนละใบ` และ `test_ออกจากระบบอุปกรณ์หนึ่งไม่กระทบอีกอุปกรณ์`

**ชุดจำลองจับไม่ได้เพราะฐานข้อมูลปลอมไม่มี unique constraint** นี่คือเหตุผลที่ข้อ 8 สำคัญ ไม่ใช่พิธีการ

### 0.3 ข้อผิดในแผน deploy ที่เจอตอนตรวจข้อ 9

ฉบับร่างของ prompt สั่งให้รันสคริปต์ย้ายข้อมูลสามตัว **บน host** ซึ่ง **รันไม่ได้ และถ้ารันได้ก็จะพัง**

| ค่า | สิ่งที่ฉบับร่างสมมติ | ความจริง |
|---|---|---|
| `DATABASE_URL` | หยิบจาก `.env` มาใช้บน host ได้ | ชี้ไป `@postgres:5432` ซึ่งเป็นชื่อบริการใน compose · **host แปลชื่อนี้ไม่ได้ และ postgres ไม่ได้เปิดพอร์ตออกมาเลย** จึงต่อไม่ติดตั้งแต่ต้น |
| `UPLOADS_DIR` | หยิบจาก `.env` มาใช้บน host ได้ | เป็น `/srv/uploads` ซึ่งเป็นพาธ **ในคอนเทนเนอร์** · ถ้ารันบน host ไฟล์จะไปกองที่ `/srv/uploads` ของ host ที่ไม่ได้ผูกเข้าคอนเทนเนอร์ แล้ว **รูปทุกใบจะ 404 หลังสคริปต์แก้ URL** |

แก้โดยให้ทั้งสามตัวรันผ่าน `docker compose run` เข้าไปในคอนเทนเนอร์ backend โดยผูก `pipeline/` เข้าไปแบบอ่านอย่างเดียว — ค่าทั้งสองจึงถูกต้องตามที่ระบบตั้งไว้ และไฟล์ลงที่ bind mount เดียวกับที่ API อ่าน

ค่าของ Supabase ส่งเข้าไปด้วย `-e ชื่อ` เปล่า ๆ **ค่าจึงไม่ปรากฏในคำสั่งและไม่ติดใน shell history**

## 2. API ที่สร้าง

### 2.1 สาธารณะ — `routes/site.py`

| เส้นทาง | คืนอะไร |
|---|---|
| `GET /api/site/courses` | หลักสูตรที่เผยแพร่ทั้งหมด |
| `GET /api/site/courses/{id}` | หลักสูตรเดียว — **รหัสเดิมจาก Supabase ลิงก์เก่าจึงยังเปิดได้** |
| `GET /api/site/news` | ข่าวที่ `status='published'` เท่านั้น |
| `GET /api/site/external-news` | ข่าว SCI Connect |
| `GET /api/site/external-news/{slug}` | ข่าว SCI Connect รายตัว |

**ร่างไม่หลุดสาธารณะ** — เส้นทางสาธารณะกรอง `is_published` / `status='published'` ทุกคำขอ และอยู่คนละไฟล์กับเส้นทางผู้ดูแลที่เห็นทุกแถว จึงไม่มีทางเผลอแก้ query ผิดที่

**อ่านฐานข้อมูลไม่ได้ตอบ `503` ไม่ใช่รายการว่าง** — รายการว่างทำให้หน้าเว็บขึ้นว่า "ไม่มีหลักสูตร" ทั้งที่ระบบมีปัญหา

### 2.2 ผู้ดูแล — `routes/site_admin.py` (21 เส้นทาง)

| กลุ่ม | เส้นทาง | ด่าน |
|---|---|---|
| หลักสูตร | `GET/POST/PUT/DELETE /api/site-admin/courses[/{id}]` | staff · **ลบ = admin** |
| ข่าว | `GET/POST/PUT/DELETE /api/site-admin/news[/{id}]` | staff · **ลบ = admin** |
| คลังความรู้ | `GET/POST/PUT/DELETE /api/site-admin/knowledge[/{id}]` | staff · **ลบ = admin** |
| ตั้งค่า AI | `GET/PUT /api/site-admin/ai-settings` | staff |
| ผู้ใช้ | `GET /api/site-admin/users` · `PUT .../role` · `PUT .../status` | **admin เท่านั้น** |

**ชุดทดสอบบังคับว่า ทุกเส้นทางต้องมีด่าน และทุกเส้นทางลบต้องเป็น admin** — เส้นทางที่ลืมใส่ด่านจะทำให้ชุดทดสอบล้ม

กันพลาดเพิ่มสองข้อ — **ผู้ดูแลลดสิทธิ์ตัวเองไม่ได้** และ **ถอนอนุมัติใครต้องถอนเซสชันของคนนั้นด้วย** ไม่ใช่รอ token หมดอายุ (ยืนยันกับฐานจริงแล้ว — `test_ถอนอนุมัติแล้วเซสชันถูกเพิกถอนจริง`)

## 3. ไฟล์ — `services/file_store.py` + `routes/uploads.py`

### 3.1 ด่านความปลอดภัย

| ด่าน | ทำอย่างไร |
|---|---|
| path traversal | **ชื่อบนดิสก์คือ sha256 ของเนื้อไฟล์** ผู้ใช้ควบคุมพาธไม่ได้เลย · และ resolve แล้วยืนยันว่ายังอยู่ใต้โฟลเดอร์ที่กำหนดอีกชั้น |
| ชนิดไฟล์ | ตรวจ **ทั้งนามสกุลและลายเซ็นไบต์** — `.png` ที่ข้างในเป็นสคริปต์ไม่ผ่าน |
| ขนาด | เพดาน `UPLOAD_MAX_BYTES` (ค่าตั้งต้น 10 MB) · ไฟล์ว่างไม่ผ่าน |
| แยกตามหมวด | `logo`/`news` รับเฉพาะรูป · `course-doc` รับเฉพาะ PDF · `knowledge` รับเอกสาร |
| ความเป็นส่วนตัว | **`knowledge` ต้องเข้าสู่ระบบก่อนอ่าน** เพราะของเดิมเป็น bucket แบบ private ที่ใช้ signed URL |

> ชุดทดสอบบังคับว่า **ชนิดที่ตรวจลายเซ็นไบต์ไม่ได้ (`.txt` `.md`) ห้ามอยู่ในหมวดสาธารณะ**

### 3.2 ที่เก็บ

| รายการ | ค่า |
|---|---|
| ในคอนเทนเนอร์ | `/srv/uploads` |
| บน host | `<project>/uploads` (เพิ่ม volume ใน `docker-compose.prod.yml` แล้ว **แบบเขียนได้**) |

ขั้น B ของ prompt มีคำสั่ง `touch` จากในคอนเทนเนอร์เพื่อยืนยันว่าเขียนได้จริง — ไม่ใช่ดูจาก compose แล้วเชื่อ

### 3.3 สคริปต์ย้ายไฟล์เดิม — `pipeline/web/migrate_storage.py`

| เรื่อง | ทำอย่างไร |
|---|---|
| ค่าที่ใช้ | อ่านจาก env ทั้งหมด (`SUPABASE_URL` · `SUPABASE_SERVICE_ROLE_KEY` · `DATABASE_URL` · `UPLOADS_DIR`) **ไม่มีค่าใดฝังในโค้ด** |
| ซ้อมก่อน | `--dry-run` บอกจำนวนไฟล์และปลายทาง โดยไม่เขียนอะไร |
| กัน token หลุด | service key ส่งใน header **ไม่เคยอยู่ใน URL** จึงไม่ติดใน log ของ proxy · ข้อความรายงานไม่พิมพ์ค่าคีย์ |
| เครือข่ายสะดุด | retry แบบถอยหลัง · **ไม่ retry กับ 401/403/404** เพราะลองอีกก็ได้ผลเดิม |
| ไฟล์เสียกลางทาง | ตรวจ sha256 **จากไฟล์ที่เขียนลงดิสก์แล้ว** ไม่ใช่จากบัฟเฟอร์ |
| ไฟล์ private | ดึงผ่าน service key ได้ตรง ๆ แล้วเก็บในหมวดที่ต้องล็อกอิน |
| **ของครึ่ง ๆ** | **แก้ URL ในฐานข้อมูลเฉพาะเมื่อทุกไฟล์สำเร็จ** — พลาดแม้ไฟล์เดียวจะไม่แก้อะไรเลย ไม่ทำให้บางรูปชี้ไปที่ว่าง |

### 4.4 รหัสผ่านเดิม — **ย้ายได้** (แก้คำกล่าวอ้างในรอบก่อน)

รอบก่อนเขียนว่า "Supabase ไม่ให้ส่งออก hash ของรหัสผ่าน ผู้ดูแลทุกคนต้องตั้งรหัสใหม่" — **เป็นการสรุปโดยไม่ตรวจ**

ตรวจจริงแล้วพบว่า

| ข้อเท็จจริง | หลักฐาน |
|---|---|
| `auth.users.encrypted_password` อ่านได้ผ่าน connection string ของ Postgres ที่ Supabase ให้มา | ไม่ได้ถูกจำกัดสิทธิ์จาก role ที่ใช้เชื่อมต่อ |
| GoTrue เก็บเป็น **bcrypt ของรหัสผ่านตรง ๆ** ขึ้นต้นด้วย `$2a$` | ทดลองเทียบกับ `bcrypt.checkpw(pw, hash)` แล้วผ่าน |
| ของเราเป็น **bcrypt ของ base64(sha256(รหัสผ่าน))** | `_prehash()` ใน [security.py](../backend/app/core/security.py) — ทำไว้เพื่อให้รหัสผ่านภาษาไทยยาวเกิน 72 ไบต์ใช้ได้ |

**วิธีที่ใช้**

1. `import_accounts.py` ย้ายแถวพร้อม hash และทำเครื่องหมาย `password_scheme = 'bcrypt'`
2. ตอนเข้าสู่ระบบ `verify_password()` ใช้รูปแบบตามที่แถวระบุ — **ผู้ใช้ใส่รหัสเดิมได้ทันที**
3. เข้าสำเร็จแล้วระบบ hash ใหม่เป็น `bcrypt_sha256` และอัปเดต `password_scheme` **เอง** โดยผู้ใช้ไม่รู้ตัว

ผลคือ **ไม่มีใครต้องตั้งรหัสใหม่ และไม่ต้องตั้ง SMTP ก่อน deploy**

| สิ่งที่สคริปต์ **ไม่** ทำ | เหตุผล |
|---|---|
| ไม่เขียน `password_hash` ทับแถวที่มีอยู่แล้ว | รันซ้ำต้องไม่ย้อนรหัสผ่านที่ผู้ใช้เปลี่ยนไปแล้ว |
| ไม่เขียน `role` ทับ | สิทธิ์ที่ผู้ดูแลตั้งบนระบบใหม่ต้องชนะค่าที่ย้ายมา |
| ข้ามบัญชี OAuth (ไม่มีรหัสผ่าน) | เอาเข้ามาจะได้แถวที่เข้าสู่ระบบไม่ได้เลย |

> **ยังไม่ได้ตั้ง SMTP** — ไม่กระทบการย้ายแล้ว แต่ปุ่ม "ลืมรหัสผ่าน" จะยังไม่ส่งอีเมลจนตั้งค่า
> ระหว่างนี้ผู้ดูแลออกลิงก์รีเซ็ตให้ทีละคนได้ที่ `/api/auth/admin/reset-link`
