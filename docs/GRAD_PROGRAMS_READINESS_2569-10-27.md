## 1. ข้อ 1 — `/compare-courses` ผ่าน backend จริง

### 1.1 สิ่งที่พบ

`WebCourse` ของ backend รับแค่ `id` กับ `title` — ช่อง `level` ที่หน้าเว็บส่งมา
**ถูก Pydantic ทิ้งเงียบ ๆ** และ `match_by_title()` จับคู่ด้วย `normalise_title()`
ซึ่ง**ตัดชื่อปริญญาออก**เพื่อให้เทียบชื่อข้ามสองฐานข้อมูลได้

ผลคือเล่มโทกับเล่มเอกของสาขาเดียวกันได้คีย์เดียวกัน แล้วเลือก "ฉบับล่าสุด" ตัวเดียว
ให้ทั้งสองรายการ — **เอาเล่มโทมาเทียบกับตัวเอง โดยไม่มีอะไรบอกผู้ใช้**

ข้อนี้ไม่เคยโผล่มาก่อน เพราะเดิมหน้าเว็บมีแต่ปริญญาตรีซึ่งมีระดับเดียว

### 1.2 หลักฐานที่ระดับ API — ก่อนแก้

ยิง `POST /compare-courses` ผ่าน backend จริง (image `counter-2569-10-16`)
บนฐาน `course_advisor_test` · ชื่อสาขาเหมือนกันทุกตัวอักษรตามที่โจทย์กำหนด
(ผลเต็มอยู่ที่ `api-compare-before.txt`)

| คำขอ | ผล |
|---|---|
| ส่ง `level` ปริญญาโท / ปริญญาเอก | HTTP 200 · `fe-m` **36 หน่วยกิต** · `fe-d` **36 หน่วยกิต** |
| ไม่ส่ง `level` | HTTP 200 · ทั้งคู่ **36 หน่วยกิต** |
| ปริญญาตรีสองสาขา | HTTP 200 · 124 / 130 หน่วยกิต (ปกติ) |

คอลัมน์ปริญญาเอกได้ตัวเลขของปริญญาโท และ `summary` ที่โมเดลเขียนเองยังบอกว่า
*"ข้อมูลในตารางเป็นหลักสูตรวิทยาศาสตรมหาบัณฑิต … ที่เหมือนกันทุกประการ"*

> **การดัก payload แล้วเห็น `level` ไม่ได้แปลว่า backend ใช้งาน** — ข้อนี้ยืนยันแล้ว
> ว่าไม่ได้ใช้จริง ต้องวัดที่ผลลัพธ์ของ API เท่านั้น

### 1.3 สิ่งที่แก้

| ไฟล์ | แก้อะไร |
|---|---|
| `backend/app/api/routes/web_compat.py` | `WebCourse` รับช่อง `level` · คีย์จับอันดับกลับรวมระดับปริญญา · ข้อความ 422 บอกทางออก |
| `backend/app/services/web_compat.py` | `match_by_title()` ทำดัชนีแยกระดับ `(ชื่อ, ปี, ระดับ)` |

หลักการที่ยึด — **ไม่รู้ระดับก็ไม่เดา**

- ผู้เรียกส่ง `level` มา → ใช้ระดับนั้น
- ไม่ส่งแต่ชื่อขึ้นต้นด้วย `(ปริญญาโท)` → อ่านระดับจากชื่อ (หน้าเว็บรุ่นเก่าจึงยังทำงาน)
- ไม่บอกระดับเลย ทั้งที่ชื่อนั้นมีหลายระดับ → **ถือว่าจับคู่ไม่ได้** ผู้เรียกได้ 422
  พร้อมข้อความว่าต้องระบุระดับ ดีกว่าได้คำตอบผิดเงียบ ๆ
- สาขาที่มีระดับเดียว (ปริญญาตรีทั้ง 12) → ทำงานเหมือนเดิมทุกประการ

### 1.4 หลักฐานที่ระดับ API — หลังแก้

ยิงซ้ำด้วย **image ที่ build จริงแล้ว ไม่ mount ไฟล์ใด** (`level-2569-10-27`)
(ผลเต็มอยู่ที่ `api-compare-after.txt`)

| คำขอ | ผล |
|---|---|
| ส่ง `level` ปริญญาโท / ปริญญาเอก | HTTP 200 · `fe-m` **36 หน่วยกิต** · `fe-d` **48 หน่วยกิต** |
| ไม่ส่ง `level` | **HTTP 422** "…(ถ้าสาขานั้นเปิดสอนหลายระดับปริญญา ต้องระบุระดับมาด้วย)" |
| ปริญญาตรีสองสาขา | HTTP 200 · 124 / 130 หน่วยกิต (ไม่กระทบ) |

ช่อง `bestFor` ก็แยกถูก — คอลัมน์ปริญญาเอกขึ้น *"สำเร็จการศึกษาปริญญาโทหรือเทียบเท่า
มีผลการสอบภาษาอังกฤษตามประกาศมหาวิทยาลัย"* ซึ่งมีเฉพาะในเล่มปริญญาเอก

### 2.3 บทสนทนาต่อเนื่อง — ถามกำกวม → ถามระดับ → ตอบ "ปริญญาโท"

ส่งบทสนทนาทั้งก้อนผ่าน `prior` เหมือนที่หน้าเว็บทำจริง

**เทิร์นที่ 1** — "การจัดการเทคโนโลยีการเกษตรและบริหารทรัพยากรชุมชน เรียนกี่หน่วยกิต"

> หลักสูตรการจัดการเทคโนโลยีการเกษตรและบริหารทรัพยากรชุมชน มีทั้งระดับปริญญาโท และ ปริญญาเอก ช่วยระบุระดับที่ต้องการด้วยครับ จะได้ตอบจากเล่มที่ถูกระดับ

ไม่มีตัวเลขหน่วยกิตของเล่มใดหลุดออกมา และเอ่ยทั้งสองระดับให้ผู้ใช้เลือก

**เทิร์นที่ 2** — ผู้ใช้ตอบระดับ

| ผู้ใช้ตอบ | คำถามที่ระบบตีความ | เอกสารที่ดึงมาใช้ |
|---|---|---|
| "ปริญญาโท" | …ระดับปริญญาโท | **วิทยาศาสตรมหาบัณฑิต (2568)** เท่านั้น |
| "ปริญญาเอก" | …ระดับปริญญาเอก | **ปรัชญาดุษฎีบัณฑิต (2568)** เท่านั้น |
| "เอาปริญญาโทครับ" | …ระดับปริญญาโท เรียนกี่หน่วยกิต | **วิทยาศาสตรมหาบัณฑิต (2568)** เท่านั้น |

ทั้งสามเคส `has_history = True` · ไม่ถามซ้ำ · **ไม่มีเล่มของอีกระดับปนเลยแม้ชิ้นเดียว**

วัดที่ `course_title` ของชิ้นข้อมูลที่ถูกดึงมา ซึ่งเป็นผลของขั้นที่ไม่มีโมเดลเกี่ยว
ผลจึงคงที่ · ถ้อยคำของคำตอบสุดท้ายเป็นของโมเดล ไม่ได้วัดในรอบนี้

### 2.4 ลำดับ deploy และ rollback

**ต้อง deploy backend พร้อมข้อมูล** เพราะข้อบกพร่องข้อ 1 จะปรากฏทันทีที่
หลักสูตรโท–เอกขึ้นหน้าเว็บ

| ขั้น | คำสั่ง | ถ้าขั้นนี้ล้ม |
|---|---|---|
| 1. backend | `./deploy_backend.sh` | ยังไม่มีข้อมูลโท–เอก ไม่มีใครเห็นอะไรเปลี่ยน · หยุดได้ทันที |
| 2. ข้อมูล | `./deploy_data.sh --db course_advisor` | backend ใหม่ + ข้อมูลเก่า = ไม่มีผลเสีย (ด่านใหม่ไม่ยิงเพราะยังไม่มีสาขาหลายระดับบนเว็บ) · `./rollback_backend.sh` |
| 3. หน้าเว็บ | `./deploy_web.sh` | เว็บเก่า + ข้อมูลใหม่ = เห็นหลักสูตรครบ แต่ไม่เห็นช่องใหม่ · `./rollback_data.sh` แล้ว `./rollback_backend.sh` |

**ย้อนกลับ** — ลำดับกลับด้าน หน้าเว็บ → ข้อมูล → backend

| สาเหตุที่ย้อน | ลำดับ |
|---|---|
| หน้าเว็บมีปัญหา | `rollback_web.sh` อย่างเดียวก็พอ (เว็บเก่าอ่านข้อมูลใหม่ได้ แค่ไม่แสดงช่องใหม่) |
| ข้อมูลมีปัญหา | `rollback_web.sh` → `rollback_data.sh` |
| backend มีปัญหา | ทั้งสามขั้น เพราะ backend เก่ากับข้อมูลโท–เอกคือข้อบกพร่องข้อ 1 |

`deploy_backend.sh` มีด่านตรวจ 6 ขั้น และ**ถาม YES ก่อน restart production**

- ตรวจ SHA-256 ของไฟล์ในชุด
- ตรวจว่า image ที่รันอยู่ตรงกับฐานที่ชุดนี้ซ้อนไว้ (ถ้าไม่ตรง หยุด — ต้องสร้างชุดใหม่)
- build แล้วตรวจ hash ของไฟล์**ในอิมเมจ**
- รันชุดทดสอบทั้งสองในอิมเมจใหม่บนฐานทดสอบ **ก่อน**สลับ production
- หลังสลับ ตรวจ hash ในคอนเทนเนอร์ที่รันจริง (scp แล้ว restart ไม่พอ)

## 3. ข้อ 3 — SHA-256 ของ bundle

### 3.1 ฐานที่ใช้ build ตรงกับ production จริงหรือไม่

รอบก่อนเทียบแค่ชื่อไฟล์ ซึ่งยังไม่พอ รอบนี้ดาวน์โหลดไฟล์จากเว็บ production จริง
แล้วเทียบ SHA-256 ของเนื้อไฟล์เต็ม (บันทึกไว้ที่ `bundle-hashes.json`)

| ไฟล์ | ฐานที่ build เอง | ที่ production เสิร์ฟ | ผล |
|---|---|---|---|
| `index-VoqZ65Zz.js` (472,427 bytes) | `5beda48b…e068ebba` | `5beda48b…e068ebba` | **ตรงกันทุกไบต์** |
| `index-CmT3E8tu.css` (48,690 bytes) | `054ba540…d7db4736` | `054ba540…d7db4736` | **ตรงกันทุกไบต์** |

ยืนยันแล้วว่างานค้าง 46 ไฟล์ในที่ทำงานของหน้าเว็บ **อยู่ใน production อยู่แล้ว**
release นี้จึงมีเฉพาะการแก้ที่ผ่านการตรวจในรอบนี้

### 3.2 ไฟล์ของ release

| ไฟล์ | ขนาด | SHA-256 |
|---|---:|---|
| `index-BP_qDdgl.js` | 481,842 | `cc36a29b10b4260d797d12beb72dc6f13942d88bfbc24c13bec141cfe15a1d95` |
| `index-lp97Jr5s.css` | 48,720 | `a36ba9d3144a0cea4932343f8c9d799b1e4a98a84a0d39f9d0136458425c6f6e` |
| `index.html` | 1,779 | `2343cce2f045d2a1361a42d0caebaebee5327caf9dc585faaed6767e9fe8cce0` |

เก็บไว้ใน `web-release/SHA256SUMS` และ `deploy_web.sh` ตรวจก่อนนำขึ้น

> รายงานรอบก่อนเขียนขนาด `index.html` เป็น 1,133 bytes ซึ่งเป็นตัวเลขที่ vite รายงาน
> ขนาดไฟล์จริงบนดิสก์คือ **1,779 bytes** · ค่า SHA-256 เท่าเดิม

### 3.3 `deploy_web.sh` ตรวจด้วย hash แล้ว

เปลี่ยนจาก 5 ขั้นเป็น 7 ขั้น ทุกขั้นที่ตรวจไฟล์ใช้ SHA-256 ไม่ใช่ชื่อไฟล์หรือ HTTP 200

| ขั้น | ตรวจอะไร |
|---|---|
| 0 | `sha256sum -c` ไฟล์ในชุด release |
| 1 | สำรอง `index.html` เดิม + บันทึก hash |
| 2 | bundle เดิมที่ rollback ต้องใช้ ยังอยู่และบันทึก hash ไว้ |
| 3 | วาง assets ผ่านไฟล์ชั่วคราวแล้ว `mv` · ตรวจ hash หลังคัดลอก · **ถ้าชื่อซ้ำแต่เนื้อต่าง หยุดทันที** |
| 4 | **ดึงไฟล์ผ่าน HTTPS จริงมาตรวจ hash** ไม่ใช่แค่ดู 200 |
| 5 | สลับ `index.html` ด้วย `mv` (จังหวะเดียว ไม่ให้ใครได้ไฟล์ครึ่งเดียว) |
| 6 | ดึงหน้าแรกจากเว็บมาตรวจ hash ว่าเป็นไฟล์ของ release นี้จริง |

ขั้น 4 สำคัญ — HTTP 200 บอกแค่ว่ามีไฟล์ตอบมา ไม่ได้บอกว่าเนื้อไฟล์ถูกต้อง
ไฟล์ที่คัดลอกไม่ครบหรือของรุ่นก่อนที่ชื่อชนกันก็ตอบ 200 ได้เหมือนกัน

## 5. ส่วนที่ผ่านแล้วและไม่ได้แตะในรอบนี้

ไม่ได้ทำซ้ำเพราะไม่ได้รับผลกระทบจากการแก้ของรอบนี้ (ทั้งหมดเป็นการแก้ฝั่ง backend)

- ข้อมูลปริญญาตรี 12 สาขา — คุณสมบัติทั่วไป 12/12 · เงื่อนไขตามรอบรับสมัคร 8/12
- ข้อความกำกับและลิงก์ 3 จุดของหลักสูตรโท–เอก
- ตัวกรองระดับในหน้ารายการ · ป้ายระดับบนการ์ดเปรียบเทียบ
- ฟอร์มผู้ดูแล — บันทึกแล้วไม่มีคีย์หายทั้ง ป.โท (10 คีย์) และ ป.ตรี (8 คีย์)
- `deploy_data.sh` / `rollback_data.sh` — ทดสอบเต็มวงจรแล้ว รวมกรณีผู้ดูแลแก้งานเพิ่ม
  หลัง deploy แล้ว rollback ต้องไม่ลบงานนั้น
- การแนะนำสำหรับนักเรียน ม.ปลาย — ส่งให้ AI 12 หลักสูตร บัณฑิตศึกษาหลุดไป 0

`round.diff` และไฟล์ใน `web-release/` **ไม่เปลี่ยนจากรอบก่อน** — ยืนยันด้วย SHA-256 เดิม

## 6. รายการที่ยังยืนยันไม่ได้

คงเดิมจากรอบก่อน ไม่มีข้อใดเปลี่ยนสถานะ

| # | เรื่อง | ทำอย่างไร |
|---|---|---|
| 1 | ค่าเล่าเรียนปริญญาเอก — ไม่มีทั้งบนเว็บและในเล่ม มคอ.2 103 หน้า | ปล่อยว่าง ขึ้น "ไม่ระบุ" |
| 2 | หน้าเว็บสรุปคุณสมบัติสั้นกว่าเล่ม มคอ.2 | ใส่ข้อความกำกับว่าเป็นฉบับย่อ + ลิงก์เล่มเต็ม ไม่รวมสองแหล่งเอง |
| 3 | ข้อความไทยใน PDF แตก (สระอำ · "ว่าเวย") | ไม่อ้างข้อความยาวจาก PDF ลงฐานข้อมูล |
| 4 | เงื่อนไขแยกตามแผนการเรียน | ไม่เลือกแผนใดมาแสดงแทนผู้อ่าน |
| 5 | ชื่อที่ใช้แสดงของโท–เอก มีวงเล็บระดับซ้ำกับป้าย | ตอนนี้ระบบแยกจาก `detail.level` แล้ว **ลบวงเล็บออกได้โดยไม่กระทบ** (พิสูจน์ในข้อ 1.4) |
| 6 | ยังไม่ผูก `course_id` กับเอกสาร มคอ. | นอกขอบเขต |
| 7 | ช่อง `important_info` รั่วมาก่อนหน้านี้ | นอกขอบเขต |

**สิ่งที่ไม่ได้วัดในรอบนี้** — ถ้อยคำของคำตอบที่โมเดลเขียนจากเส้นทางเอกสาร
ทุกข้อตรวจในรายงานนี้วัดที่ขั้นที่ไม่มีโมเดลเกี่ยว (การเลือกเล่ม · การตีความคำถาม ·
ด่านที่ตอบก่อนถึงโมเดล) ผลจึงคงที่ ส่วน `summary`/`pros` ของ `/compare-courses`
เป็นผลของโมเดล ใช้เป็นหลักฐานได้เฉพาะตัวเลขที่ตรงกับเอกสาร (36 / 48 / 124 / 130)
ซึ่งเป็นตัวเลขที่ชี้ชัดว่าใช้เล่มไหน ไม่ใช่การตัดสินคุณภาพถ้อยคำ
