## 3.3.1 ภาพรวมสถาปัตยกรรมฐานข้อมูล

ระบบ SCI Advisor ใช้ฐานข้อมูลเชิงสัมพันธ์ 2 ชุด โดยแบ่งตาม**หน้าที่ของข้อมูล** ไม่ใช่แบ่งตามผู้พัฒนา
เรียกแนวทางนี้ว่า Polyglot Persistence คือการเลือกที่เก็บข้อมูลให้เหมาะกับลักษณะงานของข้อมูลแต่ละประเภท

| | ฐานข้อมูลระบบเว็บ | ฐานข้อมูลฐานความรู้ |
|---|---|---|
| ระบบจัดการ | Supabase (PostgreSQL แบบบริการสำเร็จรูป) | PostgreSQL 16 + ส่วนขยาย pgvector |
| ติดตั้งที่ | บริการคลาวด์ของ Supabase | เครื่องแม่ข่าย Oracle Cloud (Docker) |
| หน้าที่ | ข้อมูลที่ผู้ดูแลระบบแก้ไขผ่านหน้าเว็บ | ข้อมูลที่สกัดจากเอกสารหลักสูตรเพื่อใช้ตอบคำถาม |
| ผู้เขียนข้อมูล | ผู้ดูแลระบบ ผ่านหน้าจอ Admin | กระบวนการสกัดเอกสารอัตโนมัติ และผู้ตรวจทาน |
| จำนวนตาราง | 7 ตาราง | 28 ตาราง (public 10 · mko 18) และ 6 วิว |

**เหตุผลที่ไม่รวมเป็นฐานข้อมูลเดียว**

1. **ลักษณะการใช้งานต่างกันโดยสิ้นเชิง** ข้อมูลฝั่งเว็บเป็นข้อมูลที่ถูกแก้ไขบ่อยโดยมนุษย์และต้องการ
   ระบบยืนยันตัวตนกับการควบคุมสิทธิ์ระดับแถว ส่วนข้อมูลฐานความรู้เป็นข้อมูลที่เขียนครั้งเดียวจาก
   กระบวนการสกัด แล้วอ่านซ้ำจำนวนมากพร้อมการค้นหาเชิงเวกเตอร์
2. **ข้อจำกัดของบริการ** การค้นหาเชิงเวกเตอร์บนเอกสาร 9,039 ส่วนข้อความด้วยเวกเตอร์ขนาด 1,024 มิติ
   ต้องควบคุมดัชนีและหน่วยความจำเอง ซึ่งทำได้บนเครื่องแม่ข่ายที่ดูแลเองมากกว่า
3. **การแบ่งขอบเขตความเสียหาย** หากฐานข้อมูลฝั่งเว็บมีปัญหา ระบบตอบคำถามยังทำงานได้ และในทางกลับกัน

**การเชื่อมโยงข้อมูลระหว่างสองฐาน** ใช้ **ชื่อหลักสูตร (title)** เป็นคีย์เชื่อมเชิงตรรกะ ไม่ใช่รหัสประจำตัว
เนื่องจากทั้งสองฐานสร้าง UUID ของตนเองแยกกัน ระบบส่วนหลังจึงมีฟังก์ชัน `normalise_title()` สำหรับ
ปรับรูปข้อความชื่อหลักสูตรให้เป็นรูปมาตรฐานก่อนจับคู่ (ตัดคำนำหน้า ช่องว่าง และรูปแบบวงเล็บปีการศึกษา)

## 3.3.2 การออกแบบความสัมพันธ์ของข้อมูล (ER-Diagram)

### ก. เอนทิตีหลักของฐานข้อมูลฐานความรู้

แบ่งออกเป็น 5 กลุ่มตามหน้าที่

**กลุ่มที่ 1 ผู้ใช้งานระบบ (User Domain)**

| เอนทิตี | ความหมาย |
|---|---|
| `users` | บัญชีผู้ใช้ระบบ |
| `user_profiles` | ข้อมูลภูมิหลังของผู้ใช้ เช่น ระดับการศึกษา เป้าหมายอาชีพ |
| `user_requirements` | เงื่อนไขที่ผู้ใช้ระบุพร้อมระดับความสำคัญ 1–5 |

**กลุ่มที่ 2 เอกสารหลักสูตร (Document Domain)**

| เอนทิตี | ความหมาย |
|---|---|
| `courses` | หลักสูตร/สาขาวิชา แยกตามฉบับปีการศึกษา |
| `course_documents` | ไฟล์เอกสาร มคอ.2 ของแต่ละหลักสูตร |
| `course_chunks` | ส่วนข้อความที่ตัดจากเอกสารพร้อมเวกเตอร์ความหมาย |

**กลุ่มที่ 3 ข้อมูลเชิงโครงสร้างและหลักฐาน (Structured Metadata Domain — สคีมา `mko`)**

| เอนทิตี | ความหมาย |
|---|---|
| `document_pages` | ข้อความรายหน้าของเอกสาร พร้อมระบุที่มาของข้อความ |
| `extraction_runs` | การสกัดข้อมูลแต่ละรอบ บันทึกรุ่นของตัวสกัด |
| `document_sections` | ขอบเขตหัวข้อภายในเอกสาร |
| `evidence` | ข้อความที่ยกมาจากหน้าต้นฉบับเพื่อใช้เป็นหลักฐาน |
| `programs` | สาขาวิชาในฐานะตัวตนที่ข้ามปีการศึกษา |
| `curricula` | หลักสูตรรายฉบับปี เชื่อมกับ `courses` |
| `field_values` | ค่าข้อมูลแบบค่าเดี่ยวที่สกัดได้ เช่น จำนวนหน่วยกิต |
| `field_value_evidence` | ตารางเชื่อมระหว่างค่ากับหลักฐาน (หนึ่งค่ามีหลายหลักฐานได้) |
| `list_items` | ข้อมูลแบบรายการ เช่น วัตถุประสงค์ อาชีพหลังจบ |
| `credit_groups` · `subjects` · `learning_outcomes` | โครงสร้างหมวดหน่วยกิต รายวิชา และผลลัพธ์การเรียนรู้ |

**กลุ่มที่ 4 การตรวจทานและการเผยแพร่ (Review & Publication Domain)**

| เอนทิตี | ความหมาย |
|---|---|
| `review_decisions` | ผลการตรวจทานของมนุษย์ |
| `publications` | การเผยแพร่ข้อมูลแต่ละครั้ง |
| `published_values` · `published_list_items` | ภาพถ่ายข้อมูล ณ เวลาที่เผยแพร่ |
| `shadow_answers` | บันทึกเปรียบเทียบคำตอบสำหรับการประเมินคุณภาพ |

**กลุ่มที่ 5 บันทึกการใช้งาน (Log Domain)**

| เอนทิตี | ความหมาย |
|---|---|
| `chat_sessions` · `chat_messages` | บทสนทนาของผู้ใช้กับระบบ |
| `recommendations` | ผลการแนะนำหลักสูตรพร้อมเหตุผลและส่วนข้อความที่อ้างอิง |
| `chat_answer_cache` | คำตอบที่เคยตอบแล้ว ผูกกับรุ่นของคลังเอกสาร |

### ข. ความสัมพันธ์ระหว่างเอนทิตี

| # | ความสัมพันธ์ | ชนิด | การลบข้อมูลต้นทาง |

**จุดที่ควรสังเกตในการออกแบบ**

- **ข้อ 14 เป็นคีย์นอกแบบผสม (Composite Foreign Key)** ตาราง `evidence` อ้างอิงไปยัง
  `document_pages (document_id, page_number)` ทั้งช่องหน้าเริ่มต้นและหน้าสิ้นสุด
  ทำให้ฐานข้อมูลปฏิเสธหลักฐานที่อ้างถึงหน้าที่ไม่มีอยู่จริงโดยอัตโนมัติ
- **ข้อ 18 เป็นความสัมพันธ์แบบกลุ่มต่อกลุ่ม** เพราะค่าหนึ่งค่ายืนยันได้จากหลายตำแหน่งในเอกสาร
  เช่น จำนวนหน่วยกิต 124 หน่วยกิต ปรากฏทั้งหน้า 1 หน้า 6 และหน้า 7 ระบบจึงยืนยันค่าอัตโนมัติได้
- **ข้อ 21 และ 22 เป็นความสัมพันธ์แบบวนกลับตนเอง** ใช้แทนโครงสร้างลำดับชั้นของหมวดหน่วยกิต
  (หมวดวิชาศึกษาทั่วไป → กลุ่มวิชาภาษา → รายวิชา) และของผลลัพธ์การเรียนรู้ (PLO → SubPLO)

**หลักการสำคัญ** ระบบส่วนหลังที่ให้บริการผู้ใช้ **ไม่ได้รับสิทธิ์อ่านตารางที่เก็บค่าดิบ**

## 3.3.4 กฎความถูกต้องที่บังคับในระดับฐานข้อมูล

ระบบกำหนดกฎความถูกต้องไว้ที่ชั้นฐานข้อมูล ไม่ฝากไว้กับโปรแกรมประยุกต์เพียงอย่างเดียว
เนื่องจากฐานข้อมูลนี้ถูกเขียนจากหลายทาง ทั้งระบบส่วนหลัง กระบวนการสกัดเอกสาร และเครื่องมือตรวจทาน

**ก. กฎ "ค่าที่มีข้อมูลต้องมีหลักฐานเสมอ"**

```sql
CONSTRAINT field_value_evidence_rule CHECK (
    (status IN ('not_found','not_applicable')
        AND value_text IS NULL AND value_int IS NULL AND evidence_id IS NULL)
    OR (status NOT IN ('not_found','not_applicable')
        AND evidence_id IS NOT NULL
        AND (value_text IS NOT NULL OR value_int IS NOT NULL))
)
```

ผลคือ **เป็นไปไม่ได้ในทางโครงสร้าง** ที่จะมีค่าข้อมูลลอยอยู่โดยไม่มีที่มา

**ข. กฎ "ค่าที่ยืนยันแล้วต้องระบุผู้ยืนยัน"**

```sql
CONSTRAINT field_value_verified_reviewer CHECK (status <> 'verified' OR reviewed_by IS NOT NULL)
```

**ค. ทริกเกอร์ตรวจสอบว่าข้อความที่ยกมามีอยู่ในหน้านั้นจริง**

```sql
CREATE TRIGGER trg_evidence_quote
    BEFORE INSERT OR UPDATE ON mko.evidence
    FOR EACH ROW EXECUTE FUNCTION mko.check_evidence_quote();
```

ฟังก์ชันจะประกอบข้อความของหน้าที่อ้างถึงแล้วตรวจว่าข้อความที่ยกมาปรากฏอยู่จริงหรือไม่
หากไม่พบจะปฏิเสธการบันทึกทันที **นี่คือด่านสุดท้ายที่ป้องกันข้อมูลที่ระบบสร้างขึ้นเอง
แม้โปรแกรมสกัดข้อมูลจะมีข้อผิดพลาด**

**ง. ดัชนีไม่ซ้ำแบบมีเงื่อนไข (Partial Unique Index)**

```sql
CREATE UNIQUE INDEX uq_review_decisions_active
    ON mko.review_decisions (document_id, field_key, value_key)
    WHERE superseded_at IS NULL;
```

อนุญาตให้เก็บประวัติการตรวจย้อนหลังได้ไม่จำกัด แต่บังคับว่า ณ เวลาหนึ่งการตัดสินที่ยังมีผล
ต้องมีเพียงรายการเดียวต่อหนึ่งชุด (เอกสาร, ช่องข้อมูล, ค่า)

**จ. ทริกเกอร์ปรับเวลาแก้ไขล่าสุดอัตโนมัติ**

ใช้ฟังก์ชัน `set_updated_at()` กับตาราง `users`, `user_profiles` และ `courses`
เหตุผลที่ทำที่ชั้นฐานข้อมูลแทนชั้นโปรแกรม เพราะตาราง `courses` ถูกเขียนโดยกระบวนการสกัดเอกสาร
ที่ไม่ได้ผ่านชั้น ORM การกำหนดที่ชั้นฐานข้อมูลจึงครอบคลุมทุกช่องทางเข้าถึงข้อมูล

**ฉ. ข้อกำหนดตรวจค่าที่ใช้ทั้งหมด**

| ตาราง | ข้อกำหนด |
|---|---|
| `user_requirements` | `priority BETWEEN 1 AND 5` |
| `chat_messages` | `role IN ('user','assistant','system')` |
| `mko.document_pages` | `page_number >= 1` · `text_source IN ('text_layer','ocr','text_layer+ocr','plain_text')` |
| `mko.curricula` | `edition_year_be BETWEEN 2500 AND 2700` · `total_credits BETWEEN 1 AND 400` |
| `mko.list_items` | `item_type IN ('philosophy','objective','career','admission')` · `seq >= 1` |
| `mko.publications` | `policy IN ('verified_any','verified_human_only')` |
| `mko.evidence`, `mko.document_sections` | `page_end >= page_start` |

## 3.3.5 การออกแบบดัชนีและการค้นคืนเชิงเวกเตอร์

| ดัชนี | ตาราง | ชนิด | วัตถุประสงค์ |
|---|---|---|---|
| `idx_course_chunks_embedding` | `course_chunks` | **IVFFlat (`vector_cosine_ops`, lists = 100)** | ค้นหาส่วนข้อความที่ใกล้เคียงคำถามเชิงความหมาย |

| `idx_chat_messages_session` | `chat_messages` | B-tree | ดึงบทสนทนาตามรอบ |

| `idx_extraction_runs_document` | `mko.extraction_runs` | B-tree ผสม | ดูรอบสกัดล่าสุดของเอกสาร |

**การค้นคืนเชิงเวกเตอร์** ส่วนข้อความแต่ละส่วนถูกแปลงเป็นเวกเตอร์ขนาด 1,024 มิติด้วยโมเดล
`bge-m3` แล้วเก็บในชนิดข้อมูล `VECTOR(1024)` ของส่วนขยาย pgvector การค้นหาใช้ระยะห่างแบบโคไซน์
โดยดัชนีชนิด IVFFlat แบ่งเวกเตอร์ออกเป็น 100 กลุ่ม เพื่อลดจำนวนเวกเตอร์ที่ต้องเปรียบเทียบ
จาก 9,039 รายการลงเหลือเฉพาะกลุ่มที่ใกล้เคียง

**ข้อควรระวังที่กำหนดไว้ในการออกแบบ** ขนาดมิติของเวกเตอร์ต้องตรงกับโมเดลที่ใช้เสมอ
ระบบส่วนหลังจึงตรวจสอบค่านี้ตอนเริ่มทำงานและปฏิเสธการเริ่มระบบหากไม่ตรงกัน
เนื่องจากเวกเตอร์ที่คำนวณจากคนละโมเดลไม่สามารถนำมาเปรียบเทียบกันได้

## 3.3.6 การออกแบบสิทธิ์การเข้าถึงข้อมูล

ระบบแบ่งบัญชีผู้ใช้ฐานข้อมูลตามหลักสิทธิ์น้อยที่สุด (Principle of Least Privilege)

## 3.3.7 การทำให้อยู่ในรูปบรรทัดฐาน (Normalization)

**ระดับบรรทัดฐานที่ 1 (1NF)** ทุกตารางมีคีย์หลักและไม่มีกลุ่มข้อมูลซ้ำ
ยกเว้นคอลัมน์ที่จงใจเก็บเป็นโครงสร้างกึ่งมีรูปแบบ ได้แก่ `courses.tags`,
`user_profiles.skills`, `user_profiles.interests`, `course_chunks.metadata`,
`recommendations.retrieved_chunk_ids` และ `shadow_answers.facts`

**เหตุผลของการยกเว้น** ข้อมูลเหล่านี้เป็นข้อมูลประกอบที่ไม่ถูกใช้เป็นเงื่อนไขในการเชื่อมตาราง
และรูปแบบของมันเปลี่ยนตามรุ่นของระบบ การแยกเป็นตารางต่างหากจะทำให้ต้องปรับโครงสร้าง
ฐานข้อมูลทุกครั้งที่เพิ่มชนิดข้อมูลประกอบใหม่ PostgreSQL รองรับการค้นภายใน JSONB
ด้วยดัชนีชนิด GIN อยู่แล้ว จึงยังค้นหาได้อย่างมีประสิทธิภาพ

**ระดับบรรทัดฐานที่ 2 (2NF)** ตารางที่ใช้คีย์หลักแบบผสมทุกตารางมีคุณสมบัติครบ
คอลัมน์ที่ไม่ใช่คีย์ขึ้นกับคีย์หลักทั้งชุด ไม่ขึ้นกับเพียงบางส่วน
เช่น `mko.document_pages` ที่ใช้คีย์ `(document_id, page_number)` ทุกคอลัมน์ล้วนเป็นคุณสมบัติ
ของ "หน้าหนึ่งหน้าในเอกสารหนึ่งฉบับ"

**ระดับบรรทัดฐานที่ 3 (3NF)** ตารางในกลุ่มข้อมูลปฏิบัติการไม่มีคอลัมน์ที่ขึ้นต่อกันเอง
โดยไม่ผ่านคีย์หลัก การแยก `programs` (สาขาวิชา) ออกจาก `curricula` (หลักสูตรรายฉบับปี)
เป็นตัวอย่างของการขจัดความขึ้นต่อกันแบบส่งผ่าน เพราะชื่อสาขาเป็นคุณสมบัติของสาขา
ไม่ใช่ของฉบับปีการศึกษา

**การลดรูปบรรทัดฐานโดยเจตนา (Intentional Denormalization)** ตาราง `published_values`
และ `published_list_items` เก็บข้อมูลซ้ำกับต้นทาง ได้แก่ ชื่อไฟล์ เลขหน้า ข้อความที่ยกมา
และผู้ตรวจ ทั้งที่สามารถเชื่อมกลับไปอ่านจาก `evidence` ได้

เหตุผลคือตารางทั้งสองทำหน้าที่เป็น **ภาพถ่ายข้อมูล ณ เวลาที่เผยแพร่** ซึ่งต้องคงที่ไม่เปลี่ยนแปลง
แม้ข้อมูลต้นทางจะถูกสกัดใหม่หรือแก้ไขภายหลัง หากใช้การเชื่อมตารางแทน ค่าที่เคยเผยแพร่ไปแล้ว
จะเปลี่ยนตามข้อมูลต้นทางโดยที่ไม่มีใครสั่ง ซึ่งขัดกับวัตถุประสงค์ของการเผยแพร่เป็นชุด
การลดรูปบรรทัดฐานในกรณีนี้จึงเป็นการออกแบบที่ตั้งใจ ไม่ใช่ข้อบกพร่อง
