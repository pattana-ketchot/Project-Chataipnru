* log เก่าที่ยังค้างอยู่บนเซิร์ฟเวอร์จากการวัดครั้งก่อน ๆ พบ "ตกไปใช้โมเดลในเครื่อง"

### 2.1 การเขียนเกิดตามเวลา ไม่ใช่ตามเหตุการณ์

รอบแรกใช้คำขอของผู้ใช้เป็นตัวจุดชนวนการเขียน ซึ่งผิดกับพฤติกรรมจริงของระบบนี้ —
คำถามมาเป็นช่วง ๆ แล้วเงียบไปเป็นชั่วโมง ตัวเลขของช่วงท้ายจะค้างอยู่ในหน่วยความจำ
จนกว่าจะมีคนถามอีกครั้งหรือจนกว่าจะปิดระบบ

ตอนนี้เป็น **เธรดเบื้องหลังที่ผูกกับ lifespan ของแอป**

| จังหวะ | เกิดอะไร |
|---|---|
| แอปเริ่มทำงาน | `llm_usage.start_flusher()` — เธรดตื่นทุก `FLUSH_EVERY_S` (30 วินาที) |
| ระหว่างทำงาน | เธรดเขียนเองไม่ว่าจะมีคำถามเข้ามาหรือไม่ |
| แอปปิด | `llm_usage.stop_flusher()` — หยุดเธรดแล้วเขียนครั้งสุดท้าย รออย่างมาก 3 วินาที |

ผลข้างเคียงที่ตั้งใจ: **คำขอของผู้ใช้ไม่มีงานฐานข้อมูลของตัวนับติดอยู่เลย**
`record()` ทำแค่บวกเลขในหน่วยความจำ (มีชุดทดสอบยืนยันว่าเรียก 50 ครั้งแล้วไม่เปิด
session ฐานข้อมูลแม้ครั้งเดียว)

กระบวนการที่ไม่ได้ผ่าน lifespan (สคริปต์ ชุดประเมิน) ยังมีทางสำรอง: `record()` จะสั่ง
เขียนในเธรดแยกเมื่อถึงกำหนด และ `atexit` เก็บของค้างตอนจบ

### 2.2 ชื่อเหตุการณ์ที่นับ

ฝั่ง Gemini

| เหตุการณ์ | ความหมาย |
|---|---|
| `gemini_ok` | โมเดลหลักตอบสำเร็จ |
| `gemini_backup:<ชื่อ>` | โมเดล Gemini ตัวสำรองตอบสำเร็จ |
| `gemini_quota_minute:<ชื่อ>` | ชนเพดานต่อนาทีของโมเดลนั้น |
| `gemini_quota_day:<ชื่อ>` | ชนโควตารายวันของโมเดลนั้น |
| `gemini_overload:<ชื่อ>` | โมเดลนั้นตอบ 5xx |
| `gemini_quota_midstream` | ชนโควตาหลังเริ่มส่งคำตอบแล้ว สลับโมเดลไม่ได้ |
| `gemini_all_failed` | Gemini ทุกตัวใช้ไม่ได้ในคำขอนั้น |

ฝั่งตัวสำรองในเครื่อง — **แยกการพยายามเรียกออกจากผล**

| เหตุการณ์ | ความหมาย |
|---|---|
| `fallback_local_attempt` | เริ่มเรียกโมเดลในเครื่อง |
| `fallback_local_ok` | โมเดลในเครื่องตอบจบตามปกติ |
| `fallback_local_failed` | โมเดลในเครื่องล้ม — **ผู้ใช้ไม่ได้คำตอบ** |
| `fallback_declined` | ขั้นที่ต้องอ้างอิงเอกสารจึงไม่ยอมใช้ตัวสำรอง |
| `stream_failed_midway` | สตรีมของเจ้าหลักล้มหลังส่งตัวอักษรแรกแล้ว |

รอบแรกนับรวมเป็น `fallback_local` ตัวเดียว ซึ่งอ่านผิดได้ง่าย เพราะ
**"เรียกตัวสำรอง" ไม่เท่ากับ "ผู้ใช้ได้คำตอบ"** โมเดลในเครื่องล้มได้เหมือนกัน
โดยเฉพาะเมื่อเพดานเวลาของคำขอหมดก่อนมันเขียนจบ ซึ่งเกิดได้จริงเพราะมันช้ากว่ามาก
ถ้านับรวม ความล้มเหลวจะถูกนับเป็นความสำเร็จ

**สำหรับสตรีม "สำเร็จ" คือ generator เดินจนจบโดยไม่โยนข้อผิดพลาด** ไม่ใช่แค่เริ่มส่ง
ตัวอักษรแรกได้ — ผู้ใช้ที่ได้คำตอบครึ่งเดียวคือคนที่ไม่ได้คำตอบ
ส่วนผู้ใช้ที่ปิดหน้าเว็บกลางคัน (`GeneratorExit`) ไม่ถูกนับทั้งสำเร็จและล้มเหลว
เพราะไม่ใช่ทั้งสองอย่าง

### 2.3 หน่วยของการนับ และตัวหารที่ถูกต้อง

**หน่วยคือ "การเรียกเพื่อเขียนคำตอบหนึ่งครั้ง"**
**ไม่ใช่จำนวนคำถาม และไม่ใช่จำนวนผู้ใช้**

* คำถามข้อเดียวเรียกโมเดลได้หลายครั้ง (เขียนคำถามใหม่ ตรวจว่าตอบจากเอกสารได้ไหม
  แล้วจึงเขียนคำตอบ)
* คำถามที่ตอบได้จากฐานข้อมูลหรือจากแคชไม่เรียกโมเดลเลย
* ผู้ใช้คนเดียวถามได้หลายครั้ง และระบบไม่ได้นับผู้ใช้

ห้าเหตุการณ์นี้คือ **ผลลัพธ์สุดท้าย** ของการเรียกหนึ่งครั้ง เกิดได้ครั้งละหนึ่งอย่าง
(มีชุดทดสอบยืนยันว่าทุกเส้นทางนับปลายทางพอดีหนึ่งครั้ง) ผลรวมของมันจึงเป็นตัวหารที่ถูก

```
ตัวหาร = gemini_ok + Σ gemini_backup:* + fallback_local_attempt
                   + fallback_declined + stream_failed_midway
```

`fallback_local_ok` กับ `fallback_local_failed` เป็นผลของ `fallback_local_attempt`
อีกชั้นหนึ่ง **ห้ามเอามารวมในตัวหาร** ไม่งั้นจะนับการเรียกเดียวกันสองครั้ง

## 3. สิ่งที่ตัวนับนี้ไม่เก็บ

ไม่เก็บคำถาม ไม่เก็บคำตอบ ไม่เก็บว่าใครถาม ไม่เก็บเวลาที่ละเอียดกว่าระดับวัน
หนึ่งแถวคือ `(วัน, ชื่อเหตุการณ์, จำนวนครั้ง)` เท่านั้น จึงไม่มีข้อมูลส่วนบุคคลเลย
ตารางโตประมาณ 10–15 แถวต่อวัน

| log ถูกกลบถ้ายังไม่ได้รัน migration | เขียน log เต็มเฉพาะครั้งที่ 1, 10, 100, … | — |

**ข้อจำกัดที่ยอมรับ** ถ้ากระบวนการถูกฆ่าแบบไม่ทันเก็บของ (SIGKILL) ตัวเลขช่วงไม่เกิน

**ลำดับสำคัญ: รัน migration ก่อน แล้วค่อยขึ้นโค้ด** ถ้าสลับลำดับ โค้ดจะพยายามเขียน
ตารางที่ยังไม่มีทุก 30 วินาที (ไม่พัง แต่มี log เตือนและตัวเลขค้างในหน่วยความจำ)

1. สำรองฐานข้อมูลตามขั้นตอนปกติ
2. รัน `db/migrations/008_llm_usage_counter.sql` ด้วย superuser บน `course_advisor`
3. build อิมเมจโดย **ซ้อนเฉพาะ 4 ไฟล์ทับอิมเมจ production ปัจจุบัน**
4. พิสูจน์ว่า md5 ต่างจากอิมเมจเดิมเฉพาะ 4 ไฟล์นั้น
5. ขึ้นแล้วถามคำถามจริงผ่าน `/api/chat` หนึ่งข้อ รออย่างน้อย 30 วินาที
   แล้วตรวจว่ามีแถวใน `llm_usage_daily` จริง

> ⚠ `backend/app/main.py` ใน working tree **มีงานที่ยังไม่ deploy ปนอยู่**
> (เส้นทาง `crawl_review`) ไฟล์ที่จะขึ้นต้องเป็น main.py ของอิมเมจ production
> บวกเฉพาะ 11 บรรทัดของตัวนับ ไม่ใช่ไฟล์จาก working tree
> รายละเอียดอยู่ใน `LLM_USAGE_COUNTER_RELEASE_READINESS_2569-10-16.md`

## 7. วิธีใช้ตัวเลขนี้ตัดสินใจ — และสิ่งที่มันตัดสินใจแทนไม่ได้

### 7.1 ตัวนับอย่างเดียวสรุปไม่ได้

**ห้ามสรุปว่า "ไม่ต้องมีผู้ให้บริการสำรอง" จากตัวเลขชุดนี้อย่างเดียว**
มันบอก **ความถี่** อย่างเดียว ไม่ได้บอกว่าความถี่นั้นแปลว่าอะไรกับผู้ใช้

ต้องมีอีกสามอย่างประกอบ ซึ่ง **ตัวนับนี้ไม่ได้เก็บให้**

| ข้อมูลที่ต้องมีเพิ่ม | ทำไมขาดไม่ได้ | ตอนนี้หาได้จากไหน |
|---|---|---|
| **เวลาตอบ** (p50 / p95 ของการเรียกที่จบที่ตัวสำรอง เทียบกับที่จบที่เจ้าหลัก) | `fallback_local_ok` 100 ครั้งที่ใช้เวลา 5 วินาที กับ 100 ครั้งที่ใช้เวลา 40 วินาที เป็นคนละสถานการณ์โดยสิ้นเชิง แต่ตัวนับเห็นเท่ากัน | บรรทัด timing ที่ `services/chat.py::_log_timing` เขียน — **อยู่ใน log ของคอนเทนเนอร์เท่านั้น และหายเมื่อ deploy** ยังไม่มีที่เก็บถาวร |
| **จำนวนตัวอย่างและช่วงเวลา** (มีการเรียกทั้งหมดกี่ครั้ง กี่วัน มีผู้ใช้จริงหรือเป็นช่วงที่ไม่มีคนใช้) | 3 ครั้งจาก 10 การเรียกในวันที่ไม่มีคนใช้ ไม่ใช่ 30% ที่เชื่อได้ | ตัวหารในข้อ 2.3 บอกจำนวนการเรียก แต่ **ไม่บอกจำนวนผู้ใช้หรือจำนวนคำถาม** ต้องดูจากที่อื่น |
| **คำขอที่ล้มจริง** (ผู้ใช้ไม่ได้คำตอบ) | นี่คือสิ่งที่ผู้ใช้เจอจริง ไม่ใช่ว่าใครเป็นคนตอบ | `fallback_local_failed` + `stream_failed_midway` + `fallback_declined` จากตัวนับนี้ ประกอบกับ 503 ที่ Caddy/แอปตอบ ซึ่งยังไม่มีที่เก็บถาวรเช่นกัน |

**เงื่อนไขขั้นต่ำก่อนสรุปอะไรก็ตาม** เก็บอย่างน้อย **1–2 สัปดาห์ที่มีผู้ใช้จริง**
และมีจำนวนการเรียกมากพอที่สัดส่วนจะไม่แกว่งเพราะเหตุการณ์ไม่กี่ครั้ง
ถ้าตัวหารยังน้อย ให้รายงานเป็น "ยังสรุปไม่ได้" ไม่ใช่รายงานเป็นเปอร์เซ็นต์

### 7.2 ตารางอ่านผล (ใช้เป็นตัวตั้งต้นของการสืบต่อ ไม่ใช่ข้อสรุป)

| สิ่งที่เห็น | เป็นสัญญาณว่า | ต้องตรวจอะไรต่อก่อนสรุป |
|---|---|---|
| `fallback_local_attempt` แทบไม่มี | ชั้นสำรอง Gemini รับไว้ได้เกือบทั้งหมด | ตัวหารมากพอหรือยัง · ช่วงนั้นมีผู้ใช้จริงไหม |
| `fallback_local_failed` มีสัดส่วนสูงเทียบกับ `_attempt` | ตัวสำรองรับไม่ไหวจริง | เวลาตอบของเส้นทางนั้น · เพดานเวลาของคำขอตั้งไว้เท่าไร |
| `gemini_quota_day` เยอะ | ชนโควตารายวันของโมเดล | ดูข้อ 7.3 ก่อนสรุปว่าจะเพิ่มโควตาอย่างไร |
| มีแต่ `gemini_quota_minute` | ยิงถี่เกินในบางนาที | การหมุนโมเดลรับไว้ได้อยู่แล้วไหม (ดูว่ามี `gemini_backup:*` ตามมา) |
| `gemini_overload` เยอะ | ฝั่งผู้ให้บริการรับไม่ไหวเป็นช่วง ๆ | กระจุกอยู่ที่โมเดลเดียวหรือทุกตัว · เกิดเวลาเดิมของวันไหม |
| `stream_failed_midway` เยอะ | ผู้ใช้เห็นคำตอบขาดกลางคัน | เป็นปัญหาคนละเรื่องกับโควตา ต้องดูเพดานเวลาและเครือข่าย |

### 7.3 เรื่องโควตา — สิ่งที่ยืนยันแล้วกับสิ่งที่ยังไม่ยืนยัน

**ยืนยันแล้วจากคำตอบจริงของ Google** เนื้อความ 429 ที่ระบบได้รับมี
`quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier` ซึ่งระบุว่าโควตารายวัน
ของชั้นใช้งานฟรีคิด **ต่อโปรเจกต์ ต่อโมเดล** — การที่ระบบหมุนไปโมเดลอื่นแล้วใช้งานได้ต่อ
เป็นพฤติกรรมที่สังเกตได้จริงบนเซิร์ฟเวอร์ (ดูคำอธิบายใน `llm/gemini.py`)

**ยังไม่ยืนยัน — ห้ามเขียนในรายงานใดว่าทำได้**

* **การเพิ่ม API key อีกใบแล้วจะได้โควตาก้อนใหม่** — คีย์ผูกกับโปรเจกต์ คีย์ใบที่สอง
  ในโปรเจกต์เดิมจึงน่าจะใช้โควตาก้อนเดียวกัน **ยังไม่ได้ทดลองและยังไม่ได้อ่านเงื่อนไข**
* **การเปิดโปรเจกต์ใหม่เพื่อให้ได้โควตาเพิ่ม** — ต้องอ่านเงื่อนไขการใช้งานของผู้ให้บริการ
  ก่อนว่าอนุญาตหรือถือเป็นการเลี่ยงเพดาน **ยังไม่ได้ตรวจ**
* **การเติมชื่อโมเดลใน `GEMINI_FALLBACK_MODELS`** ทำได้ทางเทคนิคโดยไม่ต้อง build ใหม่
  แต่ต้องตรวจก่อนว่าโมเดลที่เติมมีอยู่จริง ใช้ได้กับคีย์ปัจจุบัน และคุณภาพคำตอบยอมรับได้
  — ไม่ใช่การแก้ค่าแล้วจบ

เรื่องเหล่านี้ต้องตรวจกับเอกสารและเงื่อนไขของผู้ให้บริการก่อนตัดสินใจ
ไม่ใช่อนุมานจากพฤติกรรมที่สังเกตได้
