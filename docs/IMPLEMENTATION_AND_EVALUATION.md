## 2. ปัญหาที่ทำให้ระบบใช้งานไม่ได้

ก่อนเริ่มงานรอบนี้ ระบบยังไม่เคยถูกรันตั้งแต่ต้นจนจบ เมื่อทดลองรันจริงพบปัญหาที่ทำให้
ระบบทำงานไม่ได้ในทุกชั้น ดังนี้

### 2.1 ชั้นฐานข้อมูล

| # | ปัญหา | สาเหตุ | ผลกระทบ |
|---|---|---|---|
| 1 | `CREATE TABLE user_profiles` ล้มเหลว | ตั้งชื่อคอลัมน์ว่า `current_role` ซึ่งเป็น reserved keyword ของ PostgreSQL | สคริปต์หยุดที่บรรทัด 53 สร้างตารางได้ 1 จาก 9 ตาราง |
| 2 | ไม่มี role `advisor_api` / `advisor_ingest` | คำสั่ง `CREATE ROLE` ถูกคอมเมนต์ไว้ | backend เชื่อมต่อฐานข้อมูลไม่ได้เลย |
| 3 | `updated_at` ไม่เคยเปลี่ยนค่า | `DEFAULT now()` มีผลตอน INSERT เท่านั้น และไม่มี trigger | คอลัมน์เท่ากับ `created_at` ตลอดไป |

**วิธีแก้** ใส่เครื่องหมาย `"current_role"` (SQLAlchemy รู้จักคำนี้เป็น reserved word และใส่ให้อัตโนมัติอยู่แล้ว
จึงไม่ต้องแก้โค้ดฝั่ง ORM), ย้ายการสร้าง role ไปไว้ที่ `db/20-roles.sh` ซึ่งอ่านรหัสผ่านจาก
environment variable แทนการเขียนลงไฟล์ที่เก็บใน git, และเพิ่ม trigger `BEFORE UPDATE`
ที่ชั้นฐานข้อมูล

> **เหตุผลที่เลือกทำ trigger ที่ฐานข้อมูล ไม่ใช่ `onupdate` ของ SQLAlchemy**
> ตาราง `courses` ถูกเขียนโดย pipeline ผ่าน psycopg โดยตรงไม่ผ่าน ORM
> ถ้าทำที่ชั้น Python จะครอบไม่ถึงเส้นทางนั้น

### 2.2 ชั้น Backend

| # | ปัญหา | สาเหตุ | ผลกระทบ |
|---|---|---|---|
| 4 | backend เริ่มทำงานไม่ได้ | `env_file=".env"` เป็น path สัมพัทธ์ อ่านจาก working directory | รันตามคู่มือ (จากโฟลเดอร์ `backend/`) จะหาไฟล์ `.env` ที่ root ไม่เจอ |
| 5 | สมัครสมาชิกและเข้าสู่ระบบใช้ไม่ได้ | passlib 1.7.4 (เผยแพร่ปี 2020) เข้ากันไม่ได้กับ bcrypt เวอร์ชัน 4.1 ขึ้นไป | เกิด `ValueError` ตั้งแต่ตอน import |
| 6 | dummy hash ที่ใช้กัน user enumeration อาจใช้ไม่ได้จริง | เป็นสตริงที่เขียนด้วยมือ อาจมีรูปแบบไม่ถูกต้อง | ถ้ารูปแบบผิด ฟังก์ชันจะคืนค่าทันที ทำให้เวลาตอบสนองต่างจากกรณีที่พบผู้ใช้จริง |
| 7 | ทุกการเชื่อมต่อฐานข้อมูลช้า 5 วินาที | `.env` ระบุ host เป็น `localhost` ซึ่งบน Windows ถูกแปลงเป็น IPv6 (`::1`) ก่อน แต่ Docker ผูกพอร์ตไว้ที่ IPv4 เท่านั้น | ต้องรอ timeout ก่อน fallback มา IPv4 โดยไม่มีข้อความแจ้งข้อผิดพลาด |
| 8 | backend import ไม่ผ่าน | `requirements.txt` ระบุ `pydantic` แต่โค้ดใช้ `EmailStr` ซึ่งต้องการ `pydantic[email]` | ติดตั้งตามไฟล์แล้วรันไม่ได้ |

**วิธีแก้** ยึด path ของ `.env` กับตำแหน่งไฟล์แทน working directory, ตัด passlib ออกแล้วเรียก
bcrypt โดยตรง, สร้าง dummy hash จากฟังก์ชันจริงตอน import, เปลี่ยน host เป็น `127.0.0.1`,
และแก้ระบุ dependency ให้ตรงกับที่โค้ดใช้

> **หมายเหตุเรื่องรหัสผ่านภาษาไทย**
> bcrypt รับข้อมูลได้สูงสุด 72 ไบต์ ซึ่งภาษาไทยใช้ 3 ไบต์ต่อตัวอักษร จึงชนเพดานที่
> 24 ตัวอักษร แก้โดยทำ SHA-256 ก่อนแล้วเข้ารหัส base64 (ได้ความยาวคงที่ 44 ไบต์)
> ทดสอบด้วยรหัสผ่านไทย 76 ตัวอักษร (228 ไบต์) ผ่านทั้งการสร้างและตรวจสอบ

## 3. การจัดการข้อความภาษาไทยจาก PDF

เอกสาร มคอ.2 ที่นำมาใช้มีความเสียหายระดับอักขระ 3 รูปแบบ ซึ่งมองด้วยตาไม่เห็นความผิดปกติ
แต่ทำให้การค้นหาด้วยข้อความล้มเหลวทั้งหมด

### 3.1 วรรณยุกต์ถูกแม็ปไปยัง Private Use Area

**อาการ** ข้อความที่ดึงจาก PDF ได้ `คณะวิทยาศาสตรและเทคโนโลยี` แทนที่จะเป็น
`คณะวิทยาศาสตร์และเทคโนโลยี`

**สาเหตุ** ฟอนต์ไทยตระกูล Angsana/Cordia ใช้ glyph คนละตัวสำหรับวรรณยุกต์ตัวเดียวกัน
ขึ้นกับว่าวางบนพยัญชนะที่มีหางสูง (ป ฝ ฟ) หรือมีสระบนอยู่ก่อนแล้วหรือไม่ รูปแปรเหล่านี้
ไม่มีตำแหน่งใน Thai Unicode block จึงถูกกำหนดไว้ในช่วง Private Use Area (U+F700–F71F)

**การถอดรหัส** สอบทานจากบริบทจริงในเอกสารทั้ง 23 codepoint เช่น

| codepoint | จำนวนที่พบ | บริบท | ถอดได้เป็น |
|---|---|---|---|
| U+F70B | 18,251 | `ไดจัด` | ้ (ไม้โท) |
| U+F70A | 11,534 | `กลาว` | ่ (ไม้เอก) |
| U+F70E | 10,937 | `คอมพิวเตอร` | ์ (ทัณฑฆาต) |
| U+F712 | 1,562 | `จำเปน` | ็ (ไม้ไต่คู้) |
| U+F710 | 869 | `ฟง` | ั (ไม้หันอากาศ) |

รูปแบบที่ได้สอดคล้องเป็นระบบ: `F701–F709` คือกลุ่มที่วางเยื้องซ้าย, `F70A–F70E` คือกลุ่ม
ที่ลดระดับลง, `F710–F717` คือกลุ่มที่ใช้คู่กับสระ ั

**ผลกระทบและผลหลังแก้** พบใน 4 จาก 18 ไฟล์ โดยได้รับผลกระทบเกือบทุกบรรทัด

| ไฟล์ | `ให้` ก่อน → หลัง | `เป็น` ก่อน → หลัง | `วิทยาศาสตร์` ก่อน → หลัง |
|---|---|---|---|
| animation64 | 0 → 520 | 0 → 409 | 0 → 89 |
| cs61 | 0 → 469 | 0 → 394 | 0 → 281 |
| fs61 | 0 → 429 | 0 → 322 | 33 → 514 |
| it66 | 0 → 562 | 0 → 424 | 14 → 79 |

### 3.2 สระ ำ ถูกแยกเป็นช่องว่างกับสระอา

**อาการ** `จ านวน` แทน `จำนวน`, `ค าน า` แทน `คำนำ` พบ **13,292 ครั้ง** กระจายใน 12 จาก 18 ไฟล์

**วิธีแก้** เชื่อมกลับด้วยรูปแบบ `พยัญชนะ + ช่องว่าง + า` → `พยัญชนะ + ำ`
ปลอดภัยเพราะภาษาไทยไม่มีคำที่ขึ้นต้นด้วยสระ า ลำดับดังกล่าวจึงเป็นซากของ ำ เสมอ

### 3.3 สระ ำ ในรูปนิคหิตกับสระอา

**อาการ** บางไฟล์เข้ารหัส ำ เป็น U+0E4D (นิคหิต) + U+0E32 (สระอา) ซึ่งมองด้วยตาเหมือนกันทุกประการ
แต่เป็นคนละ codepoint

**ผลกระทบที่พบจริง** ไฟล์ `cos66` กับ `cosmetic61` เป็น**หลักสูตรวิทยาศาสตร์เครื่องสำอางเดียวกัน
คนละปีการศึกษา** แต่เข้ารหัสคำว่า "สำอาง" ต่างกัน ทำให้ค้นหาด้วยคำเดียวกันแล้วเจอไม่เท่ากัน

**ผลหลังแก้** ทั้งสองไฟล์ใช้รูปเดียวกันแล้ว (614 และ 490 ครั้งตามลำดับ) และไม่เหลือรูปนิคหิต+สระอา

### 3.4 ลำดับการทำงานใน clean_document

เดิมโปรแกรมตรวจหาบรรทัดซ้ำ (header/footer) จาก**ข้อความดิบ** แล้วนำไปเทียบกับ**ข้อความที่
normalize แล้ว** ทำให้ตัด header ไม่ออกจริง แก้โดยซ่อมอักขระให้เรียบร้อยก่อนแล้วจึงตรวจหาบรรทัดซ้ำ

ผลคือระบบตัดบรรทัด `คณะวิทยาศาสตร์และเทคโนโลยี  มหาวิทยาลัยราชภัฏพระนคร` ที่ปรากฏซ้ำ
ใน 297 หน้าของไฟล์ `it61` ออกได้ ถ้าไม่ตัด ทุก chunk จะมีข้อความเดียวกันเจือปนและรบกวนการ
เปรียบเทียบความคล้าย

**ผลรวมหลังแก้ทั้ง 3 รูปแบบ:** ไม่เหลืออักขระ PUA ในคลังเอกสารทั้งหมด (0 ตัว)

## 4. การเลือกโมเดล embedding

### 4.1 ปัญหาที่พบกับโมเดลเดิม

ระบบเริ่มต้นใช้ `nomic-embed-text` (768 มิติ) เมื่อทดสอบการค้นหาด้วยคำค้น 3 คำที่ต่างกัน
สิ้นเชิง พบว่าได้ผลลัพธ์ชุดเดียวกันและคะแนนเท่ากันทุกตัวถึงทศนิยมตำแหน่งที่ 3

การตรวจสอบพบว่า chunk หลายก้อนที่มีเนื้อหาต่างกันโดยสิ้นเชิงมีค่า embedding **เหมือนกันทุกตัวเลข**
เมื่อทดสอบที่ต้นทางได้ผลดังนี้

| ภาษาของข้อความทดสอบ | จำนวนข้อความ | จำนวน vector ที่ไม่ซ้ำ |
|---|---|---|
| อังกฤษ | 3 | 3 |
| **ไทย** | 3 | **1** |
| ไทยปนอังกฤษ | 2 | 2 |

**สรุปสาเหตุ** `nomic-embed-text` ฝึกด้วยคลังภาษาอังกฤษเป็นหลัก tokenizer ไม่มีหน่วยย่อยของ
อักษรไทย ข้อความภาษาไทยทุกข้อความจึงถูกแปลงเป็นลำดับโทเคนเดียวกันและได้ค่า embedding เดียวกัน

**นัยสำคัญ** ระบบค้นหาเชิงความหมายทั้งหมดไม่ทำงาน แต่**ไม่มีอาการผิดปกติให้สังเกตเห็น** —
API ตอบสถานะปกติ หน้าเว็บแสดงผลได้ และมีข้อมูล 7,301 chunk อยู่ในฐานข้อมูลจริง

### 4.2 โมเดลที่เลือกใช้แทน

เลือก `bge-m3` เนื่องจากฝึกด้วยข้อมูลหลายภาษารวมภาษาไทย มี context 8,192 โทเคน และรันบน
Ollama ได้ ผลการตรวจสอบ

| การทดสอบ | ผล |
|---|---|
| ข้อความไทย 3 ข้อความต่างกัน | ได้ vector ต่างกัน 3 ค่า |
| มิติของ vector | 1,024 |
| cosine similarity: "อยากเรียนนวดแผนไทย" กับหัวข้อการแพทย์แผนไทย | 0.654 |
| cosine similarity: คำค้นเดียวกัน กับหัวข้อการเขียนโปรแกรม | 0.375 |
| cosine similarity: คำค้นเดียวกัน กับหัวข้อเครื่องสำอาง | 0.379 |
| embedding ที่ไม่ซ้ำกันหลังนำเข้าใหม่ | 7,292 จาก 7,301 chunk |

### 4.3 ผลข้างเคียงของการเปลี่ยนโมเดล

การเปลี่ยนโมเดลทำให้มิติของ vector เปลี่ยนจาก 768 เป็น 1,024 ซึ่งกระทบ 3 จุดที่ต้องแก้ให้ตรงกัน
ได้แก่ `EMBED_MODEL`/`EMBED_DIM` ใน `.env`, ชนิดคอลัมน์ใน `db/schema.sql` และข้อมูลเดิมทั้งหมด
ที่ต้องนำเข้าใหม่เพราะคำนวณจากคนละโมเดล

เพื่อป้องกันความไม่สอดคล้องในอนาคต ได้เพิ่มการตรวจสอบตอนเริ่มระบบ โดยอ่านมิติจริงของคอลัมน์
จาก `pg_attribute` แล้วเทียบกับค่าที่ตั้งไว้ ถ้าไม่ตรงจะปฏิเสธการเริ่มทำงานพร้อมแสดงค่าทั้งสองฝั่ง

> **เหตุผลของการออกแบบให้ล้มเหลวทันที** ความไม่สอดคล้องแบบนี้ไม่แสดงอาการผิดปกติ
> ระบบยังตอบสถานะ 200 และหน้าเว็บยังทำงาน แต่ผลลัพธ์ผิดทั้งหมด การตรวจพบตั้งแต่
> ตอนเริ่มระบบจึงดีกว่าปล่อยให้ไปแสดงอาการตอนสาธิต

**เวลาที่ใช้นำเข้าข้อมูล** nomic-embed-text 3.8 นาที · bge-m3 20.5 นาที (18 ไฟล์, 7,301 chunk)

## 5. การแบ่ง chunk สำหรับภาษาไทย

**ปัญหา** โปรแกรมเดิมแบ่ง chunk ด้วย `text.split()` ซึ่งนับคำจากช่องว่าง แต่ภาษาไทยไม่เขียน
เว้นวรรคระหว่างคำ

| ตัวชี้วัด | ก่อนแก้ | หลังแก้ |
|---|---|---|
| ขนาด chunk | 22 – 3,780 ตัวอักษร | 30 – 1,000 ตัวอักษร |
| ค่ามัธยฐาน | ไม่สม่ำเสมอ | ประมาณ 950 ตัวอักษร |
| chunk ที่ยาวเกิน 2,000 ตัวอักษร | มี | 0 |
| ค่า `token_count` ที่บันทึก | 115 (ขณะที่เนื้อหาจริง 3,316 ตัวอักษร) | ประมาณการตามสัดส่วนไทย/อังกฤษ |
| ไฟล์ที่นำเข้าไม่สำเร็จ | 3 จาก 18 | 0 จาก 18 |
| จำนวน chunk รวม | 3,772 | 7,301 |

ไฟล์ที่นำเข้าไม่สำเร็จเกิดจาก chunk ที่ยาวเกิน context ของ embedding model ทำให้ได้รับ
ข้อผิดพลาด `input length exceeds the context length`

**วิธีแก้** เปลี่ยนไปแบ่งตามจำนวนตัวอักษร (1,000 ตัวอักษร ซ้อนทับ 150 ตัวอักษร) ซึ่งให้ผลที่
คาดเดาได้กับทุกภาษา และถอยหาช่องว่างในระยะ 120 ตัวอักษรก่อนตัดเพื่อไม่ให้คำขาดกลางเมื่อมี
ช่องว่างให้ตัด

**ทางเลือกที่ดีกว่าในอนาคต** ใช้ตัวตัดคำภาษาไทย (เช่น pythainlp) แล้วแบ่งตามขอบเขตคำจริง
แลกกับ dependency ที่หนักขึ้นและเวลาประมวลผลที่เพิ่มขึ้น

## 6. สถาปัตยกรรมของระบบสนทนา

`/chat` ต่างจาก `/recommend` ตรงที่จำบทสนทนาได้ ตอบเป็นภาษาธรรมชาติ และจำกัดขอบเขตเฉพาะ
เรื่องหลักสูตร ประกอบด้วย 4 ชั้นตามลำดับ

### ชั้นที่ 1 — คำทักทายและคำถามทั่วไป

ข้อความอย่าง "สวัสดีครับ" ไม่มีเนื้อหาให้ค้นในเอกสาร จึงได้คะแนนความคล้ายต่ำ (วัดได้ 0.477–0.556)
และถูกปฏิเสธด้วยข้อความว่าตอบได้เฉพาะเรื่องหลักสูตร ซึ่งเป็นสิ่งแรกที่ผู้ใช้พบเมื่อเปิดใช้งาน

แก้โดยตรวจจับคำทักทาย คำขอบคุณ คำอำลา และคำถามว่าระบบทำอะไรได้ **ก่อน**เข้าสู่ขั้นตอนค้นหา
แล้วตอบจากข้อความสำเร็จรูป ใช้เวลา 0.0–0.1 วินาที และไม่มีโอกาสที่โมเดลจะตอบนอกบทบาท

การเทียบใช้วิธีเทียบทั้งข้อความหลังตัดคำลงท้ายสุภาพ ไม่ใช่การค้นหาคำย่อยในข้อความ เพื่อไม่ให้
ข้อความอย่าง "สวัสดีครับ อยากถามเรื่องหลักสูตรวิทคอมหน่อย" ถูกดักเป็นคำทักทายจนคำถามจริงหายไป

### ชั้นที่ 2 — การเขียนคำถามใหม่ให้สมบูรณ์

คำถามต่อเนื่องอย่าง "แล้วต้องเรียนกี่หน่วยกิต" ไม่มีข้อมูลว่าหมายถึงหลักสูตรใด เมื่อนำไปทำ
embedding ตรงๆ จะค้นเจอเนื้อหาที่ไม่เกี่ยวข้อง จึงต้องเขียนคำถามใหม่โดยเติมบริบทจากประวัติก่อน

จากการทดสอบ การเขียน prompt แบบบรรยายกฎเฉยๆ ใช้ไม่ได้ผลกับ qwen2.5:7b โมเดลจะ
**ตอบคำถามแทนที่จะเขียนคำถามใหม่** เช่นได้ผลลัพธ์เป็น "คุณต้องการเรียงลำดับข้อมูลอย่างไรครับ"
ซึ่งทำให้คะแนนความคล้ายเพี้ยนจนคำถามนอกเรื่องผ่านเกณฑ์เข้ามาได้

ต้องใช้ 3 วิธีร่วมกันจึงได้ผล

1. บังคับรูปแบบผลลัพธ์เป็น JSON
2. ส่งเฉพาะคำถามของผู้ใช้เป็นประวัติ ไม่ส่งคำตอบของระบบ (โมเดลมักลอกเนื้อความจากคำตอบเก่ามาปน)
3. ให้ตัวอย่าง few-shot รวมกรณีคำถามนอกเรื่องที่ต้องคงข้อความเดิมไว้

ตัวอย่างผลหลังแก้: `"แล้วต้องเรียนกี่หน่วยกิต"` → `"หลักสูตรวิทยาการคอมพิวเตอร์ต้องเรียนกี่หน่วยกิต"`
ขณะที่ `"ช่วยเขียนโค้ด python เรียงลำดับให้หน่อย"` ถูกคงไว้เหมือนเดิมและถูกปฏิเสธตามที่ควรเป็น

### ชั้นที่ 3 — การขยายคำย่อ

เอกสาร มคอ.2 ใช้ชื่อทางการเสมอ แต่ผู้ใช้จริงพิมพ์คำย่อ ทำให้ค้นหาไม่พบ

| คำค้น | ก่อนแก้ | หลังแก้ | หลักสูตรที่ค้นเจอ (หลังแก้) |
|---|---|---|---|
| จบวิทคอมล่ะไปสายงานไหนได้บ้าง | 0.531 (ถูกปฏิเสธ) | **0.644** | วิทยาการคอมพิวเตอร์ |
| จบวิทคอมทำงานอะไรได้ | 0.559 (ถูกปฏิเสธ) | **0.671** | วิทยาการคอมพิวเตอร์ |
| จบไอทีไปทำงานอะไรได้บ้าง | 0.585 | **0.651** | เทคโนโลยีสารสนเทศ |

ก่อนแก้ คำค้น "จบวิทคอม..." นอกจากจะถูกปฏิเสธแล้ว ยังค้นเจอหลักสูตรคหกรรมศาสตร์ซึ่งไม่เกี่ยวข้อง

วิธีทำคือ **เติม**ชื่อเต็มต่อท้ายคำถาม ไม่ใช่**แทนที่**คำย่อ เพื่อให้ถ้อยคำเดิมของผู้ใช้ยังมีน้ำหนัก
ในเวกเตอร์ และถ้าจับคู่ผิดก็ไม่ได้ลบเจตนาเดิมทิ้ง

### ชั้นที่ 3.5 — จำกัดขอบเขตการค้นหาไว้ที่หลักสูตรเดียว

**ปัญหา** ผู้ใช้ถามว่า "สาขาวิชาเทคโนโลยีการจัดการสุขภาพ เรียนจบทำอาชีพไหนได้บ้าง" แล้วระบบ
ตอบว่าไม่พบข้อมูล ทั้งที่เอกสารระบุรายชื่ออาชีพไว้ชัดเจนในหน้า 7

**สาเหตุ** คลังเอกสารเป็นเอกสาร 18 เล่มที่แยกจากกัน และคำถามส่วนใหญ่เจาะจงเล่มใดเล่มหนึ่ง
เมื่อค้นทั้งคลังพร้อมกันด้วยคำถามที่มีชื่อหลักสูตรอยู่ด้วย **ชื่อหลักสูตรจะครอบงำเวกเตอร์**
จนไปจับคู่กับ chunk ทุกก้อนที่เอ่ยชื่อนั้น ซึ่งมีหลายร้อยก้อน — รวมถึงภาคผนวกกว่าร้อยหน้าที่เป็น
ตารางประเมินความพึงพอใจและเอ่ยชื่อหลักสูตรแทบทุกบรรทัดแต่ไม่มีเนื้อหาหลักสูตรเลย

**ผลการวัด** กับ chunk ที่มีรายชื่ออาชีพจริงในเอกสาร ht61 หน้า 7

| วิธีค้น | อันดับของ chunk เป้าหมาย |
|---|---|
| ค้นทั้งคลัง ด้วยคำถามเต็ม | แย่กว่า 200 |
| ค้นเฉพาะเล่มนั้น ด้วยคำถามเต็ม | แย่กว่า 60 |
| **ค้นเฉพาะเล่มนั้น ตัดชื่อหลักสูตรออก** | **อันดับ 3** |

**วิธีแก้** จับคู่ชื่อหลักสูตรจากตาราง `courses` กับข้อความคำถาม ถ้าเจอให้จำกัดขอบเขตการค้นหา
ไว้ที่หลักสูตรนั้น (รวมทุกปีการศึกษาของหลักสูตรเดียวกัน) แล้วตัดชื่อออกจากข้อความค้นหา
เพราะเมื่อรู้แล้วว่าถามถึงเล่มใด ชื่อหลักสูตรกลายเป็นตัวรบกวนการจัดอันดับ

**ปัญหาที่ตามมา: pgvector คืนผลว่างโดยไม่แจ้งข้อผิดพลาด**

เมื่อเพิ่มเงื่อนไขกรองหลักสูตรเข้าไป การค้นหาคืนผลลัพธ์ **0 รายการ** ทั้งที่หลักสูตรนั้นมี chunk
อยู่จริง 422 ก้อน

สาเหตุคือดัชนี ivfflat เลือกรายการผู้สมัคร (candidate) จากดัชนี**ก่อน** แล้วจึงกรองด้วยเงื่อนไข
`WHERE` ภายหลัง เมื่อกรองให้เหลือหลักสูตรเดียวจาก 18 หลักสูตร รายการที่ดัชนีเลือกมาจึงอาจ
ไม่มีของหลักสูตรนั้นเลย ผลลัพธ์ที่ได้คือชุดว่าง **โดยไม่มีข้อความแจ้งข้อผิดพลาดใดๆ**

แก้โดยปิดการใช้ดัชนีเฉพาะกรณีที่มีการกรอง เพราะเมื่อกรองแล้วเหลือข้อมูลไม่กี่ร้อยแถว
การไล่คำนวณระยะทางโดยตรงเร็วเพียงพอและให้ผลที่ถูกต้องแน่นอน

### ชั้นที่ 4 — การตัดสินว่าจะตอบหรือปฏิเสธ

เป็นส่วนที่ซับซ้อนที่สุด เนื่องจากต้องแยกสถานะ 3 แบบออกจากกัน

| สถานะ | ความหมาย | ข้อความที่ผู้ใช้ได้รับ |
|---|---|---|
| `answered` | ตอบได้จากเอกสาร | คำตอบพร้อมรายการอ้างอิง |
| `not_found` | เป็นเรื่องหลักสูตร แต่เอกสารไม่มีข้อมูล | แจ้งว่าไม่พบข้อมูลและแนะนำให้ติดต่อฝ่ายวิชาการ |
| `out_of_scope` | ไม่ใช่เรื่องของมหาวิทยาลัย | ปฏิเสธและชวนกลับมาถามเรื่องหลักสูตร |

**ปัญหาของการใช้เกณฑ์คะแนนอย่างเดียว** คะแนนความคล้ายตอบได้เพียงว่า "คลังเอกสารมีข้อความ
คล้ายคำถามนี้หรือไม่" ซึ่งเป็นคนละคำถามกับ "คำถามนี้เกี่ยวกับมหาวิทยาลัยหรือไม่" ผลการวัดแสดง
ว่าสองกลุ่มหลังทับซ้อนกันมาก

| กลุ่มคำถาม | ช่วงคะแนน |
|---|---|
| ตอบได้จากเอกสาร | 0.708 – 0.771 |
| เป็นเรื่องหลักสูตรแต่ไม่มีข้อมูล | 0.539 – 0.634 |
| นอกขอบเขต | 0.441 – 0.517 |

ช่องว่างระหว่างสองกลุ่มหลังกว้างเพียง **0.022** ซึ่งแคบเกินกว่าจะกำหนดเกณฑ์ที่เชื่อถือได้จาก
ตัวอย่างจำนวนนี้

**ความพยายามที่ไม่ได้ผล** ทดลองรวมการตัดสินสองเรื่อง (อยู่ในขอบเขตหรือไม่ + เอกสารตอบได้หรือไม่)
ไว้ในคำสั่งเดียวเพื่อประหยัดการเรียกโมเดล ผลคือความแม่นยำ**ลดลงทั้งสองด้าน**

| กลุ่ม | ก่อนรวม | หลังรวม |
|---|---|---|
| A ตอบได้ | 5/5 | 4/5 |
| B ไม่มีข้อมูล | 2/5 | 4/5 |
| C นอกเรื่อง | 4/4 | 3/4 |

ตัวอย่างความผิดพลาด: คำถาม "หลักสูตรคหกรรมศาสตร์เรียนเกี่ยวกับอะไร" (คะแนน 0.708) ถูกตัดสิน
ว่าเอกสารตอบไม่ได้ ขณะที่ "ทีมลิเวอร์พูลเป็นยังไงบ้าง" ถูกตัดสินว่าอยู่ในขอบเขต

**สรุปบทเรียน** โมเดลขนาด 7B ตัดสินทีละเรื่องได้แม่นยำกว่าตัดสินหลายเรื่องพร้อมกัน

**วิธีที่ใช้จริง** แยกเป็นสอง prompt ที่ถามอย่างเดียวชัดเจน แล้วเรียกใช้ตามช่วงคะแนน

```
คะแนน < 0.50        ปฏิเสธทันที ไม่เรียกโมเดลเลย
คะแนน 0.50 – 0.65   ตรวจหัวข้อก่อน แล้วจึงตรวจว่าเอกสารตอบได้หรือไม่
คะแนน > 0.65        ถือว่าอยู่ในขอบเขตแน่นอน ตรวจเฉพาะว่าเอกสารตอบได้หรือไม่
```

การจัดลำดับเช่นนี้ทำให้คำถามที่ตอบได้จริงเสียค่าเรียกโมเดลเพิ่มเพียง 1 ครั้ง ไม่ใช่ 2 ครั้ง
และคำถามนอกเรื่องที่ชัดเจนยังถูกปฏิเสธทันทีโดยไม่เรียกโมเดล (ใช้เวลา 0–3 วินาที)

### การป้องกันการแต่งข้อมูล

การเขียนกฎใน prompt ว่า "ถ้าไม่มีข้อมูลให้บอกว่าไม่มีแล้วหยุด" **ใช้ไม่ได้จริง** โมเดลจะเขียนว่า
"จากข้อมูลที่ให้มาไม่มีการกล่าวถึง..." แล้วเขียนต่ออีกหลายย่อหน้าจากความรู้ทั่วไปของตัวเอง

ตัวอย่างที่พบ: เมื่อถามจำนวนหน่วยกิต โมเดลตอบว่าเอกสารไม่ได้ระบุ แล้วเติมต่อว่า
"โดยทั่วไปหลักสูตรวิทยาศาสตรบัณฑิตมักต้องการประมาณ 120–150 หน่วยกิต"

พฤติกรรมนี้อันตรายเป็นพิเศษเพราะคำตอบฟังดูน่าเชื่อถือ และผู้อ่านแยกไม่ออกว่าส่วนใดมาจาก
เอกสารจริง การแก้จึงต้องทำที่ระดับโครงสร้าง (ตรวจก่อนตอบตามที่อธิบายข้างต้น) ไม่ใช่ที่ระดับคำสั่ง

หลังแก้ คำถามเดียวกันได้คำตอบว่า **130 หน่วยกิต พร้อมรายละเอียดแยกตามหมวด** ซึ่งตรงกับเอกสาร

### 7.5 กรณีที่ชุดประเมินจับความผิดพลาดได้ก่อนส่งมอบ

ระหว่างแก้ปัญหาการค้นหาไม่พบรายวิชาบังคับ ได้ปรับให้ตัดคำห่อ (`หลักสูตร`, `สาขาวิชา`,
ชื่อปริญญา) ออกจากข้อความค้นหา**ทุกตำแหน่ง** การแก้นี้ทำให้คำถามเรื่องรายวิชาใช้งานได้จริง

แต่การรันชุดประเมินพบว่า **กลุ่ม A5 (อาจารย์ผู้รับผิดชอบหลักสูตร) ตกจาก 2/2 เหลือ 0/2**

สาเหตุคือคำว่า "หลักสูตร" เป็นส่วนหนึ่งของศัพท์เฉพาะที่ใช้ในเอกสาร มคอ.2

```
"ใครเป็นอาจารย์ผู้รับผิดชอบหลักสูตรวิทยาการคอมพิวเตอร์บ้าง"
        ↓ ตัดชื่อหลักสูตร + ตัดคำห่อทุกตำแหน่ง
"ใครเป็นอาจารย์ผู้รับผิดชอบ บ้าง"      ← ศัพท์เฉพาะขาด ค้นไม่เจอ
```

แก้โดยแยกคำห่อเป็นสองระดับ: **ชื่อปริญญาและคำว่า "สาขาวิชา" ตัดได้ทุกตำแหน่ง** เพราะเป็นคำห่อเสมอ
ส่วน **"หลักสูตร" ตัดเฉพาะเมื่ออยู่ต้นประโยค** เพราะถ้าอยู่กลางประโยคมักเป็นส่วนของศัพท์เฉพาะ

> **ข้อสังเกตสำคัญ** อาการของความผิดพลาดนี้ไม่ใช่ error แต่เป็นคำตอบว่า "ไม่พบข้อมูล"
> ซึ่งดูเหมือนระบบทำงานปกติทุกประการ หากไม่มีชุดประเมินที่รันซ้ำได้ ความผิดพลาดนี้จะถูก
> ส่งมอบไปโดยไม่มีใครสังเกตเห็น — เป็นเหตุผลเชิงรูปธรรมว่าเหตุใดจึงต้องมีชุดทดสอบอัตโนมัติ

## 8. การนำระบบขึ้นใช้งาน

### 8.1 ข้อจำกัดที่กำหนดสถาปัตยกรรม

ระบบใช้โมเดลภาษาที่ทำงานบนเครื่องตนเอง (Ollama) ซึ่งต้องการหน่วยความจำของการ์ดจอประมาณ 6GB
จึงไม่สามารถใช้บริการประเภท serverless หรือเซิร์ฟเวอร์เสมือนทั่วไปที่ไม่มีการ์ดจอได้

เมื่อจำเป็นต้องมีเครื่องที่มีการ์ดจออยู่แล้ว การเก็บฐานข้อมูลและไฟล์บนเครื่องเดียวกันจึงเป็น
ทางเลือกที่เหมาะสมที่สุด และไม่จำเป็นต้องใช้บริการเก็บไฟล์ภายนอก

### 8.2 การตั้งค่าที่ต้องเปลี่ยนเมื่อย้ายเข้า container

| ค่า | บนเครื่องโดยตรง | ใน container |
|---|---|---|
| `DATABASE_URL` | `127.0.0.1:5432` | `postgres:5432` |
| `OLLAMA_BASE_URL` | `127.0.0.1:11434` | `ollama:11434` |
| ที่อยู่ที่ backend รับฟัง | `127.0.0.1` | `0.0.0.0` |

### 8.3 การเปิดให้ผู้อื่นเข้าใช้

ใช้ Cloudflare Tunnel เชื่อมจากเครื่องที่รันระบบออกสู่อินเทอร์เน็ต ได้ที่อยู่แบบ HTTPS โดยไม่ต้องมี
หมายเลข IP สาธารณะและไม่ต้องเปิดพอร์ตที่เราเตอร์

ก่อนหน้านี้หน้าเว็บเรียก API ด้วยที่อยู่เต็มซึ่งถูกฝังตอน build ทำให้เปิดจากเครื่องอื่นไม่ได้
แก้โดยให้ Next.js ส่งต่อ `/api/*` ไปยัง backend ผลพลอยได้คือไม่ต้องตั้งค่า CORS เพราะกลายเป็น
origin เดียวกัน และเปลี่ยนที่อยู่สาธารณะได้โดยไม่ต้อง build ใหม่

### 8.4 การสำรองข้อมูล

ใช้ `scripts/backup_db.sh` ซึ่งเรียก `pg_dump` ผ่าน container แล้วบีบอัดเก็บไว้ พร้อมเก็บย้อนหลัง 10 ชุด
ขนาดไฟล์สำรองประมาณ 38MB

เลือกใช้ `pg_dump` แทนการคัดลอกโฟลเดอร์ข้อมูลโดยตรง เนื่องจากการคัดลอกไฟล์ขณะเซิร์ฟเวอร์
กำลังเขียนอยู่จะได้ข้อมูลที่ไม่สอดคล้องกัน

### 8.5 การจำกัดอัตราการใช้งาน

เดิมนับจากหมายเลข IP ซึ่งใช้ไม่ได้เมื่อคำขอถูกส่งต่อผ่าน frontend เพราะ backend จะเห็นเป็น
IP เดียวกันทั้งหมด ผู้ใช้ทุกคนจึงใช้โควตาก้อนเดียวร่วมกัน เปลี่ยนเป็นนับจากบัญชีผู้ใช้แทน
ซึ่งปลอมแปลงไม่ได้ด้วย ต่างจาก header ที่ผู้เรียกตั้งค่าเองได้

### 8.6 การจัดการหน่วยความจำของการ์ดจอ

การ์ดที่ใช้ทดสอบมี VRAM 8GB และต้องแบ่งให้ระบบแสดงผลของเครื่องด้วย ขณะที่โมเดลสองตัว
รวมกันใช้ประมาณ 5.4GB (qwen2.5:7b 4.7GB + bge-m3 664MB) จึงเหลือพื้นที่ว่างไม่มาก

**พฤติกรรมที่วัดได้**

| การตั้งค่า | ผลที่เกิดขึ้น |
|---|---|
| ค่าเริ่มต้น (ถอดโมเดลหลังว่าง 5 นาที) | คำถามแรกหลังเว้นช่วงใช้เวลา 102 วินาที (โมเดลตอบคำถาม) และ 39 วินาที (embedding) จนฝั่ง frontend ตัดการเชื่อมต่อ |
| ตรึงโมเดลไว้ตลอดกาล | การยิงคำถามติดกัน 17–22 ข้อทำให้ตัวรันโมเดลถูกฆ่ากลางคัน (`model runner has unexpectedly stopped`) |
| **ถือไว้ 30 นาที + ยิง warmup ทุก 20 นาที** | โมเดลไม่ถูกถอดขณะเซิร์ฟเวอร์ทำงาน และไม่ตรึงหน่วยความจำเมื่อปิดเซิร์ฟเวอร์ |

วิธีที่เลือกใช้คือกำหนดให้ถือโมเดลไว้ 30 นาที แล้วให้ backend ยิงคำขอขนาดเล็กไปที่โมเดล
ทุก 20 นาทีเพื่อรีเซ็ตตัวนับก่อนหมดเวลาเสมอ ปิดได้ด้วย `WARMUP_INTERVAL_MINUTES=0`

เมื่อโมเดลไม่พร้อม API จะตอบรหัส 503 พร้อมข้อความอธิบายว่ากำลังโหลดโมเดล แทนรหัส 500
ที่ไม่บอกอะไร และหน้าเว็บแสดงข้อความเดียวกันเมื่อการเชื่อมต่อถูกตัด

> **ข้อควรปฏิบัติก่อนสาธิต** เปิดระบบล่วงหน้าอย่างน้อย 5 นาทีและถามคำถามหนึ่งข้อเพื่อให้
> โมเดลเข้าสู่หน่วยความจำ จากนั้นเวลาตอบจะอยู่ในช่วง 6–21 วินาทีตลอด

### 8.7 อุปสรรคเฉพาะของระบบปฏิบัติการ Windows

**ช่วงพอร์ตที่ระบบจองไว้ล่วงหน้า** Windows จองช่วงพอร์ตให้ Hyper-V และ WSL โดยอัตโนมัติ
บนเครื่องที่ใช้พัฒนาพบว่าช่วงที่จองคือ 7916–8715 ซึ่งคลุมพอร์ต 8000 ที่ตั้งใจใช้ ทำให้
`uvicorn` ผูกพอร์ตไม่ได้และแจ้ง `[Errno 13] ... forbidden by its access permissions`
โดยที่ไม่มีโปรแกรมใดใช้พอร์ตนั้นอยู่จริง

ตรวจสอบได้ด้วย `netsh interface ipv4 show excludedportrange protocol=tcp`
ช่วงนี้ถูกสุ่มใหม่ทุกครั้งที่รีสตาร์ทเครื่อง จึงเลือกใช้พอร์ต 9000 ซึ่งอยู่นอกช่วงที่จอง

**โปรแกรมซ้ำซ้อนแย่งพอร์ตเดียวกัน** เครื่องที่ใช้พัฒนาติดตั้ง Ollama ไว้ทั้งบน Windows
โดยตรงและใน container โดย Ollama บน Windows เริ่มทำงานอัตโนมัติเมื่อเปิดเครื่องและยึด
พอร์ต 11434 ก่อน ทำให้ container ที่มีโมเดลอยู่ถูกบัง ระบบจึงได้รับคำตอบว่า
`model "bge-m3" not found` ทั้งที่โมเดลมีอยู่จริง

แก้โดยปิดการเริ่มอัตโนมัติของ Ollama บน Windows แล้วใช้เฉพาะตัวใน container

## 9. ข้อจำกัดที่ทราบ

| ข้อจำกัด | รายละเอียด |
|---|---|
| ผลของการเขียนคำถามใหม่ไม่คงที่ | ขั้นตอนนี้เป็นการสร้างข้อความ ผลจึงต่างกันได้ในแต่ละครั้ง เมื่อเขียนคำถามใหม่ได้ต่างกัน chunk ที่ค้นเจอก็ต่างกัน และผลตัดสินอาจต่างตาม พบกรณีนี้ 1 ครั้งระหว่างทดสอบ |
| ตัวชี้วัดการแต่งข้อมูลเป็น heuristic | ให้ผลบวกลวงได้เมื่อคำตอบที่ถูกต้องมีคำว่า "ไม่ได้ระบุ" ประกอบอยู่ |
| ชุดประเมินยังไม่ครอบคลุมทุกหลักสูตร | 38 คำถามครอบคลุมขอบเขตครบทั้ง 6 ด้าน แต่ทดสอบเจาะจงเพียงบางหลักสูตรจาก 18 หลักสูตร |
| ยังไม่ได้ทดสอบคำถามต่อเนื่องในชุดประเมิน | ทุกคำถามเริ่มบทสนทนาใหม่ จึงยังไม่ได้วัดความถูกต้องของขั้นเขียนคำถามใหม่อย่างเป็นระบบ |
| หน่วยความจำการ์ดจอเป็นขีดจำกัด | การ์ด 8GB รองรับ qwen2.5:7b คู่กับ bge-m3 ได้แบบไม่มีพื้นที่เหลือมาก การยิงคำถามติดกันจำนวนมากทำให้ตัวรันโมเดลถูกฆ่า (ดูหัวข้อ 8.6) |
| ระบบตอบทีละคำขอ | Ollama ตั้งค่ารับ 1 คำขอพร้อมกัน ผู้ใช้หลายคนพร้อมกันจะต่อคิว |
| ตัวจำกัดอัตราเก็บสถานะในหน่วยความจำ | ใช้ไม่ได้ถ้ามีหลาย worker เพราะแต่ละ process นับแยกกัน |
| ยังไม่มีระบบจัดการเวอร์ชันฐานข้อมูล | การแก้โครงสร้างต้องสร้างฐานข้อมูลใหม่และนำเข้าข้อมูลใหม่ |
| ไฟล์ PDF ต้นฉบับไม่ได้ถูกเก็บถาวร | คอลัมน์ `storage_path` บันทึกที่อยู่ไฟล์บนเครื่องที่นำเข้า ไม่ใช่ที่เก็บของระบบ |
| ยังไม่มี endpoint ต่ออายุ token | ผู้ใช้ต้องเข้าสู่ระบบใหม่ทุก 30 นาที |
