`https://admission.pnru.ac.th/info/announce` — ตรงกับที่อาจารย์ให้มา และตรวจแล้วว่า
เป็น URL เดียวกับที่ระบบใช้อยู่เดิมในแถบเมนู ตอบ HTTP 200

ระบบนี้ **ไม่รับสมัครเองและไม่เก็บข้อมูลผู้สมัคร** ส่งต่อไปที่ระบบของมหาวิทยาลัยอย่างเดียว

### 4.5 ทดสอบ deploy และ rollback เต็มวงจร

คืนฐานทดสอบกลับสภาพเดิม → `deploy.sh` → `rollback.sh` → `deploy.sh`

| ขั้น | ผล |
|---|---|
| `deploy.sh` ผ่านครบ 4 ขั้น · บันทึกรหัสแถวที่แก้ได้ (ใหม่ 2 · เติมระดับ 10) | ผ่าน |
| `rollback.sh` ลบ 2 แถว · ถอนคีย์ level ออก 10 แถว · กลับเป็น 12 แถว / 2 ระดับ | ผ่าน |
| เทียบข้อมูลหลัง rollback กับไฟล์สำรองก่อน deploy | **sha256 ตรงกันเป๊ะ** |

**ข้อเดียวที่ไม่กลับ** คือ `updated_at` ของ 10 แถวที่ถูกแตะ ซึ่ง trigger ของตารางขยับให้เอง
ตั้งใจไม่ย้อนค่านี้ เพราะมันบันทึกว่าแถวถูกแก้จริง การย้อนเท่ากับลบประวัติทิ้ง
เนื้อข้อมูลทุกช่องรวม `detail` ทั้งก้อนเหมือนเดิมทุกไบต์

## 6. แผนสำรองข้อมูล · นำขึ้นใช้งาน · ย้อนกลับ

ทุกคำสั่งรันบนเซิร์ฟเวอร์ ไม่ใช่บนเครื่องตัวเอง —
คอนเทนเนอร์ชื่อเดียวกันมีทั้งสองที่ ถ้ารันผิดที่จะโดนฐานผิดตัวโดยไม่มีอะไรเตือน

### 6.1 สำรองข้อมูล

`deploy.sh` สำรองให้เองเป็นขั้นแรก ก่อนแตะอะไรทั้งสิ้น

- `pg_dump` เฉพาะตาราง `web.site_courses` แบบ `--column-inserts` อ่านและแก้ด้วยมือได้
- คำนวณ `sha256` เก็บไว้
- ถ้าไฟล์สำรองว่าง สคริปต์หยุดทันที ไม่รันต่อ

### 6.2 นำขึ้นใช้งาน

```bash
scp -i ~/.ssh/oci.key -r docs/raw/grad-programs-2569-10-27 ubuntu@161.118.237.37:/home/ubuntu/
ssh -i ~/.ssh/oci.key ubuntu@161.118.237.37
cd /home/ubuntu/grad-programs-2569-10-27 && ./deploy.sh --db course_advisor
```

สคริปต์จะถามให้พิมพ์ `YES` ก่อนแตะ production และหยุดเองถ้าตรวจไม่ผ่านข้อใดข้อหนึ่ง

**ฝั่งหน้าเว็บ** ต้อง build และวางไฟล์ใหม่ด้วย เพราะเว็บที่ใช้งานจริงเป็นไฟล์สถิต
ที่ bind-mount เข้า Caddy — **ไม่ใช่คอนเทนเนอร์** การ restart เฉย ๆ จะยังได้โค้ดเก่า

```bash
cd D:/workspace/LastProject && npm run build
scp -i ~/.ssh/oci.key -r dist/* ubuntu@161.118.237.37:/home/ubuntu/course-advisor-system/web/
```

### 6.3 ย้อนกลับ

```bash
cd /home/ubuntu/grad-programs-2569-10-27
./rollback.sh --db course_advisor --run /home/ubuntu/grad-programs-2569-10-27/run-<เวลาที่ deploy>
```

**อ้างรหัสแถวที่ deploy บันทึกไว้โดยตรง** (`touched-ids.txt`) ไม่ใช่เดาจากเงื่อนไขเดิม
เพราะถ้าผู้ดูแลแก้หลักสูตรอื่นหลัง deploy เงื่อนไขเดิมจะจับแถวผิดชุด

ลำดับที่ถูกต้องคือ **ย้อนข้อมูลก่อน แล้วค่อยย้อนโค้ด** ถ้าย้อนโค้ดก่อน
หน้าเว็บเก่าจะยังอ่านข้อมูลใหม่อยู่ ซึ่งแสดงผลไม่ครบ

คืนไฟล์หน้าเว็บเดิมด้วยการ build จากคอมมิตก่อนหน้าแล้ว scp ทับ

ไฟล์สำรองเต็มมีไว้เป็น **ทางสุดท้าย** เท่านั้น — การคืนทั้งตารางจะทับงานที่ผู้ดูแล
แก้ไว้หลัง deploy ไปด้วย

## 7. ที่ยังไม่ได้ทำ และทำไม

- **ไม่ทำระบบซิงก์อัตโนมัติกับเว็บคณะ** — โจทย์ระบุว่ารอบนี้ยังไม่ทำ
- **ไม่ทำระบบรับสมัครเอง และไม่เก็บข้อมูลผู้สมัคร** — ส่งต่อไปที่ของมหาวิทยาลัยอย่างเดียว
- **ไม่ผูกหลักสูตรเว็บกับเอกสาร มคอ. ในคลังความรู้** — นอกขอบเขต (ข้อ 5.5)
- **ไม่แก้ช่อง `important_info` ที่รั่วมาก่อน** — นอกขอบเขต (ข้อ 5.6)
- **ไม่ใส่รูปโลโก้และรายชื่ออาจารย์ของสองหลักสูตรใหม่** — ต้องอัปโหลดไฟล์เข้าระบบ
  ซึ่งทำจากหน้าผู้ดูแลได้โดยตรงและไม่ต้องแก้โค้ด
- **ยังไม่ deploy และไม่แตะข้อมูล production** — ตามที่โจทย์กำหนด
