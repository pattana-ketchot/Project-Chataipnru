### คำกล่าวที่ถอนออกจากรายงาน

รอบแรกเขียนว่า "เพิ่มคีย์ชุดที่สองได้โควตาก้อนใหม่ โดยคำตอบไม่เปลี่ยนสำนวน"
**ถอนแล้ว** เพราะยังไม่ได้ตรวจ

* สิ่งที่ยืนยันได้จริงคือเนื้อความ 429 ของ Google ระบุ `quotaId` เป็น
  `…PerDayPerProjectPerModel-FreeTier` → โควตารายวันคิดต่อโปรเจกต์ **ต่อโมเดล**
  การหมุนไปโมเดลอื่นแล้วใช้ได้ต่อ เป็นพฤติกรรมที่สังเกตได้จริง
* คีย์ผูกกับโปรเจกต์ คีย์ใบที่สองในโปรเจกต์เดิมจึงน่าจะใช้โควตาก้อนเดียวกัน
  **ยังไม่ได้ทดลอง** · ส่วนการเปิดโปรเจกต์ใหม่ **ยังไม่ได้อ่านเงื่อนไขของผู้ให้บริการ**
  ว่าอนุญาตหรือถือเป็นการเลี่ยงเพดาน

### 3.2 migration บนฐานทดสอบ ด้วย role `advisor_api` จริง — ผ่าน 16/16

ต่อด้วยผู้ใช้ `advisor_api` ตัวจริงผ่าน unix socket ของคอนเทนเนอร์
(`pg_hba` เป็น `local all all trust`) จึงไม่ต้องใช้รหัสผ่าน และไม่มีค่าลับถูกพิมพ์ออกมา

ยืนยันแยกต่างหากว่า `advisor_api` ไม่ใช่ superuser · ไม่ได้เป็นสมาชิก role ใด ·
ไม่ได้เป็นเจ้าของตาราง · มีสิทธิ์บน schema `public` แค่ `USAGE`

| ข้อตรวจ | ผล |
|---|---|
| สร้างตารางและบันทึก migration หนึ่งแถว | ผ่าน |
| primary key `(day, event)` | ผ่าน |
| สิทธิ์เป็น `INSERT, SELECT, UPDATE` เท่านั้น | ผ่าน |
| UPSERT บวกทับของเดิม ไม่เขียนทับ (7+3 = 10) | ผ่าน |
| รันซ้ำแล้วตัวเลขอยู่ครบ ไม่เพิ่มแถว migration ไม่เปลี่ยนสิทธิ์ | ผ่าน |
| `advisor_api` ลบข้อมูลไม่ได้ / สร้างตารางไม่ได้ | ผ่าน |
| 6 connection × 50 ครั้ง = 300 ไม่มีตัวเลขหาย | ผ่าน |

### 3.3 โค้ดจริงในคอนเทนเนอร์ ผ่าน lifespan จริง ต่อฐานทดสอบจริง — ผ่าน 8/8

| ข้อตรวจ | ผล |
|---|---|
| เขียนเองตามเวลาโดยไม่มีเหตุการณ์ใหม่ — ตัวเลขลงฐานครบ กองรอว่าง | ผ่าน |
| ปิดแอปทันทีโดยไม่รอรอบเขียน — ตัวเลขช่วงท้ายลงฐานครบ | ผ่าน |
| ฐานล่มระหว่างทำงาน — ไม่มีข้อผิดพลาดหลุด และตัวเลขไม่ถูกทิ้ง | ผ่าน |
| ฐานกลับมา — ของค้างถูกเขียนครบ (4 ก่อนล่ม + 3 ตอนล่ม = 7 พอดี) | ผ่าน |

| ฐานต่อไม่ได้ตั้งแต่ต้น — แอปไม่ขึ้นตามพฤติกรรมเดิม และข้อผิดพลาดไม่ได้มาจากตัวนับ | ผ่าน |

> หมายเหตุความซื่อตรงของการทดสอบ: รอบแรกของสคริปต์ทดสอบ migration รายงานว่า

> และยืนยันซ้ำจาก `pg_roles` · บันทึกของทั้งสองรอบอยู่ในไฟล์หลักฐาน

## 5. ขั้นตอน deploy ที่เสนอ (ยังไม่ทำ)

1. สำรองฐานข้อมูลตามขั้นตอนปกติ
2. รัน migration บน `course_advisor` ด้วย superuser
   ตรวจ: ตารางถูกสร้าง · สิทธิ์เป็น `INSERT,SELECT,UPDATE` · `mko.schema_migrations`
   มีแถว `008_llm_usage_counter` หนึ่งแถว
3. build อิมเมจใหม่โดยแตก `/app` จากอิมเมจ production ปัจจุบัน แล้วซ้อนทับ **4 ไฟล์**
   (`main.py` ใช้ตัวที่ซ้อนไว้แล้ว ไม่ใช่จาก working tree)
4. พิสูจน์ว่า md5 ของไฟล์ในอิมเมจใหม่ต่างจากอิมเมจเดิม **เฉพาะ 4 ไฟล์นั้น**
5. ขึ้นแล้วตรวจ
   * log ตอนสตาร์ตต้องมีบรรทัด `เปิดตัวนับการใช้โมเดล เขียนทุก 30 วินาที`
   * ถามคำถามจริงผ่าน `/api/chat` หนึ่งข้อ รอ 35 วินาที
   * `select event, n from public.llm_usage_daily order by n desc;` ต้องมีแถว
   * หน้าแชตยังตอบได้ตามปกติ และเวลาตอบไม่ต่างจากเดิมอย่างสังเกตได้
