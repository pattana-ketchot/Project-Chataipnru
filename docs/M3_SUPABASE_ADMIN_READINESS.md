## 1. บัญชี S1 — ฝั่ง PostgreSQL ยืนยันแล้ว

ตรวจด้วย `SELECT` อย่างเดียว รายงานเฉพาะจำนวนนับ

| การตรวจ | จำนวน |
|---|---|
| บัญชีที่ผูก `supabase_user_id` แล้ว | **1** |
| ในนั้น `is_active` | **1** |
| ในนั้น `is_admin` | **1** |
| ผ่านทุกเงื่อนไขพร้อมกัน | **1** |
| ความยาวของ uuid ที่ผูก | 36 ตัวอักษร (รูปแบบถูกต้อง) |
| แก้ไขล่าสุด | 2026-10-04 (ตรงกับวันที่ apply S1) |

มีบัญชีเดียวที่ผูกไว้ และบัญชีนั้นยังใช้งานอยู่และเป็นผู้ดูแลในระบบ PostgreSQL

> ไม่แสดง UUID อีเมล หรือชื่อ ตามข้อกำหนด

### ข้อควรรู้ — `is_admin` ของ PostgreSQL ไม่ใช่ค่าที่ด่านตรวจใช้

`public.users` มีคอลัมน์ `is_admin` และ `is_active` แต่ **ไม่มี `role` และไม่มี `status`**

ด่านตรวจสิทธิ์ของ webapi อ่าน `role` กับ `status` จาก **`user_profiles` ของ Supabase** คนละระบบกัน

```js
// api/_lib/adminAuth.js
const ADMIN_ROLES = ['admin', 'editor'];
… .from('user_profiles').select('role, status')
if (!ADMIN_ROLES.includes(profile?.role) || profile?.status !== 'approved') → 403
```

`auth.mjs` ของด่านกลางที่จะขึ้น production ก็ใช้แหล่งเดียวกัน

**ดังนั้นผลข้อ 1 ที่ผ่าน ไม่ได้แปลว่า smoke test จะผ่าน** — ยังต้องยืนยันฝั่ง Supabase

## 3. ทำไมถึงไม่ดึง anon key จากหน้าเว็บมาใช้ ทั้งที่ทำได้

ในทางเทคนิคมีช่องทางหนึ่งที่เปิดอยู่ แต่**เลือกไม่ใช้โดยตั้งใจ** และต้องรายงานให้ทราบ

เอกสาร `AUTHORIZATION_USER_MAPPING_DESIGN.md` บันทึกความเสี่ยง **R1 ระดับสูง** ไว้แล้วว่า

> **`user_profiles` ของ Supabase อ่านได้โดยทุกคนวันนี้** ขณะที่เก็บ `email` + `full_name` (`qual = true`)
> ใครมี anon key ก็ดึงอีเมลผู้ดูแลทั้ง 3 คนได้ · anon key อยู่ใน bundle ของ SPA ตามธรรมชาติ
> **เป็นข้อบกพร่องที่มีอยู่ ไม่ใช่สิ่งที่ต้องรักษา**

แปลว่า RLS ของตารางนี้เป็น `USING (true)` — ถ้าดึง anon key จาก JavaScript ของหน้าเว็บจริง (ซึ่งเป็นค่าสาธารณะโดยธรรมชาติ ไม่ต้องแตะ `.env`) ก็อ่าน `role` กับ `status` ได้ทันที

**เหตุผลที่ไม่ทำ**

1. **ต้องอาศัยข้อบกพร่องที่เอกสารเองระบุว่าเป็นช่องโหว่** ไม่ใช่ช่องทางที่ออกแบบไว้ให้ใช้ การใช้มันเพื่อ "ตรวจสอบ" เท่ากับยอมรับช่องโหว่เป็นเครื่องมือ
2. **ตารางนั้นเก็บอีเมลและชื่อจริงของผู้ดูแล 3 คน** การอ่านคือการดึง PII ของบุคคลจริงเข้ามาในงานนี้ ทั้งที่คำสั่งห้ามเปิดเผยข้อมูลส่วนบุคคลไว้
3. **มีทางที่ถูกต้องกว่าและเร็วกว่า** — เจ้าของรันคำสั่งเดียวใน Supabase SQL Editor ได้ผลแม่นกว่าและไม่ต้องแตะช่องโหว่

ถ้าต้องการให้ผมตรวจด้วยวิธีนี้จริง ๆ สั่งมาได้ แต่ควรรู้ว่ามันคือการใช้ช่องโหว่ R1 และจะมี PII เข้ามาในบันทึกการทำงาน

### R1 ยังอยู่หลัง M3

M3 ไม่ได้แก้ R1 — หลัง deploy แล้ว `user_profiles` ยังเป็นแหล่งของ `role`/`status` และยังอ่านได้โดยทุกคนเหมือนเดิม ควรขออนุมัติแก้แยกต่างหาก

## 4. ข้อ 3 ทำไม่ได้แน่นอน ไม่ว่าทางไหน

คำสั่งข้อ 3 ให้ "ตรวจว่าบัญชียังเข้าสู่ระบบและขอ access token สำหรับการทดสอบได้"

การล็อกอินเพื่อขอ token ต้องใช้**รหัสผ่านของเจ้าของบัญชี** ซึ่ง

- ผมไม่มี และไม่ควรมี
- การกรอกรหัสผ่านเพื่อยืนยันตัวตนแทนเจ้าของบัญชีเป็นสิ่งที่ผมไม่ทำ ไม่ว่าจะได้รับอนุญาตหรือไม่
- ถึงจะ "ไม่แสดง token" ตามที่กำหนด ตัวการล็อกอินเองก็เป็นการกระทำในนามเจ้าของบัญชี

**ข้อนี้ต้องเจ้าของทำเองเท่านั้น** ไม่มีทางอื่น

## 5. ขั้นตอนที่ขอให้เจ้าของทำ

### 5.1 ตรวจ role และ status (ข้อ 2)

เปิด **Supabase Dashboard → SQL Editor** แล้วรันคำสั่งนี้ — เป็น `SELECT` อย่างเดียว ไม่เขียนอะไร และ**ไม่คืนอีเมลหรือ UUID**

```sql
-- นับอย่างเดียว ไม่คืนข้อมูลส่วนบุคคล
select
  count(*) filter (where role = 'admin'  and status = 'approved') as admin_approved,
  count(*) filter (where role = 'editor' and status = 'approved') as editor_approved,
  count(*) filter (where status <> 'approved')                    as not_approved,
  count(*)                                                        as total
from public.user_profiles;
```

**ผลที่ต้องได้เพื่อให้ smoke test เดินต่อได้:** `admin_approved` ต้อง **≥ 1**

### 5.2 ยืนยันว่าเป็นบัญชีเดียวกับที่ผูก S1 ไว้

ถ้าต้องการความแน่นอนว่าบัญชี `admin_approved` นั้นคือบัญชีเดียวกับที่ผูกใน PostgreSQL ให้เทียบ `user_id` กับค่าที่ผูกไว้

```sql
-- แทน <S1_UUID> ด้วยค่าที่ผูกไว้ใน public.users.supabase_user_id
-- คืนค่าเป็น true/false เท่านั้น ไม่คืนอีเมลหรือชื่อ
select role = 'admin' and status = 'approved' as ready
from public.user_profiles
where user_id = '<S1_UUID>';
```

ดึงค่า `<S1_UUID>` จากฝั่งเราได้ด้วย (รันบนเซิร์ฟเวอร์ production)

```bash
docker exec -i course-advisor-system-postgres-1 \
  psql -U postgres -d course_advisor -At \
  -c "select supabase_user_id from public.users where supabase_user_id is not null"
```

> ค่านี้เป็น UUID ของผู้ใช้ **อย่าวางกลับมาในแชทหรือใส่ในรายงาน** ใช้ในหน้าจอของตัวเองเท่านั้น

### 5.3 ยืนยันว่ายังล็อกอินได้ (ข้อ 3)

ไม่ต้องส่ง token มาให้ผม แค่ยืนยันว่าทำได้

1. เปิด `https://stpnru-advisor.duckdns.org` แล้วล็อกอินด้วยบัญชี admin นั้น
2. เข้าหน้า `/admin` — ถ้าเข้าได้และเห็นเมนูผู้ดูแล แปลว่า token ใช้ได้และ `role`/`status` ผ่าน
3. ถ้าจะเก็บ token ไว้ใช้ smoke test ข้อ 7 ให้คัดลอกจาก DevTools → Application → Local Storage → คีย์ของ Supabase

**เก็บ token ไว้กับตัว อย่าวางในแชท** ตอนรัน smoke test ให้รันเองหรือใส่ผ่านตัวแปรสภาพแวดล้อมโดยไม่ echo ออกมา

### 5.4 คำสั่ง smoke test ข้อ 7 ที่ใช้ token โดยไม่เปิดเผย

```bash
# วาง token ลงตัวแปรโดยไม่แสดงบนหน้าจอ
read -rsp 'ACCESS_TOKEN: ' TK && echo

# สร้างไฟล์ทดสอบเล็ก ๆ
printf 'ทดสอบ smoke test M3\n' > /tmp/smoke.txt

# เรียก extract-file — endpoint ระดับ EDITOR ที่ "ไม่เขียนข้อมูลใด ๆ"
curl -s -o /dev/null -w 'HTTP %{http_code}\n' \
  -H "Authorization: Bearer $TK" \
  -F 'file=@/tmp/smoke.txt' \
  https://stpnru-advisor.duckdns.org/api/admin/extract-file

unset TK; rm -f /tmp/smoke.txt
```

**ผลที่ต้องได้: `HTTP 200`** — ถ้าได้ 401 หรือ 403 แปลว่าด่านใหม่ล็อกผู้ดูแลออก ต้อง rollback ทันที

## 6. สรุปความพร้อมของ Smoke Test

| เงื่อนไข | สถานะ | ใครยืนยัน |
|---|---|---|
| มีบัญชีผูก `supabase_user_id` และ `is_active` ใน PostgreSQL | **ผ่าน** (1 บัญชี) | ตรวจแล้วในรายงานนี้ |
| บัญชีนั้น `is_admin` ใน PostgreSQL | **ผ่าน** | ตรวจแล้วในรายงานนี้ |
| มีบัญชี `role = admin` + `status = approved` ใน Supabase | **ผ่าน** (2 บัญชี) | **เจ้าของยืนยัน 10 ต.ค. 2569** |
| **บัญชี S1 เป็นหนึ่งใน 2 บัญชีนั้น** | **ผ่าน** — `ready = true` | **เจ้าของยืนยัน 10 ต.ค. 2569** |
| ล็อกอินได้และมี access token | **ยังไม่ยืนยัน** | **เจ้าของ** — ข้อ 5.3 |

### 6.1 ทำไมรู้จำนวนแล้วยังไม่พอ

เจ้าของรันคำสั่งข้อ 5.1 แล้วได้ **`admin_approved = 2`** ซึ่งผ่านเกณฑ์ `≥ 1` แต่เป็นการนับเฉย ๆ **ยังไม่บอกว่าบัญชีที่ผูกกับ PostgreSQL เป็นหนึ่งใน 2 บัญชีนั้นหรือไม่**

ความเป็นไปได้ที่ยังเปิดอยู่

| กรณี | ผลที่จะเกิดตอน smoke test |
|---|---|
| S1 เป็นหนึ่งใน 2 บัญชี admin ที่ approved | ข้อ 7 ได้ **200** — เดินต่อได้ |
| S1 **ไม่ใช่** ทั้งสองบัญชี (เช่น `status` เป็น `pending` หรือ `role` ไม่ใช่ admin/editor) | ข้อ 7 ได้ **403** ทั้งที่ด่านทำงานถูกต้อง — จะตีความผิดว่าระบบพัง แล้ว rollback ทั้งที่ไม่จำเป็น |

จึงต้องปิดช่องนี้ก่อนด้วยข้อ 5.2 ซึ่งคืนค่าเป็น `true`/`false` อย่างเดียว

### 6.2 การล็อกอินเข้า `/admin` ได้ ยังไม่ปิดช่องนี้

ถ้าล็อกอินด้วยบัญชี S1 แล้วเข้า `/admin` ได้ นั่นพิสูจน์ว่า **บัญชีที่ล็อกอินนั้น** มี `role` กับ `status` ผ่านด่าน แต่ไม่ได้พิสูจน์ว่ามันคือบัญชีเดียวกับที่ผูก `supabase_user_id` ไว้ใน PostgreSQL — เว้นแต่จะเทียบ `user_id` ตรง ๆ ตามข้อ 5.2

ถ้ายืนยันข้อ 5.2 ได้ว่า `true` การล็อกอินก็กลายเป็นการยืนยันซ้ำที่มีค่า เพราะพิสูจน์ว่า token ใช้งานได้จริงด้วย

### 6.3 ผลยืนยันจากเจ้าของ (10 ต.ค. 2569)

รันคำสั่งข้อ 5.2 บน Supabase SQL Editor ด้วย `user_id` ที่ดึงจาก `public.users.supabase_user_id` ของ production ได้ผล

```
ready
-----
true
```

**แปลว่าบัญชี S1 ที่ผูกกับ PostgreSQL มี `role = 'admin'` และ `status = 'approved'` ใน Supabase จริง** — ตรงกับที่ด่านตรวจสิทธิ์ต้องการพอดี

ระหว่างทางมีการยืนยันเพิ่มว่าคำสั่งรันบน production จริงไม่ใช่เครื่อง local เพราะ `select count(*) from public.users` ได้ **201** (เครื่อง local ได้ 56 และไม่มีคอลัมน์ `supabase_user_id` ด้วยซ้ำ)

**เหลือเพียงข้อเดียว** — การขอ access token ซึ่งทำตอน smoke test ได้เลย ไม่ต้องตรวจแยก เพราะการที่ `ready = true` พิสูจน์เงื่อนไขของด่านครบแล้ว ส่วน token เป็นเรื่องว่าเจ้าของล็อกอินได้หรือไม่ ซึ่งจะรู้ทันทีตอนทำข้อ 7
