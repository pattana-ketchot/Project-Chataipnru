## 3. refresh — ผ่าน **พิสูจน์สองฝั่ง**

ที่เคยเขียนไว้ว่า "เปิดหลายเมนู" ไม่พิสูจน์อะไร — ถูกต้อง จึงยิง `/api/auth/refresh` จริงแล้วตรวจทะเบียนเซสชัน

### ฝั่งเบราว์เซอร์

```
HTTP: 200 · ได้token: true · access_เปลี่ยน: true · refresh_เปลี่ยน: true · role: admin
```

เทียบเฉพาะ **8 ตัวท้าย** ของ token ว่าเปลี่ยนหรือไม่ · **ไม่มีการแสดงค่า token**

### ฝั่งฐานข้อมูล — หลักฐานว่าหมุนจริง

| สร้างเมื่อ | ยังใช้ได้ | เพิกถอนเมื่อ | ตัวเรียก |
|---|---|---|---|
| 04:57:25 | t | — | `curl/7.81.0` |
| 05:45:14 | t | — | Mozilla |
| **05:46:19** | **f** | **06:34:43** | Mozilla |
| **06:34:43** | **t** | — | Mozilla |

| | ก่อน | หลัง |
|---|---|---|
| แถวทั้งหมด | 3 | **4** |
| ยังใช้ได้ | 3 | 3 |
| **ถูกเพิกถอน** | **0** | **1** |

**ใบเดิมถูกเพิกถอนทันทีที่ออกใบใหม่** — ไม่ใช่แค่ API ตอบ 200

### การเก็บ token

`token_hash` ยาว **64 ตัวอักษร** = sha256 — **ไม่เก็บ token ดิบในฐานข้อมูล**

## 4.3 สิทธิ์ `role=user` — ผ่าน

สร้างบัญชีทดสอบ `role=user` `status=approved` ที่ล็อกอินได้จริง แล้วยิงด้วย token ของบัญชีนั้น

| เส้นทาง | HTTP |
|---|---|
| `GET /site-admin/courses` | **403** |
| `GET /site-admin/users` | **403** |
| `GET /site-admin/news` | **403** |
| `POST /site-admin/sync-news` | **403** |
| `DELETE /site-admin/courses/<id>` | **403** |
| **`GET /uploads/<ไฟล์ private>`** | **403** |
| เทียบ: `GET /auth/me` | **200** |

**403 ไม่ใช่ 401** — ระบบรู้ว่าเป็นใคร แต่ปฏิเสธเพราะสิทธิ์ไม่พอ ต่างจากกรณีไม่มี token ที่ได้ 401

## 4.4 บัญชีที่นำเข้าจาก Supabase — **ยังไม่ผ่านการยืนยัน**

เจ้าของ **จำรหัสผ่านเดิมของ `6610122115004@pnru.ac.th` ไม่ได้**

| ข้อเท็จจริง | ค่า |
|---|---|
| บัญชีที่นำเข้า | 2 บัญชี · `password_scheme = bcrypt` ทั้งคู่ |
| เคยเข้าสู่ระบบสำเร็จไหม | **ยังไม่เคย** · `last_login_at` ว่าง · เซสชัน 0 |
| สถานะข้อนี้ | **ยังไม่ผ่านการยืนยัน** |

> **การ reset รหัสผ่านไม่นับเป็นหลักฐานข้อนี้** — พิสูจน์แค่ว่าระบบตั้งรหัสใหม่ได้
> ไม่ได้พิสูจน์ว่า hash ที่ย้ายมาจาก Supabase ใช้งานได้

**ยืนยันได้ทางเดียว:** เจ้าของบัญชีนั้นเข้าสู่ระบบด้วยรหัสเดิมของตัวเอง
ถ้าภายหลังมีคนจำได้ ทำได้ทันทีโดยไม่ต้องแก้อะไร — ระบบพร้อมรับอยู่แล้ว

**ปิดรายการนี้ไว้ที่ "ยังไม่ผ่านการยืนยัน" และจะไม่ถามหารหัสเดิมอีก**
ทั้งสองบัญชียังอยู่ในฐานข้อมูลตามเดิม ไม่ลบ ไม่รีเซ็ต ไม่แก้ `password_scheme`
ถ้าเจ้าของบัญชีเข้าใช้งานไม่ได้จริง ให้ใช้ทางปกติคือตั้งรหัสใหม่ — แต่ตอนนั้นข้อนี้จะยังปิดไม่ได้เหมือนเดิม

## 4.5 กลไกการย้ายรหัสผ่าน — ผ่าน (ทดสอบแยกจากข้อ 4.4)

เพื่อแยกสองเรื่องออกจากกัน: **กลไกใช้ได้ไหม** กับ **hash ของบัญชีจริงใช้ได้ไหม**

สร้างบัญชีทดสอบที่เก็บ hash แบบ Supabase คือ `bcrypt(รหัสผ่าน)` ตรง ๆ แล้วตั้ง `password_scheme = 'bcrypt'`

| ขั้น | ผล |
|---|---|
| ก่อนเข้าสู่ระบบ | `password_scheme = bcrypt` |
| เข้าสู่ระบบด้วยรหัสนั้น | **HTTP 200** |
| หลังเข้าสู่ระบบ | **`password_scheme = bcrypt_sha256`** |
| อัปเกรดอัตโนมัติ | **True** |

**พิสูจน์ว่าเส้นทางโค้ดทำงานถูก** — รับ hash แบบ Supabase ได้ และอัปเกรดรูปแบบเองหลังเข้าสำเร็จ
**ไม่ได้พิสูจน์ว่า hash สองก้อนจากโปรเจกต์จริงใช้ได้** ซึ่งยังเป็นข้อ 4.4 ที่ค้างอยู่

## 6. รายการพึ่งพา Supabase ที่เหลือ

| จุด | รายละเอียด | ใครใช้ |
|---|---|---|
| **`webapi`** | **เป็น Supabase client จริง ไม่ใช่แค่มี env ค้าง** — ดูหัวข้อ 6.1 | หน้าเว็บไม่เรียก แต่เส้นทางยังเปิดต่อสาธารณะ |
| Caddyfile บรรทัด 33–39 | `/api/sci-connect-news*` และ `/api/admin/*` → `webapi:3001` | หน้าเว็บไม่เรียก |
| `.env` | `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY` (ส่งให้ webapi เท่านั้น) | webapi |
| cron เก่าใน Supabase | `sync-sci-news-every-30-min-v2` ทุก 30 นาที | เขียนลงตารางที่ไม่มีใครอ่าน |

### 6.1 แก้ข้อสรุปเรื่อง webapi — ตรวจจากโค้ดที่รันอยู่จริง

ฉบับก่อนเขียนว่า webapi "ไม่ได้ต่อ Supabase แล้ว" โดยอ่านจาก startup log บรรทัดเดียวที่บอกว่า
ต่อ `advisor_web@postgres:5432` **นั่นพิสูจน์แค่เส้นทางเดียว ไม่ได้พิสูจน์ทุกเส้นทาง**

อ่านไฟล์ `.mjs`/`.js` ทั้ง 13 ไฟล์ในคอนเทนเนอร์แล้วพบว่า **ทุกเส้นทางที่ให้บริการเรียก Supabase ผ่านเครือข่าย**

| ไฟล์ | ทำอะไรกับ Supabase |
|---|---|
| `api/_lib/adminAuth.js:29–39` | `supabase.auth.getUser(token)` + อ่าน `user_profiles` |
| `api/sci-connect-news.js:5–29` | อ่านตาราง `external_news` **จาก Supabase** |
| `api/sci-connect-news-detail.js:9–30` | อ่าน `external_news` **จาก Supabase** |
| `api/_lib/rag.js:16–39` | เรียก RPC `match_rag_documents` **บน Supabase** |
| `api/_lib/ingest.js:35–62` | `delete` / `upsert` ตาราง `rag_documents` **บน Supabase** |
| `api/_lib/aiConfig.js:18–24` | อ่าน `ai_settings` **จาก Supabase** |
| `api/admin/sync-sci-news.js:28` | เรียก Edge Function `/functions/v1/sync-sci-news` |
| `db.mjs` | **ที่เดียวที่ต่อ PostgreSQL ของเรา** — แปลง `supabase_user_id` → `users.id` เท่านั้น |

**ข้อสรุปที่ถูก: `webapi` เป็นองค์ประกอบสุดท้ายใน production ที่ยังเรียก Supabase จริง**

และ `https://stpnru-advisor.duckdns.org/api/sci-connect-news` **ยังเปิดต่อสาธารณะ ตอบ 200
ด้วยข้อมูลจาก Supabase** ไม่ใช่จากฐานของเรา — ใครยิงเข้ามาก็ยังทำให้เกิดการเรียก Supabase ได้

### ยืนยันว่าส่วนอื่นไม่พึ่งแล้ว

| ตรวจ | ผล |
|---|---|
| env `SUPABASE` ใน backend / frontend / caddy / postgres / ollama | **0 ตัวทุกคอนเทนเนอร์** |
| ไฟล์ JS ที่เสิร์ฟอยู่จริง อ้าง `api/sci-connect-news` | **0 ครั้ง** |
| อ้าง `api/admin/` | **0 ครั้ง** |
| Network ของหน้าเว็บ (88 คำขอ) | ไปโดเมน supabase **0** |

> **ขอบเขตของข้อสุดท้าย:** 0/88 เป็นความจริงเฉพาะ**ฝั่งเบราว์เซอร์**
> การเรียก Supabase ของ `webapi` เกิดฝั่งเซิร์ฟเวอร์ จึงไม่ปรากฏใน Network ของเบราว์เซอร์เลย
> ข้อนี้พิสูจน์ว่า **หน้าเว็บ**ไม่พึ่ง Supabase ไม่ได้พิสูจน์ว่า **ระบบ**ไม่พึ่ง

เส้นทางที่หน้าเว็บเรียกจริง **ไปที่ backend ทั้งหมด**

## 7. แก้เงื่อนไขก่อนลบ Supabase — **เพิ่มขั้น G0**

ที่เคยเขียนไว้ว่า "import 5 ตาราง + ย้ายบัญชี = สำรองต้นทางครบ" **ไม่ถูกต้อง**
นั่นคือสิ่งที่เรา**ใช้** ไม่ใช่สิ่งที่โปรเจกต์ต้นทาง**มี**

### สิ่งที่ยังไม่รู้เลยเกี่ยวกับโปรเจกต์ต้นทาง

| ส่วน | สถานะความรู้ |
|---|---|
| `public.*` | รู้แค่ 5 ตารางที่ย้ายมา · **ไม่รู้ว่ามีทั้งหมดกี่ตาราง** |
| `auth.*` | รู้แค่ `auth.users` 3 แถว · ยังไม่ดู `auth.identities` `auth.sessions` `auth.refresh_tokens` `auth.audit_log_entries` |
| `storage.*` | รู้ไฟล์ 5 ไฟล์ · **ไม่รู้ metadata ของ bucket และ policy** |
| functions / triggers / RLS policies | **ไม่รู้เลย** |
| Edge Functions | รู้ว่ามี `sync-sci-news` · ไม่รู้ว่ามีตัวอื่นไหม |
| Vault secrets | รู้ว่ามี `project_url` `anon_key` `cron_secret` จากงาน C2 · ไม่รู้ว่ามีตัวอื่น |
| `cron.job` | รู้ 2 job · ไม่รู้ว่ามีอื่นอีกไหม |
| `c2_sync_runs` และตารางบันทึกอื่น | ยังไม่ได้สำรอง |

### ขั้น G0 — ทำแล้ว ผลโดยย่อ

| # | ทำอะไร | ผล |
|---|---|---|
| G0.1 | รายการ schema และตารางทั้งหมด พร้อมจำนวนแถว | **ครบ** — 8 schema · 52 ตาราง · 2,156 แถว |
| G0.2 | `pg_dump -Fc` ทั้งฐานข้อมูล + restore ลงฐานทดสอบแยก | **ทำแล้ว ไม่ใช่ครบ** — `pg_restore` คืน **exit 1** · กู้ได้ **47 จาก 52 ตาราง** (47 ตารางนั้นแถวตรงกันทุกตาราง) · ที่เหลือเป็นตารางภายในของ extension |
| G0.2.1 | สิทธิ์และ role ในไฟล์สำรอง | **ขาด** — `GRANT` 0 บรรทัด · `CREATE ROLE` 0 บรรทัด (เก็บ `OWNER TO` ได้ 135) → ต้องทำขั้น G0.9 |
| G0.3 | รายการ function / trigger / RLS policy / extension | **ครบ** — trigger 14/14 · policy 33/35 · function 182/204 (ที่ขาดเป็นของ extension) |
| G0.4 | รายการ Edge Functions และโค้ด | **ยังไม่ได้** — `pg_dump` ไม่ครอบคลุม ต้องใช้ access token ของบัญชี Supabase |
| G0.5 | รายการ `cron.job` ทั้งหมด | **ครบ** — 2 job (ของเก่า `active=false` · v2 `active=true`) |
| G0.6 | Storage ครบทุก bucket | **ครบ** — 2 bucket · 5 ไฟล์ สำรองไว้ก่อนแล้วพร้อม checksum |
| G0.7 | เทียบรายการที่สำรองได้กับที่สำรวจเจอ | **ยังไม่ครบ 100%** — ขาดโค้ด Edge Function และการตั้งค่าระดับโปรเจกต์ |

รายละเอียดทั้งหมดอยู่ใน **`PHASE4_G0_SUPABASE_BACKUP_2569-10-12.md`**

**ลำดับต่อไป: G1 ปิด cron เก่า → G2 เฝ้าดู → G3 หยุด webapi → G4 ลบ Caddy routes → G5 ลบ env → G6 ตัดสินใจไฟล์ → G7 ลบโปรเจกต์**

แผนขั้น G1–G6 พร้อมวิธีย้อนกลับทุกขั้น เตรียมไว้ใน **`PHASE4_REMOVAL_PLAN_2569-10-12.md`**
**G7 ลบโปรเจกต์ ยังเสนอไม่ได้** จนกว่าจะเก็บโค้ด Edge Function และบันทึกการตั้งค่าที่ `pg_dump` ไม่ครอบคลุมได้ครบ
