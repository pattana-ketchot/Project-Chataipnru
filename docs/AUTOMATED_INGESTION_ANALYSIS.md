## 1. Ingestion pipeline ปัจจุบันทำงานอย่างไร

รันเป็น **CLI อย่างเดียว** ไม่มี HTTP endpoint สำหรับนำเข้าเอกสาร

```bash
python -m pipeline.ingest --pdf <ไฟล์> --title <ชื่อหลักสูตร> --course-code <รหัส>
python -m pipeline.ingest_batch --dir <โฟลเดอร์> --provider <ชื่อสถาบัน>
```

### ขั้นตอนใน `pipeline/ingest.py`

| ลำดับ | ทำอะไร | โมดูล |
|---|---|---|
| 1 | อ่าน PDF เป็นข้อความรายหน้า และคำนวณ **sha256 ของไฟล์** | `extract_pdf.py:63` |
| 2 | **เช็คว่าเคยนำเข้าแล้วหรือยัง — ก่อนทำ embedding** | `ingest.py:80` |
| 3 | เติมข้อความจาก OCR ที่ถอดไว้ล่วงหน้าเป็นไฟล์ JSON | `ocr.py` |
| 4 | ล้างข้อความ (ตัดหัวกระดาษ เลขหน้า) | `clean.py` |
| 5 | ตัดเป็นท่อนพร้อมเลขหน้ากำกับ | `chunker.py` |
| 6 | สร้างเวกเตอร์ผ่าน Ollama (`bge-m3`, 1024 มิติ) | `embed.py` |
| 7 | เขียนฐานข้อมูลแบบ 3 transaction | `ingest.py:198-223` |

### โครงสร้าง transaction ที่ออกแบบมาดี

| Transaction | ทำอะไร | ทำไมต้องแยก |
|---|---|---|
| **A** | จองแถว `courses` + `course_documents` สถานะ `processing` | ให้การเช็คซ้ำเห็นผลทันที และถ้า B พังก็ไม่ลบแถวนี้ทิ้ง |
| **B** | ลบ chunk เดิม → ใส่ chunk ใหม่ → mark `done` | ทำทั้งหมดหรือไม่ทำเลย ไม่เหลือข้อมูลครึ่ง ๆ |
| **C** | ถ้า B พัง ให้ mark `failed` พร้อมข้อความผิดพลาด | ต้องแยกเพราะ B rollback ไปแล้ว |

**ส่วนนี้ห้ามแตะ** การเพิ่ม crawler ไม่ควรเข้าไปแก้ตรรกะนี้เลย

### `ingest_batch.py` — จุดเสียบที่ดีที่สุด

อ่านทุกไฟล์ `.pdf` และ `.txt` ในโฟลเดอร์ แล้วหาชื่อหลักสูตรจาก

- `<dir>/titles.json` → `{"<ชื่อไฟล์ไม่รวมนามสกุล>": "<ชื่อหลักสูตร>"}`
- `<dir>/codes.json` → รูปแบบเดียวกัน สำหรับรหัสหลักสูตร

ไฟล์เดียวพังไม่ทำให้ทั้งชุดหยุด เก็บไว้รายงานท้ายสุด

## 2. Duplicate / Change Detection ที่มีอยู่แล้ว

**มีแล้ว 3 ด่าน และแข็งแรงพอสมควร**

| ด่าน | กลไก | ตำแหน่ง |
|---|---|---|
| 1 | `already_ingested()` — เช็ค `file_sha256` + `extraction_status = 'done'` **ก่อน** embedding | `ingest.py:80-101` |
| 2 | `ON CONFLICT (course_id, file_sha256) DO UPDATE ... WHERE extraction_status <> 'done'` | `ingest.py:120-140` |
| 3 | `UNIQUE (course_id, file_sha256)` ที่ระดับฐานข้อมูล | `course_documents` |

### บทเรียนที่บันทึกไว้ในโค้ด

คอมเมนต์ที่ `ingest.py:84-87` ระบุว่าเดิมเช็คซ้ำ **หลัง** ทำ embedding ผลคือ

> ต้องคำนวณ 7,301 chunk ทิ้งบนเครื่องที่ไม่มีการ์ดจอ ราวสองชั่วโมง เพื่อจะเก็บของจริงแค่ 140 chunk

**crawler ต้องรักษาลำดับนี้ไว้** — เช็คให้ถูกก่อน ค่อยจ่ายค่า embedding

อีกจุดที่ต้องรู้: ด่านที่ 1 นับเฉพาะ `status = 'done'` เอกสารที่นำเข้าค้างไว้จะถูกหยิบมาทำต่อ ไม่ถูกข้ามถาวร

### สิ่งที่ยังไม่มี

**ไม่มีคอลัมน์เก็บ URL ต้นทางเลย** ระบบรู้ว่า "ไฟล์นี้เคยเข้าแล้ว" แต่ไม่รู้ว่า

- URL ไหนเคยตรวจไปแล้วบ้าง
- ตรวจครั้งล่าสุดเมื่อไร
- ตอนนั้นได้ `ETag` / `Last-Modified` อะไร

ผลคือถ้าไม่เพิ่มอะไร crawler จะต้อง**ดาวน์โหลดไฟล์ทุกไฟล์ทุกรอบ**เพื่อคำนวณ sha256 ซึ่งสิ้นเปลืองทั้งแบนด์วิดท์และเวลา

## 3. ส่วนที่ reuse ได้ — เกือบทั้งหมด

| ส่วน | reuse | หมายเหตุ |
|---|---|---|
| `pipeline/ingest.py::run()` | ✅ ทั้งดุ้น | เป็นฟังก์ชันปกติ เรียกจากโค้ดอื่นได้เลย ไม่ต้องผ่าน CLI |
| `pipeline/ingest_batch.py` | ✅ จุดเสียบหลัก | crawler เตรียมโฟลเดอร์ + `titles.json` แล้วเรียกตัวนี้ |
| การเช็คซ้ำด้วย sha256 | ✅ | ใช้ต่อได้ทันที |
| `httpx` | ✅ | **มีใน `pipeline/requirements.txt` แล้ว** (`ocr.py` ใช้อยู่) ไม่ต้องเพิ่ม dependency |
| `document_store.py` | ✅ | หาไฟล์ด้วย sha256 ไม่ใช่ path — ย้ายไฟล์แล้วยังหาเจอ |
| `documents/MANIFEST.tsv` | ✅ ขยายได้ | มีคอลัมน์ `copied_from` อยู่แล้ว เพิ่ม `source_url` ได้ |
| role `advisor_ingest` | ✅ | สิทธิ์จำกัดเฉพาะ 3 ตาราง เหมาะกับงานอัตโนมัติอยู่แล้ว |

### สิ่งที่ reuse ไม่ได้ และต้องรู้ไว้

**หน้าอัปโหลดของผู้ดูแลในเว็บ ไม่ได้ต่อกับ pipeline นี้**

`src/lib/ragIngest.js` เรียก `/api/admin/ingest` ซึ่งไปที่ **Supabase `rag_documents`** เป็นคนละระบบกับ `course_chunks` ที่ใช้ตอบคำถาม

แปลว่าปัจจุบัน**ไม่มีทางนำเอกสารเข้าคลังความรู้ผ่านหน้าเว็บได้เลย** ต้องรัน CLI เท่านั้น

## 4. ต้องเพิ่ม Crawler ตรงไหน

เสียบข้างหน้า ไม่แตะของเดิม

```
[ crawler ใหม่ ]
      │
      ├─ 1. อ่านรายการ URL ที่เฝ้าดู
      ├─ 2. HEAD เช็ค ETag/Last-Modified      ← ไม่โหลดถ้าไม่เปลี่ยน
      ├─ 3. โหลด → sha256 → เทียบ DB          ← ไม่นำเข้าถ้าซ้ำ
      └─ 4. เก็บลงโฟลเดอร์ + เขียน titles.json
                    │
                    ▼
      [ pipeline/ingest_batch.py เดิม ]  ← ไม่แก้อะไรเลย
                    │
                    ▼
      extract → chunk → embed → PostgreSQL/pgvector
```

### ไฟล์ที่เสนอให้เพิ่ม

| ไฟล์ | หน้าที่ | ประมาณขนาด |
|---|---|---|
| `pipeline/crawl/__init__.py` | — | เล็ก |
| `pipeline/crawl/fetch.py` | ดึงหน้าเว็บ หา `<a href>` ที่ลงท้าย `.pdf` · อ่าน `robots.txt` · หน่วงเวลาระหว่างคำขอ | ~120 บรรทัด |
| `pipeline/crawl/state.py` | อ่าน/เขียนสถานะการตรวจ URL (ตาราง `mko.crawl_sources`) | ~100 บรรทัด |
| `pipeline/crawl/download.py` | HEAD → GET → sha256 → เทียบ DB → เก็บไฟล์ | ~120 บรรทัด |
| `pipeline/crawl/run.py` | ตัวสั่งงาน มีโหมด `--check-only` และ `--ingest` | ~150 บรรทัด |
| `pipeline/crawl/sources.json` | รายการ URL ตั้งต้น 12 สาขา + หน้ารวมหลักสูตร | ข้อมูล |

**ไม่ต้องแก้ไฟล์เดิมสักไฟล์** ถ้าออกแบบให้ `run.py` เรียก `ingest_batch` ผ่าน subprocess หรือ import ฟังก์ชัน

### ลำดับการเช็ค เรียงจากถูกไปแพง

| ลำดับ | วิธี | ประหยัดอะไร |
|---|---|---|
| 1 | `HTTP HEAD` ดู `ETag` / `Last-Modified` | ไม่โหลดไฟล์เลย |
| 2 | เทียบ `Content-Length` กับ `byte_size` ที่บันทึกไว้ | ไม่โหลดไฟล์เลย |
| 3 | โหลดแล้วคำนวณ `sha256` เทียบ `course_documents.file_sha256` | ไม่ต้อง extract |
| 4 | เข้า pipeline เดิม | — |

## 5. ⚠️ อุปสรรคใหญ่ที่สุด — pipeline รันบนเซิร์ฟเวอร์ไม่ได้

ตรวจบนเซิร์ฟเวอร์ production แล้วพบว่า

| รายการ | สถานะ | หลักฐาน |
|---|---|---|
| dependency ของ pipeline บน host | ❌ **ไม่มี** | `python3 -c "import psycopg, pgvector, fitz"` ล้มเหลว |
| container สำหรับ pipeline | ❌ **ไม่มี** | compose มี 6 service: `ollama` `postgres` `backend` `frontend` `webapi` `caddy` |
| cron ของโปรเจกต์ | ❌ **ไม่มีเลย** | `crontab -l` ว่าง · `/etc/cron.d/` มีแต่ `e2scrub_all` |
| systemd timer ของโปรเจกต์ | ❌ **ไม่มี** | มีแต่ของระบบปฏิบัติการ (`apt-daily`, `fwupd-refresh`, `motd-news`) |
| Ollama สำหรับทำ embedding | ✅ **มี รันอยู่** | container `ollama` สถานะ running |

### แปลว่าอะไร

**ปัจจุบันการนำเข้าเอกสารทำจากเครื่อง dev แล้วคัดลอกไฟล์ขึ้นเซิร์ฟเวอร์**

หลักฐาน — `documents/MANIFEST.tsv` คอลัมน์ `copied_from` ชี้ไป path บนเครื่องอื่น และ `document_store.py` ระบุว่า `storage_path` ในฐานข้อมูล **ปนกันสองรูปแบบ Windows 18 แถว / POSIX 13 แถว** จึงใช้หาไฟล์ไม่ได้ ต้องหาด้วย sha256 แทน

### ต้องตัดสินใจก่อนอย่างอื่น

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| **A. เพิ่ม container `ingest` บนเซิร์ฟเวอร์** | อัตโนมัติจริง · ใช้ Ollama ในเครือข่ายเดียวกัน · ไม่ต้องเปิดพอร์ต DB | เพิ่ม service ใหม่ใน production · แย่ง CPU กับ Ollama ที่ให้บริการผู้ใช้อยู่ |
| **B. รันบนเครื่อง dev ตามตารางเวลา** | ไม่แตะ production เลย | ต้องเปิดเครื่องไว้ · ยังต้องคัดลอกไฟล์ขึ้นเอง · ไม่ใช่อัตโนมัติจริง |
| **C. เครื่องอื่น / CI** | แยกขาดจาก production | ต้องเปิดพอร์ต PostgreSQL ออกนอก = **ความเสี่ยงด้านความปลอดภัย** ไม่แนะนำ |

## 7. Database schema ที่ต้องเพิ่ม

**เป็นการเพิ่มอย่างเดียว ไม่แตะโครงสร้างเดิม ไม่กระทบ API และหน้าเว็บ**

### ทางเลือก A — เพิ่มคอลัมน์ใน `course_documents` (เบาที่สุด)

```sql
ALTER TABLE public.course_documents
  ADD COLUMN source_url        text,
  ADD COLUMN source_etag       text,
  ADD COLUMN source_checked_at timestamptz;
```

ทั้งสามเป็น nullable แถวเดิม 31 แถวใช้ได้ปกติ

**ข้อจำกัด** — บันทึกได้เฉพาะ URL ที่นำเข้าสำเร็จแล้ว ถ้าตรวจ URL หนึ่งแล้วพบว่าไม่มีอะไรเปลี่ยน จะไม่มีที่บันทึกว่า "เคยตรวจแล้ว" เพราะยังไม่มีแถวเอกสาร

### ทางเลือก B — ตารางใหม่ใน schema `mko` (แนะนำ)

```sql
CREATE TABLE mko.crawl_sources (
    id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    source_url        text        NOT NULL UNIQUE,
    page_url          text,                       -- หน้าเว็บที่พบลิงก์นี้
    course_code       text,                       -- ผูกกับ courses.code ถ้าเดาได้
    label             text,                       -- ชื่อที่แสดงบนเว็บ
    -- สถานะการตรวจ
    last_checked_at   timestamptz,
    last_status       text        NOT NULL DEFAULT 'new'
                      CHECK (last_status IN ('new','unchanged','changed','downloaded',
                                             'ingested','ignored','error')),
    last_error        text,
    -- ลายนิ้วมือฝั่งเซิร์ฟเวอร์ปลายทาง
    http_etag         text,
    http_last_modified text,
    content_length    bigint,
    -- ลายนิ้วมือของไฟล์จริง
    file_sha256       text,
    document_id       uuid REFERENCES public.course_documents(id) ON DELETE SET NULL,
    -- การอนุมัติ
    approved_at       timestamptz,
    approved_by       text,
    created_at        timestamptz NOT NULL DEFAULT now(),
    updated_at        timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_crawl_sources_status  ON mko.crawl_sources (last_status);
CREATE INDEX idx_crawl_sources_checked ON mko.crawl_sources (last_checked_at);

CREATE TRIGGER trg_crawl_sources_updated_at
    BEFORE UPDATE ON mko.crawl_sources
    FOR EACH ROW EXECUTE FUNCTION public.set_updated_at();
```

### ทำไมต้องอยู่ใน schema `mko` ไม่ใช่ `public`

`public` เก็บข้อมูลที่ระบบใช้ตอบคำถาม ส่วน `mko` เก็บข้อมูลกระบวนการทำงานและหลักฐาน — สถานะการ crawl เป็นข้อมูลกระบวนการ ตรงกับหลักการแบ่ง schema ที่ใช้อยู่แล้ว

ผลพลอยได้คือ role `advisor_ingest` ไม่ต้องได้สิทธิ์เพิ่มใน `public`

### ข้อดีเพิ่มเติมของทางเลือก B

- ใช้ `set_updated_at()` ฟังก์ชันที่มีอยู่แล้วได้เลย ไม่ต้องเขียนใหม่
- `document_id` เป็น `ON DELETE SET NULL` — ลบเอกสารแล้วประวัติการ crawl ยังอยู่
- สถานะ `ignored` ใช้บอกว่า "PDF นี้ไม่เกี่ยว ไม่ต้องนำเข้า" กันไม่ให้ระบบถามซ้ำทุกรอบ

## 8. ความเสี่ยงต่อ Production

เรียงจากหนักไปเบา

### 🔴 สูง — ขัดกับหลักการ "ตอบจากข้อมูลที่ตรวจแล้ว"

**นี่คือความเสี่ยงที่ใหญ่ที่สุด และไม่ใช่เรื่องเทคนิค**

ระบบมี schema `mko` ที่บังคับว่าค่าต้องมีสถานะ `verified` ก่อนนำไปตอบได้ — ปัจจุบันสกัดได้ 403 ค่า แต่ระบบใช้ตอบจริงแค่ **103 ค่า** ผ่านวิว `v_live_values`

แต่ **`course_chunks` ที่ RAG ใช้ตอบคำถามไม่มีด่านตรวจแบบนั้น** เอกสารเข้ามาแล้วระบบตอบจากมันได้ทันที

ถ้าให้ crawler นำเข้าอัตโนมัติ เท่ากับยอมให้**เนื้อหาที่ไม่มีใครดูเลยกลายเป็นคำตอบต่อผู้ใช้จริง** ซึ่งขัดกับสิ่งที่ระบบประกาศไว้ว่า "ตอบจากเอกสารที่ตรวจสอบย้อนกลับได้"

**ทางแก้** — ให้ crawler หยุดที่ขั้น "ดาวน์โหลดแล้วแจ้งเตือน" มีคนอนุมัติก่อนนำเข้า ได้ประโยชน์เกือบทั้งหมดโดยไม่เสียหลักการ

### 🔴 สูง — Ollama ถูกแย่งใช้

Ollama ตัวเดียวทำสองงานพร้อมกัน

1. สร้างเวกเตอร์ให้**คำถามของผู้ใช้ทุกคำถาม**
2. สร้างเวกเตอร์ตอนนำเข้าเอกสาร

การนำเข้าเอกสารหนึ่งเล่มคือการคำนวณหลายร้อย chunk บนเครื่องที่ไม่มีการ์ดจอ ถ้าทับเวลาที่มีคนใช้งาน **ผู้ใช้จะเจอคำถามค้าง**

**ทางแก้** — รันตอนกลางคืน จำกัดจำนวนเอกสารต่อรอบ และตั้ง nice/cpu limit ให้ container ingest

### 🟠 ปานกลาง — แคชคำตอบถูกล้างทั้งหมด

`answer_cache.corpus_version` คำนวณจาก `count(*)` และ `max(created_at)` ของ `course_chunks`

**การนำเข้าเอกสารใหม่แม้เล่มเดียว จะทำให้แคชทั้ง 157 แถวใช้ไม่ได้ทันที**

ผลคือคำถามทุกคำถามหลังจากนั้นต้องเรียก Gemini ใหม่หมด ซึ่งมีเพดานต่อนาที อาจเจอ 429 และผู้ใช้เจอคำตอบช้าผิดปกติอยู่ช่วงหนึ่ง

**ทางแก้** — นำเข้าตอนกลางคืน และถ้าเป็นไปได้ให้รวมหลายเล่มเป็นรอบเดียว แทนการนำเข้ากระจายทีละเล่ม

### 🟠 ปานกลาง — crawler หยิบไฟล์ผิด

เว็บคณะอาจมี PDF ที่ไม่ใช่ มคอ.2 เช่น ประกาศ ใบสมัคร ตารางสอบ ปฏิทินการศึกษา

ถ้า crawler เหมาเอาหมดแล้วนำเข้า คลังความรู้จะปนเปื้อน และระบบจะตอบจากเอกสารที่ไม่เกี่ยวข้อง โดยยังอ้างอิงได้ว่า "มาจากเอกสารหน้านี้" ทำให้คำตอบผิดดูน่าเชื่อถือ

**ทางแก้** — กรองด้วยรูปแบบ URL ขนาดไฟล์ และจำนวนหน้าขั้นต่ำ บวกกับด่านอนุมัติด้วยคน

### 🟡 ต่ำ — มารยาทในการดึงข้อมูล

ต้องอ่าน `robots.txt` ตั้ง `User-Agent` ที่ระบุตัวตนได้ และหน่วงเวลาระหว่างคำขออย่างน้อย 1–2 วินาที

เป็นเว็บของคณะตัวเอง ถ้ายิงถี่จนเว็บช้าจะเป็นเรื่องใหญ่กว่าปัญหาเทคนิค

### 🟡 ต่ำ — สิทธิ์ฐานข้อมูล

pipeline ใช้ role `advisor_ingest` ที่จำกัดสิทธิ์เฉพาะ `courses` / `course_documents` / `course_chunks` อยู่แล้ว

ถ้าเพิ่มตาราง `mko.crawl_sources` ต้องให้สิทธิ์ตารางนั้นเพิ่ม แต่ไม่ต้องขยายสิทธิ์ใน `public` **ถือว่าออกแบบไว้ดีอยู่แล้ว**

## 9. แผนที่เสนอ — แบ่ง 3 เฟส

| เฟส | ทำอะไร | แตะ production | ความเสี่ยง | ได้อะไร |
|---|---|---|---|---|
| **1** | crawler ที่**ตรวจอย่างเดียว** รันบนเครื่อง dev เขียนรายงานว่าเจอ PDF อะไรใหม่ | ❌ ไม่แตะเลย | **ไม่มี** | รู้ว่าเว็บคณะเปลี่ยนอะไรบ้าง |
| **2** | เพิ่มตาราง `mko.crawl_sources` + ดาวน์โหลดไฟล์ใหม่ลงโฟลเดอร์รอ **ยังไม่นำเข้า** | เพิ่มตารางใหม่ 1 ตาราง | ต่ำ | มีไฟล์พร้อมให้คนตรวจแล้วสั่งนำเข้า |
| **3** | เพิ่ม systemd timer + ช่องทางอนุมัติ | เพิ่ม timer (+ container ถ้าเลือกทาง A) | ปานกลาง | อัตโนมัติเต็มรูปแบบโดยยังมีคนคุม |

### เฟส 1 ทำได้ทันทีโดยไม่มีความเสี่ยงใด ๆ

เป็นแค่สคริปต์อ่านเว็บแล้วเขียนรายงาน **ไม่ต่อฐานข้อมูล production ด้วยซ้ำ** อ่าน `course_documents.file_sha256` จากไฟล์ดัมป์ที่มีอยู่แล้วก็พอ

ผลลัพธ์ที่ได้จะตอบคำถามสำคัญว่า **"เว็บคณะมี PDF กี่ไฟล์ และกี่ไฟล์ที่เรายังไม่มี"** ซึ่งเป็นข้อมูลที่ใช้ตัดสินใจเฟสต่อไปได้

path · original_filename · sha256 · page_count · byte_size · document_id · course_title · copied_from

id · course_id · original_filename · file_sha256 · storage_path

`extraction_status` รับค่า `processing` / `done` / `failed`
