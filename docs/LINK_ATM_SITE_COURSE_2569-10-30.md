### หลักฐานว่าเป็นหลักสูตรเดียวกัน

1. **ฐานทดสอบผูกคู่นี้ไว้อยู่แล้วด้วยรหัสเดียวกันเป๊ะ** — `eb3812e5…` → `1bcfb69c…`
   ค่าที่เสนอจึงไม่ใช่ของที่คิดขึ้นเอง แต่คือสิ่งที่ production ขาดไปจากชุดข้อมูลเดียวกัน
2. **ชื่อเป็นชื่อเดียวกันแต่คนละความยาว** — เว็บตัดคำว่า "การจัดการ" ออก ซึ่งเป็นกรณีที่
   หมายเหตุในโค้ด (`_course_for_site_title`) ยกเป็นตัวอย่างไว้ตั้งแต่ 15 ต.ค. 2569 ว่าคือ
   เหตุผลที่ต้องมีคอลัมน์ `course_id`
3. **ระดับปริญญาตรงกัน** — แถวเว็บระบุ `ปริญญาตรี` · ชื่อเล่มขึ้นต้น "วิทยาศาสตรบัณฑิต"
4. **ในคลังมีเล่มเดียวที่ชื่อเข้าข่าย** — ค้นด้วย `ilike '%เกษตรสมัยใหม่%'` ได้แถวเดียว
   จึงไม่มีความกำกวมเรื่องปีหรือระดับ
5. เล่มนั้นมีเอกสารจริง `atm.pdf` 255 หน้า

### ตรวจว่าไม่มีแถวอื่นถูกผูกผิดหรือซ้ำ

* `select count(*) from web.site_courses where course_id is not null` บน production = **0**
  (ทั้ง 14 แถวยังว่างทั้งหมด) จึงไม่มีทางซ้ำกับของเดิม
* สคริปต์มีด่านตรวจว่าหลังแก้ต้องมีแถวที่ผูกไปเล่มนี้ **เท่ากับ 1 แถว** ไม่งั้นยกเลิกทั้งชุด

## 2. SQL ที่เตรียมไว้

ทั้งสองไฟล์ห่อด้วย `BEGIN … COMMIT` และใช้ `DO` block ที่อ่าน `ROW_COUNT` จริง

```sql
UPDATE web.site_courses
   SET course_id = '1bcfb69c-...', updated_at = now()
 WHERE id = 'eb3812e5-...'                      -- แถวเป้าหมายแถวเดียว
   AND title = 'เทคโนโลยีการเกษตรสมัยใหม่'        -- กันกรณีรหัสชี้ไปแถวที่ชื่อเปลี่ยนแล้ว
   AND course_id IS NULL;                        -- กันเขียนทับค่าที่มีคนใส่ไว้ก่อน
GET DIAGNOSTICS n = ROW_COUNT;
IF n <> 1 THEN RAISE EXCEPTION ... END IF;       -- ไม่เท่ากับ 1 = ยกเลิกทั้งชุด
```

ด่านตรวจเพิ่มอีกสองข้อ: เล่มปลายทางต้องมีจริงและ `is_active` · หลังแก้ต้องมีแถวผูกไป
เล่มนี้แถวเดียว

**คืนค่า** ใช้ `…-rollback.sql` ซึ่งตั้ง `course_id = NULL` เฉพาะเมื่อค่าปัจจุบันเป็นรหัสที่
สคริปต์นี้ใส่ไว้ (ถ้ามีใครเปลี่ยนเป็นค่าอื่นภายหลังจะยกเลิกแทนการเขียนทับ)

## 3. ผลทดลองบนฐานทดสอบ

ทำให้ฐานทดสอบเหมือน production ก่อน (ตั้ง `course_id` เป็น NULL) แล้วเดินครบวงจร ·
ยิงผ่าน API จริงของ backend ที่รันในคอนเทนเนอร์ชั่วคราว ลบทิ้งหลังตรวจเสร็จ

| ขั้น | ผล |
|---|---|
| ก่อนแก้ — `/course-facts?title=เทคโนโลยีการเกษตรสมัยใหม่&level=ปริญญาตรี` | `{}` (อาการเดียวกับ production) |
| รัน apply.sql | พิมพ์ค่าก่อน/หลัง · แก้ 1 แถว · `COMMIT` |
| หลังแก้ — `/course-facts` เดิม | `…การจัดการเทคโนโลยีการเกษตรสมัยใหม่ (พ.ศ. 2564)` · ปี 2564 · 4 ปี · 130 หน่วยกิต · เอกสาร `atm.pdf` (brief=False) |
| หน้าเปรียบเทียบ (เว็บจริงที่ต่อ API นี้) | แถวปีขึ้น `ฉบับ พ.ศ. 2564 · อ้างอิงจาก atm.pdf` · ระยะเวลา `4 ปี / 130 หน่วยกิต` · ปุ่มดูเอกสารชี้ `/api/documents/68f72b12…/pdf` · คอลัมน์คณิตศาสตร์ที่เทียบอยู่ข้าง ๆ ยังเป็นของตัวเอง (`ma69.pdf`) ไม่ปนกัน |

| รัน rollback.sql ซ้ำ | **ยกเลิกทั้งชุด** — `ต้องคืน 1 แถว แต่คืนไป 0 แถว` |

## 4. ถ้าอนุมัติให้เขียน production

1. สำรองค่าเดิมไว้ในรายงานนี้แล้ว (`course_id = NULL`) และ rollback script พร้อม
2. รัน `apply.sql` ด้วย `psql -v ON_ERROR_STOP=1` บนฐาน `course_advisor`
3. ตรวจรับผ่านเว็บจริง: หน้าเปรียบเทียบของสาขานี้ต้องขึ้นปี/เอกสาร และหน้ารายละเอียด
   หลักสูตรต้องมีหน่วยกิตกับค่าเทอมครบ
4. ไม่ต้องรีสตาร์ท backend — เส้นทางนี้อ่านฐานทุกครั้ง ไม่ได้แคชการจับคู่

## 5. แยกต่างหาก — ยังไม่ได้ทำ

* **หน่วยกิตของสาขาการจัดการสิ่งแวดล้อมฯ 130 กับ 135** ยังเป็นงานค้างอีกเรื่องหนึ่ง
  ไม่เกี่ยวกับการเติม `course_id` ครั้งนี้ และยังไม่ได้ตรวจในรอบนี้
* อีก 13 แถวบนเว็บยังไม่มี `course_id` เช่นกัน แต่ชื่อของมันเทียบกับคลังได้อยู่แล้ว
  จึงยังไม่เสนอให้แก้ในรอบนี้
