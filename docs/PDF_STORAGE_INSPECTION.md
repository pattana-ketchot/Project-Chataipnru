## 2. แผนที่เสนอ (ยังไม่ทำ รออนุมัติ)

### 2.1 จัดโฟลเดอร์กลางบนเซิร์ฟเวอร์

```
~/course-advisor-system/documents/          ← ที่เก็บกลางใหม่
├── curriculum/                             เอกสาร มคอ.2 ฉบับเต็ม (19 ไฟล์)
├── curriculum-brief/                       ฉบับย่อที่ใช้สกัด (11 ไฟล์)
├── web/                                    ข้อมูลจากหน้าเว็บคณะ (ph_web.txt)
└── MANIFEST.tsv                            ชื่อไฟล์ · sha256 · หลักสูตร · จำนวนหน้า · document_id
```

- **คัดลอก ไม่ใช่ย้าย** ในขั้นแรก (`cp -a`) แล้วตรวจ SHA-256 ให้ครบ 31/31 ก่อน จึงค่อยตัดสินใจว่าจะลบของเดิมหรือเก็บไว้เป็นสำรอง
- พื้นที่ดิสก์: ใช้เพิ่ม 85 MB จากที่เหลือ 66 GB ไม่มีปัญหา
- ตั้งสิทธิ์ 600/700 เพราะเป็นเอกสารของคณะ

### 2.2 อัปเดต `storage_path` ให้ชี้ที่เก็บกลาง (ต้องอนุมัติแยก)

- `UPDATE course_documents SET storage_path = ...` 31 แถว ใน transaction เดียว มี backup ก่อน
- **ไม่กระทบระบบที่ทำงานอยู่** เพราะไม่มีโค้ดอ่านคอลัมน์นี้ เป็นการทำให้ข้อมูลตรงความจริงเท่านั้น
- ถ้าไม่อยากแตะ DB เลย ข้ามข้อนี้ได้ แล้วใช้ `MANIFEST.tsv` เป็นตัวอ้างอิงแทน

## 3. เรื่อง "เก็บ PDF ไว้ในฐานข้อมูลด้วย"

ตรวจแล้วทำได้ในทางเทคนิค (`bytea` หรือ large object) แต่ขอเสนอข้อมูลให้ตัดสินใจก่อน เพราะเป็น **การเปลี่ยน schema ของ production**

| ผลกระทบ | ตัวเลขจริง |
|---|---|
| ขนาด dump ปัจจุบัน | 52 MB |
| ขนาดไฟล์ PDF ที่จะใส่เพิ่ม | 84.7 MB (PDF บีบอัดแล้ว ใส่ใน `bytea` แทบไม่เล็กลง) |
| ขนาด dump หลังใส่ | ประมาณ 135–140 MB (**โตขึ้นราว 2.6 เท่า**) |
| เวลาที่ใช้ backup / restore | เพิ่มตามสัดส่วนขนาด ทุกครั้งที่ deploy เราสำรองฐานข้อมูลก่อนเสมอ |
| ประโยชน์ต่อการตอบคำถาม | **ไม่มี** — ไม่มีโค้ดใดอ่านตัวไฟล์ตอนทำงาน |
| ประโยชน์ที่ได้จริง | เอกสารไม่หายแม้เครื่องที่นำเข้าหาย · สำรองที่เดียวได้ทั้งข้อมูลและเอกสาร · พิสูจน์ provenance ได้ครบในที่เดียว |

**ทางเลือก 3 แบบ**

| | วิธี | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **A** (แนะนำ) | โฟลเดอร์กลาง + `MANIFEST.tsv` + รวมโฟลเดอร์นี้ในการสำรองข้อมูล | ไม่แตะ schema · dump ยังเล็ก · แก้ปัญหา "ไฟล์หายตามเครื่อง" ได้จริง | ต้องจำสำรองสองอย่าง (ฐานข้อมูล + โฟลเดอร์) |
| **B** | เพิ่มตารางใหม่ `document_files(document_id, content bytea, byte_size, sha256)` | เอกสารอยู่กับข้อมูลในที่เดียว สำรองครั้งเดียวได้ทุกอย่าง | dump โต 2.6 เท่า · ต้อง migration บน production · ต้องเขียนสคริปต์นำเข้า |
| **C** | ทั้ง A และ B | ปลอดภัยที่สุด | ซ้ำซ้อน เปลืองพื้นที่สองเท่า |

**ข้อเสนอของผม: เริ่มที่ A ก่อน** เพราะแก้ปัญหาที่รายงานบันทึกไว้ ("ไฟล์ต้นฉบับไม่ได้เก็บถาวร") ได้ครบ โดยไม่ต้องแตะ schema ของ production ในช่วงที่โปรเจกต์เน้นความเสถียรและใกล้สาธิต · ถ้าต้องการ B ทำเป็นรอบแยกหลังสาธิตเสร็จ พร้อม migration ที่ย้อนกลับได้

ถ้าเลือก B ต้องเตรียม: migration ไฟล์ใหม่ใน `db/migrations/`, สคริปต์นำเข้าไฟล์ที่ตรวจ SHA-256 ทุกไฟล์, แผน rollback, และยืนยันว่าเวลาสำรอง/กู้คืนที่นานขึ้นยอมรับได้
