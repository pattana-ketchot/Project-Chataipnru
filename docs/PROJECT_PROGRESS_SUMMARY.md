# สรุปความคืบหน้าโครงการ Course Advisor System

ช่วงเวลา **13 – 17 สิงหาคม 2569** · 15 รอบการเปลี่ยนแปลง · แก้ไข 46 ไฟล์ · เพิ่มโค้ดและเอกสาร 2,907 บรรทัด

เอกสารนี้สรุปว่าตั้งแต่เริ่มจนถึงปัจจุบันได้ทำอะไรไปบ้าง เหมาะสำหรับใช้อธิบายความคืบหน้าต่ออาจารย์ที่ปรึกษา
ตัวเลขทุกตัวมาจากการวัดกับคลังเอกสารจริง 18 หลักสูตร

## 1. จุดเริ่มต้น

โครงการมีโค้ดครบทุกส่วนแล้ว ได้แก่ ฐานข้อมูล, ขั้นตอนนำเข้า PDF, ตัวเชื่อมโมเดลภาษา,
API และหน้าเว็บ พร้อมเอกสารประกอบ 3 ฉบับ

แต่เมื่อทดลองรันจริงพบว่า **ระบบไม่เคยถูกรันตั้งแต่ต้นจนจบมาก่อน** และมีข้อผิดพลาดที่ทำให้
ใช้งานไม่ได้อยู่ในทุกชั้นของระบบ ตั้งแต่ฐานข้อมูลไปจนถึงการประมวลผลภาษา

## 2. ระยะที่ 1 — ทำให้ระบบทำงานได้จริง

### 2.1 ข้อผิดพลาดที่ทำให้ระบบใช้งานไม่ได้

พบและแก้ไขทั้งหมด **13 รายการ** แบ่งตามชั้นของระบบ

**ชั้นฐานข้อมูล**

| ปัญหา | ผลกระทบ |
|---|---|
| ตั้งชื่อคอลัมน์ว่า `current_role` ซึ่งเป็นคำสงวนของ PostgreSQL | สคริปต์สร้างฐานข้อมูลหยุดกลางคัน สร้างตารางได้เพียง 1 จาก 9 ตาราง |
| คำสั่งสร้างบัญชีผู้ใช้ฐานข้อมูลถูกปิดการทำงานไว้ | ระบบเชื่อมต่อฐานข้อมูลไม่ได้เลย |
| ไม่มีกลไกอัปเดตเวลาแก้ไขล่าสุด | คอลัมน์ `updated_at` มีค่าเท่ากับเวลาสร้างตลอดไป |

**ชั้น Backend**

| ปัญหา | ผลกระทบ |
|---|---|
| อ่านไฟล์ตั้งค่าจากตำแหน่งสัมพัทธ์ | รันตามคู่มือแล้วหาไฟล์ไม่เจอ ระบบเริ่มทำงานไม่ได้ |
| ไลบรารีเข้ารหัสรหัสผ่านเวอร์ชันไม่เข้ากัน | สมัครสมาชิกและเข้าสู่ระบบใช้งานไม่ได้ทั้งคู่ |
| ค่าเปรียบเทียบรหัสผ่านสำรองเขียนด้วยมือ | อาจไม่ทำงานจริง ทำให้กลไกป้องกันการคาดเดาบัญชีเสียไป |
| ระบุที่อยู่ฐานข้อมูลเป็น `localhost` | ทุกการเชื่อมต่อช้าเพิ่ม 5 วินาที โดยไม่มีข้อความแจ้งเตือน |
| ระบุไลบรารีไม่ครบตามที่โค้ดใช้ | ติดตั้งตามเอกสารแล้วระบบยังเริ่มทำงานไม่ได้ |

**การตั้งค่าเชื่อมต่อ**

พบเพิ่มเติมระหว่างพัฒนา ได้แก่ การอนุญาตให้หน้าเว็บเรียก API ไม่ครบทุกที่อยู่,
ระบบแนะนำหลักสูตรซ้ำรายการเดิม, และโมเดลตอบเป็นภาษาจีนเมื่อคำถามกำกวม

### 2.2 การเตรียมสภาพแวดล้อม

ติดตั้ง Docker และ Ollama, ตั้งค่าฐานข้อมูลพร้อมบัญชีผู้ใช้แยกสิทธิ์ 2 ระดับ
(บัญชีสำหรับ API อ่านข้อมูลหลักสูตรได้อย่างเดียว ส่วนบัญชีสำหรับนำเข้าข้อมูลแตะข้อมูลผู้ใช้ไม่ได้)
และสร้างสภาพแวดล้อม Python แยกของโครงการ

**ผลลัพธ์:** ระบบเริ่มทำงานได้ครบทุกส่วนเป็นครั้งแรก ผ่านการทดสอบ API 12 รายการ

## 3. ระยะที่ 2 — คุณภาพข้อมูลภาษาไทย

เมื่อนำเอกสาร มคอ.2 จำนวน 18 หลักสูตรเข้าระบบ พบว่าข้อความที่ดึงจาก PDF **เสียหายในระดับ
อักขระ 3 รูปแบบ** ซึ่งมองด้วยตาไม่เห็นความผิดปกติ แต่ทำให้การค้นหาล้มเหลวทั้งหมด

### 3.1 วรรณยุกต์ถูกแทนที่ด้วยรหัสอักขระที่ไม่มีความหมาย

ฟอนต์ไทยที่ใช้ในเอกสารกำหนดวรรณยุกต์ไว้ในช่วงรหัสสำรอง ทำให้คำว่า "คอมพิวเตอร์" กลายเป็น
"คอมพิวเตอร" ที่ค้นหาไม่พบ ได้ถอดรหัสและแปลงกลับครบทั้ง **23 รหัสอักขระ**

พบใน **4 จาก 18 ไฟล์** โดยได้รับผลกระทบเกือบทุกบรรทัด

| ไฟล์ | คำว่า "ให้" ก่อน → หลัง | คำว่า "เป็น" ก่อน → หลัง |
|---|---|---|
| animation64 | 0 → 520 | 0 → 409 |
| cs61 | 0 → 469 | 0 → 394 |
| fs61 | 0 → 429 | 0 → 322 |
| it66 | 0 → 562 | 0 → 424 |

### 3.2 สระถูกแยกออกจากกัน

สระ ำ ถูกแยกเป็นช่องว่างกับสระอา ทำให้ "จำนวน" กลายเป็น "จ านวน" พบ **13,292 จุด**
กระจายใน 12 จาก 18 ไฟล์

### 3.3 การเข้ารหัสสระเดียวกันคนละแบบ

เอกสารหลักสูตรวิทยาศาสตร์เครื่องสำอางสองปีการศึกษาเข้ารหัสคำว่า "สำอาง" ต่างกัน
ทั้งที่มองด้วยตาเหมือนกันทุกประการ ทำให้ค้นหาด้วยคำเดียวกันแล้วเจอไม่เท่ากัน

**ผลรวมหลังแก้:** ไม่เหลืออักขระผิดปกติในคลังเอกสารทั้งหมด

## 4. ระยะที่ 3 — ความถูกต้องของการค้นหา

### 4.1 โมเดลแปลงข้อความเดิมอ่านภาษาไทยไม่ออก

ทดสอบพบว่าโมเดล `nomic-embed-text` ที่เลือกไว้แต่แรก **แปลงข้อความภาษาไทยทุกข้อความ
เป็นค่าเดียวกันหมด**

| ภาษาของข้อความทดสอบ | จำนวนข้อความ | ผลลัพธ์ที่ไม่ซ้ำกัน |
|---|---|---|
| อังกฤษ | 3 | 3 |
| **ไทย** | 3 | **1** |

นั่นหมายความว่าระบบค้นหาเชิงความหมายไม่ทำงานเลย **แต่ไม่มีอาการผิดปกติให้สังเกตเห็น** —
API ตอบสถานะปกติ หน้าเว็บแสดงผลได้ และมีข้อมูลอยู่ในฐานข้อมูลจริง

เปลี่ยนไปใช้ `bge-m3` ซึ่งรองรับหลายภาษารวมภาษาไทย ผลทดสอบหลังเปลี่ยน: คำค้น
"อยากเรียนนวดแผนไทย" ใกล้เคียงหัวข้อการแพทย์แผนไทย 0.654 เทียบกับการเขียนโปรแกรม 0.375

การเปลี่ยนโมเดลทำให้ต้องปรับโครงสร้างฐานข้อมูลและนำเข้าข้อมูลใหม่ทั้งหมด จึงเพิ่มการตรวจสอบ
ตอนเริ่มระบบว่าค่าที่ตั้งไว้ตรงกับฐานข้อมูลจริงหรือไม่ ถ้าไม่ตรงจะปฏิเสธการเริ่มทำงานทันที

### 4.2 การแบ่งข้อความไม่รองรับภาษาไทย

โปรแกรมเดิมแบ่งข้อความโดยนับคำจากช่องว่าง ซึ่งภาษาไทยไม่เขียนเว้นวรรคระหว่างคำ

| ตัวชี้วัด | ก่อนแก้ | หลังแก้ |
|---|---|---|
| ขนาดส่วนข้อความ | 22 – 3,780 ตัวอักษร | 30 – 1,000 ตัวอักษร |
| ไฟล์ที่นำเข้าไม่สำเร็จ | 3 จาก 18 | 0 จาก 18 |

### 4.3 ชื่อหลักสูตรในคำถามรบกวนการค้นหา

ผู้ใช้ถามเรื่องอาชีพของหลักสูตรหนึ่ง ระบบตอบว่าไม่พบข้อมูลทั้งที่เอกสารระบุไว้ชัดเจน

สาเหตุคือคำถามมีชื่อหลักสูตรอยู่ด้วย ชื่อนั้นจึงไปจับคู่กับข้อความทุกส่วนที่เอ่ยชื่อเดียวกัน
รวมถึงภาคผนวกกว่าร้อยหน้าที่เป็นตารางประเมินความพึงพอใจ

แก้โดยระบุให้ได้ก่อนว่าถามถึงหลักสูตรใด แล้วจำกัดขอบเขตการค้นหาพร้อมตัดชื่อออกจากคำค้น

| วิธีค้น | อันดับของส่วนข้อความที่มีคำตอบ |
|---|---|
| ค้นทั้งคลัง ด้วยคำถามเต็ม | แย่กว่า 200 |
| ค้นเฉพาะเล่มนั้น ตัดชื่อหลักสูตรออก | **อันดับ 3** |

ระหว่างแก้พบว่าเมื่อจำกัดขอบเขต ระบบคืนผลลัพธ์เป็นศูนย์รายการ ทั้งที่หลักสูตรนั้นมีข้อมูล 422 ส่วน
เนื่องจากดัชนีค้นหาเลือกรายการก่อนแล้วจึงกรองภายหลัง **โดยไม่มีข้อความแจ้งข้อผิดพลาด**

## 5. ระยะที่ 4 — ระบบสนทนาถามตอบ

เดิมระบบรับข้อมูลผู้ใช้แล้วแนะนำหลักสูตรครั้งเดียวจบ ไม่สามารถถามต่อเนื่องได้
ได้เพิ่มความสามารถสนทนา ประกอบด้วย 5 ชั้นการทำงาน

| ชั้น | หน้าที่ | เหตุผล |
|---|---|---|
| 1 | ตอบคำทักทายทันที | คำทักทายไม่มีเนื้อหาให้ค้น เดิมถูกปฏิเสธ ซึ่งเป็นสิ่งแรกที่ผู้ใช้เจอ |
| 2 | เขียนคำถามใหม่ให้สมบูรณ์ | คำถามต่อเนื่องอย่าง "แล้วกี่หน่วยกิต" ไม่มีข้อมูลว่าหมายถึงหลักสูตรใด |
| 3 | ขยายคำย่อเป็นชื่อทางการ | ผู้ใช้พิมพ์ "วิทคอม" และ "Comsci" ส่วนเอกสารใช้ชื่อเต็มเสมอ |
| 4 | จำกัดขอบเขตการค้นหา | ตามที่อธิบายในหัวข้อ 4.3 |
| 5 | ตัดสินว่าจะตอบ ปฏิเสธ หรือแจ้งว่าไม่มีข้อมูล | ต้องแยกสามกรณีนี้ออกจากกันให้ชัด |

### 5.1 การป้องกันการแต่งข้อมูล

พบว่าการเขียนกฎในคำสั่งว่า "ถ้าไม่มีข้อมูลให้บอกว่าไม่มีแล้วหยุด" **ใช้ไม่ได้จริง** โมเดลจะเขียนว่า
"จากข้อมูลที่ให้มาไม่มีการกล่าวถึง..." แล้วเขียนต่ออีกหลายย่อหน้าจากความรู้ทั่วไปของตัวเอง

ตัวอย่าง: เมื่อถามจำนวนหน่วยกิต โมเดลตอบว่าเอกสารไม่ได้ระบุ แล้วเติมว่า "โดยทั่วไปมักต้องการ
ประมาณ 120–150 หน่วยกิต" ซึ่งอันตรายเพราะฟังดูน่าเชื่อถือและผู้อ่านแยกไม่ออกว่าส่วนใดมาจาก
เอกสารจริง

แก้ที่ระดับโครงสร้าง โดยถามโมเดลเป็นคำถามปิดก่อนว่าเอกสารตอบได้หรือไม่ แล้วให้โปรแกรม
เป็นผู้ตัดสิน ไม่ปล่อยให้โมเดลยับยั้งตัวเองระหว่างเขียนคำตอบยาว

**ผลหลังแก้:** คำถามเดียวกันได้คำตอบว่า 130 หน่วยกิต พร้อมรายละเอียดแยกตามหมวด ตรงกับเอกสาร

### 5.2 บทเรียนเรื่องขีดความสามารถของโมเดลขนาดเล็ก

ทดลองรวมการตัดสินสองเรื่องไว้ในคำสั่งเดียวเพื่อประหยัดการเรียกโมเดล ผลคือ**ความแม่นยำลดลง
ทั้งสองด้าน** จึงแยกกลับเป็นสองคำสั่งที่ถามอย่างเดียวชัดเจน

### 5.3 หน้าเว็บ

ปรับหน้า "คุยกับที่ปรึกษา" จากเดิมที่เรียกฟังก์ชันแนะนำหลักสูตรครั้งเดียว ให้เป็นหน้าสนทนาจริง
มีข้อความสองฝั่ง จำบทสนทนาได้ และกดดูแหล่งอ้างอิงของคำตอบได้ พร้อมแยกผลจากแบบสอบถาม
ออกเป็นหน้าของตัวเอง

### 6.1 กรณีที่ชุดประเมินพิสูจน์คุณค่าตัวเอง

## 7. ระยะที่ 6 — การนำระบบขึ้นใช้งาน

### 7.1 การเปิดให้ผู้อื่นทดสอบ

เดิมหน้าเว็บเรียก API ด้วยที่อยู่ที่ฝังไว้ตอนสร้าง ทำให้เปิดจากเครื่องอื่นแล้วใช้งานไม่ได้
แก้โดยให้หน้าเว็บส่งต่อคำขอไปยัง API เอง ทำให้เปิดผ่านอินเทอร์เน็ตได้โดยไม่ต้องตั้งค่าเพิ่ม
และเปลี่ยนที่อยู่สาธารณะได้โดยไม่ต้องสร้างใหม่

ปรับการจำกัดอัตราการใช้งานจากเดิมนับตามหมายเลขเครื่อง เป็นนับตามบัญชีผู้ใช้
เพราะเมื่อส่งต่อคำขอแล้วระบบจะเห็นผู้ใช้ทุกคนเป็นเครื่องเดียวกัน

### 7.2 การสำรองข้อมูล

สร้างสคริปต์สำรองและกู้คืนฐานข้อมูล เก็บย้อนหลัง 10 ชุด ขนาดไฟล์ประมาณ 38 MB
มีการตรวจสอบว่าไฟล์ที่ได้ไม่เล็กผิดปกติเพื่อไม่ให้เก็บไฟล์เสียไว้โดยไม่รู้ตัว

### 7.3 การจัดการหน่วยความจำการ์ดจอ

การ์ดจอที่ใช้มีหน่วยความจำ 8GB และต้องแบ่งให้ระบบแสดงผลด้วย ขณะที่โมเดลสองตัวใช้รวม 5.4GB

| การตั้งค่า | ผลที่เกิดขึ้น |
|---|---|
| ค่าเริ่มต้น | คำถามแรกหลังเว้นช่วงใช้เวลา 102 วินาที จนหน้าเว็บแจ้งข้อผิดพลาด |
| ตรึงโมเดลไว้ตลอด | การยิงคำถามติดกันจำนวนมากทำให้ตัวรันโมเดลถูกหยุดกลางคัน |
| **วิธีที่ใช้** | ถือไว้ 30 นาที และให้ระบบยิงคำขอเล็กๆ ทุก 20 นาทีเพื่อไม่ให้หมดอายุ |

พร้อมปรับให้ระบบแจ้งผู้ใช้ว่ากำลังเตรียมโมเดล แทนข้อความผิดพลาดที่ไม่บอกสาเหตุ

### 7.4 อุปสรรคเฉพาะของระบบปฏิบัติการ

พบหลังรีสตาร์ทเครื่องว่าระบบเปิดไม่ขึ้น 2 สาเหตุ

1. **Windows จองช่วงพอร์ตไว้ให้ระบบเสมือน** โดยช่วงที่จองคลุมพอร์ตที่ตั้งใจใช้ และ
   **สุ่มใหม่ทุกครั้งที่รีสตาร์ท** จึงย้ายไปใช้พอร์ตที่อยู่นอกช่วงดังกล่าว
2. **มีโปรแกรมโมเดลภาษาสองชุดแย่งพอร์ตเดียวกัน** โดยชุดที่ติดตั้งบนเครื่องเริ่มทำงานอัตโนมัติ
   และยึดพอร์ตก่อน ทั้งที่โมเดลทั้งหมดอยู่ในอีกชุดหนึ่ง

## 10. สิ่งที่ได้เรียนรู้และนำไปเขียนในรายงานได้

1. **ความล้มเหลวที่ไม่แสดงอาการอันตรายที่สุด** — ทั้งกรณีโมเดลอ่านภาษาไทยไม่ออก และกรณี
   ดัชนีค้นหาคืนผลว่าง ระบบยังตอบสถานะปกติทุกอย่าง หน้าเว็บยังแสดงผลได้ แต่คำตอบผิดทั้งหมด
2. **การแก้ที่ระดับคำสั่งไม่พอสำหรับการควบคุมโมเดล** — ต้องแก้ที่ระดับโครงสร้างการทำงาน
   โดยให้โปรแกรมเป็นผู้ตัดสินใจแทนที่จะขอให้โมเดลยับยั้งตัวเอง
3. **โมเดลขนาดเล็กตัดสินทีละเรื่องได้ดีกว่าหลายเรื่องพร้อมกัน** — พิสูจน์ด้วยการวัดที่แสดงว่า
   การรวมคำสั่งทำให้ความแม่นยำลดลงทั้งสองด้าน
4. **ชุดทดสอบอัตโนมัติมีค่าเมื่อความผิดพลาดไม่แสดงอาการ** — มีกรณีจริงที่การแก้ปัญหาหนึ่ง
   ทำให้อีกส่วนพัง และตรวจพบได้เพราะมีชุดประเมินเท่านั้น
5. **การประมวลผลภาษาไทยต้องการการเตรียมข้อมูลเฉพาะทาง** — ทั้งการถอดรหัสอักขระ
   การประกอบสระ และการแบ่งข้อความที่ไม่พึ่งช่องว่าง
