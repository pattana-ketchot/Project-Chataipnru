### การตัดสินใจสามข้อที่อยากให้ตรวจ

**1. `needs_review` แยกจาก `status` ไม่ได้ยัดเป็นสถานะที่แปด**

`status` บอกว่าไฟล์เดินทางไปถึงไหน ส่วน `needs_review` บอกว่าคนต้องเข้ามาดูก่อนไปต่อ
เป็นคนละเรื่องและเกิดพร้อมกันได้ — ไฟล์ที่โหลดเก็บไว้แล้วแต่ยังระบุหลักสูตรไม่ได้
คือ `status='downloaded'` **และ** `needs_review=true`

ถ้ายัดรวมเป็นค่าเดียวจะต้องมีสถานะลูกผสมเพิ่มขึ้นเรื่อย ๆ และคิวงานจะกรองยากขึ้นทุกครั้งที่เพิ่มสถานะใหม่

**2. ไม่ให้สิทธิ์ `DELETE` กับ role ใดเลยบนตารางนี้**

```sql
GRANT SELECT, INSERT, UPDATE ON mko.crawl_sources TO advisor_ingest;
```

ประวัติการตรวจต้องไม่หาย แม้เว็บคณะถอดลิงก์ออกแล้ว การไม่ให้สิทธิ์ตั้งแต่ระดับฐานข้อมูล
ปลอดภัยกว่าการหวังว่าโค้ดจะไม่เผลอสั่งลบ — ตรงกับข้อห้าม "ห้ามลบเอกสารเก่าเมื่อ Crawler หา URL ไม่พบ"

**3. อยู่ใน schema `mko` ไม่ใช่ `public`**

`public` เก็บข้อมูลที่ระบบใช้ตอบคำถาม ส่วน `mko` เก็บข้อมูลกระบวนการ
สถานะการ crawl ไม่เคยถูกอ่านตอนตอบผู้ใช้ และ `advisor_api` ได้สิทธิ์อ่านแค่วิวคิวงานเท่านั้น

## 3. ผลการทดสอบ

### วิธีทดสอบ

ใช้ **HTTP จำลอง** ไม่ยิงเว็บจริง เพราะสถานการณ์อย่าง "ไฟล์เดิมแต่เนื้อหาเปลี่ยน"
กับ "เซิร์ฟเวอร์ตอบ 500" สร้างขึ้นบนเว็บจริงไม่ได้ และการยิงเว็บคณะซ้ำ ๆ ก็ไม่สุภาพ

แต่ต่อกับ **PostgreSQL จริง** ที่ลง migration 003 แล้ว เพราะสิ่งที่ต้องพิสูจน์คือ
CHECK constraint, ตัวกันซ้ำ และ trigger ทำงานถูกหรือไม่ — ของปลอมพิสูจน์แทนไม่ได้

```bash
python eval/crawl_state_check.py --database-url postgresql://.../crawl_test
```

### วิธีทดสอบที่ใช้ และเหตุผล

เครื่องนี้**ไม่มี PostgreSQL และไม่มี Docker** จึงทดสอบ migration ที่ไหนไม่ได้เลย
ทางเลือกที่ผมใช้คือสร้างฐานข้อมูลชื่อ `crawl_test` **แยกต่างหาก** ในคอนเทนเนอร์
postgres ของเซิร์ฟเวอร์ ผ่านอุโมงค์ SSH แล้วลบทิ้งเมื่อเสร็จ

- **ไม่แตะ `course_advisor`** เลยสักคำสั่ง
- ไม่ restart service ใด
- ลบฐานทดสอบแล้ว ยืนยันด้วยการ list ฐานข้อมูลที่เหลือ
- อ่านข้อมูลจาก production ด้วย `SELECT` อย่างเดียวเพื่อเอาไปใส่ฐานทดสอบ

ถ้าไม่ต้องการให้แตะเซิร์ฟเวอร์แม้แต่แบบนี้ ทางเลือกคือติดตั้ง Docker บนเครื่องพัฒนา

ไม่ต้องทำอะไร — ลบไฟล์ที่เพิ่มมาทิ้งได้ทันที ไม่มีอะไรเชื่อมโยงกับระบบเดิม

### ถ้ารัน migration 003 ไปแล้ว

```sql
BEGIN;
DROP VIEW  IF EXISTS mko.v_crawl_pending;
DROP TABLE IF EXISTS mko.crawl_sources;      -- trigger และ index หายไปพร้อมตาราง
DELETE FROM mko.schema_migrations WHERE version = '003_crawl_sources';
COMMIT;
```

**ปลอดภัยเพราะ**

- ไม่มีตารางอื่นอ้างอิง `mko.crawl_sources` — คีย์นอกเส้นเดียวชี้ **ออกไป** หา `course_documents` ไม่ใช่ชี้เข้ามา
- ไม่มีโค้ดใน `backend/` หรือ `pipeline/ingest.py` อ่านตารางนี้
- `public.set_updated_at()` เป็นฟังก์ชันเดิมที่ตารางอื่นใช้อยู่ **ห้ามลบ**
- ใช้เวลาไม่ถึงวินาที ไม่ต้อง restart service

### ถ้าต้องการเก็บข้อมูลไว้ก่อนลบ

```bash
pg_dump -t mko.crawl_sources --data-only > crawl_sources_backup.sql
```

### ไฟล์ใน staging

ลบได้อย่างปลอดภัย เป็นสำเนาของไฟล์ที่ยังดาวน์โหลดใหม่ได้จากเว็บคณะเสมอ
ไม่มีอะไรในฐานข้อมูลพึ่งพาไฟล์เหล่านี้ นอกจากคอลัมน์ `staging_path` ที่เป็นข้อความเฉย ๆ

## 8. ขั้นตอนถ้าอนุมัติให้ deploy

```bash
# 1. สำรองฐานข้อมูลก่อน
bash scripts/backup_db.sh

# 2. รัน migration (ใช้เวลาไม่ถึงวินาที ไม่ต้อง restart อะไร)
docker compose -f docker-compose.prod.yml exec -T postgres \
    psql -U $POSTGRES_USER -d $POSTGRES_DB < db/migrations/003_crawl_sources.sql

# 3. ยืนยัน
#    SELECT version FROM mko.schema_migrations ORDER BY 1;   -> ต้องเห็น 003
#    SELECT count(*) FROM mko.crawl_sources;                 -> 0
#    SELECT count(*) FROM course_documents;                  -> ต้องยัง 31
```

จากนั้นรัน crawler **จากเครื่องพัฒนา** (ยังไม่ตั้งเวลาอัตโนมัติ)

```bash
CRAWL_DATABASE_URL=... python -m pipeline.crawl.sync --staging staging/crawl
```

## 9. คำถามที่ต้องตัดสินใจก่อน Phase 3

1. **ช่องทางอนุมัติ** — คำสั่ง CLI · หน้าจอในเว็บผู้ดูแล · หรือแก้ในฐานข้อมูลตรง ๆ
2. **staging เก็บที่ไหน** — เครื่องพัฒนา หรือบนเซิร์ฟเวอร์ (ผูกกับคำตอบเรื่อง "รัน ingest ที่ไหน" ในเอกสารวิเคราะห์ข้อ 5)
3. **แจ้งเตือนอย่างไรเมื่อพบของใหม่** — ยังไม่ได้ออกแบบ
4. **เก็บไฟล์ใน staging นานแค่ไหน** ถ้าไม่มีใครอนุมัติ
