### 3.3 โค้ดเดิมอ่านข้อมูล `required_in_group` ได้หรือไม่ — และลำดับย้อนกลับ

ทดสอบทั้งสองทิศทางบนฐานทดสอบแล้ว

| สถานะ | ผล |
|---|---|
| โค้ด**ใหม่** + ข้อมูล**เก่า** (`choose_group`) | ทำงานถูกต้องทุกอย่าง ป้ายกำกับเดิมยังแสดงปกติ |
| โค้ด**เก่า** + ข้อมูล**ใหม่** (`required_in_group`) | **ไม่ระเบิด** แต่พฤติกรรมเสีย 2 อย่าง: ผู้ใช้เห็นค่าดิบ `required_in_group` ในคำตอบวิชาเดี่ยว และ `4124813` หายจากท้ายรายการวิชาบังคับ (ท้ายรายการเขียนว่า "นอกจากนี้มี 2 วิชา…") |

สรุปสองข้อ

1. **ลำดับ deploy = ข้อมูลก่อน แล้วค่อยโค้ด** — ช่วงคาบเกี่ยวจะเป็นแบบที่ถูกต้อง
   (ถ้าขึ้นโค้ดก่อน จะได้โค้ดใหม่ + ข้อมูลเก่า ซึ่งก็ถูกต้องเช่นกัน แต่ไม่ได้ประโยชน์ใด
   และทำให้มีสองสถานะให้ตรวจแทนหนึ่ง)
2. **ลำดับ rollback = ข้อมูลก่อน แล้วค่อยโค้ด** ด้วยเหตุผลเดียวกัน — ถ้าย้อนโค้ดก่อน
   ระบบจะผ่านสถานะ "โค้ดเก่า + ข้อมูลใหม่" ที่ผู้ใช้เห็นค่าดิบ

### 3.4 rollback.sh — อ้าง publication ID ของ release นี้โดยตรง

| ขั้น | ทำอะไร | ด่านที่ต้องผ่าน |
|---|---|---|
| 0 | อ่าน `PUBLICATION_AFTER` / `PUBLICATION_BEFORE` ที่ deploy.sh เขียนไว้ | ไฟล์ต้องมี · ค่าไม่ว่าง · สองค่าต้องไม่เท่ากัน · **publication ที่ระบบใช้อยู่ต้องเป็นของ release นี้** · publication เดิมต้องยังมีอยู่ |

| 3 | ย้อนโค้ดกลับ `counter-2569-10-16` | อิมเมจของคอนเทนเนอร์ต้องเป็นตัวเก่า · log มี `Application startup complete` |

  **คือชุดของ release นี้จริง** ถ้าไม่ใช่จะหยุดทันทีและไม่ลบอะไร
- ตัวย้อนที่เรียกใช้คือ `rollback_publish.sh` ตัวเดิมที่ใช้มาแล้วในรอบก่อน

### 5.1 คำเตือนจากตัวแยกข้ออ้าง

คำตอบของคำถามระดับกลุ่มยังมีบรรทัด "ยังยืนยันไม่ได้จากหน้าที่อ้าง" ติดมา โดยสิ่งที่
ค้างเป็นเศษประโยคที่ตัวแยกข้ออ้างตัดมาไม่ครบ ไม่ใช่ข้อเท็จจริงที่ผิด

| ข้อ | สิ่งที่ค้าง |
|---|---|
| ก | `ไม่น้อยกว่า 5 หน่วยกิต` |
| ข | `มีรายวิชาดังนี้` |
| ค | `มีเงื่อนไขว่าทั้งสองรายวิชาเลือก` · `มีวิชาบังคับก่อนคือ` |

เก็บเป็นงานแยกตามที่ตกลงไว้ **ไม่ได้ปิดข้อความเตือนเพื่อให้ดูผ่าน** — ชั้นเติมหน้าอ้างอิง
จะไม่ขึ้นคำเตือนเฉพาะเมื่อหาหน้าที่ยืนยันข้ออ้างได้จริงเท่านั้น

### 5.2 `verify_publish_content.py` ยังไม่รู้จักค่าที่สี่

จุดตรวจ `set(by_req) == {'required','elective','choose_group'}` จะตกหลัง release นี้
วัดจริงบนฐานทดสอบแล้ว: **15 จุดตรวจ ผ่าน 14 ตก 1** และข้อที่ตกคือข้อนี้ข้อเดียว

```
[ไม่ผ่าน] มีข้อกำหนดครบทั้งสามค่า — {'required_in_group': 1, 'elective': 44, 'choose_group': 2, 'required': 35}
```

รอบนี้**ไม่แก้ไฟล์นี้** ตามที่สั่งว่าไม่เพิ่มงานแก้อื่น — deploy.sh ขั้นที่ 5 จึงไม่ปิด
ข้อความเตือน แต่ยืนยันสามอย่าง: ตกข้อเดียว · ข้อที่ตกเป็นข้อนี้จริง · ข้ออื่นผ่านหมด
ถ้าตกเพิ่มหรือตกข้ออื่นจะหยุดการ deploy ทันที
(ไฟล์นี้เป็นเครื่องมือฝั่ง pipeline ไม่ได้อยู่ในอิมเมจและไม่กระทบคำตอบที่ผู้ใช้เห็น)

**ตรวจรับ** แต่ยังไม่ถูกเผยแพร่เป็นค่าใน `mko.published_values`
คำถามระดับกลุ่มยังตอบ 7 ได้เพราะอ่านจากหน้าเอกสารตรง ๆ จึงไม่กระทบเกณฑ์ใน §4
การเก็บตัวเลขขั้นต่ำของกลุ่มลงข้อมูลที่ตรวจรับเป็นงานแยก
