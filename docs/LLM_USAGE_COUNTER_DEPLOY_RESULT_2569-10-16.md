## 4. ข้อสังเกตที่พบระหว่าง deploy

### 4.1 ความล้มเหลวของเจ้าหลักที่ไม่ใช่โควตา ไม่ถูกนับเป็นเหตุการณ์ฝั่ง Gemini

เห็นจากของจริงในข้อ 3.1: Gemini ล้มด้วย `ReadTimeout` สามครั้ง แต่ในตารางตัวนับ
**ไม่มีแถว `gemini_*` สำหรับเหตุการณ์นั้นเลย** มีแต่ `fallback_local_attempt/failed`

เป็นไปตามที่โค้ดเขียนไว้ — `gemini_all_failed` ถูกนับเฉพาะเส้นทางที่วนครบทุกโมเดล
จากการชนโควตา ส่วน `LLMConnectionError` จากการหมดเวลาจะทะลุออกจากลูปทันที

**ผลกระทบ: ไม่มีต่อตัวหาร** เพราะการเรียกครั้งนั้นถูกนับที่ `fallback_local_attempt`
อยู่แล้ว ไม่ขาดไม่เกิน · แต่ **ทำให้แยกไม่ออกว่าเจ้าหลักล้มเพราะหมดเวลาหรือเพราะโควตา**
ถ้าต้องการแยก ต้องเพิ่มเหตุการณ์ `gemini_timeout:<ชื่อ>` ในรอบหน้า — **ยังไม่ได้ทำ**

### 4.2 คำขอที่รูปแบบผิดได้ 500 แทน 4xx (ของเดิม ไม่ใช่ของรอบนี้)

ระหว่างทดสอบ ผมส่ง `/api/recommend-major` ด้วยคีย์ผิด (`interest` แทน `interests`)
ได้ HTTP 500 จาก `ValueError` ใน `program_match.py:468` แทนที่จะเป็น 400/422

ตรวจแล้วว่า **เป็นพฤติกรรมเดิมของโค้ดที่ไม่ได้แก้ในรอบนี้** (ไฟล์ `program_match.py`
ไม่อยู่ใน 4 ไฟล์ที่ขึ้น) และเมื่อส่งรูปแบบที่ถูกต้องก็ได้ 200 ตามปกติ
บันทึกไว้เป็นงานแยก ไม่ได้แก้ในรอบนี้

### 4.3 คำถามแรกช้าเพราะโมเดลในเครื่องยังไม่ถูกโหลด ไม่ใช่เพราะ Ollama restart

**รายงานฉบับแรกเขียนว่า "โมเดลในเครื่องเพิ่งถูก restart จึงยังไม่อุ่น" ซึ่งผิด**
ตรวจย้อนหลังแล้วพบว่า

| หลักฐาน | ค่า |
|---|---|
| `course-advisor-system-ollama-1` StartedAt | **2026-08-18T14:17:25Z** · `RestartCount=0` |
| `course-advisor-system-backend-1` StartedAt | 2026-10-16T10:24:02Z |

คอนเทนเนอร์ Ollama **ทำงานต่อเนื่องมาเกือบสองเดือนและไม่เคย restart เลย**
ตัวที่ถูกสร้างใหม่ในรอบ deploy นี้คือ backend เท่านั้น ข้อความเดิมจึงไม่ถูกต้อง

สาเหตุจริงอ่านได้จาก log ของ Ollama ช่วงเวลาเดียวกัน

```
srv    load_model: loading model '/root/.ollama/models/blobs/sha256-5ee4f07c…'
cmn  common_init_: fitting params to device memory ...
10:25:05.972Z level=WARN msg="client connection closed before llama-server finished loading, aborting load"
10:25:05.972Z level=INFO msg="Load failed" … error="timed out"
[GIN] 2026/10/16 - 10:25:05 | 499 | 448.221855ms | 172.18.0.4 | POST "/api/chat"
```

คือ **โมเดลเขียนคำตอบในเครื่องไม่ได้ถูกโหลดค้างไว้ในหน่วยความจำ** พอถูกเรียกจึงต้อง
โหลดจากดิสก์ก่อน และเพดานเวลาของคำขอหมดระหว่างกำลังโหลด ฝั่ง backend จึงตัดการ
เชื่อมต่อ (Ollama บันทึกเป็น HTTP 499 และ `aborting load`)

เหตุที่มันไม่ถูกโหลดค้างไว้เป็นเรื่องที่ออกแบบไว้แล้ว ไม่ใช่ความผิดพลาด —
`_keep_models_warm()` ใน `app/main.py` อุ่น **เฉพาะโมเดล embedding** และจะอุ่นโมเดล
เขียนคำตอบต่อเมื่อ `LLM_PROVIDER != "gemini"` เท่านั้น เพราะถ้าอุ่นทุก 20 นาทีตอนใช้
Gemini ก็เป็นการกินโควตาเปล่า ๆ

ยืนยันจากสถานะปัจจุบันของ Ollama: `ollama ps` แสดงเฉพาะ `bge-m3:latest` ที่ถูกโหลด
ค้างไว้ (`OLLAMA_KEEP_ALIVE=60m`) ไม่มีโมเดลเขียนคำตอบอยู่ในรายการ

**ผลที่ตามมา** ตราบใดที่ผู้ให้บริการหลักเป็น Gemini โมเดลสำรองในเครื่องจะ "เย็น" เสมอ
การตกมาใช้มันจึงมีค่าโหลดโมเดลบวกเข้าไปทุกครั้ง ซึ่งเป็นเหตุผลหนึ่งที่ทำให้
`fallback_local_failed` เกิดขึ้นได้แม้ตัวโมเดลเองไม่มีปัญหา
(เรื่องนี้เป็นข้อมูลตั้งต้นของการพิจารณาผู้ให้บริการสำรองบนคลาวด์)
