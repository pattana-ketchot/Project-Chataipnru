## 1. ระดับความเชื่อถือของข้อมูลในเอกสารนี้

เอกสารนี้**ไม่รับรองว่าระบบ production ถูกต้อง** รับรองเพียงว่า *ได้อ่านอะไรมา และอ่านเมื่อไร*
แบ่งเป็นสามระดับ ใช้สัญลักษณ์กำกับตลอดเอกสาร

| สัญลักษณ์ | ความหมาย | ตรวจอย่างไร |
|---|---|---|
| **[ไฟล์]** | ยืนยันได้จากไฟล์ในโปรเจกต์ | อ่านซอร์สโค้ด ไฟล์ compose ไฟล์ตั้งค่า |
| **[prod]** | ยืนยันจากเครื่อง production เมื่อ 25 ต.ค. 2569 | `docker ps` · `docker exec … env` · `SELECT` บนฐานข้อมูล |
| **[รอยืนยัน]** | ยังไม่ได้ตรวจ หรือตรวจไม่ได้ | ระบุเหตุผลไว้ทุกข้อในหัวข้อ 6 |

ข้อควรระวังสองข้อ

1. **[ไฟล์] ไม่ได้แปลว่าตรงกับ production** — working tree มีงานที่ยังไม่ deploy อยู่
   สิ่งที่ไดอะแกรมอธิบายคือ **อิมเมจที่รันอยู่จริง** (`counter-2569-10-16`) ซึ่งอ่านซอร์สออกมา
   จากในอิมเมจโดยตรง ไม่ได้อ่านจาก working tree
2. **[prod] เป็นภาพ ณ เวลาที่ตรวจ** ตัวเลขแถวและสถานะคอนเทนเนอร์เปลี่ยนได้ตลอด

## 3. ไดอะแกรมทั้งหมด — 18 ภาพ

ต้นฉบับเป็น **PlantUML (`.puml`)** ทุกภาพ พร้อม `.svg` และ `.png` ที่ render แล้ว
ทุกภาพเป็น **ขาวดำ กล่องพื้นขาวขอบดำ เส้นเชื่อมมุมฉาก**

**ชื่อภาพไม่ได้ฝังอยู่ในรูป** ให้ใส่เป็นคำบรรยายใต้รูปในรายงานตามรูปแบบ "ภาพที่ N ..."
ซึ่งเป็นวิธีที่รายงานวิชาการใช้ และทำให้เลขภาพตรงกับสารบัญรูปโดยไม่ต้องแก้ไฟล์ภาพ

> **ใช้ `.svg` ในรายงาน** ซูมแล้วตัวอักษรไม่แตก และไม่ติดเพดาน 4,096 px ที่ทำให้ `.png`

### 3.1 สถาปัตยกรรมระบบ

**ภาพที่ 1** `architecture` — คอนเทนเนอร์ทั้ง 7 ตัว ลำดับการจัดเส้นทางของ Caddy ทั้ง 6 ลำดับ
ที่เก็บข้อมูลถาวร และบริการภายนอก กล่อง**ขอบเส้นประ**คือส่วนที่ยังรันอยู่แต่หน้าเว็บรุ่นที่
deploy ไม่ได้เรียกใช้ (webapi, frontend, db-viewer, Supabase) และตัวนำเข้าที่ไม่ได้รันอยู่

คำอธิบายใต้ภาพที่ควรใส่ในรายงาน

- Caddy เป็นตัวเดียวที่เปิดพอร์ต 80/443 คอนเทนเนอร์อื่นเปิดพอร์ตเฉพาะในเครือข่ายภายใน

- ลำดับของ Caddy มีความหมาย เลือกบล็อกแรกที่ตรงกับเส้นทาง ถ้าสลับลำดับ `/api/admin/*`
  จะถูก `/api/*` กลืนไปหา backend แล้วได้ 404

### 3.3 แผนภาพความสัมพันธ์ของข้อมูล (ERD) — 5 ภาพ

| ภาพ | ไฟล์ | ขอบเขต |
|---|---|---|
| 7 | `er` | schema `public` — บัญชีผู้ใช้ บทสนทนา ผลแนะนำ (9 ตาราง) |
| 8 | `er-docs` | schema `public` — เอกสาร คลังเวกเตอร์ แคช สถิติ (5 ตาราง) |
| 9 | `er-web` | schema `web` (6 ตาราง) และ FK ที่ชี้ไป `public` |
| 10 | `er-mko` | schema `mko` |
| 11 | `er-supabase` | ฝั่ง Supabase — **คนละฐาน** |

**การอ่าน cardinality** **[prod]** — ตรวจจาก `pg_attribute` ว่าคอลัมน์ FK ตัวใด `NOT NULL`

| สัญลักษณ์ | หมายถึง |
|---|---|
| `\|\|--o{` | FK เป็น `NOT NULL` → ลูกต้องมีแม่เสมอ |
| `\|o--o{` | FK เป็น null ได้ (`ON DELETE SET NULL` หรือ `NO ACTION`) → ลูกอาจไม่มีแม่ |
| `\|\|--o\|` | FK เป็น primary key ของลูกด้วย → หนึ่งแม่มีลูกได้ไม่เกินหนึ่ง |

**ข้อที่แก้จากฉบับก่อน**

1. ฉบับก่อนเขียนว่า schema `web` ไม่มี Foreign Key เลย — **ผิด** มี **8 ข้อ** และภาพ
   `er-web` วาดไว้**ครบทั้ง 8 ข้อ**
2. ฉบับก่อนวาดความสัมพันธ์ `public` ↔ `mko` เป็นเส้นประว่า "อ้างด้วย course_id" —
   ของจริงเป็น Foreign Key จริง
3. ฉบับก่อน `er-mko` อ้างว่า "มี FK 52 ข้อ" ทั้งที่วาดไม่ครบ — ภาพ `er-mko` เป็น
   **ภาพสรุป** ไม่ได้วาด FK ทุกข้อ และระบุไว้ในภาพแล้ว

**ข้อควรระวังที่พบ** `web.site_courses.course_id` **มี FK จริงแต่เก็บค่า `NULL` ทั้ง 12 แถว**
หน้าเว็บจึงยังจับคู่ชื่อสาขาด้วยโค้ด — "มี FK" กับ "ใช้ FK" เป็นคนละเรื่อง **[prod]**

**ข้อที่แก้จากฉบับก่อน**

   ทางหนึ่ง — ของจริงคือ **ด่านเรียงกัน** ด่านที่ตอบไม่ได้ไหลลงด่านถัดไป
   โดยเฉพาะกรณี**ไม่พบในแคชต้องไหลต่อจริง** รอบนี้ใช้ `group` ซ้อนตามลำดับจริง
2. `sequence-ai-chat` แยก **header `X-Source-*`** ออกจาก **รายการที่มาท้ายคำตอบ** แล้ว
   สองอย่างนี้เป็นคนละชุด: header เป็นเอกสาร**ฉบับเดียว**ที่ใช้ทำปุ่มเปิดไฟล์ รู้ก่อนเริ่มสตรีม
   และ **ว่างสำหรับคำตอบสาย RAG** ส่วนรายการที่มาจริงคัด**หลัง**รู้ข้อความคำตอบทั้งหมด
3. `sequence-doc-ingest` เปลี่ยนกรณีสัญญา embedding ไม่ตรง และ sha256 ไม่ตรง จาก `alt`
   เป็น **`break`** ซึ่งเป็นสัญลักษณ์ UML ที่หมายถึงออกจากลำดับทันที — ของจริงหยุดทั้งงาน

**ขั้นที่เติมเข้ามาในรอบนี้** — ฉบับก่อนตกไปสองขั้น

- **D2 เรียบเรียงคำถามใหม่แล้วค้นซ้ำ** เมื่อมีประวัติบทสนทนาหรือคำถามเป็นภาษาอังกฤษ
  (ด่าน 2 และ 2.5 — เรียกโมเดลหนึ่งครั้ง)
- **G2 เก็บผลกลับ** บันทึกบทสนทนา เก็บแคชเมื่อไม่มีประวัติ และนับสถิติการเรียกโมเดล
- ขั้น G ขยายให้เห็นว่ามี **ชั้นที่สอง** (ตรวจข้ออ้างกับข้อความทั้งหน้า) และ
  **ชั้นที่สาม** (ตัดหน้าที่ไม่รองรับข้ออ้างใดเลย)

## 8. คำอธิบายสั้นสำหรับตอบคำถามอาจารย์

**ระบบนี้ใช้ AI ตอบทุกคำถามเลยไหม**
ไม่ใช่ คำถามผ่านด่านเรียงกัน ด่านแรก ๆ ตอบจากข้อมูลหลักสูตรที่สกัดจาก มคอ.2 และผ่าน
การตรวจรับแล้ว ตามด้วยด่านแคช คำถามที่ตอบได้จากสองด่านนี้ไม่เรียกโมเดลเลย

**ทำไมต้องมีทั้ง Gemini และ Ollama**
Ollama ทำ embedding เสมอเพราะต้องใช้โมเดลเดียวกับที่สร้างคลัง (bge-m3, 1024 มิติ)
ถ้าเปลี่ยนต้องคำนวณคลังทั้ง 9,039 ชิ้นใหม่ ส่วน Gemini เขียนคำตอบเพราะเครื่องนี้ไม่มีการ์ดจอ

**ระบบรู้ได้ยังไงว่าคำตอบมาจากหน้าไหน**
เวกเตอร์แต่ละชิ้นเก็บเลขหน้าไว้ตั้งแต่ตอนนำเข้า และหลังโมเดลเขียนคำตอบ ยังมีขั้นตรวจว่า
หน้าที่จะอ้างรองรับข้ออ้างในคำตอบจริงหรือไม่ หน้าที่ไม่รองรับถูกตัดออก ข้ออ้างที่หาหน้า
รองรับไม่ได้จะถูกแจ้งให้ผู้ใช้เห็น ไม่ถูกซ่อน

**ข้อมูลหลักสูตรเข้าระบบได้เองโดยอัตโนมัติไหม**
ไม่ได้ ต้องมีคนอนุมัติไฟล์ก่อน แล้วต้องมีคนสั่งรันตัวนำเข้าอีกครั้ง ก่อนเริ่มงานยังตรวจว่า
โมเดล embedding ตรงกับที่ใช้สร้างคลัง และเทียบ sha256 ของไฟล์กับค่าที่บันทึกตอนอนุมัติ

**การซ่อนปุ่มลบบนหน้าเว็บถือเป็นระบบรักษาความปลอดภัยไหม**
ไม่ถือ ด่านจริงอยู่ที่ backend และทำงานทุกคำขอ ยิงตรงไปที่ API ก็ยังติด `require_admin_role`

**ใช้ Supabase อยู่ไหม**
ไม่ใช้ในเส้นทางหลักแล้ว ตรวจยืนยันได้ว่าคอนเทนเนอร์ `backend` ไม่มีค่าตั้งของ Supabase
เลยแม้ตัวเดียว ที่ยังเหลือคือคอนเทนเนอร์ `webapi` ที่หน้าเว็บรุ่นที่ใช้งานอยู่ไม่เรียกใช้

**ฐานข้อมูลมีกี่ฐาน**
ฐานของระบบคือ PostgreSQL 16 + pgvector ชื่อ `course_advisor` แบ่งเป็น 3 schema
(42 ตาราง 10 วิว) ส่วน Supabase เป็นอีกฐานที่แยกกันเด็ดขาด ไม่มี FK เชื่อมกัน

## 10. วิธีแก้ไขและสร้างภาพใหม่

### แก้โครงผัง → PlantText

<https://www.planttext.com> — วางเนื้อไฟล์ `.puml` ทั้งไฟล์ลงช่องซ้าย

> **พรีวิวในหน้านี้ภาษาไทยจะเพี้ยน** สระบนล่างและวรรณยุกต์กลายเป็นกล่อง เพราะเครื่อง
> ของ PlantText ไม่มีฟอนต์ไทย ใช้ดูได้แค่โครงผังและไวยากรณ์
> **อย่า export ภาพจากหน้านี้** และการตั้ง `skinparam defaultFontName` ก็ไม่ช่วย
> เพราะเครื่องนั้นไม่มีฟอนต์นั้นอยู่

เมื่อแก้เสร็จ copy โค้ดกลับมาบันทึกทับไฟล์ `.puml` เดิม — PlantText ไม่ได้ผูกกับไฟล์ในเครื่อง

### สร้างภาพจริง → kroki.io

วางเนื้อไฟล์ที่ <https://kroki.io> เลือกชนิด PlantUML แล้วดาวน์โหลด SVG
หรือใช้คำสั่งในเครื่อง

```bash
curl -X POST -H "Content-Type: text/plain" --data-binary @ชื่อไฟล์.puml \
     -o ชื่อไฟล์.svg https://kroki.io/plantuml/svg
```

สร้างใหม่ทุกไฟล์ในครั้งเดียว: `bash render.sh`

### Lucid

**Lucid ไม่รองรับ PlantUML** รองรับ Mermaid 8 ชนิด และการอัปโหลด `.svg` เข้าไปจะได้
**รูปในคลังรูปทรง ไม่ใช่ไดอะแกรมที่แก้กล่องและเส้นได้** ถ้าจะใช้ Lucid ต้องแปลงเป็น
Mermaid ก่อน ซึ่งจะเสีย `legend`, `note`, สัญลักษณ์ DFD ที่แยก process กับ data store
และรายละเอียดใน ERD
