| `cron.job_run_details` | 1,793 | **มี** | เมื่อมี extension `pg_cron` |
| `public.rag_documents` | 12 | **มี** | **กู้ได้แล้วจริงในรอบที่ 2** (ต้องมี `vector`) |

### `vault.secrets` — มีในไฟล์สำรอง แต่อ่านค่าไม่ได้ตลอดไป

Supabase Vault เก็บค่าที่เข้ารหัสไว้ในตาราง แต่ **กุญแจหลักอยู่ในระบบของ Supabase ไม่ได้อยู่ในฐานข้อมูล**
`pg_dump` จึงได้มาแต่ ciphertext · เมื่อลบโปรเจกต์แล้ว **ค่าทั้ง 3 จะถอดกลับไม่ได้อีก**

สามค่านั้นคือคีย์ของโปรเจกต์ Supabase เอง (`project_url`, `anon_key`, `cron_secret` จากงาน C2)
**ฝั่งเราไม่ได้ใช้ค่าเหล่านี้แล้ว** จึงยอมรับได้ — แต่ต้องรู้ว่าเป็นทางเดียว ย้อนกลับไม่ได้

### 5.1 ไฟล์สำรองไม่มีสิทธิ์และไม่มี role — ช่องที่ยังไม่ได้อุด

ตรวจโดยแปลงไฟล์สำรองเป็น SQL ข้อความแล้วนับบรรทัด

| สิ่งที่ค้น | พบ | ความหมาย |
|---|---|---|
| `ALTER … OWNER TO` | **135 บรรทัด** | **เจ้าของ object ถูกเก็บไว้ครบ** |
| `CREATE POLICY` | 33 | RLS policy ถูกเก็บ |
| `GRANT` | **0 บรรทัด** | **สิทธิ์ระดับตารางของ `anon` / `authenticated` / `service_role` ไม่ถูกเก็บ** |
| `REVOKE` | **0 บรรทัด** | เหมือนกัน |
| `ALTER DEFAULT PRIVILEGES` | **0 บรรทัด** | เหมือนกัน |
| `CREATE ROLE` | **0 บรรทัด** | **role ไม่ถูกเก็บ** — `pg_dump` ไม่เคยเก็บ ต้องใช้ `pg_dumpall --globals-only` |

สาเหตุของสามแถวที่เป็น 0: ตอน dump ใช้ `--no-privileges`

**ผลที่ตามมาจริง:** ถ้าวันหนึ่งต้อง restore กลับขึ้นโปรเจกต์ Supabase ใหม่
**จะต้องสร้าง role และให้ `GRANT` เองทั้งหมด** ไม่งั้น PostgREST เข้าถึงตารางไม่ได้ทั้งที่ข้อมูลอยู่ครบ

วิธีอุด เตรียมไว้เป็น **ขั้น G0.9** ใน `PHASE4_REMOVAL_PLAN_2569-10-12.md`
ทำตอนกรอก credentials รอบหน้า: `pg_dump` อีกชุดโดยไม่ใส่ `--no-privileges`
และ `pg_dumpall --globals-only --no-role-passwords`

## 8. สิ่งที่ยังไม่ได้ทำตามที่คุณสั่ง

- **ไม่ปิด cron เก่า** — job 2 ที่ต้นทางยัง `active=true`
- **ไม่หยุด webapi** — `course-advisor-system-webapi-1` ยัง Up (healthy)
- **ไม่ลบโปรเจกต์ Supabase** และไม่ลบข้อมูลใดที่ต้นทาง
- **ไม่แก้อะไรที่ต้นทาง** — การเชื่อมต่อทั้งหมดเป็น `select` และ `pg_dump` อย่างเดียว
- credentials ที่ใช้ในขั้นนี้ **ลบออกจากเซิร์ฟเวอร์แล้ว**
