## 4. วัด Ollama บนเซิร์ฟเวอร์: ทำแยกไม่ได้ จึงไม่วัดซ้ำ

### 4.1 ทำไมถึงไม่รันการวัดบนเซิร์ฟเวอร์

| | สภาพจริง |
|---|---|
| Ollama บนเซิร์ฟเวอร์ | มี **ตัวเดียว** (`course-advisor-system-ollama-1`) ที่ production ใช้ทำ embedding ทุกคำถาม |
| CPU | 8 core ใช้ร่วมกันทั้งเครื่อง · ไม่มีการ์ดจอ |
| ตั้งคอนเทนเนอร์ Ollama ตัวที่สอง | **ไม่ได้แยกทรัพยากรจริง** เพราะยังแย่ง CPU ชุดเดียวกัน งานที่กิน CPU หลายนาทีจะทำให้ embedding ของผู้ใช้จริงช้าลงอยู่ดี |

ตามเงื่อนไขที่ได้รับ ("ห้ามทดสอบหนักกับ Ollama ที่ production ใช้ร่วมกัน · ถ้าไม่มี
ทรัพยากรทดสอบแยก ให้แจ้งและหยุด") จึง **หยุด ไม่ฝืนวัด**

### 4.2 แต่ตัวเลขที่ต้องการมีอยู่แล้ว

วัดบนเซิร์ฟเวอร์เครื่องนี้เองเมื่อ 28 ต.ค. 2569 **โดยคงด่านตรวจหลักฐานไว้** และเปิด
เพดานเวลากว้างถึง 300 วินาที (ที่มา: `MODEL_SWITCH_2569-10-28.md` ข้อ 6.5)

| คำถาม | เวลา | ผล | ที่มาที่อ้างได้ |
|---|---|---|---|
| หลักสูตรวิทยาการคอมพิวเตอร์เรียนเกี่ยวกับอะไร | **233.1 วินาที** | `not_found` — ด่านตรวจของโมเดลในเครื่องตัดสินว่าตอบไม่ได้ | ไม่มี (ไม่ถึงขั้นเขียนคำตอบ) |
| หลักสูตรวิทยาการคอมพิวเตอร์มีวิชาอะไรบ้าง | **248.9 วินาที** | `not_found` | ไม่มี |
| คุณสมบัติผู้สมัครของหลักสูตรวิทยาการคอมพิวเตอร์ | 0.0 วินาที | `answered` แต่ `answer_model = null` — ตอบจากฐานหลักสูตร **ไม่ได้เรียกโมเดลเลย** | จากฐานข้อมูล |

**อ่านผล**: Gemini ตอบสองข้อแรกได้จากเนื้อหาชุดเดียวกัน แต่โมเดลในเครื่องตัดสินว่า
หลักฐานไม่พอ · นักศึกษาที่กดเลือก "ประมวลผลในเครื่อง" จะ **รอราว 4 นาทีแล้วได้
"ไม่พบข้อมูลนี้ในเอกสารหลักสูตร"** ซึ่งแย่กว่าไม่มีปุ่มให้กด

ข้อที่สามเป็นตัวอย่างของกับดักการวัด: ถ้าวัดด้วย "ตอบได้หรือไม่" อย่างเดียวจะสรุปว่า
Ollama ใช้งานได้ ทั้งที่ Ollama ไม่ได้เกี่ยวข้องกับคำตอบนั้นเลย — ต้องดู `answer_model`
ประกอบเสมอ

## 5. ข้อเสนอเดิม — **ทำแล้ว** (ดูข้อ 7)

ให้ตัวเลือก "ประมวลผลในเครื่อง" โผล่เฉพาะเมื่อเปิดสวิตช์ environment
(เช่น `PUBLIC_LOCAL_CHOICE=1`) โดย**ค่าตั้งต้นคือปิด**

* นักศึกษาเห็นสองตัวเลือกที่ใช้งานได้จริงทั้งคู่
* ผู้ดูแลยังสลับทั้งระบบไปใช้ Ollama ได้จากหน้าแอดมินเหมือนเดิม (ไม่กระทบของเดิม)
* วันที่ได้เครื่องที่มีการ์ดจอ แค่เปิดสวิตช์ ไม่ต้องแก้โค้ดหรือ build ใหม่
* โค้ดที่ทำไว้ทั้งหมดไม่เสียเปล่า และยังตอบอาจารย์ได้ว่า "รองรับแล้ว วัดแล้ว
  เลือกไม่เปิดใช้เพราะฮาร์ดแวร์ ไม่ใช่เพราะทำไม่ได้"

แก้ใช้เวลาไม่ถึง 10 นาที ทดสอบในเครื่องได้ทั้งหมด

## 7. สวิตช์ `PUBLIC_LOCAL_CHOICE` — ทำแล้ว ค่าตั้งต้นคือปิด

commit `8add55b` · แก้ `backend/app/services/ai_settings.py` ไฟล์เดียว (+19 บรรทัด)

```diff
+def public_local_enabled() -> bool:
+    """อ่านทุกครั้งที่ใช้ ไม่ cache — จะได้สลับค่าในชุดทดสอบได้โดยไม่ต้อง import ใหม่"""
+    return (os.getenv("PUBLIC_LOCAL_CHOICE", "") or "").strip().lower() in ("1", "true", "yes", "on")

 def public_choices() -> list[dict]:
     for c in PUBLIC_CHOICES:
         if c["provider"] == "gemini" and not has_gemini_key():
             continue
+        # ปิดอยู่ = ไม่อยู่ในรายการ และ public_choice() ก็ปฏิเสธ id นี้ไปด้วย
+        # เพราะมันตรวจกับรายการเดียวกันนี้ คำขอที่ยิง model_choice=local ตรง ๆ จึงไม่ได้ผล
+        if c["provider"] == "ollama" and not public_local_enabled():
+            continue
```

**ปิดสองชั้นด้วยการแก้จุดเดียว** — `public_choice()` (ตัวแปลง id ที่คำขอส่งมา) ตรวจกับ
รายการที่ `public_choices()` คืนอยู่แล้ว การซ่อนจากรายการจึงปิดการรับคำขอตรงไปพร้อมกัน
ไม่ใช่ซ่อนที่หน้าเว็บแล้วยังรับคำขอที่ยิงตรงอยู่

**ไม่กระทบสวิตช์ของผู้ดูแล** — `PROVIDERS` และ `resolve()` ไม่ถูกแตะ ผู้ดูแลยังเลือก
`ollama` ให้ทั้งระบบได้จากหน้าหลังบ้านเหมือนเดิม

### 8.1 รุ่นที่ตอบจริงของ `fast` และ `detailed`

**(ก) ตัวเลือกสองตัวถือคนละ connector จริง** (ถามจากในคอนเทนเนอร์)

```

fast     | choice.key = ('gemini', 'gemini-3.5-flash-lite') | chat_model = gemini-3.5-flash-lite | answer_model = gemini:gemini-3.5-flash-lite
detailed | choice.key = ('gemini', 'gemini-3.5-flash')      | chat_model = gemini-3.5-flash      | answer_model = gemini:gemini-3.5-flash
```

**(ข) คำถามเดียวกัน สองตัวเลือก ได้คนละคำตอบ** — `POST /chat-web`
คำถาม: *หลักสูตรเทคโนโลยีสารสนเทศมีโครงสร้างหน่วยกิตอย่างไรบ้าง*

| `model_choice` | HTTP | เวลา | ขนาด | ที่มาที่อ้าง |
|---|---|---|---|---|
| `fast` | 200 | **6.2 วินาที** | 452 ไบต์ | `it66.pdf หน้า 19` |
| `detailed` | 200 | **14.4 วินาที** | 582 ไบต์ | `it66_brief.pdf หน้า 1; it66.pdf หน้า 19; it61.pdf หน้า 21` — ครอบคลุมทั้งฉบับ 2566 และ 2561 |

**(ค) เซิร์ฟเวอร์บันทึกชื่อรุ่นที่เขียนคำตอบเอง** — `corpus_version` ของแถวแคชที่เขียน
หลังตอบเสร็จ มีชื่อรุ่นต่อท้าย (ขึ้นต้นด้วย `m`) คำนวณจาก connector ของคำขอนั้นเอง

```
2026-10-29 01:06:23 | ...k25/v34/mgemini:gemini-3.5-flash-lite   <- คำขอ model_choice="fast"
2026-10-29 01:05:30 | ...k25/v34/mgemini:gemini-3.5-flash        <- คำขอ model_choice="detailed"
```

### 8.2 ข้อพิสูจน์ว่า `fast` มาจากตัวเลือกของผู้ใช้ ไม่ใช่บังเอิญตรงกับค่าตั้งต้น

หลักฐานชุดแรกยังไม่พอ เพราะ `fast` ชี้ไปที่รุ่นเดียวกับค่าตั้งต้นของ env จึงใช้
connector ที่แคชไว้แล้วและไม่พิมพ์ log ใหม่ — แยกไม่ออกว่าตัวเลือกมีผล หรือบังเอิญเหมือนกัน

จึงตั้งค่าของผู้ดูแล **ในฐานทดสอบ** ให้เป็นคนละเจ้าชั่วคราว แล้วยิง `fast` เข้าไป

```
ค่าที่ผู้ดูแลตั้ง (ฐานทดสอบ): ollama / qwen2.5:3b · ที่มา: db
ขอ fast ขณะที่ผู้ดูแลตั้งเป็น ollama: HTTP 200 · 2.8 วินาที
log: ใช้โมเดลเขียนคำตอบ: gemini / gemini-3.5-flash-lite (ที่มา: user)
```

ค่าตั้งต้นของเครื่องนั้นเป็น `ollama` แต่คำขอได้ `gemini-3.5-flash-lite` และตอบใน
2.8 วินาที (โมเดลในเครื่องบนเซิร์ฟเวอร์นี้ใช้เวลาหลักนาที) · `(ที่มา: user)` เกิดได้
ทางเดียวคือผ่าน `public_choice()` ซึ่งเรียกจาก `model_choice` ของคำขอเท่านั้น

คืนค่าแถวฐานทดสอบกลับเป็น `provider=NULL, model=gemini-3.1-flash-lite` แล้ว ·
แถวของฐานจริงไม่ถูกแตะ (`1|NULL|gemini-3.1-flash-lite`)

### 8.3 ปิดแล้วยิงคำขอตรงก็เรียก Ollama ไม่ได้

| ตรวจ | ผล |
|---|---|
| `model_choice="local"` คำถามที่เคยถาม | HTTP 200 · 0.0 วินาที — ได้คำตอบจากแคช ไม่แตะโมเดลเลย |
| `model_choice="local"` **คำถามใหม่ไม่ติดแคช** | HTTP 200 · **3.4 วินาที** · `write_answer=1478ms` — เป็นความเร็วของ Gemini ไม่ใช่ของโมเดลในเครื่องที่ต้องใช้หลักนาที |
| log ที่เอ่ยถึง ollama ตลอดการทดสอบ | **5 บรรทัด และเป็น `POST /api/embeddings` ทั้งหมด** — คือขั้นค้นเอกสารตามปกติ · **ไม่มี `/api/chat` ไปที่ ollama แม้แต่ครั้งเดียว** |

**หน้าแชทเดิมยังใช้ได้** — คำขอที่ไม่ส่ง `model_choice` (แบบที่หน้าเว็บรุ่นปัจจุบันส่ง)
ตอบได้ปกติใน 3.1 วินาที ใช้ค่าที่ผู้ดูแลตั้งไว้เหมือนเดิม

### 8.4 กับดักที่เจอระหว่างเก็บหลักฐาน

* **build ผิดพาธ** — รอบแรกคัดไฟล์ไป `/app/app/...` แทน `/app/backend/app/...`
  คอนเทนเนอร์จึงรันโค้ดเดิมของ production และเมิน `model_choice` เงียบ ๆ สองคำขอได้
  คำตอบเดียวกันเพราะตัวที่สองไปโดนแคชของตัวแรก · ผลรอบนั้นถูกทิ้ง และรอบที่ใช้จริง
  เทียบ connector ก่อนเริ่มยิงทุกครั้ง
* **คำถามที่ตอบจากฐานข้อมูลตรง ๆ ใช้วัดไม่ได้** — เช่น "เตรียมนักศึกษาให้ทำงานด้านใดได้บ้าง"
  ซึ่งประกอบจากรายการอาชีพในฐาน คืนคำตอบเดียวกันใน 0.0 วินาทีทั้งสองตัวเลือกเพราะไม่เรียก
  โมเดลเลย · ตัวเลือกของผู้ใช้จึงไม่มีผลกับคำถามกลุ่มนี้ ซึ่งถูกต้องตามการออกแบบเดิม
  แต่ผู้ใช้จะเห็นว่า "เลือกแล้วไม่ต่าง" — ควรบอกอาจารย์ไว้
