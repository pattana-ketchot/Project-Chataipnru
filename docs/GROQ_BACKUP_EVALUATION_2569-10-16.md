## 1. ชื่อโมเดลและโควตา — ตรวจจากเอกสารของผู้ให้บริการ ไม่ได้ยึดจากบทสนทนา

### 1.1 โมเดล Qwen ที่เปิดให้ใช้บน Groq วันนี้

**เป็น Qwen ตัวเดียวที่เหลืออยู่ในรายการ** ส่วนรุ่นที่ใช้ชื่อว่า Qwen อื่น ๆ ถูกปลดระวางไปหมดแล้ว

### 1.2 โมเดลสถานะ production ของ Groq (ถ้าเปลี่ยนใจไปใช้ตัวที่เขารับประกัน)

### 1.3 ประวัติการปลดระวาง Qwen บน Groq — เหตุผลหลักที่ยังไม่แนะนำ

จากหน้า `console.groq.com/docs/deprecations`

| `qwen-qwq-32b` | 14/07/2025 | `qwen/qwen3-32b` |
| `qwen/qwen3-32b` | 17/07/2026 | `openai/gpt-oss-120b` |
| `qwen/qwen3.6-27b` | **14/09/2026** | `qwen/qwen3.8-27b` |

**ตัวที่เหลืออยู่ตอนนี้ (`qwen3.8-27b`) เพิ่งมาแทนตัวที่ถูกปิดไปเมื่อเดือนที่แล้ว**
และเอกสารของ Groq เขียนถึงโมเดล preview ไว้ตรง ๆ ว่า

> โมเดล preview มีไว้สำหรับประเมินผลเท่านั้น **ไม่ควรใช้ในสภาพแวดล้อม production**
> และ **อาจถูกยกเลิกโดยแจ้งล่วงหน้าไม่นาน**

ส่วนโมเดล production เขาระบุว่าจะมีเส้นทางย้ายและตัวแทนที่ชัดเจนให้

> นี่คือสิ่งที่รายงานรอบก่อนบอกว่าต้องตรวจก่อนตัดสินใจ และผลการตรวจคือ
> **เงื่อนไขของผู้ให้บริการไม่รองรับการเอา preview มาเป็นสำรองของระบบที่ให้บริการจริง**

### 1.4 โควตาของบัญชีปัจจุบัน — **ยังยืนยันไม่ได้**

* ระบบ **ไม่มีบัญชี Groq และไม่มีคีย์** ตรวจแล้วทั้งใน `.env` ของเซิร์ฟเวอร์และใน
  ตัวแปรสภาพแวดล้อมของคอนเทนเนอร์ backend — ไม่มีตัวแปรใดขึ้นต้นด้วย `GROQ`
* หน้าเอกสาร rate-limits ของ Groq **ไม่ได้ระบุเพดานของชั้นใช้งานฟรีเป็นตัวเลขเดียว**
  มีตารางรายโมเดลแต่ไม่ได้บอกว่าแถวไหนเป็นของแพ็กเกจใด และเขียนให้ไปดูที่
  `/settings/limits` ของบัญชีตัวเอง
* ตัวอย่างที่เห็นในเอกสาร (ของ `openai/gpt-oss-120b`): 30 คำขอ/นาที · 1,000 คำขอ/วัน ·
  8,000 โทเคน/นาที · 200,000 โทเคน/วัน — **ตัวเลขนี้ใช้อ้างอิงไม่ได้** จนกว่าจะเทียบกับ
  หน้า limits ของบัญชีจริง
* เมื่อชนเพดาน Groq ตอบ **HTTP 429** พร้อม header `retry-after` และรายงานโควตาที่เหลือใน
  `x-ratelimit-remaining-requests` / `x-ratelimit-remaining-tokens`
  → ตัวเชื่อมต่อที่เขียนไว้เก็บ header เหล่านี้ทุกครั้งเพื่อใช้รายงานโควตาจริง

## 4. วิธีวัดและเกณฑ์ตัดสิน

ชุดวัด `eval/groq_candidate_check.py` เรียก `services/chat.py` ตรง ๆ ในคอนเทนเนอร์ทดสอบ
ที่ชี้ฐานข้อมูลทดสอบ **ไม่ผ่านเว็บจริงและไม่แตะ production**

สิ่งที่คุมให้เหมือนกันทั้งสองฝั่ง: คลังเอกสาร · ขั้นค้นเอกสาร · พรอมต์ · คำถาม ·
และ **embedding ทำด้วย Ollama (bge-m3) เสมอ** — ต่างกันจุดเดียวคือโมเดลที่เขียนคำตอบ

| วัดอะไร | อย่างไร |
|---|---|
| เวลาตอบแรก (TTFT) | เวลาจนตัวอักษรแรกออกจากสตรีม — ตัวเลขที่ผู้ใช้รู้สึกได้ |
| เวลารวม | จนคำตอบจบ |
| ความถูกต้อง | สถานะที่ระบบรายงาน + คำที่ต้องมี + การอ่านด้วยตาอีกชั้น |
| แหล่งอ้างอิง | จำนวนที่มาที่ระบบแนบมากับคำตอบ |
| ข้อผิดพลาด | แยกชนิด |

### ไม่นับ HTTP 200 ว่าสำเร็จ

ชุดวัดนี้ **ไม่ดูสถานะ HTTP เลย** แต่ตัดสินจาก

1. มีข้อความคำตอบออกมาจริงไหม
2. ข้อความนั้นเป็นข้อความแจ้งข้อผิดพลาดมาตรฐานของระบบหรือเปล่า
   (`ระบบตอบไม่ได้ในขณะนี้`, `ระบบใช้เวลาตอบนานเกินเพดาน`, `ผู้ให้บริการโมเดลใช้ไม่ได้`, …)
3. สถานะที่ระบบรายงานตรงกับที่คาดไว้ไหม

เรื่องนี้สำคัญเพราะเส้นทาง `/chat-web` **ตอบ 200 เสมอแม้ตอบไม่ได้** (ดูรายงานตัวนับ)
การนับ 200 ว่าสำเร็จจะได้ผลวัดที่สวยกว่าความจริง

### แยกโควตา/บริการขัดข้อง ออกจากคำตอบผิด

ผลของแต่ละข้อเป็นหนึ่งใน `ok` / `wrong` / `needs_review` / `provider_error`
โดย **ข้อที่ล้มเพราะ 429 หรือ 5xx นับเป็น `provider_error` ไม่ใช่ `wrong`**
เพราะโมเดลไม่เคยได้ตอบเลย การนับรวมกันจะสรุปว่าคุณภาพแย่ทั้งที่ยังไม่รู้

ตัวเชื่อมต่อแยกข้อยกเว้นไว้คนละชนิดตั้งแต่ต้นทาง: `GroqQuotaExceeded` (429) ·
`GroqServiceError` (5xx) · `LLMConnectionError` (อื่น ๆ)

## 6. ถ้าใช้จริงต้องแก้ไฟล์ใด (ยังไม่ได้แก้)

**Ollama ยังทำ embedding เสมอ** ทุกข้อด้านล่างแตะเฉพาะ "ผู้เขียนคำตอบ"

| # | ไฟล์ | ต้องทำอะไร | แก้แล้วหรือยัง |
|---|---|---|---|
| 1 | `llm/groq.py` | ตัวเชื่อมต่อ | **เขียนแล้ว** (ยังไม่มีใครเรียก) |
| 2 | `backend/app/core/config.py` | เพิ่ม `groq_api_key` (alias `GROQ_API_KEY`) และ `groq_model` (alias `GROQ_MODEL`) แบบเดียวกับ `gemini_*` บรรทัด 38–39 | ยังไม่แก้ |

### ข้อ 3 ขยายความ — ทำไมไม่ใช่การแก้เล็ก

`_SplitConnector.chat_stream()` ตัดสินใจอยู่สองอย่าง: จะสลับไปตัวสำรองได้ไหม
(ต้องยังไม่ส่งตัวอักษรแรก) และจะยอมใช้ตัวสำรองไหม (`allow_fallback`)
พอมีสามชั้น ต้องตอบเพิ่มว่า

* ชั้นกลางล้มแล้วจะลงไปชั้นสามเลย หรือหยุด
* `allow_fallback=False` ซึ่งตอนนี้แปลว่า "ห้ามใช้โมเดลในเครื่องเพราะตรวจกับเอกสารไม่ได้"
  จะหมายถึงห้ามใช้ Groq ด้วยหรือไม่ — **คำถามเชิงนโยบาย ไม่ใช่เชิงเทคนิค**
  (Groq เป็นโมเดลบนคลาวด์เหมือน Gemini แต่คนละเจ้าและคนละคุณภาพ)
* เพดานความยาวคำตอบต้องปรับตามชั้น เหมือนที่ `_fallback_kwargs()` ทำอยู่

ต้องตอบสามข้อนี้ให้ชัดก่อนเขียนโค้ด

## 7. ข้อเสนอ

### 7.1 เรื่อง Qwen บน Groq โดยเฉพาะ — **ยังไม่แนะนำ**

ไม่ใช่เพราะคุณภาพ (ยังไม่ได้วัด) แต่เพราะ **เงื่อนไขของผู้ให้บริการ**

* เป็นโมเดลสถานะ preview ที่ Groq เขียนเองว่าไม่ควรใช้ใน production
  และอาจถูกยกเลิกโดยแจ้งล่วงหน้าไม่นาน
* ตระกูล Qwen บน Groq ถูกปลดระวางมาแล้ว 4 รอบในราวหนึ่งปีครึ่ง
  รอบล่าสุดเมื่อ 14/09/2026 ซึ่งเพิ่งผ่านมาเดือนเดียว
* สิ่งที่เรากำลังจะสร้างคือ **ชั้นสำรองที่ต้องพึ่งได้ตอนเจ้าหลักล้ม**
  การเอาของที่ผู้ให้บริการบอกเองว่าอาจหายไปได้ทุกเมื่อมาเป็นชั้นนั้น ย้อนแย้งกับเป้าหมาย

### 7.2 ถ้ายังอยากได้ผู้ให้บริการที่สอง

วัด **โมเดลสถานะ production ของ Groq** แทน (เช่น `openai/gpt-oss-120b` ซึ่งเป็นตัวที่
Groq เองแนะนำให้ใช้แทน Qwen ที่ปลดระวางไป) ด้วยชุดวัดชุดเดียวกันนี้
ถ้าผลวัดผ่านเกณฑ์ ค่อยพิจารณาแก้ไฟล์ตามข้อ 6

### 7.3 ก่อนจะถึงขั้นนั้น — มีข้อมูลที่ยังขาดอยู่

รายงานตัวนับระบุไว้ว่ายัง **ไม่มีข้อมูลเวลาตอบและจำนวนคำขอที่ล้มแบบเก็บถาวร**
และตัวนับเพิ่งเริ่มเก็บวันนี้ ยังไม่มีข้อมูลสะสมพอจะบอกว่า **ปัญหาเกิดบ่อยแค่ไหน**

สิ่งที่รู้แล้วและเกี่ยวข้องกับการตัดสินใจ (จากการ deploy ตัวนับวันนี้)

* ชั้นสำรองปัจจุบัน (Ollama ในเครื่อง) **เย็นเสมอ** เพราะ `_keep_models_warm()` อุ่น
  เฉพาะโมเดล embedding เมื่อผู้ให้บริการหลักเป็น Gemini การตกมาใช้มันจึงมีค่าโหลด
  โมเดลบวกเข้าไปทุกครั้ง และเคยทำให้คำขอชนเพดานเวลาจนผู้ใช้ไม่ได้คำตอบ (วัดได้จริง 1 ครั้ง)
* **นี่เป็นเหตุผลที่หนักแน่นกว่าเรื่องโควตา** ในการมีผู้ให้บริการบนคลาวด์รายที่สอง
  เพราะของบนคลาวด์ไม่มีปัญหา "เย็น"
* แต่ก่อนจะลงทุนแก้ ควรดูก่อนว่ามีทางที่ถูกกว่าไหม เช่นอุ่นโมเดลในเครื่องไว้ด้วย
  (แลกกับหน่วยความจำของเครื่อง) ซึ่งเป็นการแก้ที่ไฟล์เดียวและไม่เพิ่มผู้ให้บริการเลย
  — **ยังไม่ได้วัดว่าทางนี้พอหรือไม่**

## 8. สิ่งที่ยังยืนยันไม่ได้ในรายงานนี้

| เรื่อง | สถานะ |
|---|---|
| คุณภาพคำตอบของ Qwen บน Groq กับคำถามไทยของระบบ | **ยังไม่ได้วัด** — ไม่มีคีย์ |

| การอุ่นโมเดลในเครื่องไว้จะแก้ปัญหาได้พอไหม | **ยังไม่ได้วัด** (ข้อ 7.3) |
