**`url_rejection(url) -> str`** — คืน *เหตุผล* เป็นข้อความ ไม่ใช่ `bool`
เพราะต้องเอาไปเก็บใน `crawl_sources.last_error` ให้คนอ่านได้ว่าลิงก์นี้ไม่ผ่านเพราะอะไร

**`Download`** — dataclass ผลการดาวน์โหลด (`ok`, `reason`, `size`, `sha256`, `etag`,
`last_modified`, `content_type`, `final_url`, `path`) พร้อม property `content_type_mismatch`

**`PoliteClient.download(url, dest_dir, max_bytes)`** — ลำดับการตรวจเรียงจากถูกไปแพง

```
1. scheme / โฮสต์ / พอร์ต ของ URL ที่ขอ      ← ไม่ยิงคำขอเลยถ้าไม่ผ่าน
2. robots.txt
3. สถานะ HTTP
4. scheme / โฮสต์ / พอร์ต ของ URL ปลายทางหลังตาม redirect
5. content-length ที่ประกาศมา เทียบเพดาน      ← ไม่อ่านเนื้อถ้าประกาศเกิน
6. ลายเซ็น %PDF- จากก้อนแรก                   ← ยังไม่สร้างไฟล์ก่อนผ่านข้อนี้
7. ขนาดจริงระหว่างอ่าน เทียบเพดาน             ← หยุดทันทีที่เกิน
8. อ่านครบตามที่ประกาศไว้
```

**`get()` และ `head()`** — เพิ่มด่าน `url_rejection` ทั้งของ URL ที่ขอและของ URL ปลายทาง
หลัง redirect (คืน `None` เมื่อไม่ผ่าน ซึ่งเป็นสัญญาเดิมของสองเมธอดนี้ ผู้เรียกไม่ต้องแก้)

**`_robots_for()`** — เพิ่มด่านซ้ำ เพราะเป็นที่เดียวที่ยิงผ่าน `_raw_get()` ที่ไม่ตรวจอะไรเลย
ถ้าใครเรียก `allowed()` ด้วย URL นอกขอบเขตโดยตรง จะไม่มีคำขอวิ่งออกไปหาโฮสต์นั้น

## 4. การตัดสินใจเรื่อง `content-type` ที่ขอให้กำหนดให้ชัด

> **เนื้อไฟล์ชนะ header — ลายเซ็น `%PDF-` เป็นตัวชี้ขาด ส่วน `content-type` เป็นเพียงข้อมูลประกอบ**

| สถานการณ์ | ผล | เหตุผล |
|---|---|---|
| `content-type: application/pdf` + เนื้อเป็น PDF | **รับ** ไม่มีหมายเหตุ | ปกติ |
| `content-type` อย่างอื่น (เช่น `application/octet-stream`) + เนื้อเป็น PDF | **รับ** และต่อท้าย `review_reason` ว่า *"เซิร์ฟเวอร์ประกาศ content-type เป็น …"* | เว็บคณะเป็น Apache ที่ตั้ง MIME ไม่ครบ ชื่อไฟล์เป็นค่าแฮชไม่มีนามสกุลบอก การปฏิเสธด้วย header อย่างเดียวจะทิ้งเอกสารหลักสูตรจริง แต่คนตรวจควรรู้ว่ามีอะไรไม่ปกติ |
| `content-type: application/pdf` + เนื้อไม่ใช่ PDF | **ปฏิเสธ** | header ปลอมได้และตั้งผิดได้ เนื้อไฟล์ปลอมไม่ได้ |
| `content-type: text/html` + เนื้อไม่ใช่ PDF | **ปฏิเสธ** | มักเป็นหน้า error ที่เซิร์ฟเวอร์ตอบ 200 |

ผลที่ตามมาโดยเจตนา: หน้า error ที่ตอบ 200 (พบบ่อยบนเว็บที่ตั้งค่าไม่ดี) จะไม่กลายเป็น
"เอกสารหลักสูตรฉบับใหม่" ในคิวของคนตรวจอีก

ตรวจแล้วด้วยว่าทุกโมดูลใน `pipeline/crawl/` ยัง import ได้ และ CLI ทั้งสอง Phase
ยังทำงาน (`python -m pipeline.crawl.run --help`, `python -m pipeline.crawl.sync --help`)
และรัน `probe()` ของ Phase 1 จริงกับเซิร์ฟเวอร์ทดสอบแล้วได้ผลถูกต้องทุกเคส ไม่มีไฟล์ค้าง

### ⚠️ สิ่งที่ยังไม่ได้พิสูจน์

`eval/crawl_state_check.py` **รันในเครื่องนี้ไม่ได้** เพราะต้องมี PostgreSQL ที่ลง
migration 003 แล้ว ซึ่งเครื่องพัฒนาไม่มีทั้ง PostgreSQL และ Docker
สิ่งที่พิสูจน์แทนไปแล้วคือ **ตรรกะลำดับสถานะ** (หมวด [5]) และ `StubClient.download()`
ตัวใหม่ (ทดสอบแยกว่าคืน `ok`/`sha256`/`content_type`/เหตุผลถูกต้อง)

สิ่งที่พิสูจน์แทนไม่ได้คือข้อบังคับในฐานข้อมูลจริง (CHECK, UNIQUE, trigger) และข้อ 4e–4h
ที่เพิ่มใหม่ — **งานรอบนี้ไม่ได้แตะ schema เลย** ข้อบังคับเหล่านั้นจึงไม่มีเหตุให้เปลี่ยน
แต่ควรรันชุดนี้บนเครื่องที่มีฐานข้อมูลทดสอบก่อน deploy

```bash
python eval/crawl_state_check.py --database-url postgresql://postgres:PASS@HOST:5432/crawl_test
```

| เรื่อง | ผล |
|---|---|

| `store.upsert()` | สัญญาเดิมทุกพารามิเตอร์ ไม่แก้ `state.py` แม้บรรทัดเดียว |

| ชื่อไฟล์ใน staging | `_safe_name()` เดิม รูปแบบ `<sha12>_<ชื่อเดิม>` ไม่เปลี่ยน |

| `--no-download` | ทำงานเหมือนเดิม (ทดสอบไว้แล้ว) |
| ผลต่อ crawl รอบถัดไปบน production | 12 ลิงก์เดิมทั้งหมดอยู่บน `sci.pnru.ac.th` และเป็น PDF จริง จึงยังได้ `unchanged` เหมือนเดิม — **คาดว่าไม่มีแถวใดเปลี่ยนสถานะ** แต่ต้องยืนยันด้วยการรันจริงหลังอนุมัติ |

**หมายเหตุสำคัญต่อ Phase 3** — เพดาน 50 MB ในไฟล์นี้ต้องตรงกับ
`backend/app/core/config.py::max_pdf_size_mb` เสมอ ถ้าวันหนึ่งขยายเพดานฝั่ง crawler
แต่ไม่ขยายฝั่ง backend จะได้ไฟล์ที่อยู่ในคิวแต่เปิดดูไม่ได้ ซึ่งคนตรวจจะอนุมัติแบบไม่ได้เห็นของ
