## 0. บั๊ก 3 ตัวที่เจอระหว่างทำรอบนี้

ทั้งสามตัวชุดทดสอบเดิม**ผ่านหมด** — เจอจากการใช้งานจริงเท่านั้น

| # | บั๊ก | ผลถ้าไม่เจอ |
|---|---|---|
| 1 | โมเดลประกาศ `email` เป็น `String` ทั้งที่ฐานข้อมูลเป็น `citext` | **ผู้ดูแลเข้าระบบไม่ได้เลย** |
| 2 | `sync_sci_news` ต่อ slug เข้า URL โดยไม่เข้ารหัส | **งานดึงข่าวล้มทุกรอบ ไม่มีข่าวใหม่เลย** |
| 3 | หน้าเว็บ 3 จุดยังเรียก `/api/sci-connect-news` ของ webapi | **ยังพึ่ง Supabase อยู่ ทั้งที่ค้นคำว่า supabase ในซอร์สไม่เจอ** |

### บั๊ก 1 — `citext` กับ `String`

เบาะแสคือ **`failed_login_count` ไม่เพิ่ม** หลังได้ 401 · ถ้ารหัสผิดจริงตัวนับต้องเพิ่ม แปลว่าระบบ**หาแถวไม่เจอ**

| เทียบแบบ | ผล |
|---|---|
| `email = 'tester@gmail.com'` | **พบ 1** |
| `email = 'tester@gmail.com'::varchar` (ที่ SQLAlchemy ส่ง) | **พบ 0** |

ฐานข้อมูลเก็บเป็น `citext` (เทียบไม่สนตัวพิมพ์) แต่โมเดลประกาศ `String` → SQLAlchemy ผูกพารามิเตอร์เป็น `varchar`
Postgres ต้อง cast `citext → text` ก่อนเทียบ **กลายเป็นเทียบตรงตัวพิมพ์**

อีเมลที่เก็บไว้คือ `Tester@gmail.com` (T ใหญ่) จึงไม่มีทางเข้าได้

| ผลกระทบ | 2 จาก 204 บัญชี — **หนึ่งในนั้นคือ admin** |
|---|---|
| จุดที่พลาดด้วย | ตรวจอีเมลซ้ำตอนสมัคร → ผ่านด่านแอป แล้วไปชน unique constraint เป็น **500 แทน 400** |

**แก้:** เปลี่ยนโมเดลเป็น `CITEXT` — แก้ทุกจุดที่ค้นด้วยอีเมลในที่เดียว
**พิสูจน์:** กับ PostgreSQL จริง — `String` หา 0 แถว · `CITEXT` หา 1 แถว
**บน production:** หลัง deploy ยิง login รหัสผิด → ตัวนับ **0 → 1** แปลว่าหาแถวเจอแล้ว

### บั๊ก 2 — URL ไม่เข้ารหัส

```
http.client.InvalidURL: URL can't contain control characters.
'/sciconnect_detail.php?slug=SCI Connect ฉบับที่ 24 ปีที่ 1 เดือนกรกฎาคม 2569'
```

slug ของเว็บต้นทางเป็นชื่อเรื่องเต็ม มีช่องว่างและภาษาไทย · `fetch_url(f"{DETAIL_URL}?slug={slug}")` ต่อสตริงตรง ๆ

**งานล้มทั้งรอบตั้งแต่รายการแรก ไม่มีข่าวใดถูกบันทึกเลย** และ `dry-run` ไม่เจอเพราะอ่านแค่หน้ารายการ ไม่เปิดหน้ารายละเอียด

> **จุดที่เกือบรายงานผิด** — รอบแรกผมสรุปว่า "รันซ้ำไม่เพิ่มข่าวซ้ำ" เพราะจำนวนเท่าเดิม 15 แถว
> แต่จำนวนเท่าเดิมเพราะ **งานพังก่อนเขียน** ไม่ใช่เพราะกันซ้ำได้ · `exit=1` อยู่ใน log

**แก้:** เพิ่ม `detail_url_for()` ใน `sci_news.py` ใช้ `urlencode` — แก้ทั้งงานตั้งเวลาและปุ่มผู้ดูแลพร้อมกัน

### บั๊ก 3 — หน้าเว็บยังเรียก webapi

ตรวจ Network ของหน้าเว็บจริงหลัง deploy พบ `GET /api/sci-connect-news → 200`
เส้นทางนี้ดูเหมือนของเราเอง แต่ Caddy ส่งต่อไป `webapi` ซึ่งอ่าน **Supabase** ด้วย anon key

| ไฟล์ | เรียกอะไร |
|---|---|
| `SciConnectNews.jsx` | `/api/sci-connect-news` |
| `SciConnectAll.jsx` | `/api/sci-connect-news?limit=15` |
| `SciConnectDetail.jsx` | `/api/sci-connect-news-detail?slug=…` |

หน้าผู้ดูแลเรียก `/api/site/external-news` ถูกแล้ว — พลาดเฉพาะหน้าสาธารณะ

**ชุดทดสอบ `noSupabase` เดิมจับไม่ได้** เพราะค้นแค่คำว่า "supabase" ในซอร์สกับ `dist/`

**แก้:** เปลี่ยนทั้งสามจุดไปที่ `/api/site/external-news` และเพิ่มข้อทดสอบที่**ห้ามเรียกเส้นทางของ webapi**

### รอบสอง (หลังแก้บั๊ก 3) — **เว็บล่มชั่วคราวราว 2 นาที**

```
ไฟล์ที่ไม่ตรง: index.html
< script src="/assets/index-BJ4iLcmO.js"   (ชุดใหม่)
> script src="/assets/index-BYSigOEx.js"   (ชุดเก่า — ถูก --delete ลบไปแล้ว)
```

**สาเหตุ:** ชุดหน้าเว็บถูกสร้างด้วย **mtime คงที่** เพื่อให้ build ซ้ำได้ checksum เดิม
`rsync -a` เปรียบเทียบด้วย **ขนาด + mtime** · `index.html` เก่ากับใหม่ขนาดเท่ากันพอดี (1,779 ไบต์) จึงถูก**ข้าม**

ผลคือ `index.html` เก่ายังอ้างไฟล์ JS ที่ `--delete` ลบไปแล้ว → `/assets/index-BYSigOEx.js` **404** → ทั้งเว็บขึ้นหน้าว่าง

| | |
|---|---|
| ตรวจพบ | ทันทีจาก manifest หลังวาง (`ผิด 1`) |
| แก้ | `rsync -a --delete --checksum` (เทียบเนื้อหา ไม่ดู mtime) |
| หลังแก้ | manifest **19/19** · `index.html` อ้าง `index-BJ4iLcmO.js` · ทุกหน้า **200** |
| ป้องกันต่อไป | แก้คำสั่งใน `PHASE4_DEPLOY_PROMPT_2569-10-12.md` ให้ใส่ `--checksum` ทั้งขั้น E และ rollback |

> ถ้าไม่ได้ตรวจ manifest หลังวาง จะไม่มีใครรู้ว่าเว็บล่ม จนกว่าจะมีคนเปิดเว็บ

| ตรวจ | ผล |

| รอบที่ 2 (รันซ้ำ) | **exit 0** · จำนวนคงที่ **15 แถว** |
| `detail_url` ซ้ำ | **0** |
| `slug` ซ้ำ | **0** |
| ข่าวที่มีคำบรรยาย | **15 จาก 15** |
| ข่าวที่มีลิงก์เฟซบุ๊ก | **15 จาก 15** |

**ทั้ง 15 มีคำบรรยายและลิงก์ครบ** คือหลักฐานว่าเปิดหน้ารายละเอียดได้จริง (ก่อนแก้บั๊ก 2 ไม่มีเลย)

### ทดสอบ `flock`

รันสองรอบพร้อมกัน

```
22:15:11Z เริ่มรอบใหม่ (pid 1034359)
22:15:12Z ข้ามรอบนี้ — รอบก่อนยังทำงานอยู่
22:15:16Z จบรอบ exit=0
```

**รอบที่สองถูกข้าม 1 ครั้ง** ตามที่ออกแบบ

> **ข้อสังเกต:** ต้นทางมี 55 ข่าว แต่ระบบเก็บแค่ 15 ล่าสุด (`KEEP_LATEST`)
> ทุกรอบจึงเขียน 41 แล้วลบ 41 · ผลสุทธิคงที่และ 15 รายการบนสุดไม่เปลี่ยน id
> ไม่ใช่ข้อผิดพลาด แต่เป็นการทำงานซ้ำที่ลดได้ถ้าต้องการ
