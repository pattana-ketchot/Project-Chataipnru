## 3. Review workflow — `pipeline/mko/review.py`

```
python -m pipeline.mko.review status
python -m pipeline.mko.review export --out backups/mko_local/review_queue.csv
python -m pipeline.mko.review apply --file <csv> --reviewer "<ชื่อ>"
```

- **ส่งออกคิว:** ไฟล์ CSV (เปิดใน Excel ได้) หนึ่งแถวต่อหนึ่งค่า มีค่า หน้า ข้อความที่ยกมา และเหตุผลของสถานะ ผู้ตรวจกรอก `verified`/`rejected` (หรือ ผ่าน/ไม่ผ่าน)
- **บันทึกผล:** ตรวจทุกแถวก่อนเขียน ถ้ามีแถวผิดรูปแบบจะไม่บันทึกอะไรเลย และต้องมีชื่อผู้ตรวจ ผู้ตรวจถูกบันทึกเป็น `human:<ชื่อ>` แยกจากกฎอัตโนมัติ (`auto:…`)
- **สกัดใหม่:** `run.py` นำผลตรวจกลับมาใช้กับรอบใหม่ทุกครั้ง ถ้าค่าที่สกัดได้ต่างจากที่คนตรวจไว้ ผลตรวจเดิมไม่ถูกใช้และค่าใหม่กลับเข้าคิว
- **คิวปัจจุบัน (local):** 189 แถว
  - careers 20 + 1 needs_review
  - admission 19
  - objectives 16 + 2 needs_review
  - ชื่อ/ปริญญา 121
  - total_credits 4, edition_year 3, revision_type 3
  - ผลตรวจของคน = 0 (ยังไม่มีใครตรวจ)

## 4. Publish workflow — `pipeline/mko/publish.py`

```
python -m pipeline.mko.publish --by "<ชื่อ>" [--human-only] [--dry-run]
python -m pipeline.mko.publish --rollback-latest
```

- เผยแพร่เฉพาะสถานะ `verified` ของรอบสกัดล่าสุด ส่วน candidate / needs_review / rejected ไม่ถูกเผยแพร่
- นโยบาย `verified_any` (ค่าตั้งต้น) รับทั้งกฎอัตโนมัติและคน ใช้กับโหมด shadow ส่วน `verified_human_only` รับเฉพาะคนตรวจ ควรใช้ก่อนเปิดให้ผู้ใช้จริง
- ถ้าเอกสารของหลักสูตรเดียวกันให้ค่า verified ต่างกัน field นั้นไม่ถูกเผยแพร่และถูกรายงาน ระบบไม่เลือกให้
- รายการเผยแพร่เมื่อทุกข้อ verified เท่านั้น
- ย้อนกลับได้ด้วยการลบการเผยแพร่ครั้งล่าสุด

**ผลการเผยแพร่บน local** (`verified_any`)

## 6. Routing — `backend/app/services/structured_intent.py`

ไป **structured** เมื่อครบทุกข้อ ถ้าขาดข้อใดไป **RAG** ตามเดิม (ถ้าไม่แน่ใจให้พลาดไปทาง RAG)
1. ถามหา field ที่รองรับเพียงหนึ่ง field: หน่วยกิตรวม, ปีหลักสูตร, อาชีพ, วัตถุประสงค์, คุณสมบัติผู้เข้าศึกษา
2. ไม่ถามเรื่องที่ยังไม่มีใน DB: หน่วยกิตรายหมวด, รายวิชา, PLO, ระยะเวลาเรียน, ค่าเทอม, อาจารย์, การรับสมัคร/TCAS
3. ไม่ใช่คำถามเชิงบรรยาย เปรียบเทียบ แนะนำ หรือขอให้ตัดสิน (ทำไม/อย่างไร/ต่างกัน/เหมาะ/ได้ไหม …)
4. เอ่ยถึงหลักสูตรเดียว (ใช้ `course_scope.resolve_scopes` ตัวเดียวกับ RAG) ระบุปีได้ไม่เกินหนึ่งปี และไม่ถามข้ามหลักสูตร (สาขาไหน/ที่สุด)

- ไม่มีชื่อหลักสูตรในโค้ด ชื่อมาจากตาราง `courses`
- ตัดชื่อหลักสูตรออกก่อนตรวจคำ ชื่อสาขาที่มีคำว่า "อาชีพ" จึงไม่ถูกนับเป็นคำถามอาชีพ
- ทุกการตัดสินมีรหัสเหตุผลบันทึกไว้: `single_programme_field`, `unsupported_topic`, `narrative_or_comparison`, `across_programmes`, `multiple_fields`, `multiple_years`, `multiple_programmes`, `no_programme`, `no_supported_field`

**Regression tests ตามที่ขอ** (`eval/structured_routing_check.py` + `eval/curriculum_facts_check.py`)

| ปีหลักสูตร | "เป็นหลักสูตรปีอะไร", "พ.ศ. อะไร", "ปรับปรุงล่าสุด"; "เรียนกี่ปี" ต้องไป RAG |

| คำถามเชิงบรรยาย → RAG | ทำไม / อธิบาย / เหมาะกับใคร / เรียนเกี่ยวกับอะไร / ได้ไหม |

## 7. Feature flag และ shadow hook

`STRUCTURED_ANSWERS` (`backend/app/core/config.py`; ค่าเริ่มต้นใน `docker-compose.prod.yml` คือ `off`)

| ค่า | พฤติกรรม |
|---|---|
| `off` (ค่าตั้งต้น) | ไม่ทำอะไรเลย ไม่เปิด thread ไม่แตะฐานข้อมูล |
| `shadow` | หลังได้คำตอบครบแล้ว คำนวณคำตอบจาก DB ใน thread แยก เทียบกับคำตอบที่ผู้ใช้ได้รับ แล้วบันทึกลง `mko.shadow_answers` |
| `on` | Phase 2 ยังไม่อนุญาต ระบบทำงานเป็น `shadow` และเตือนใน log |
| ค่าอื่น | ถือเป็น `off` ไม่ทำให้ backend เปิดไม่ขึ้น |

**จุดที่แก้ใน `chat.py`** (+14 บรรทัด ไม่ลบบรรทัดเดิม)
- `Prepared` มี field ใหม่ 2 ตัวที่มีค่าเริ่มต้น คือ `interpreted` และ `has_history`
- `answer_question` / `stream_answer` เรียก `shadow_submit(...)` หลังบันทึกบทสนทนาและแคชเสร็จ ในสตรีมเรียกหลังตัวอักษรสุดท้าย ก่อน `done`

**ข้อรับประกัน** (มีเทสต์ทุกข้อ)
- `submit` ไม่โยน exception ไม่ว่ากรณีใด
- worker ที่ล้มเหลว (เช่น ยังไม่มี schema mko หรือ DB ล่ม) ลงแค่ log
- คิวมีเพดาน 32 งาน เกินแล้วทิ้ง ไม่รอ

**ผลการเทียบ:** `agree` / `partial` / `disagree` / `served_no_answer` / `unclear` / `not_compared`
- เป็นกฎตรวจข้อความ ไม่ใช่ตัวตัดสินความถูกต้อง
- หน่วยกิตดูเฉพาะเลข ≥ 100 ที่ตามด้วย "หน่วยกิต"
- รายการดูสัดส่วน 4-gram ที่พบในคำตอบ

- **ระบบเดิม:** รายการ 5 ข้อของฉบับ 2566
- **DB:** วัตถุประสงค์ 5 ข้อตาม (พ.ศ. 2566) + "ยังไม่มีข้อมูลที่ผ่านการตรวจของ … (พ.ศ. 2561)" — ที่มา: it66.pdf หน้า 13
- **เทียบ:** agree (ครอบคลุม 0.98–1.0 ทุกข้อ)

### ตัวอย่าง 4 — หลายฉบับ แต่ DB มีข้อมูลที่ตรวจแล้วเพียงฉบับเดียว (partial)
- **ถาม:** หลักสูตรคณิตศาสตร์ต้องเรียนทั้งหมดกี่หน่วยกิต
- **ระบบเดิม:** "…พ.ศ. 2564 … 130 หน่วยกิต ส่วนหลักสูตร พ.ศ. 2569 … 124 หน่วยกิต"
- **DB:** (พ.ศ. 2564) 130 หน่วยกิต + "ยังไม่มีข้อมูลที่ผ่านการตรวจของ … (พ.ศ. 2569)" — ที่มา: ma64.pdf หน้า 6
- **เทียบ:** partial (expected [130], พบ [124, 130]) — ค่า 124 ของ 2569 ถูกต้องตาม gold แต่ใน DB ยังเป็น candidate จึงไม่เผยแพร่ **DB ไม่เดา** และบอกว่าฉบับไหนยังไม่มีข้อมูล

### ตัวอย่าง 5 — ระบบเดิมตอบผิด แต่กฎเทียบให้ unclear
- **ถาม:** หลักสูตรแอนิเมชันและมัลติมีเดียต้องเรียนทั้งหมดกี่หน่วยกิต
- **ระบบเดิม (คำตอบที่บันทึกใน v16):** "คณะวิทยาศาสตร์และเทคโนโลยีไม่มีสาขาแอนิเมชันและมัลติมีเดีย ครับ สาขาที่เปิดสอนอยู่มีดังนี้ … คอมพิวเตอร์แอนิเมชันและมัลติมีเดีย …"
- **DB:** (พ.ศ. 2564) 127 หน่วยกิต + "ยังไม่มีข้อมูลที่ผ่านการตรวจของ … (พ.ศ. 2569)" — ที่มา: animation64.pdf หน้า 6
- **เทียบ:** unclear เพราะคำตอบเดิมไม่มีตัวเลขหน่วยกิต กรณีนี้คือคำตอบเดิมผิด ป้าย `unclear` จึงต้องให้คนอ่านซ้ำเสมอ ห้ามนับว่าผ่าน
- กรณีเดียวกัน: "หลักสูตรการจัดการเทคโนโลยีการเกษตรต้องเรียนทั้งหมดกี่หน่วยกิต" (DB 130 จาก atm.pdf หน้า 6)

### ตัวอย่าง 6 — อาชีพ ยังไม่มีข้อมูลที่ผ่านการตรวจ (no_data)
- **ถาม:** หลักสูตรวิทยาการคอมพิวเตอร์ จบไปแล้วสามารถประกอบอาชีพอะไรได้บ้าง
- **route:** structured / careers
- **DB:** no_data — "ยังไม่มีข้อมูลที่เผยแพร่" → not_compared ระบบเดิมตอบตามปกติ (8 อาชีพ)

### ตัวอย่าง 7 — เปรียบเทียบ ไม่ถูกบังคับเข้า DB
- **ถาม:** ค่าเทอมวิทคอมกับไอทีต่างกันไหม
- **route:** RAG (`unsupported_topic`) / structured_status `not_applicable`
- คำถามเปรียบเทียบอื่นในเทสต์ เช่น "วิทยาการคอมพิวเตอร์กับเทคโนโลยีสารสนเทศเรียนกี่หน่วยกิต" → RAG (`multiple_programmes`)

## 10. ข้อจำกัดที่ต้องรู้ก่อนไปต่อ

1. **อาชีพและคุณสมบัติผู้เข้าศึกษายังเผยแพร่ไม่ได้** — ไม่มีรายการใดผ่านกฎอัตโนมัติ ถ้าเปิด shadow ตอนนี้ คำถามกลุ่มนี้จะได้ `no_data` ทั้งหมดจนกว่าอาจารย์จะตรวจคิว (`review_queue.csv`, 189 แถว)
2. **ข้อมูลที่ยืนยันแล้วทั้งหมดมาจากกฎอัตโนมัติ** (`auto:two_locations_agree` / `auto:documents_agree`) ยังไม่มีผลตรวจของคน ก่อน Phase 3 ควรเผยแพร่แบบ `--human-only`
3. **กฎเทียบคำตอบเป็นแนวโน้ม** — `unclear` อาจหมายถึงคำตอบเดิมผิด (ตัวอย่าง 5) และ `partial` อาจหมายถึง DB ยังไม่ครบ (ตัวอย่าง 4) ต้องอ่านคู่คำตอบใน `shadow_answers` ประกอบ
4. **Routing ตั้งใจให้แคบ** — ถ้อยคำที่ไม่ตรงกฎจะไป RAG (ปลอดภัย แต่ครอบคลุมน้อย) คำถามต่อเนื่องใช้คำถามที่ตีความแล้วจาก `prepare_answer` คำตอบสำเร็จรูปที่ตอบก่อนขั้นตีความใช้ข้อความดิบ
5. **`shadow_answers` เก็บคำถามและคำตอบที่ผู้ใช้ได้รับ** — เป็นข้อมูลเดียวกับที่ `chat_messages` เก็บอยู่แล้ว `advisor_api` เขียนได้อย่างเดียว อ่านไม่ได้
6. **ค่าใช้จ่ายต่อคำถามในโหมด shadow:** อ่าน courses + view 2–4 query ใน thread แยก (local 3–20 ms)

## 12. แผนแตะ production (ยังไม่ทำ — รออนุมัติ)

1. **Backup:** `pg_dump -Fc` ทั้งฐาน เก็บบนเซิร์ฟเวอร์ และบันทึก sha256 ของไฟล์
2. **Snapshot ก่อน:** รายชื่อตาราง public และจำนวนแถว (courses, course_documents, course_chunks, users, chat_*)
3. **Migration:** apply `001_mko_structured.sql` + `002_mko_review_publish.sql` (additive, `mko` เท่านั้น) แล้วเทียบ snapshot หลังรัน ต้องเหมือนเดิมทุกตาราง
4. **ข้อมูล mko:**
   - `pg_dump --schema=mko --data-only` จาก local แล้ว restore
   - id ของ `course_documents` ตรงกัน เพราะ local restore มาจาก production — ตรวจ sha256 ของเอกสารก่อน
   - ได้การเผยแพร่ `verified_any` ชุดเดียวกับที่ทดสอบ
5. **Deploy backend:**
   - build image ใหม่จาก commit ของ `mko-phase2` (backend = `b78b3f8` + ไฟล์ Phase 2 เท่านั้น ไม่มีงานค่าเทอมที่ค้างอยู่)
   - ติด rollback tag และตั้ง `STRUCTURED_ANSWERS=shadow`
   - ตรวจ sha ในคอนเทนเนอร์ และอัปเดต `~/DEPLOYED_COMMIT`
6. **ตรวจหลัง deploy:**
   - ถามผ่าน `/api/chat` แล้วเทียบคำตอบกับก่อน deploy
   - `mko.shadow_answers` มีแถวเพิ่ม
   - log ไม่มี error
7. **Rollback:** ตั้ง `STRUCTURED_ANSWERS=off` แล้ว recreate คอนเทนเนอร์ หรือกลับ image เดิม ส่วน schema `mko` ปล่อยไว้ได้เพราะไม่มีอะไรอ่าน
