# สวิตช์เลือกโมเดล Gemini / Ollama จากหลังบ้าน

**วันที่** 28 ต.ค. 2569 · **สถานะ** ตรวจเสร็จแล้ว **ยังไม่ deploy** และยังไม่แก้การตั้งค่า production
**ฐานที่ทดสอบ** `course_advisor_test` · **อิมเมจฐาน** `course-advisor-system-backend:followup-2569-10-28` (ตัวที่ production รันอยู่)

---

## 1. โจทย์และข้อสรุป

โจทย์คือ *ต่อสวิตช์ Gemini/Ollama ในหลังบ้านให้เปลี่ยนโมเดลสร้างคำตอบได้จริง*

| ข้อ | ผล |
|---|---|
| 1. ใช้ของเดิม ไม่สร้างระบบซ้ำ | ใช้หน้า AI Settings เดิม ตาราง `web.ai_settings` เดิม และ `get_llm_connector()` เดิม · เพิ่มคอลัมน์ `provider` หนึ่งคอลัมน์ |
| 2. อ่านค่าที่บันทึกและใช้กับคำขอใหม่ โดยไม่ต้อง restart | ทำได้ · มีผลทันทีในกระบวนการที่รับคำขอบันทึก และไม่เกิน 10 วินาทีในกรณีอื่น · รวมถึงผูกแคชคำตอบไว้กับโมเดล ไม่งั้นคำถามที่เคยถามจะได้คำตอบของเจ้าเดิม (ข้อ 3.7) |
| 3. เปลี่ยนเฉพาะโมเดลสร้างคำตอบ · embedding ยังเป็น bge-m3 | ทำได้ · จำนวนชิ้นเอกสารและมิติเวกเตอร์ก่อน/หลังทดสอบเท่ากัน (9,039 ชิ้น · 1,024 มิติ) |
| 4. รักษาสิทธิ์ผู้แก้ไข · ห้ามส่ง API key ให้ frontend | ทำได้ · `require_staff` เหมือนเดิม · คำตอบของเส้นทางนี้ไม่มีคำว่า `api_key` เลย คืนแค่ `has_gemini_key: true/false` |
| 5. แสดง provider/model ที่ตั้งใจเลือกและสถานะจริง | ทำได้ · แยก "ที่บันทึก" ออกจาก "ที่ใช้จริง" และมีปุ่มตรวจที่ยิงคำขอจริงสองขั้น |
| 6. fallback ชัดเจน · ไม่สลับโมเดลกลางคำตอบ · รักษาเพดานเวลาเดิม | ทำได้ · กฎของ fallback อยู่ที่ข้อ 3.6 · ไม่แตะเพดานเวลาเดิมเลย (ข้อ 6.7) |

**ข้อจำกัดที่ต้องอ่านก่อนใช้งาน:** สวิตช์ทำงานถูกต้อง แต่ **เลือก Ollama แล้วระบบตอบคำถามที่ต้องอ้างอิงเอกสารไม่ได้**
ที่เพดานเวลา 30 วินาทีของ production — วัดได้ 0 สำเร็จจาก 3 ครั้ง รายละเอียดและสาเหตุอยู่ที่หัวข้อ 6
เรื่องนี้เป็นขีดความสามารถของโมเดลในเครื่อง ไม่ใช่ข้อผิดพลาดของสวิตช์ และหน้าผู้ดูแลรายงานตามจริงแล้ว

## 2. ของเดิมเป็นอย่างไร — หลักฐานว่าสวิตช์ไม่เคยทำงาน

สำรวจก่อนแก้ ตามที่โจทย์กำหนด พบว่าชิ้นส่วนมีอยู่ครบแล้วแต่ไม่ได้ต่อถึงกัน

| ชิ้นส่วน | สภาพเดิม |
|---|---|
| หน้า `/admin/ai-settings` | มีช่องกรอกชื่อโมเดลช่องเดียว บันทึกได้ ขึ้นว่าสำเร็จ |
| `PUT /site-admin/ai-settings` | เขียน `web.ai_settings.model` ลงฐานจริง (`require_staff`) |
| `web.ai_settings` | มีคอลัมน์ `id, model, updated_by, updated_at` · ไม่มี `provider` |
| `get_llm_connector()` | สร้าง connector **ครั้งเดียว** เก็บเป็น singleton ระดับโมดูล เลือกจาก `settings.llm_provider` (env) |
| โค้ดที่อ่าน `web.ai_settings` | **ไม่มีเลย** — `grep -rn "ai_settings" backend/app` เจอแต่เส้นทางที่เขียนลงฐาน |

หลักฐานที่ตรงที่สุดคือค่าในฐาน production เทียบกับค่าที่ระบบใช้จริง:

```
web.ai_settings (production)   model = 'gemini-3.1-flash-lite'   ตั้งไว้ 25 ส.ค. 2569
.env ของ production            GEMINI_MODEL=gemini-3.5-flash-lite
                               LLM_PROVIDER=gemini
```

ค่าสองตัวนี้ไม่ตรงกันมาสองเดือน และตัวที่ตอบจริงคือตัวที่มาจาก env
**ถ้าค่าที่บันทึกถูกนำไปใช้ ระบบต้องล่มไปแล้ว** เพราะ `gemini-3.1-flash-lite` ไม่ใช่รุ่นที่เรียกได้

ยืนยันซ้ำด้วยการยิง API ผ่านอิมเมจ production ล้วน (`run-20261028-022011/before-api.txt`):
ตั้ง `provider='ollama', model='qwen2.5:3b'` ไว้ในฐานทดสอบ แล้วถามหนึ่งคำถาม

```
GET /site-admin/ai-settings  ->  {"id":1,"model":"qwen2.5:3b","updated_at":"..."}
ตัวนับก่อนถาม : gemini_ok=8
ตัวนับหลังถาม : gemini_ok=10        <- Gemini ตอบ ทั้งที่ฐานบอกว่าให้ใช้ ollama
```

## 3. สิ่งที่แก้

### 3.1 ที่เก็บค่า — เพิ่มคอลัมน์เดียว

`db/migrations/010_ai_settings_provider.sql` เป็น **DDL ล้วน ไม่แก้ข้อมูลในแถวเดิมแม้แต่ค่าเดียว**

```sql
alter table web.ai_settings add column if not exists provider varchar(16);
alter table web.ai_settings alter column model drop not null;
-- check (provider is null or provider in ('gemini','ollama'))
```

* `provider` NULL = ยังไม่เลือก ให้ใช้ค่าจาก env
* `model` NULL = เลือกผู้ให้บริการแล้วแต่ไม่ระบุรุ่น ให้ใช้รุ่นตั้งต้นของเจ้านั้นจาก env
  (จึงต้องปลด `NOT NULL` ออก ไม่งั้นเขียน "เลือกเจ้า ใช้รุ่นตั้งต้น" ลงฐานไม่ได้)

### 3.2 กฎที่ทำให้ "deploy แล้วพฤติกรรมไม่เปลี่ยน"

**ค่าที่บันทึกจะถูกใช้ก็เมื่อ `provider` ถูกระบุไว้เท่านั้น**

แถวเดิมใน production มีแต่ `model = 'gemini-3.1-flash-lite'` ซึ่งไม่มีใครอ่านมาสองเดือน
ถ้าถือว่าคอลัมน์นั้นมีความหมายทันทีที่โค้ดใหม่ขึ้น ระบบจะเริ่มส่งชื่อรุ่นที่ไม่เคยถูกตรวจ
ไปให้ Gemini จริงตั้งแต่วินาทีแรกของการ deploy — เป็นการเปลี่ยนพฤติกรรมโดยที่ไม่มีใครสั่ง
จึงกำหนดว่า `model` ที่ไม่มี `provider` กำกับ = ยังไม่ได้เลือก และหน้าผู้ดูแลจะขึ้นข้อความบอกว่า
ค่านั้นยังไม่มีผล ต้องเลือกผู้ให้บริการแล้วกดบันทึกอีกครั้ง

ผลคือ **การ deploy ชุดนี้เพียงอย่างเดียวไม่เปลี่ยนโมเดลที่ตอบ** จนกว่าผู้ดูแลจะเลือกเอง

### 3.3 ตัวตัดสิน — `backend/app/services/ai_settings.py` (ไฟล์ใหม่)

จุดเดียวที่ตอบคำถามว่า "ตอนนี้ใช้อะไร" โดยรวมสามแหล่ง: ค่าที่บันทึก → ตรวจความถูกต้อง → ค่าตั้งต้นจาก env
คืน `Choice` ที่แยก **ที่ผู้ดูแลสั่ง** (`saved_provider`, `saved_model`) ออกจาก **ที่ใช้จริง** (`provider`, `model`)
พร้อม `note` อธิบายเมื่อสองอย่างไม่ตรงกัน

| สถานการณ์ | ที่ใช้จริง | หมายเหตุที่หน้าเว็บแสดง |
|---|---|---|
| ไม่มีแถว / `provider` NULL | env | ว่าง หรือ "ค่าที่บันทึกไว้ยังไม่ถูกใช้ เพราะไม่ได้ระบุผู้ให้บริการกำกับ" |
| `provider` ไม่รองรับ (แก้ในฐานด้วยมือ) | env | "ผู้ให้บริการ … ที่บันทึกไว้ไม่รองรับ" |
| เลือก `gemini` แต่เซิร์ฟเวอร์ไม่มีคีย์ | **ollama** | "เลือก Gemini ไว้ แต่เซิร์ฟเวอร์ไม่มี GEMINI_API_KEY จึงยังใช้โมเดลในเครื่องตอบ" |
| เลือกเจ้าแต่ไม่ระบุรุ่น | เจ้านั้น + รุ่นจาก env | "ไม่ได้ระบุรุ่น จึงใช้รุ่นตั้งต้นของผู้ให้บริการจาก environment" |
| เลือกครบ | ตามที่เลือก | ว่าง (`honoured = true`) |
| อ่านฐานไม่ได้ | env | "อ่านค่าที่บันทึกไม่ได้ จึงใช้ค่าจาก environment" |

แถวสุดท้ายสำคัญ: ฐานข้อมูลล่มต้องไม่ทำให้ตอบคำถามไม่ได้ เพราะค่าตั้งต้นจาก env ใช้งานได้อยู่แล้ว

### 3.4 ไม่ต้อง restart — และไม่สลับโมเดลกลางคำตอบ

`get_llm_connector()` เปลี่ยนจาก singleton ตัวเดียว เป็น **แคชตามตัวเลือก** `{(provider, model): connector}`

* อ่านค่าที่บันทึกผ่านแคชอายุ 10 วินาที (ต้นทุนคือหนึ่งแถวจากตารางที่มีแถวเดียว
  แต่ `get_llm_connector()` ถูกเรียกหลายครั้งต่อคำขอ จึงไม่อ่านฐานทุกครั้ง)
* เส้นทางบันทึกเรียก `ai_settings.invalidate()` → **ค่าใหม่มีผลกับคำขอถัดไปทันที**
  (production รัน uvicorn กระบวนการเดียว · TTL เป็นตัวกันพลาดสำหรับการแก้ค่าในฐานโดยตรง)
* คืน **วัตถุหนึ่งตัว** ให้ผู้เรียกถือไว้ตลอดคำขอ และ **ไม่เคยแก้ไขวัตถุที่แจกไปแล้ว**
  การเปลี่ยนค่าระหว่างที่คำขออื่นกำลังทำงานจึงสร้าง connector ตัวใหม่ให้คำขอถัดไปเท่านั้น
* แคชมีเพดาน 4 ตัว (แต่ละตัวถือ httpx client ของตัวเอง และผู้ดูแลเปลี่ยนชื่อรุ่นได้ไม่จำกัดครั้ง)

### 3.5 embedding เปลี่ยนไม่ได้

`_build_ollama(chat_model)` รับได้แค่ชื่อโมเดลที่ใช้ **เขียนคำตอบ** · `embed_model` อ่านจาก `EMBED_MODEL`
ของ env เสมอ เวกเตอร์ของเอกสารทั้งคลังถูกสร้างด้วย bge-m3 ขนาด 1,024 มิติ และคอลัมน์ในฐานประกาศ
ขนาดนั้นไว้ตายตัว การเปลี่ยน `embed_model` จึงไม่ใช่การตั้งค่า แต่คือการสร้างเวกเตอร์ใหม่ทั้งคลัง
พร้อมแก้โครงสร้างตาราง — หน้าผู้ดูแลแสดงไว้ว่าเปลี่ยนไม่ได้ (`embedding.changeable = false`)

### 3.6 fallback — ต่างกันตามเจ้าที่เลือก โดยเจตนา

| เลือก | ล้มแล้วทำอะไร |
|---|---|
| **Gemini** | ตกไปใช้โมเดลในเครื่อง **เฉพาะเมื่อยังไม่ได้ส่งตัวอักษรแรกออกไป** และเฉพาะคำถามที่ยอมให้ตอบด้วยตัวสำรองได้ (พฤติกรรมเดิม ไม่เปลี่ยน) · ล้มกลางสตรีม = แจ้งข้อผิดพลาด |
| **Ollama** | **แจ้งข้อผิดพลาด ไม่ไปเรียก Gemini แทน** |

เหตุผลของแถวที่สอง: การเลือกโมเดลในเครื่องคือการเลือกไม่ส่งคำถามของผู้ใช้ออกนอกเครื่อง
ถ้าระบบแอบตกไปหาเจ้าบนคลาวด์ตอนมีปัญหา มันจะละเมิดเงื่อนไขนั้นเงียบ ๆ ในจังหวะที่ไม่มีใครดู

### 3.7 แคชคำตอบต้องผูกกับโมเดล ไม่งั้นสวิตช์ไม่มีผลกับคำถามเดิม

ตัวระบุรุ่นของแคช (`answer_cache.corpus_version`) รวม "ทุกอย่างที่เปลี่ยนคำตอบ" ไว้อยู่แล้ว —
จำนวนชิ้นเอกสาร เวลานำเข้าล่าสุด รุ่นของตรรกะ และ `CHAT_TOP_K` พร้อมคอมเมนต์ของมันเองที่
อธิบายว่าถ้าไม่รวม `CHAT_TOP_K` ไว้ *"การปรับค่านี้แล้ววัดผลจะได้คำตอบเก่าจากแคชมาแทน
แล้วสรุปว่าปรับแล้วไม่ต่างเลย ทั้งที่ยังไม่ได้ลองของใหม่สักครั้ง"*

โมเดลที่เขียนคำตอบเปลี่ยนคำตอบด้วยเหตุผลเดียวกันและชัดกว่าด้วย จึงเพิ่มเข้าไปในตัวระบุรุ่น
ถ้าไม่เพิ่ม ผู้ดูแลที่สลับไป Ollama แล้วถามคำถามที่เคยถาม จะได้คำตอบของ Gemini กลับมา
แล้วสรุปว่าสวิตช์ไม่ทำงาน — อาการเดียวกับที่ทำให้ต้องมีงานรอบนี้

ผลข้างเคียงที่ยอมรับ: แคชถูกแบ่งตามโมเดล การสลับโมเดลครั้งแรกจึงยังไม่มีแคชให้ใช้
และคำตอบเก่าของโมเดลเดิมยังอยู่ ใช้ได้ทันทีเมื่อสลับกลับ · **การ deploy ชุดนี้ทำให้แคช
ที่มีอยู่กลายเป็นของรุ่นเก่าทั้งหมดครั้งเดียว** คำถามชุดแรกหลัง deploy จะช้ากว่าปกติ
(เกิดขึ้นทุกครั้งที่รุ่นตรรกะขยับอยู่แล้ว ไม่ใช่เรื่องใหม่)

### 3.8 หลักฐานว่าโมเดลไหนตอบ — สองช่องทาง

**ก. ช่อง `answer_model` ในคำตอบของ `/chat`** (และในเหตุการณ์ `done` ของ `/chat/stream`)

เช่น `"gemini:gemini-3.5-flash-lite"` หรือ `"ollama:qwen2.5:3b"` และ **`null` เมื่อคำตอบนั้นไม่ได้เรียกโมเดลเลย**
— คำตอบจากฐานหลักสูตร คำตอบที่หยิบจากแคช ด่านถามย้อนกลับ และการปฏิเสธ

ช่องนี้จำเป็นตอนตรวจสวิตช์ เพราะคำถามที่ตอบจากแคชจะ "ผ่าน" ทุกการตั้งค่าโดยไม่เคยแตะผู้ให้บริการเลย
ถ้าดูแค่ว่า *ตอบได้หรือไม่* การทดสอบจะผ่านโดยไม่ได้พิสูจน์อะไร (ดูผลทดสอบข้อ 5 ในหัวข้อ 5.2)

ย้ำว่าเป็นตัวที่ **ถูกสั่งให้เขียน** ไม่ใช่ตัวที่เขียนสำเร็จ — เส้นทาง Gemini มีตัวสำรองรับช่วงต่อได้
กรณีนั้นค่านี้ยังเป็น `gemini` และการรับช่วงถูกบันทึกไว้ที่ตัวนับ (`fallback_local_ok`)

**ข. ตัวนับการใช้โมเดล** — เพิ่มเหตุการณ์ `local_primary_attempt` / `local_primary_ok` / `local_primary_failed`

ตัวนับเดิมรู้จักแต่เหตุการณ์ของ Gemini และของโมเดลในเครื่อง **ในฐานะตัวสำรอง** ไม่มีเหตุการณ์ใดบอกว่า
โมเดลในเครื่องถูกเลือกเป็นตัวหลัก การพิสูจน์ว่า "เลือก Ollama แล้วเรียก Ollama จริง" จึงไม่มีหลักฐานจากบัญชีของระบบเอง

งานอุ่นโมเดลเบื้องหลัง **ไม่ถูกนับ** (`warm_chat` เรียกโมเดลตรงโดยไม่ผ่านตัวนับ) เพราะมันยิงทุก 20 นาที
ไม่ว่ามีผู้ใช้หรือไม่ ถ้านับรวมจะบวกวันละ 72 ครั้งจากคำขอที่ไม่มีใครถาม แล้วสถิติจะตอบคำถาม
"ผู้ใช้ได้คำตอบจากโมเดลไหน" ผิดไปทั้งหมด

### 3.9 งานอุ่นโมเดลต้องตามสวิตช์

`_keep_models_warm()` เดิมเรียก `get_llm_connector()` **ครั้งเดียวตอนเปิดเซิร์ฟเวอร์** แล้วถือไว้ตลอด
และตัดสินว่าจะอุ่นโมเดลตอบคำถามหรือไม่จาก `settings.llm_provider` (env)
ถ้าปล่อยไว้ หลังผู้ดูแลสลับโมเดล งานนี้จะอุ่นโมเดลที่เลิกใช้แล้ว และกันตัวที่ถูกเลิกใช้ไม่ให้ถูกปิด
จึงย้ายมาขอ connector ใหม่ทุกรอบ และตัดสินจากชนิดของ connector แทนค่าใน env

### 3.10 หน้าผู้ดูแล

* เปลี่ยนจากช่องกรอกชื่อโมเดลช่องเดียว เป็น **ผู้ให้บริการ** (ใช้ค่าจากเซิร์ฟเวอร์ / Gemini / Ollama) + **ชื่อรุ่น** (เว้นว่างได้)
* กล่องบนสุดแสดง **ที่ระบบใช้ตอบอยู่จริงตอนนี้** พร้อมที่มา (ค่าที่ตั้งในหน้านี้ / ค่าตั้งต้นของเซิร์ฟเวอร์) และหมายเหตุเมื่อไม่ตรงกับที่บันทึก
* ปุ่ม **ตรวจการเชื่อมต่อ** → `POST /site-admin/ai-settings/check`
* ไม่มีช่องสำหรับ API key หรือ Base URL **โดยเจตนา** — ถ้าเก็บลงตารางนี้ คีย์จะไหลออกทาง `GET` ของเส้นทางนี้
  ไปอยู่ในเบราว์เซอร์ของทุกคนที่เป็น staff และอยู่ใน log ของ proxy ทุกชั้นที่ผ่าน
* บันทึกแล้ว **ล้างผลตรวจครั้งก่อน** เพราะผลนั้นเป็นของคู่ผู้ให้บริการ/รุ่นเดิม ใช้ยืนยันต่อไม่ได้
* ยังไม่กดตรวจ → ขึ้นข้อความว่า *"การบันทึกสำเร็จยืนยันแค่ว่าค่าถูกเก็บแล้ว ไม่ได้ยืนยันว่าผู้ให้บริการตอบคำถามจริงได้ทันเวลา"*

### 3.11 ปุ่มตรวจต้องวัดงานขนาดเท่าของจริง

การตรวจทำ **สองขั้น** และรายงานแยกกัน:

| ขั้น | ถามว่า | เพดานเวลา | พรอมต์ |
|---|---|---|---|
| `hello` | เรียกผู้ให้บริการได้ไหม | 25 วินาที | สั้น |
| `work` | ผ่าน **ด่านตรวจหลักฐาน** ทันเพดานของคำขอจริงไหม | `RAG_TIME_BUDGET_S` ชุดเดียวกับผู้ใช้ | เนื้อหาจริงจากคลังเอกสาร `CHAT_TOP_K` ชิ้น · `json_mode=True` · ไม่จำกัดความยาวผลลัพธ์ เหมือนด่านจริง |

เดิมออกแบบไว้ขั้นเดียว แล้วการทดสอบจับได้ว่า `qwen2.5:3b` ผ่านขั้นสั้นทุกครั้งในราวหนึ่งวินาที
แต่ตอบคำถามจริงไม่ได้เลย — ปุ่มตรวจจะขึ้นเขียวให้ผู้ให้บริการที่ใช้งานไม่ได้
ซึ่งเป็นการโกหกชนิดเดียวกับการขึ้นว่า "พร้อม" เพราะบันทึกสำเร็จ จึงต้องเป็นสองขั้น

เลือกวัดขั้น "ด่านตรวจหลักฐาน" เพราะวัดแล้วพบว่าเวลาที่หายไปทั้งหมดอยู่ที่ขั้นนั้น
ไม่ใช่ขั้นเขียนคำตอบ (ดูข้อ 6.2)

การตรวจ **ไม่ถูกนับในตัวนับการใช้โมเดล** (ไม่ส่ง `on_event`) เพราะการตรวจของผู้ดูแลไม่ใช่การใช้งาน
ของผู้ใช้ · แต่ยังกินโควตาของผู้ให้บริการจริง จึงแยกเป็นปุ่มของตัวเอง ไม่ยิงตอนเปิดหน้าเว็บ

**ข้อจำกัดที่เหลืออยู่และเขียนกำกับไว้แล้ว** — ผลที่ผ่านไม่ได้รับประกันว่าคำถามจริงจะทันเพดาน
ดูข้อ 6.4

คำถามทุกข้อในชุดนี้เติมรหัสสุ่มต่อท้ายเพื่อไม่ให้ซ้ำกับของเดิม ยกเว้นข้อที่ตั้งใจทดสอบแคช

### 5.3 ผ่าน API จริง ที่เพดานเวลากว้างพอให้โมเดลในเครื่องทำงานจบ — **ผ่าน 8 / 8 จุด**

`RAG_TIME_BUDGET_S=300` และ `CHAT_TOP_K=8` **เฉพาะคอนเทนเนอร์ทดสอบ** · ไฟล์เต็ม `api-checks-slow.txt`

ชุดนี้มีไว้ตอบคำถามที่ชุด 5.2 ตอบไม่ได้ — *สวิตช์ส่งงานไปถึงโมเดลในเครื่องจริงไหม*
ที่ค่าของ production โมเดลในเครื่องตายก่อนเขียนคำตอบทุกครั้ง จึงไม่มีคำตอบให้ดูเลย
**ไม่ใช่ข้อเสนอให้เปลี่ยนค่าของ production**

| หัวข้อ | ผล |
|---|---|
| S1. เลือก Ollama แล้วถามสามคำถาม | ผ่าน 1/1 — ไม่มีคำตอบใดมาจาก Gemini |
| S2. สลับ Gemini ↔ Ollama สามรอบในกระบวนการเดิม | ผ่าน 2/2 — ค่าที่ใช้จริงตามทุกรอบ |
| S3. เปลี่ยนค่าระหว่างที่คำขอหนึ่งกำลังทำงาน | ผ่าน 2/2 — **คำขอนั้นคืน `answer_model = ollama:qwen2.5:3b`** |
| S4. เวลาของด่านตรวจหลักฐานของทั้งสองเจ้า | ผ่าน 2/2 |

**S3 คือหลักฐานที่ตรงที่สุดสองเรื่องในชุดเดียว**

```
เริ่มคำขอตอนเลือก ollama ไว้  ->  สลับเป็น gemini หลังจากนั้น 8 วินาที
คำตอบที่ได้: HTTP 200 · answer_model = ollama:qwen2.5:3b
คำขอถัดไป  : answer_model = gemini:gemini-3.5-flash-lite
```

* **Ollama เขียนคำตอบให้ผู้ใช้ได้จริง และสวิตช์ส่งงานไปถึงมันจริง** — ไม่ใช่แค่ถูกเรียก
* **คำขอที่เริ่มก่อนสลับไม่ถูกเปลี่ยนเจ้ากลางทาง** ซึ่งเป็นข้อที่ *เคยตก* และนำไปสู่การแก้
  ในข้อ 5.4 ข · ก่อนแก้ ข้อเดียวกันนี้คืน `gemini:gemini-3.5-flash-lite`

**S1 รายงานเป็นตัวเลขที่วัดได้ ไม่ใช่ข้อตรวจตายตัว**

```
คำถาม 1  HTTP 503  — เกินเพดานเวลา
คำถาม 2  HTTP 200  status=not_found   — ด่านตรวจหลักฐานตัดสินว่าตอบไม่ได้
คำถาม 3  HTTP 200  status=answered    answer_model=null — ตอบจากฐานหลักสูตร ไม่ได้เรียกโมเดล
```

รวมทั้งชุด 5.3 มีคำขอที่โมเดลในเครื่องเขียนคำตอบเอง **1 จาก 4 ครั้ง** (คำถามของ S1 สามข้อ
และของ S3 หนึ่งข้อ)

"โมเดลในเครื่องเขียนคำตอบจบไหม" ขึ้นกับภาระของเครื่องและคำตัดสินของด่านตรวจหลักฐาน
ซึ่งไม่คงที่ — คำถามเดียวกันให้ผลทั้ง `answered` และ `not_found` ในการรันต่างรอบ
ตั้งเป็นข้อตรวจตายตัวไม่ได้ จึงยืนยันเฉพาะข้อที่ **สวิตช์รับผิดชอบจริง** คือ
*เลือก Ollama แล้วต้องไม่มีคำตอบใดมาจาก Gemini*

ส่วนข้อ "หนึ่งคำขอใช้เจ้าเดียวตั้งแต่ด่านตรวจหลักฐานถึงขั้นเขียนคำตอบ" ยังตรวจซ้ำแบบที่
ผลคงที่ไว้ที่ `tests/test_model_switch.py` ด้วย ซึ่งไม่เรียกโมเดลและไม่แตะฐานข้อมูลเลย

### 5.4 สิ่งที่ชุดทดสอบจับได้ และถ้าไม่รันคงหลุดไป

สามข้อนี้ผ่านการตรวจด้วยตาและผ่าน type check มาแล้วทั้งหมด แต่ผิดจริง

**ก. ชุดทดสอบเดิมแปดไฟล์หยุดทำงานเงียบ ๆ**

`get_llm_connector()` เดิมเก็บ connector ไว้ที่ตัวแปรระดับโมดูลชื่อ `_connector`
และชุดทดสอบเดิมแปดไฟล์ใช้ช่องนั้นใส่ของปลอมเข้าไป (`llm_client._connector = DEAD`)
เพื่อจำลองโมเดลล่ม หรือเพื่อยืนยันว่าเส้นทางหนึ่งไม่เรียกโมเดลเลย

รอบนี้เปลี่ยนจาก singleton ตัวเดียวมาเป็นแคชตามตัวเลือก ชื่อ `_connector` จึงหายไป
ผลคือการตั้งค่าในชุดทดสอบ **ไม่มีผลและไม่มี error ให้เห็น** ชุดทดสอบไปเรียกโมเดลจริง
แล้วตรวจผลผิดทั้งหมด:

```
test_sse_format             AttributeError: ... has no attribute '_connector'
test_chatweb_stream_budget  AttributeError: ... has no attribute '_connector'
test_model_outage_n1        ตก 6 จุด — ได้คำตอบจริงมาแทนข้อความบริการขัดข้องที่มันตรวจ
```

สองไฟล์แรกล้มดัง ๆ แต่ `test_model_outage_n1` **ล้มแบบเงียบกว่า** คือรันผ่านจนจบแล้ว
รายงานว่าตก ซึ่งถ้าไม่ได้อ่านเหตุผลจะคิดว่าโค้ดใหม่ทำให้ระบบไม่แจ้งสถานะขัดข้อง
ทั้งที่ของจริงคือชุดทดสอบใส่ของปลอมไม่สำเร็จ

แก้โดยคืนชื่อ `_connector` ไว้เป็น **ช่องให้ชุดทดสอบใส่ของปลอม** (production ปล่อยเป็น
`None` เสมอ) พร้อมคอมเมนต์กำกับว่าห้ามตัดทิ้ง เพราะการตัดทิ้งไม่ทำให้อะไรพังทันที

**ข. คำขอเดียวใช้สองผู้ให้บริการได้ — เจอจากข้อตรวจที่ตั้งใจตรวจเรื่องอื่น**

ข้อตรวจ "เปลี่ยนค่าระหว่างที่คำขอหนึ่งกำลังทำงาน" ตก โดยรายงานว่าคำขอที่เริ่มตอนเลือก
Ollama ไว้ กลับคืน `answer_model = gemini:gemini-3.5-flash-lite`

สาเหตุ: `get_llm_connector()` ถูกเรียก **สองรอบ** ในหนึ่งคำขอ — `prepare_answer()`
เรียกครั้งหนึ่งแล้วส่งต่อให้ทุกขั้นที่ใช้โมเดลภายในตัวมันเอง (เขียนคำถามใหม่ ·
ด่านตรวจขอบเขต · ด่านตรวจหลักฐาน) แล้วขั้นเขียนคำตอบเรียกใหม่อีกครั้ง
ระหว่างสองรอบนั้นผู้ดูแลเปลี่ยนค่าได้

ผลคือคำขอเดียวใช้ Ollama ตรวจหลักฐาน แล้วใช้ Gemini เขียนคำตอบ ซึ่งแย่กว่าที่ฟังดู
เพราะด่านที่ตัดสินว่า "เอกสารตอบคำถามนี้ได้" กับตัวที่เขียนคำตอบเป็นคนละเจ้า
คำตอบจึงถูกเขียนบนคำตัดสินของโมเดลอื่น

แก้โดยให้ `Prepared` พา connector ที่ใช้ไปด้วย แล้วขั้นเขียนคำตอบใช้ตัวเดียวกันนั้น
(`p.connector or get_llm_connector()`) · เส้นทางที่ตอบด้วยข้อความสำเร็จรูปไม่มีขั้น
เขียนคำตอบ ค่านี้จึงเป็น `None` ได้โดยไม่มีใครใช้

**ค. ปุ่มตรวจเกือบกลายเป็นปุ่มที่โกหก**

ออกแบบไว้ตอนแรกเป็นขั้นเดียวด้วยพรอมต์สั้น · `qwen2.5:3b` ผ่านทุกครั้งในไม่ถึงหนึ่งวินาที
ขณะที่คำถามจริงล้มทุกครั้ง · ถ้าปล่อยไว้ ผู้ดูแลจะกดตรวจแล้วเห็นเขียว เลือก Ollama
แล้วแชตทั้งระบบพัง · แก้เป็นสองขั้นแล้ว (ข้อ 3.11) และยังเขียนข้อจำกัดที่เหลือไว้ด้วย (ข้อ 6.4)

## 6. ข้อจำกัดที่วัดได้ — Ollama กับเพดานเวลา 30 วินาที

### 6.1 อาการ

เลือก Ollama ที่การตั้งค่าของ production (เพดาน 30 วินาที · `CHAT_TOP_K=25`) แล้วถามคำถามที่ต้อง
อ้างอิงเอกสาร **สำเร็จ 0 จาก 3 ครั้ง** ทุกครั้งได้ HTTP 503 พร้อมข้อความ
*"ระบบใช้เวลาตอบนานเกินเพดานที่ตั้งไว้ จึงหยุดรอครับ"*

สองอย่างที่ต้องแยกให้ชัด:

* คำขอ **ไม่ได้ถูกส่งไป Gemini แทน** — ข้อความผิดพลาดเป็นของเพดานเวลา และตัวนับฝั่งฐานทดสอบ
  ขึ้น `local_primary_*` ไม่ขึ้น `gemini_ok` เพิ่ม · สวิตช์ทำงานถูก
* สิ่งที่ล้มคือ **ความเร็วของโมเดล** ไม่ใช่ตัวสวิตช์

### 6.2 สาเหตุ — ด่านตรวจหลักฐาน ไม่ใช่ขั้นเขียนคำตอบ

บรรทัด timing ของคำขอที่ล้มชี้ตรงไปที่ขั้นเดียว:

```
timing /chat total=30141ms prepare=29938ms | ... decide=29545ms | outcome=ล้ม:LLMBudgetExceeded
                                                 ^^^^^^^^^^^^^^
```

`decide` คือด่านตรวจหลักฐาน (`_grounding_verdict`) ที่ถามโมเดลว่า *"เนื้อหาที่ค้นเจอตอบคำถามนี้ได้จริงไหม"*
มันกินเวลาเกือบทั้งเพดาน คำขอจึงตายก่อนถึงขั้นเขียนคำตอบ — `write_answer` ไม่ได้เริ่มเลย

การเรียกของด่านนี้ส่ง `json_mode=True` และ **ไม่ส่ง `num_predict`** คือไม่จำกัดความยาวผลลัพธ์
Gemini จบเร็วเพราะเขียนสั้น แต่โมเดลในเครื่องเขียนยาวได้ไม่จำกัด และเครื่องนี้
**ไม่มีการ์ดจอ** (`ollama ps` รายงาน `100% CPU`) จึงช้ากว่ามาก

### 6.3 ขนาดพรอมต์เป็นตัวกำหนด ไม่ใช่ตัวโมเดลเพียว ๆ

วัดด้วยเนื้อหาจริงจากคลังเอกสาร ที่จำนวนชิ้นต่างกัน (28 ต.ค. 2569 · วัดครั้งละหนึ่งรอบ)
ตาราง ก. คือเวลาของ **ด่านตรวจหลักฐานขั้นเดียว** · ตาราง ข. คือคำขอจริงทั้งคำขอ

**ก. ด่านตรวจหลักฐานขั้นเดียว วัดผ่านปุ่มตรวจด้วยเนื้อหาจากคลัง** — เทียบสองเจ้าตรง ๆ

| ขนาดพรอมต์ | Ollama `qwen2.5:3b` | Gemini `gemini-3.5-flash-lite` | ต่างกัน |
|---|---|---|---|
| 18,178 ตัวอักษร *(`CHAT_TOP_K=25` — ค่าของ production)* | **29,936 ms ถูกเพดาน 30 วินาทีตัด**<br>(160,135 ms เมื่อให้เพดาน 300 วินาที) | 1,745 ms | **92 เท่า** |
| 8,588 ตัวอักษร *(`CHAT_TOP_K=12`)* | 6,823 ms | ไม่ได้วัด | — |
| 6,233 ตัวอักษร *(`CHAT_TOP_K=8`)* | 14,675 ms | 1,264 ms | 11.6 เท่า |
| 2,541 ตัวอักษร *(`CHAT_TOP_K=4`)* | 6,156 ms | 3,336 ms | 1.8 เท่า |

**ข. คำขอจริงทั้งคำขอ ผ่าน `POST /chat` เมื่อเลือก Ollama**

| `CHAT_TOP_K` | ด่านตรวจหลักฐาน | ขั้นเขียนคำตอบ | รวมทั้งคำขอ | ผลที่ผู้ใช้ได้ |
|---|---|---|---|---|
| **25** *(ค่าของ production)* | 232,795 ms | ไม่ได้เริ่ม | 233,059 ms | `not_found` — ด่านตัดสินว่าตอบไม่ได้ |
| 12 | 100,815 ms | 160,209 ms | **261,304 ms** | ตอบได้ · `answer_model = ollama:qwen2.5:3b` |
| 8 | 60,003 ms | 70,099 ms | **130,367 ms** | ตอบได้ |

สามข้อที่อ่านได้จากสองตารางนี้:

**ก. โมเดลในเครื่องเขียนคำตอบได้จริง และสวิตช์ส่งงานไปถึงมันจริง** — แถว `CHAT_TOP_K=12`
คือคำขอที่เดินครบทุกขั้นแล้วคืน `answer_model = ollama:qwen2.5:3b` พร้อมเนื้อหาคำตอบ
และยืนยันซ้ำที่ข้อ S3 ของหัวข้อ 5.3 · นี่เป็นหลักฐานตรงที่สุดว่าขั้นเขียนคำตอบ
ถูกส่งไปที่ผู้ให้บริการที่เลือกไว้

**ข. แต่เร็วไม่พอกับเพดาน 30 วินาที ในทุกค่าที่ยังได้คำตอบ** — ค่าที่ถูกสุดที่ยังตอบได้คือ
`CHAT_TOP_K=8` ซึ่งใช้ 130 วินาที หรือราว **4.3 เท่าของเพดาน** · เครื่องนี้ไม่มีการ์ดจอ
(`ollama ps` รายงาน `100% CPU`) จึงไม่ใช่เรื่องที่ปรับค่าตั้งค่าแล้วหาย

**ค. ที่ค่าของ production มีปัญหาสองชั้นซ้อนกัน ไม่ใช่ชั้นเดียว** — นอกจากช้าเกินเพดาน
ด่านตรวจหลักฐานของโมเดลในเครื่องยัง **ตัดสินว่า "ตอบไม่ได้"** กับคำถามที่ Gemini ตอบได้
จากเนื้อหาชุดเดียวกัน ถึงให้เวลา 300 วินาทีก็ยังได้ `not_found`
การขยายเพดานเวลาอย่างเดียวจึงไม่ทำให้ Ollama ใช้งานได้ที่ `CHAT_TOP_K=25`

### 6.4 ปุ่มตรวจเป็นสัญญาณ ไม่ใช่การรับประกัน

ตาราง ก. กับ ข. ข้างบนคือการเรียกแบบเดียวกัน แต่ตัวเลขต่างกันมาก —
ที่ `CHAT_TOP_K=12` ต่างกันราว 15 เท่า (6.8 วินาที เทียบกับ 101 วินาที)

สาเหตุ: เนื้อหาที่ปุ่มตรวจส่งเข้าไปหยิบจากคลังตามลำดับ `id` ไม่ใช่ชิ้นที่การค้นเลือกให้คำถามจริง
และด่านนี้ไม่จำกัดความยาวผลลัพธ์ ความยาวที่โมเดลเขียนจึงแปรไปตามเนื้อหาที่ได้รับ
(ที่ `CHAT_TOP_K=8` ก็ต่างกัน 14,675 ms เทียบกับ 60,003 ms คือราว 4 เท่า)

จึงเขียนข้อจำกัดนี้ไว้ทั้งในโค้ด (`services/llm_client.py::probe`) และบนหน้าผู้ดูแล
(*"เป็นการวัดด้วยเนื้อหาตัวอย่าง คำถามจริงอาจใช้เวลามากกว่านี้"*)

**ผลตรวจที่ไม่ผ่าน เชื่อถือได้ว่าใช้งานไม่ได้จริง · ผลตรวจที่ผ่าน ไม่ได้ยืนยันว่าคำถามจริงทุกข้อจะทันเพดาน**
ถ้าไม่เขียนไว้ ปุ่มที่ขึ้นเขียวจะถูกอ่านว่า "ใช้งานได้แน่" ซึ่งเป็นความผิดพลาดชนิดเดียวกับที่
ปุ่มนี้ตั้งใจจะกันตั้งแต่แรก


### 6.5 ที่เพดานกว้างมาก Ollama ก็ยังตอบคำถามเอกสารไม่ได้ที่ `CHAT_TOP_K=25`

ลองขยายเพดานเป็น 300 วินาทีเพื่อแยกเรื่องเวลาออกจากเรื่องคุณภาพ:

| คำถาม | เวลา | ผล |
|---|---|---|
| หลักสูตรวิทยาการคอมพิวเตอร์เรียนเกี่ยวกับอะไร | 233.1 วินาที | `not_found` |
| หลักสูตรวิทยาการคอมพิวเตอร์มีวิชาอะไรบ้าง | 248.9 วินาที | `not_found` |
| คุณสมบัติผู้สมัครของหลักสูตรวิทยาการคอมพิวเตอร์คืออะไร | 0.0 วินาที | `answered` — ตอบจากฐานหลักสูตร ไม่ได้เรียกโมเดล |

สองข้อแรก **ด่านตรวจหลักฐานของโมเดลในเครื่องตัดสินว่า "ตอบไม่ได้"** ผู้ใช้จึงได้ข้อความสำเร็จรูป
*"ไม่พบข้อมูลนี้ในเอกสารหลักสูตร"* ทั้งที่ Gemini ตอบคำถามเดียวกันได้จากเนื้อหาชุดเดียวกัน
แปลว่าที่ `CHAT_TOP_K=25` โมเดลในเครื่องมีปัญหาสองชั้นซ้อนกัน — ช้าเกินเพดาน และตัดสินผิด

ข้อที่สามเป็นตัวอย่างที่ดีของช่อง `answer_model`: ตอบสำเร็จใน 0.0 วินาทีโดย `answer_model = null`
เพราะมาจากฐานหลักสูตร ไม่ได้เรียกโมเดลเลย — ถ้าวัดด้วย *"ตอบได้หรือไม่"* คำถามนี้จะทำให้สรุปว่า
Ollama ใช้งานได้ ทั้งที่ Ollama ไม่ได้เกี่ยวข้องกับคำตอบนั้นเลย

### 6.6 สิ่งที่ทำไปแล้วเพื่อไม่ให้ผู้ดูแลถูกหลอก

ปุ่มตรวจการเชื่อมต่อแยกสองขั้น และ **ผลรวมไม่ขึ้นเขียวถ้าขั้นที่สองไม่ผ่าน**
เดิมออกแบบไว้ขั้นเดียวด้วยพรอมต์สั้น ซึ่ง `qwen2.5:3b` ผ่านทุกครั้งในไม่ถึงหนึ่งวินาที
ถ้าปล่อยไว้แบบนั้น ผู้ดูแลจะกดตรวจแล้วเห็นเขียว เลือก Ollama แล้วแชตทั้งระบบพัง

ขั้นที่สองจึงเรียกแบบเดียวกับด่านตรวจหลักฐาน — พรอมต์ชุดเดียวกัน เนื้อหาจริงจากคลัง
เท่าจำนวนชิ้นที่ใช้ตอบ `json_mode=True` ไม่จำกัดความยาวผลลัพธ์ และเพดานเวลาชุดเดียวกับ
คำขอของผู้ใช้ · ยังไม่ใช่ของจริงทั้งหมด ด้วยเหตุผลในข้อ 6.4

### 6.7 ไม่ได้แก้อะไรเพื่อให้ตัวเลขดูดีขึ้น

สามทางที่จะทำให้ Ollama ดูใช้งานได้ และเหตุผลที่ไม่ทำในรอบนี้:

| ทางเลือก | ทำไมไม่ทำ |
|---|---|
| ขยาย `RAG_TIME_BUDGET_S` ของ production | โจทย์กำหนดว่า *"รักษาเพดานเวลา...เดิม"* และเพดานนี้มีเหตุผลของตัวเอง (คำขอหนึ่งเคยใช้ 408 วินาทีจนฝั่งหน้าเว็บตัดการเชื่อมต่อ) |
| ใส่ `num_predict` ให้ด่านตรวจหลักฐาน | ด่านนี้ให้โมเดล **เขียนเหตุผลก่อนตัดสิน** ถ้าตัดสั้นเกินไป ผลลัพธ์จะขาดก่อนถึงคีย์ `can_answer` แล้ว JSON พัง · โค้ดเดิมดักไว้ว่าอ่านผลไม่ได้ให้ถือว่า "ตอบได้" ด่านจึงกลายเป็นด่านที่ผ่านทุกครั้งเงียบ ๆ ซึ่งละเมิด *"ข้อกำหนดตรวจหลักฐานเดิม"* · ต้องวัดคุณภาพของคำตัดสินซ้ำหลายรอบก่อน จึงเป็นงานของตัวเอง |
| ลด `CHAT_TOP_K` ของ production | เปลี่ยนคำตอบของทุกคำถามและทุกผู้ให้บริการ ไม่ใช่แค่ของ Ollama · `answer_cache.py` บันทึกไว้เองว่า *"คำถามที่ k=8 ตอบไม่ได้ กลับตอบได้ที่ k=25"* การลดค่าจึงต้องวัดคุณภาพคำตอบทั้งชุดก่อน |

ทั้งสามทางเป็นงานที่ควรทำแยกและวัดผลของตัวเอง รอบนี้จึงรายงานตัวเลขตามที่วัดได้
และทำให้หน้าผู้ดูแลบอกความจริง

## 7. แผน deploy และ rollback

ชุดอยู่ที่ `docs/raw/model-switch-2569-10-28/` · อัปขึ้นเซิร์ฟเวอร์ที่
`/home/ubuntu/switch-release-2569-10-28/` แล้วรันตามลำดับ **ฐาน → backend → หน้าเว็บ**

| ขั้น | สคริปต์ | แตะอะไร | ย้อนด้วย |
|---|---|---|---|
| 1 | `./deploy_db.sh` | `web.ai_settings` เพิ่มคอลัมน์ `provider` (DDL ล้วน) | `./rollback_db.sh` |
| 2 | `./deploy_backend.sh` | อิมเมจ backend เท่านั้น (`--no-deps`) | `./rollback_backend.sh` |
| 3 | `./deploy_web.sh` | ไฟล์ static ของหน้าเว็บ | `./rollback_web.sh --run <โฟลเดอร์ผล>` |

**ทำไมเรียงลำดับนี้**

* ฐานต้องมาก่อน backend เพราะโค้ดใหม่อ่านคอลัมน์ `provider`
  (ถ้า backend ขึ้นก่อน ระบบยังตอบคำถามได้ปกติเพราะ `resolve()` ดักข้อผิดพลาดแล้วถอยไปใช้ env
  แต่จะมีบรรทัดเตือนใน log ทุก 10 วินาที)
* หน้าเว็บต้องมาท้ายสุด เพราะหน้ารุ่นใหม่ส่งช่อง `provider` และเรียก `/ai-settings/check`
  ที่โค้ดเก่าไม่มี · ถ้าขึ้นก่อน หน้าตั้งค่า AI จะใช้ไม่ได้ในช่วงนั้น

**ด่านที่สคริปต์หยุดเอง**

* `deploy_db.sh` — เทียบลายนิ้วมือของแถวก่อน/หลัง ถ้าข้อมูลเปลี่ยนให้ถือว่าล้ม · สำรองตารางไว้ก่อนแก้
* `deploy_backend.sh` — ตรวจว่า migration ลงแล้ว · อิมเมจฐานต้องเป็นตัวที่รันอยู่จริง ·
  ตรวจ hash ของไฟล์ทั้ง 9 ทั้งในอิมเมจและในคอนเทนเนอร์ที่รันจริงเทียบกับค่าที่คาด ·
  รันชุดทดสอบ 7 ไฟล์ในอิมเมจใหม่ก่อนสลับ production · dry-run ตรวจว่าไม่แตะ postgres/ollama/caddy/frontend/webapi ·
  **หยุดเมื่อ health ไม่ใช่ 200** แทนการพิมพ์ว่าสำเร็จต่อ
* `deploy_web.sh` — ตรวจ bundle เดิมที่ rollback ต้องใช้ · วาง assets ให้ครบและตรวจด้วย hash
  ของไฟล์ที่ **เว็บเสิร์ฟจริง** ก่อน แล้วค่อยสลับ `index.html` เป็นขั้นสุดท้าย

**การย้อนไม่ทำลายอะไร** — ย้อน backend แล้วไม่จำเป็นต้องย้อนฐาน เพราะคอลัมน์ `provider`
เป็นคอลัมน์ที่โค้ดเก่าไม่รู้จัก มันอยู่เฉย ๆ ได้ · ข้อมูลใน `model/updated_by/updated_at`
ไม่ถูกแตะทั้งตอน deploy และตอนย้อน

**หลัง deploy ค่าที่ระบบใช้ตอบยังเป็นค่าจาก env เหมือนเดิม** (เพราะ `provider` ยัง NULL)
การเปลี่ยนโมเดลที่ตอบจริงเป็นการกระทำของผู้ดูแลที่หน้าเว็บ ไม่ใช่ผลข้างเคียงของการ deploy

**ผลข้างเคียงที่คาดไว้แล้วหนึ่งอย่าง** — แคชคำตอบที่มีอยู่กลายเป็นของรุ่นเก่าทั้งหมด
ครั้งเดียวตอน deploy เพราะตัวระบุรุ่นของแคชรวมชื่อโมเดลเข้าไปด้วย (ข้อ 3.7)
คำถามชุดแรกหลัง deploy จะช้ากว่าปกติ · เกิดขึ้นทุกครั้งที่รุ่นตรรกะขยับอยู่แล้ว ไม่ใช่เรื่องใหม่

## 8. สิ่งที่ยังยืนยันไม่ได้ และงานที่แยกออกไป

* **ยังไม่ได้ทดสอบบน production** — ทุกผลในรายงานนี้มาจากฐาน `course_advisor_test`
* **ตัวเลขของ Ollama วัดบนเครื่องนี้เท่านั้น** เครื่องนี้ไม่มีการ์ดจอ (`100% CPU`)
  เครื่องที่มีการ์ดจอจะได้ผลต่างออกไปมาก · ตัวเลขทุกตัวในหัวข้อ 6 เป็นค่าที่วัดได้
  ในวันที่ 28 ต.ค. 2569 ไม่ใช่การรับประกัน
* **คำตัดสินของด่านตรวจหลักฐานไม่คงที่** คำถามเดียวกันที่ `CHAT_TOP_K=8` ให้ผลทั้ง
  `answered` และ `not_found` ในการรันต่างรอบ · ตัวเลขทุกตัวที่เกี่ยวกับ "ตอบได้หรือไม่"
  ของโมเดลในเครื่องจึงต้องอ่านเป็น **อัตราจากจำนวนครั้งที่วัด** ไม่ใช่พฤติกรรมที่รับประกัน
  และจำนวนครั้งที่วัดในรายงานนี้ยังน้อย (3 ครั้งต่อการตั้งค่า)
* **ตัวนับของ Ollama เป็นหลักฐานประกอบ ไม่ใช่หลักฐานเดี่ยว** — คอนเทนเนอร์ ollama ใช้ร่วมกับ
  production คำขอของผู้ใช้จริงที่เกิดระหว่างทดสอบจะปนอยู่ใน log ของมัน
  หลักฐานหลักคือตัวนับในฐาน `course_advisor_test` ซึ่งแยกจาก production และช่อง `answer_model` ของแต่ละคำตอบ
* **พบปัญหาที่มีอยู่ก่อนรอบนี้ ไม่ได้แก้ในรอบนี้:** ตัวนับของ production วันที่ 28 ต.ค. แสดง
  `fallback_local_attempt = 10` และ `fallback_local_failed = 10` — ตัวสำรองในเครื่องถูกเรียก 10 ครั้ง
  และ **ล้มทั้ง 10 ครั้ง** ด้วยสาเหตุเดียวกับหัวข้อ 6 แปลว่าผู้ใช้ที่เจอ Gemini ล่มจะไม่ได้คำตอบเลย
  ทั้งที่ระบบออกแบบไว้ว่าจะมีตัวสำรองรับช่วง · เป็นเรื่องของเพดานเวลากับความเร็วของโมเดล
  ไม่เกี่ยวกับสวิตช์ และควรแยกเป็นงานของตัวเอง

### งานถัดไปที่เสนอ (ยังไม่ลงมือ)

เรียงตามลำดับที่ควรทำ ทั้งสามข้อต้องวัดผลของตัวเองก่อนสรุป

1. **ตัวสำรองในเครื่องล้มทุกครั้งใน production** — ปัญหาที่มีอยู่ก่อนรอบนี้ (ย่อหน้าข้างบน)
   กระทบผู้ใช้จริงอยู่ตอนนี้ ไม่ต้องรอสวิตช์ · ต้นเหตุเดียวกับหัวข้อ 6
2. **จำกัดความยาวผลลัพธ์ของด่านตรวจหลักฐาน** — ด่านนี้ไม่ส่ง `num_predict` เลย
   ต้องหาเพดานที่ยังได้ JSON ครบ (มี `can_answer`) และวัด **คุณภาพของคำตัดสินซ้ำหลายรอบ**
   เพราะอ่านผลไม่ได้ = ถือว่า "ตอบได้" ซึ่งทำให้ด่านกลายเป็นด่านที่ผ่านทุกครั้งเงียบ ๆ
3. **ถ้าอาจารย์ต้องการสาธิตโมเดลในเครื่องจริง** — คันโยกคือ `CHAT_TOP_K` (ดูหัวข้อ 6.3)
   แต่ `answer_cache.py` บันทึกไว้เองว่า *"คำถามที่ k=8 ตอบไม่ได้ กลับตอบได้ที่ k=25"*
   การลดค่าจึงต้องวัดคุณภาพคำตอบทั้งชุดก่อน · ทางที่ตรงกว่าคือเครื่องที่มีการ์ดจอ
