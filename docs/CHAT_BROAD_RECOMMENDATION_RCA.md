## 1. Browser / conversation context

**1.1 Browser ใหม่เริ่มบทสนทนาใหม่หรือไม่ — ใช่**
`ChatAdvisor.jsx:16` เก็บบทสนทนาไว้ใน React state (`useState([])`) เท่านั้น ไม่มี `localStorage`, `sessionStorage`, cookie หรือ conversation id ใด ๆ เปิดแท็บใหม่หรือ browser ใหม่ = `messages` ว่าง

**1.2 context ถูกส่งไป backend อย่างไร**
`ChatAdvisor.jsx:39–51` ส่ง `{messages: [...ประวัติทั้งหมด, ข้อความล่าสุด]}` ไปที่ `POST /api/chat` → Caddy rewrite เป็น `/chat-web` → `web_compat.py:100–118` หยิบข้อความ user ตัวสุดท้ายเป็นคำถาม ที่เหลือเป็น `prior` แล้วเรียก `stream_answer(..., session_id=None, prior=prior)` · `chat.py:1061` ใช้ `prior[-HISTORY_LIMIT:]` ไม่มี session ฝั่ง server (`session_id=None` เสมอ)

**1.3 previous messages มีผลหรือไม่ — มี แต่ไม่เกี่ยวกับเคสนี้**
เมื่อมี history จะมีผลกับ: cache (ใช้แคชเฉพาะตอน `not history`, `chat.py:1072`), การจับคำตอบต่อยอด `_refinement_of_recommendation` (`chat.py:1131`), การแทนคำอ้างอิง `_context_programme` / `_resolve_reference`, `swap_follow_up`, และขั้นเขียนคำถามใหม่

**1.4 มีหลักฐานว่าสอง browser ใช้ context ต่างกันไหม — มี และหลักฐานบอกว่า "ไม่ต่างกัน"**

## 2. Intent / routing

**2.1 route จริง** — เส้นทาง "แนะนำสาขา" ของแชท ไม่ใช่ RAG ปกติ
ลำดับใน `prepare_answer` (`chat.py`): แคช (1072) → คำถามรายชื่อสาขา (1102) → ค่าเทอม (1123) → คำตอบต่อยอด (1131) → **`_recommendation_intent` + `_recommendation_reply` (1147–1163)** → …
`_recommendation_intent` (`chat.py:488`) ให้ LLM ตัดสินว่าเป็นการขอคำแนะนำหรือไม่ (`temperature=0.0`, `json_mode`) โดยมีด่านที่ไม่ใช้โมเดลกันไว้ก่อน (คำอ้างอิง `สาขานี้`, คำถามข้อเท็จจริงที่เอ่ยชื่อสาขา) คำตอบที่ผู้ใช้ได้รับในทั้ง 5 แถวเป็นรูปแบบของ `_recommendation_reply` จึงยืนยันว่าเข้าเส้นทางนี้จริง

**2.2 Structured Answers เกี่ยวข้องหรือไม่ — ไม่**
`servable_answer` รับเฉพาะ route `structured` + field ใน allow-list (`total_credits, edition_year, careers, objectives`) log บันทึก `structured_status = not_applicable` ทุกแถว

**2.3 มี deterministic recommendation logic ก่อน LLM หรือไม่ — มี**
`program_match.match_programs` ให้คะแนนทุกหลักสูตรด้วยเวกเตอร์ (SQL `score_all_programs` + คะแนนชื่อสาขา) เรียงลำดับ คัดเฉพาะปริญญาตรีที่ยังเปิดรับ ยุบฉบับซ้ำ แล้ว `_close_to_best` — ทั้งหมดนี้ไม่มีการสุ่มและไม่ผ่าน LLM

**2.4 มี rewrite ก่อน retrieval หรือไม่ — มี 2 จุด แต่คนละแบบ**
- ในเส้นทางนี้: `_recommendation_intent` ให้ LLM คัด "ส่วนที่บอกความสนใจ" ออกจากข้อความ (`interest`) และโค้ดบังคับว่า `interest` ต้องเป็น substring ของข้อความเดิม ไม่งั้นใช้ข้อความเต็มแทน (`chat.py:544–548`) จากนั้น `program_match._interest_of` ตัดคำนำหน้าอย่าง "สาขาไหนเหมาะกับคน" ออกด้วย regex (deterministic)
  → ขั้น LLM นี้ **อาจไม่ deterministic** แต่ผลลัพธ์ถูกบีบให้เป็นข้อความย่อยของคำถามเดิมเสมอ
- ขั้นเขียนคำถามใหม่จาก history (`condense`) ไม่ทำงานเมื่อไม่มี history

## 3. Retrieval (ของเส้นทางแนะนำสาขา)

**3.1 คำถามเดียวกัน retrieve ต่างกันได้ไหม — ไม่ ถ้าข้อความ query เหมือนกัน**
เส้นทางนี้ไม่ได้ใช้ vector search แบบ top-k ทั่วคลัง แต่ใช้ `score_all_programs` ซึ่งคำนวณให้ทุกหลักสูตร

**3.2 embedding deterministic — ใช่ (หลักฐานเชิงประจักษ์)** `bge-m3` บน Ollama · ผลทดสอบที่บันทึกไว้ (`eval/result_match_26.json` เทียบ `eval/match_result.json` คนละวัน) ให้เปอร์เซ็นต์ตรงกัน 26/26 โปรไฟล์

**3.3 vector search deterministic หรือ approximate — deterministic สำหรับเส้นทางนี้**
`score_all_programs` ใช้ `row_number() OVER (PARTITION BY course_id ORDER BY distance)` ซึ่ง index `ivfflat` แบบประมาณค่าใช้ไม่ได้ จึงสแกนครบทุก chunk (วิเคราะห์จากโค้ด ยังไม่ได้รัน EXPLAIN)
*หมายเหตุ:* เส้นทาง RAG ปกติ (`vector_search`, `CHAT_TOP_K=25`) ใช้ index นี้และเป็น approximate ได้ แต่ไม่ใช่เส้นทางของคำถามนี้

**3.4 tie handling** — `ORDER BY score DESC` ไม่มี tiebreaker รอง ถ้าคะแนนเท่ากันเป๊ะลำดับอาจสลับได้ตามลำดับที่ Postgres คืนมา · ในเคสนี้คะแนนสามสาขาไม่เท่ากัน (§4) จึงไม่ใช่สาเหตุ

**3.5 / 3.6 Top-K** — `CHUNKS_PER_COURSE = 5` เป็น **top-5 ต่อหลักสูตร** (ไม่ใช่ top-k รวมทั้งคลัง) แล้วเฉลี่ยเป็นคะแนนของหลักสูตรนั้น · หลักฐานที่ส่งให้ Gemini ใช้ `_EVIDENCE_CHUNKS = 4` ชิ้นต่อหลักสูตร + แก่นหลักสูตร (อาชีพ/วัตถุประสงค์) รวมไม่เกิน `_EVIDENCE_CHARS = 3000` ตัวอักษร

**3.7 หลักสูตรที่ไม่มี chunk ติด top-k จะถูกมองเห็นไหม** — คำถามนี้ไม่เกิดกับเส้นทางแนะนำ เพราะทุกหลักสูตรถูกให้คะแนนเสมอ แต่หลักสูตรที่ **ไม่ติด 3 อันดับแรกหลังกรอง** จะไม่ถูกส่งให้ Gemini เลย (§4)

## 4. ความครบถ้วนของคำแนะนำแบบกว้าง

**4.1 evaluate ครบทุกหลักสูตรที่เปิดรับหรือไม่ — ครบในขั้นให้คะแนน**
`score_all_programs` ให้คะแนนทุก `courses.is_active` ที่ไม่ใช่ปริญญาโท/เอก แล้ว `match_programs` กรองด้วย `is_offered()` (12 หลักสูตรใน `programs_offered.json`) และยุบฉบับซ้ำ

**4.2 แต่สิ่งที่ส่งต่อไปให้ Gemini ไม่ครบ** — ถูกตัดสองชั้นก่อนถึง LLM
1. `_close_to_best`: เก็บเฉพาะหลักสูตรที่คะแนน ≥ (คะแนนอันดับ 1 − `_RELEVANCE_MARGIN 0.04`)
2. `limit=3` (hard cap ใน `chat.py:846`)

**4.3 / 4.4 มี candidate selection ก่อน LLM หรือไม่ — มี และ deterministic**
`backend/app/services/program_match.py` → `match_programs()`
- คะแนน = `0.5 × ค่าเฉลี่ย cosine ของ 5 chunk ที่ใกล้ที่สุด + 0.5 × cosine กับชื่อสาขา`
- เรียงคะแนน → กรองปริญญาตรี/เปิดรับ → ยุบฉบับซ้ำ → `_close_to_best` (margin 0.04) → ตัดเหลือ 3
- ไม่มีการสุ่ม (ข้อยกเว้นเดียวคือ `interest` ที่ LLM คัดมา ซึ่งถูกบังคับให้เป็นข้อความย่อยของคำถามเดิม)

**ค่าที่วัดไว้แล้วในโค้ดสำหรับคำถามนี้โดยตรง** (`program_match.py` หมายเหตุของ `_RELEVANCE_MARGIN`)
```
"ชอบทำงานกับคอมพิวเตอร์"  วิทยาการคอมพิวเตอร์ .561  แอนิเมชัน .542  เทคโนโลยีสารสนเทศ .528
                           แล้วตกไปที่คณิตศาสตร์ .480
```
เกณฑ์ margin: .561 − .04 = .521 → candidate set = **{CS, Animation, IT}** ทั้งสามผ่าน ส่วนคณิตศาสตร์ (.480) ตกไป

**4.5 ถ้ามี candidate selection แล้ว Gemini ยังเลือกได้อีกไหม — ได้ และนี่คือจุดที่ผลไม่นิ่ง**
`_recommendation_reply` (`chat.py:867`)
```python
supported = [m for m in matches if m.rationale.strip() and NO_EVIDENCE_MARKER not in m.rationale][:3]
```
หลักสูตรใดที่ Gemini เขียนเหตุผลไม่ได้ (คีย์ไม่ตรง/ตอบไม่ครบ) หรือตอบว่า `[[ไม่มีข้อมูลรองรับ]]` **จะถูกตัดออกจากรายการที่ผู้ใช้เห็น** ทั้งที่อันดับและคะแนนยังถูกต้อง

**4.6 hard limit — มี**: `limit=3` ใน `chat.py:846` และ `[:3]` ที่บรรทัด 867 (หน้าแบบสอบถามใช้คนละค่า: `/recommend-major` ใช้ 10 แล้วแสดง 1 + 2)

**4.7 prompt สั่งจำกัดจำนวนหรือไม่ — ไม่สั่งจำนวน แต่สั่งให้ตัดออกได้**
`MATCH_RATIONALE_SYSTEM_PROMPT` (`llm/prompts.py:487`) บอกว่า "เขียนเหตุผลให้ครบทุกหลักสูตรที่ให้มา ห้ามข้าม" และ "ห้ามจัดอันดับใหม่" แต่มีกฎ "แก่นของหลักสูตร": ถ้าเรื่องที่นักเรียนสนใจปรากฏในฐานะ *เครื่องมือ / รายวิชาเดียว / วิชาศึกษาทั่วไป* ให้ตอบ `[[ไม่มีข้อมูลรองรับ]]` — กฎนี้เองคือสิ่งที่ทำให้บางสาขาหายไปจากคำตอบ

**4.8 ถ้า CS, IT, Animation ต่างมีหลักฐาน ระบบตรวจครบไหม — ตรวจครบเฉพาะขั้นคะแนน** ทั้งสามเข้ามาถึง Gemini ทุกครั้ง แต่การจะได้แสดงผลขึ้นกับว่ารอบนั้น Gemini เขียนเหตุผลให้หรือไม่

**4.9 รับประกันได้ไหมว่ารายชื่อที่ตอบคือ "ทุกสาขาที่เกี่ยวข้อง" — ไม่ได้** ด้วยสามเหตุผล: margin 0.04, cap 3 รายการ และการคัดออกโดย Gemini ที่ไม่นิ่ง

## 5. บทบาทของ Gemini

**5.1 Gemini ได้รับอะไร** — สองครั้งต่อคำถาม
1. `_recommendation_intent`: ได้เฉพาะข้อความของผู้ใช้ (ไม่มี history ไม่มี chunk) คืน `{recommendation, interest}`
2. `_generate_rationales`: ได้ `profile_text` (ข้อความ/ความสนใจ) + บล็อกหลักฐานของ **หลักสูตรที่ backend เลือกมาแล้ว** แต่ละบล็อกมีชื่อหลักสูตร + แก่นหลักสูตร + chunk ที่ค้นได้ (≤ 3000 ตัวอักษร) · ไม่ได้รับรายชื่อหลักสูตรทั้งคณะ ไม่ได้รับ history

**5.2 ใครเลือกสาขา — backend เลือก candidate, Gemini มีสิทธิ์ veto**
backend กำหนด candidate ได้แน่นอน แต่โค้ดตัดรายการที่ Gemini ไม่เขียนเหตุผลออก จึงเป็น "Gemini เลือกได้ว่าอันไหนจะถูกแสดง" โดยปริยาย

**5.3 Gemini ตัดสาขาออก / เปลี่ยนจำนวนที่กล่าวถึงได้ไหม — ตัดออกได้ (ผ่านกลไก §5.2) แต่เพิ่มสาขาใหม่ไม่ได้** เพราะคำตอบประกอบจากรายการของ backend (`_rationale_for` จับคู่ตามชื่อ) ไม่ได้ให้ Gemini เขียนคำตอบทั้งก้อน

**5.4 model** — `gemini-3.5-flash-lite` (`GEMINI_MODEL` ใน `.env` ของ production) สำรอง `gemini-3.1-flash-lite, gemini-3.5-flash, gemini-3.6-flash` เมื่อโควตาหมด (log: ยังไม่มีการใช้สำรองเลยตั้งแต่ container เริ่ม)

**5.5 temperature** — `0.0` ทั้งขั้นตรวจ intent และขั้นเขียนเหตุผล

**5.6 config อื่นที่ทำให้ผลต่างกันได้**
- `maxOutputTokens = answer_token_cap (2048)` · `json_mode` · ไม่ได้ตั้ง `topP`, `topK`, `seed` หรือ `candidateCount` จึงใช้ค่าเริ่มต้นของผู้ให้บริการ
- temperature 0 **ไม่ใช่การรับประกันว่าผลเหมือนเดิม** — โค้ดเองบันทึกการวัดไว้ว่ายังพลาดเป็นครั้งคราว: คำถามนี้ถูกปฏิเสธทุกสาขา 1/20 รอบหลังตั้ง temperature 0 (`chat.py` หมายเหตุใน `_generate_rationales`/`_interest_of`) และรอบตอบต่อยอดพลาด 4/12
- ถ้าสลับไปโมเดลสำรองหรือโมเดลในเครื่อง (quota) ถ้อยคำและการตัดสินก็เปลี่ยนได้

## 6. ทำไม CS+IT กับ CS+Animation

จากตาราง §0 ซึ่งเป็น log จริง: คำถามเดียวกัน ไม่มี history ห่างกันไม่ถึงนาที ได้ผล 3 แบบ (CS อย่างเดียว / CS+IT / CS+Animation) และก่อนหน้านั้นได้ "ไม่พบสาขา"

- **A. context ต่างกัน** — ตัดออก (`has_history = false` ทุกแถว)
- **B. rewritten query ต่างกัน** — เป็นไปได้น้อย เพราะ `interest` ถูกบังคับเป็น substring ของข้อความเดิม และ `_interest_of` ตัดคำนำหน้าแบบ deterministic · แต่ log ไม่ได้เก็บ `interest` ที่ใช้จริง จึงตัดออก 100% ไม่ได้
- **C. retrieved chunks ต่างกัน** — เป็นไปได้น้อยมาก การให้คะแนนและการเลือกหลักฐานเป็น deterministic เมื่อ query เหมือนกัน
- **D. candidate set ต่างกัน** — เป็นไปได้น้อย ด้วยเหตุผลเดียวกับ C และค่าคะแนนที่วัดไว้ (.561/.542/.528 vs .480) ห่างจากเส้น margin พอสมควร
- **E. Gemini ได้หลักฐานชุดเดียวกันแต่เขียนเหตุผลไม่เหมือนกัน → โค้ดตัดสาขาที่ไม่มีเหตุผลออก** — **ตรงกับหลักฐานมากที่สุด** อธิบายได้ทั้งสามรูปแบบที่พบ (CS เดียว = ตัดสองสาขา, CS+IT = ตัด Animation, CS+Animation = ตัด IT) และอธิบายแถว 15:50 ที่ไม่มีสาขาเลยได้ด้วย ซึ่งเป็นอาการที่โค้ดเองบันทึกไว้ว่าวัดได้ 1/20 รอบ
- **F. อื่น ๆ** — แคชไม่เกี่ยว เพราะเส้นทางนี้ `cacheable=False` (`chat.py:1162`) และไม่พบการใช้โมเดลสำรองใน log

**ข้อสรุป:** หลักฐานชี้ไปที่ **E** อย่างหนัก โดยข้อ B ยังตัดออกไม่ได้ 100% เพราะ log ไม่ได้เก็บ `interest` และเนื้อหา prompt ที่ส่งให้ Gemini — **การแยก B ออกจาก E ให้เด็ดขาดต้องมี controlled test** (ตรึง `interest` แล้วเรียกขั้นเขียนเหตุผลซ้ำหลายรอบ) ซึ่งรอบนี้ห้ามทำ

## 7. ถ้า request เหมือนกันทุกอย่าง

| | คำตอบ | เหตุผล |
|---|---|---|
| 7.1 retrieved chunks เหมือนกันไหม | **ควรเหมือน** | คะแนนและการเลือกหลักฐานคำนวณจากเวกเตอร์แบบ deterministic (ยกเว้น `interest` ที่ผ่าน LLM) |
| 7.2 candidate programmes เหมือนกันไหม | **ควรเหมือน** | margin + limit เป็นค่าคงที่ |
| 7.3 ชื่อสาขาในคำตอบสุดท้ายเหมือนกันไหม | **ไม่รับประกัน — และ log พิสูจน์แล้วว่าไม่เหมือน** | รายชื่อสุดท้าย = candidate ลบสิ่งที่ Gemini ไม่ยอมเขียนเหตุผลให้ |
| 7.4 ถ้อยคำต่างกันได้ไหม | **ได้ และยอมรับได้** | เหตุผลเป็นข้อความที่ LLM เขียนใหม่ทุกครั้ง |

**แยกให้ชัด:** "ถ้อยคำต่างกัน" คือพฤติกรรมปกติของ LLM ที่ยอมรับได้ · แต่ "รายชื่อสาขาที่แนะนำต่างกัน" คือ *candidate/result instability* ซึ่งไม่ใช่เรื่องของถ้อยคำ และเป็นสิ่งที่ผู้ใช้ตีความว่าเป็นคำตอบคนละคำตอบ

## 9. Classification

- **REAL BUG** (ระดับกลาง): รายชื่อสาขาที่ผู้ใช้เห็นขึ้นกับผลของขั้นเขียนเหตุผลซึ่งไม่นิ่ง ทั้งที่การจัดอันดับถูกต้องและคงที่ — หลักฐาน §0 + `chat.py:867`
- **INCOMPLETE BROAD RECOMMENDATION**: คำถามกว้างถูกจำกัดไว้ที่ 3 อันดับและ margin 0.04 จึงไม่เคยตอบว่า "ทุกสาขาที่เกี่ยวข้อง" ได้ — `chat.py:846`, `program_match.py:284`
- **EXPECTED LLM VARIATION** (เฉพาะถ้อยคำ): ข้อความเหตุผลต่างกันทุกครั้งเป็นเรื่องปกติ
- **UNKNOWN / NEEDS CONTROLLED TEST**: ยังแยกไม่ได้ 100% ว่ามีส่วนของ `interest` ที่ LLM คัดมาต่างกันปนอยู่ด้วยหรือไม่ (ข้อ B) เพราะ log ไม่ได้เก็บค่านี้
- **CONTEXT DIFFERENCE**: ตัดออกด้วยหลักฐาน
- **RETRIEVAL VARIATION**: ไม่พบหลักฐานสนับสนุน

## 10. Minimal fix ที่เสนอ (ยังไม่ implement)

เป้าหมาย: คำถามกว้างเดียวกัน + context เดียวกัน + คลังเดียวกัน ต้องได้ **ชุดสาขาเดียวกัน** ส่วนถ้อยคำต่างได้

**ข้อเสนอหลัก (เล็กที่สุด แก้ root cause ตรงจุด):** เปลี่ยนความหมายของขั้นเขียนเหตุผลจาก "ตัวตัดสินว่าจะแสดงสาขาไหน" เป็น "ตัวเขียนคำอธิบาย" — คือ **ไม่ตัดสาขาออกจากรายการเพราะเขียนเหตุผลไม่ได้**
- จุดแก้: `chat.py:867` จุดเดียว — แสดง candidate ที่ backend เลือกไว้ครบ และรายการที่ไม่มีเหตุผลให้ใส่ข้อความมาตรฐานแทน (เช่น "ระบบยังเขียนคำอธิบายให้สาขานี้ไม่ได้ในขณะนี้") แบบเดียวกับที่ `/recommend-major` ทำอยู่แล้ว (`NO_REASON` ใน `web_compat.py`)
- ผลที่ได้: รายชื่อสาขาเท่ากันทุกครั้ง เพราะมาจากคะแนนล้วน ๆ
- ข้อแลกเปลี่ยนที่ต้องตัดสินใจ: กรณีที่ Gemini ตอบ `[[ไม่มีข้อมูลรองรับ]]` จริง ๆ (ไม่ใช่ล้มเหลว) จะยังถูกแสดง — ทางเลือกคือแสดงต่อพร้อมข้อความว่าเอกสารไม่ได้ระบุความเชื่อมโยงไว้ตรง ๆ ซึ่งซื่อตรงกว่าการหายไปเงียบ ๆ และเป็นเหตุผลเดียวกับที่ `/recommend-major` เลือกไว้แล้ว
- ต้องมี offline test: ตรึง candidate + จำลองผลของขั้นเขียนเหตุผลหลายแบบ (ครบ / ว่างบางตัว / มี marker) แล้วยืนยันว่ารายชื่อสาขาที่แสดงเท่ากันทุกกรณี

**ส่วนขยายที่ควรตัดสินใจแยก (ไม่จำเป็นต่อ root cause):**
- ถ้าต้องการ "รายงานให้ครบทุกสาขาที่เกี่ยวข้อง" ต้องทบทวน `limit=3` และ margin 0.04 ซึ่งเปลี่ยนพฤติกรรมเชิงนโยบาย ควรทำเป็นรอบแยกพร้อมชุดวัด
- ถ้าต้องการปิดช่องของข้อ B ให้หมด: ทำให้ `interest` มาจากกฎแบบ deterministic แทนการเรียก LLM — ใหญ่กว่าและควรมีผลวัดรองรับก่อน

ห้าม implement จนกว่าจะได้รับอนุมัติ

---

ROOT CAUSE: การจัดอันดับสาขาเป็น deterministic และได้ candidate ชุดเดิมทุกครั้ง ({วิทยาการคอมพิวเตอร์ .561, คอมพิวเตอร์แอนิเมชัน .542, เทคโนโลยีสารสนเทศ .528}) แต่ `chat.py:867` ตัดสาขาที่ Gemini ไม่ได้เขียนเหตุผลให้ (ว่าง หรือ `[[ไม่มีข้อมูลรองรับ]]`) ออกจากคำตอบ ขั้นเขียนเหตุผลนี้แม้ตั้ง temperature 0 ก็ยังให้ผลไม่เหมือนเดิมทุกครั้ง รายชื่อสาขาที่ผู้ใช้เห็นจึงเปลี่ยนไปมา

DO BROWSERS HAVE DIFFERENT CONTEXT: ไม่ — log ทั้ง 5 ครั้งของคำถามนี้เป็น `has_history = false` และหน้าเว็บไม่เก็บบทสนทนาไว้ใน storage ใด ๆ

ROUTE / INTENT: เส้นทางแนะนำสาขาของแชท (`_recommendation_intent` → `_recommendation_reply` → `match_programs`) ไม่ใช่ RAG ปกติและไม่ใช่ Structured Answers

DO RETRIEVED CHUNKS DIFFER: ไม่ควรต่าง — คะแนนคำนวณครบทุกหลักสูตรแบบ exact ไม่ผ่าน ANN index (log ไม่ได้เก็บ chunk ที่ใช้ จึงเป็นข้อสรุปจากโค้ด)

DOES BROAD RECOMMENDATION EVALUATE ALL PROGRAMMES: ให้คะแนนครบทุกหลักสูตรปริญญาตรีที่เปิดรับ 12 หลักสูตร แต่ส่งต่อให้ LLM เพียง ≤ 3 หลักสูตร

HOW ARE CANDIDATE PROGRAMMES SELECTED: `program_match.match_programs()` — `0.5 × เนื้อหา + 0.5 × ชื่อสาขา` → กรองปริญญาตรี/เปิดรับ → ยุบฉบับซ้ำ → `_close_to_best` (margin 0.04) → `limit=3` ทั้งหมด deterministic

WHY ONLY SOME PROGRAMMES ARE SHOWN: margin 0.04 + cap 3 รายการ + การตัดออกโดยผลของขั้นเขียนเหตุผล

IS NUMBER OF PROGRAMMES LIMITED: ใช่ — สูงสุด 3 (`chat.py:846`, `chat.py:867`) prompt ไม่ได้กำหนดจำนวน แต่มีกฎให้ตอบ `[[ไม่มีข้อมูลรองรับ]]` ได้

DOES GEMINI SELECT FINAL PROGRAMMES: ไม่ได้เลือกโดยตรง แต่มีสิทธิ์ veto — เพิ่มสาขาไม่ได้ ตัดออกได้

WHY CS+IT vs CS+ANIMATION: หลักฐานชี้ไปที่ข้อ E (หลักฐานชุดเดียวกัน แต่ขั้นเขียนเหตุผลให้ผลต่างกัน แล้วโค้ดตัดสาขาที่ไม่มีเหตุผลออก) · ข้อ B (ข้อความ `interest` ที่ LLM คัดมาต่างกัน) ยังตัดออกไม่ได้ 100% เพราะ log ไม่ได้เก็บค่านี้ → NEEDS CONTROLLED TEST เพื่อยืนยันขั้นสุดท้าย

SAME EXACT REQUEST SHOULD RETURN SAME CANDIDATES: ควรได้ candidate ชุดเดียวกัน (และหลักฐานบอกว่าได้จริง) แต่ **รายชื่อที่แสดงไม่รับประกัน** ส่วนถ้อยคำต่างกันได้เป็นปกติ

CAN CURRENT SYSTEM CLAIM RESULTS ARE COMPLETE: ไม่ได้ — จำกัดด้วย margin 0.04, cap 3 และการตัดออกที่ไม่นิ่ง

EXPECTED OR BUG: REAL BUG (ความไม่นิ่งของรายชื่อ) + INCOMPLETE BROAD RECOMMENDATION (ความครบถ้วน) + EXPECTED LLM VARIATION (เฉพาะถ้อยคำ) + UNKNOWN บางส่วน (ข้อ B)

MINIMAL FIX IF NEEDED: แก้ `chat.py:867` จุดเดียว — ไม่ตัดสาขาออกเพราะเขียนเหตุผลไม่ได้ ให้แสดง candidate ที่ backend จัดอันดับไว้ครบ พร้อมข้อความมาตรฐานแทนเหตุผลที่ขาด (แบบเดียวกับ `NO_REASON` ของ `/recommend-major`) พร้อม offline test ว่ารายชื่อคงที่ทุกกรณีของผลจาก LLM · ส่วน `limit` และ margin เป็นการตัดสินใจเชิงนโยบาย ควรแยกรอบ

SHOULD FIX BEFORE FINAL DEMO: YES — ถามคำถามเดิมซ้ำในเดโมแล้วได้สาขาไม่เท่ากันเป็นอาการที่เห็นได้ง่ายมาก และจุดแก้เล็กมาก แต่ต้องขออนุมัติแก้โค้ดและ deploy แยก

EVIDENCE CONFIDENCE: HIGH สำหรับความไม่นิ่งของรายชื่อและกลไกที่ทำให้เกิด (มี log จริงของคำถามเดียวกัน 5 ครั้ง + จุดตัดในโค้ด) · MEDIUM สำหรับการตัดข้อ B ออกทั้งหมด (log ไม่ได้เก็บ `interest` และ prompt ที่ส่งจริง)
