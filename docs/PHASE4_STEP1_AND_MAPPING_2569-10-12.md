### ยืนยันว่าเข้าถึงผ่านเว็บไม่ได้ — ตรวจด้วยเนื้อหา ไม่ใช่ status code

ตอนตรวจครั้งแรกเห็น `HTTP 200` ซึ่งดูเหมือนไฟล์หลุด **แต่ไม่ใช่**

| ขอ path | ได้อะไรจริง |
|---|---|
| `/supabase-storage-backup/manifest.json` | `text/html` **762 ไบต์** ขึ้นต้น `<!doctype html>` |
| `/supabase-storage-backup/knowledge-files/1f6796fe-….pdf` | `text/html` **762 ไบต์** ขึ้นต้น `<!doctype html>` |
| `/assets/logo.png` (ไฟล์ที่มีจริง) | `image/png` **198,620 ไบต์** |

`200` มาจาก **SPA catch-all** ของ Caddy (`try_files {path} /index.html`) ที่คืน `index.html` ให้ทุก path ที่ไม่รู้จัก
ถ้า PDF หลุดจริงต้องได้ `application/pdf` ขนาด 6.2 MB

เหตุผลเชิงโครงสร้าง: Caddy เสิร์ฟจาก `$WEB = /home/ubuntu/course-advisor-system/web` ซึ่งมีแค่ `assets` กับ `index.html`
โฟลเดอร์สำรองอยู่ที่ `/home/ubuntu/supabase-storage-backup` **อยู่นอก `$WEB` และนอก `uploads/`**

## 2. mapping หลักสูตร 3 รายการที่ค้าง — **ตัดสินได้แล้ว ครบ 12/12**

### ทำไมรอบก่อนตัดสินไม่ได้

รอบก่อนใช้ **จำนวน chunk** เป็นเกณฑ์ ซึ่งชี้ไปทางฉบับเก่า

```
คณิตศาสตร์          2569 มี  92 chunk  ·  2564 มี 325
คอมพิวเตอร์แอนิเมชัน  2569 มี 100 chunk  ·  2564 มี 404
วิทยาการคอมพิวเตอร์   2566 มี 220 chunk  ·  2561 มี 420
```

**จำนวน chunk บอกแค่ว่าเอกสารยาวแค่ไหน ไม่ได้บอกว่าฉบับไหนคือหลักสูตรที่ใช้จริง**

## 4. รอเจ้าของ — ทดสอบ login

แท็บเทอร์มินัลว่างแล้ว วางคำสั่งนี้

```bash
ssh -i C:\Users\User\.ssh\oci.key -t ubuntu@161.118.237.37 "bash /home/ubuntu/phase4-test-login.sh"
```

| รอบ | บัญชี | คาดว่าจะได้ |
|---|---|---|
| 1 | **admin เดิม** `te*****@gmail.com` | `role=admin` · `scheme` เป็น `bcrypt_sha256` อยู่แล้ว · เซสชันเพิ่มขึ้น 1 |
| 2 | **นำเข้าจาก Supabase** `66*****@365.pnru.ac.th` หรือ `66*****@pnru.ac.th` | `scheme` เริ่มที่ **`bcrypt`** → หลังเข้าสำเร็จต้องเป็น **`bcrypt_sha256`** |

**รอบที่ 2 คือหลักฐานว่าการย้ายรหัสผ่านจาก Supabase ใช้ได้จริง** — ถ้าเข้าได้ แปลว่าไม่มีใครต้องตั้งรหัสใหม่

สคริปต์รายงานแค่ HTTP status · `role`/`status` · จำนวนเซสชัน · `password_scheme` ก่อน/หลัง
**ไม่แสดง token** · ไฟล์ชั่วคราวโหมด 600 ลบทิ้งด้วย `trap` แม้กด Ctrl-C
