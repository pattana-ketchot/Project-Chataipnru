> **ไม่ได้ใช้ช่องโหว่เพื่อดึงข้อมูลจริง** ตามที่คำสั่งระบุ

## 0. ข้อจำกัดของการตรวจรอบนี้ — อ่านก่อน

**ผมตรวจ RLS policy จริงบน Supabase ด้วยตนเองไม่ได้** เพราะไม่มีสิทธิ์เข้าถึงโดยชอบ และ**ไม่ใช้ช่องโหว่ R1 เพื่อดึงข้อมูลมาดู**

สิ่งที่ทำแทนคือรวบรวมหลักฐานจากสิ่งที่ตรวจได้จริง

| แหล่ง | ตรวจได้ไหม | ใช้ทำอะไร |
|---|---|---|
| โค้ด `webapi/` ในรีโป | **ได้** | รู้ว่า M3 อ่านอะไรและอ่านในนามใคร |
| ไฟล์ JavaScript ของหน้าเว็บจริงบนเซิร์ฟเวอร์ | **ได้** (อ่านไฟล์ ไม่ได้รันหรือดึงข้อมูล) | รู้ครบว่า SPA ทำอะไรกับตารางนี้บ้าง |
| เอกสารออกแบบรอบก่อน | **ได้** | รู้ policy ที่บันทึกไว้ |
| **RLS policy จริงใน Supabase** | **ไม่ได้** | **ต้องให้เจ้าของรันเอง — ข้อ 1.1** |

> ระหว่างอ่านไฟล์ของหน้าเว็บ **พบ anon key ฝังอยู่ใน bundle** ตามที่เอกสาร R1 เตือนไว้จริง ผมไม่บันทึกค่า ไม่คัดลอก และไม่นำไปใช้เรียกข้อมูลใด ๆ

**แผนนี้ตั้งอยู่บน policy ที่เอกสารบันทึกไว้ ต้องยืนยันกับของจริงก่อนลงมือ**

## 1. สภาพปัจจุบัน

### 1.1 ต้องให้เจ้าของรันก่อน — ดู policy จริง

เปิด **Supabase Dashboard → SQL Editor** แล้วรัน คำสั่งนี้อ่านอย่างเดียวและ**ไม่คืนข้อมูลผู้ใช้เลย**

```sql
select
  policyname,
  cmd,
  roles::text,
  qual        as using_expression,
  with_check  as with_check_expression
from pg_policies
where schemaname = 'public' and tablename = 'user_profiles'
order by cmd, policyname;
```

ตรวจเพิ่มว่า RLS เปิดอยู่จริง และมีฟังก์ชันช่วยอยู่แล้วหรือยัง

```sql
select relrowsecurity as rls_enabled, relforcerowsecurity as rls_forced
from pg_class where oid = 'public.user_profiles'::regclass;

select proname, prosecdef as is_security_definer
from pg_proc
where pronamespace = 'public'::regnamespace
  and proname in ('is_approved_staff','is_admin','current_user_role');
```

**ผลที่ต้องดู**

| สิ่งที่เห็น | ความหมาย |
|---|---|
| มี policy `SELECT` ที่ `using_expression` เป็น `true` | **ยืนยัน R1** — เดินตามแผนนี้ได้ |
| `SELECT` policy เป็นอย่างอื่น | **หยุด** — แผนนี้ใช้ไม่ได้ ต้องออกแบบใหม่ตามของจริง |
| `UPDATE` policy อ้างถึง `user_profiles` ตรง ๆ | **สำคัญมาก** ดูข้อ 4.3 เรื่อง recursion |
| มีฟังก์ชัน `is_approved_staff` อยู่แล้ว | ใช้ของเดิม ไม่ต้องสร้างใหม่ |

### 1.2 สิ่งที่เอกสารบันทึกไว้

| คำสั่ง | สิทธิ์ตามเอกสาร |
|---|---|
| `SELECT` | **ทุกคน ⚠** (`qual = true`) |
| `INSERT` | — ไม่มี policy |
| `UPDATE` | ตัวเอง (`auth.uid() = user_id`) · admin ที่ `status='approved'` แก้ของคนอื่นได้ |
| `DELETE` | — ไม่มี policy |

ความเสี่ยง R1 บันทึกไว้ว่า *"ใครมี anon key ก็ดึงอีเมลผู้ดูแลทั้ง 3 คนได้ · anon key อยู่ใน bundle ของ SPA ตามธรรมชาติ"* และระบุว่า **"เป็นข้อบกพร่องที่มีอยู่ ไม่ใช่สิ่งที่ต้องรักษา"**

### 1.3 anon กับ authenticated อ่านอะไรได้บ้าง (ไม่ได้ทดลองจริง)

ถ้า `SELECT` policy เป็น `USING (true)` จริง

| ผู้เรียก | อ่านได้ |
|---|---|
| **anon** (แค่มี anon key จากหน้าเว็บ) | **ทุกแถว ทุกคอลัมน์** รวม `email`, `full_name`, `role`, `status` |
| authenticated ทั่วไป | เหมือน anon |
| editor / admin | เหมือน anon |

คอลัมน์ที่เป็นข้อมูลส่วนบุคคลและหลุดได้คือ **`email`** และ **`full_name`**

> ไม่ได้ยิงคำขอเพื่อยืนยัน เพราะนั่นคือการใช้ช่องโหว่ ซึ่งคำสั่งห้ามไว้

## 2. ใครใช้ตารางนี้บ้าง — สำรวจครบแล้ว

### 2.1 ฝั่ง M3 WebAPI (รีโปของเรา)

| ไฟล์ | คำสั่ง | อ่านในนามใคร |
|---|---|---|
| `webapi/auth.mjs:312` | `.select("role, status").eq("user_id", userId).single()` | **ผู้เรียกเอง** — ใช้ client ที่ผูกกับ token ของผู้เรียก |
| `webapi/api/_lib/adminAuth.js:31` | `.select('role, status').eq('user_id', user.id).single()` | **ผู้เรียกเอง** — `createClient(url, anonKey, { headers: Authorization: Bearer <token ของผู้เรียก> })` |

โค้ดมีคอมเมนต์กำกับไว้เองว่า *"ใช้ supabase client ที่ scope ด้วย token ของผู้เรียกเอง (ไม่ใช่ shared key) เพื่อให้ RLS บังคับด้วยตัวตนจริงของผู้เรียกด้วย"*

**ทั้งสองจุดอ่านแถวของตัวเองเท่านั้น** → การจำกัดเป็น "อ่านแถวตัวเองได้" **ไม่กระทบ M3 เลย**

### 2.2 ฝั่งหน้าเว็บ (รีโปทีมออกแบบ — อ่านจากไฟล์ที่ deploy จริง)

พบการใช้งาน **8 แบบ ไม่มี `INSERT` และไม่มี `DELETE` เลย**

| # | คำสั่ง | ขอบเขต | ใช้ที่หน้าไหน |
|---|---|---|---|
| 1 | `.select("role, status").eq("user_id", <ตัวเอง>).single()` | ตัวเอง | ตรวจสิทธิ์ตอนเข้าหน้า (2 จุด) |
| 2 | `.select("full_name").eq("user_id", <ตัวเอง>).single()` | ตัวเอง | หน้าโปรไฟล์ |
| 3 | `.update({ full_name }).eq("user_id", <ตัวเอง>)` | ตัวเอง | หน้าโปรไฟล์ |
| 4 | `.select("user_id, full_name, email").in("user_id", [...])` | **คนอื่น** | **แสดงชื่อผู้สร้าง/ผู้แก้ไข ในรายการเนื้อหาของผู้ดูแล** |
| 5 | `.select("id", { count: "exact", head: true })` | **ทั้งตาราง** | **แดชบอร์ดผู้ดูแล** (นับคู่กับ courses / news / knowledge_articles) |
| 6 | `.select("id, user_id, role, status, full_name, email, created_at").order(...)` | **ทั้งตาราง** | **หน้า `/admin/users`** |
| 7 | `.update({ role }).eq("user_id", <คนอื่น>)` | คนอื่น | `/admin/users` |
| 8 | `.update({ status }).eq("user_id", <คนอื่น>)` | คนอื่น | `/admin/users` |

### 2.3 ข้อสรุปที่สำคัญที่สุดของการสำรวจ

> **การอ่านข้อมูลของคนอื่นเกิดขึ้นเฉพาะในหน้าของผู้ดูแลเท่านั้น (ข้อ 4, 5, 6)**
> **ไม่มีหน้าสาธารณะใดอ่าน `user_profiles` เลย**

ตรวจยืนยันจากบริบทในโค้ด — ข้อ 4 ถูกเรียกจากสองที่ที่ map `created_by`/`updated_by` เป็น `creator`/`updater` ในรายการเนื้อหา · ข้อ 5 อยู่ใน `Promise.all` เดียวกับการนับ `courses`, `news`, `knowledge_articles` และอ่าน `ai_settings` ซึ่งเป็นแดชบอร์ดผู้ดูแล

**แปลว่าการปิดไม่ให้ anon อ่าน จะไม่ทำให้หน้าสาธารณะพัง**

## 3. ผลกระทบต่อแต่ละระบบ

| ระบบ | ใช้ `user_profiles` อย่างไร | กระทบไหมถ้าจำกัดสิทธิ์ |
|---|---|---|
| **หน้าเว็บสาธารณะ** (หน้าแรก, หลักสูตร, เปรียบเทียบ, แชท, ค้นหาสาขา) | **ไม่ใช้เลย** | **ไม่กระทบ** |
| **Login** | Supabase Auth จัดการเอง ไม่ได้อ่าน `user_profiles` ตอนล็อกอิน | **ไม่กระทบ** |
| **ตรวจสิทธิ์ตอนเข้าหน้าผู้ดูแล** | อ่าน `role, status` ของตัวเอง | **ไม่กระทบ** — ยังอ่านแถวตัวเองได้ |

| **แดชบอร์ดผู้ดูแล** | นับทั้งตาราง | **ไม่กระทบ** ถ้า policy ให้ staff อ่านได้ทุกแถว |
| **รายการเนื้อหาของผู้ดูแล** | อ่านชื่อผู้สร้าง/ผู้แก้ไข | **ไม่กระทบ** ถ้าให้ staff อ่านได้ (ต้องรวม `editor` ด้วย) |

### 3.1 พฤติกรรมเมื่ออ่านไม่ได้ — ปลอดภัยอยู่แล้วฝั่ง M3

`readProfile` ใช้ `.single()` ถ้า RLS ปฏิเสธจะได้ error แล้วคืน `null` ซึ่ง webapi ตีความว่า**ไม่มีสิทธิ์** → 403

มีชุดทดสอบครอบไว้แล้วชื่อ *"อ่าน user_profiles ไม่ได้ ต้องไม่เดาว่ามีสิทธิ์"* (`webapi/auth.test.mjs:368`)

### 3.2 ⚠ พบจุดที่ควรแก้ฝั่งหน้าเว็บ (ไม่ใช่ของรอบนี้)

ในโค้ดหน้าเว็บจุดหนึ่งเขียนว่า

```js
const role = profile?.role || "user";
const status = profile?.status || "approved";
```

**ถ้าอ่านโปรไฟล์ไม่สำเร็จ จะถือว่าสถานะเป็น `approved`** ซึ่งเป็นค่าตั้งต้นที่หละหลวม

| ประเด็น | ประเมิน |
|---|---|
| เป็นช่องโหว่สิทธิ์จริงไหม | **ไม่** — เป็นแค่การตัดสินใจฝั่งหน้าจอเพื่อ UX · ด่านจริงคือ RLS และ `requireAdminUser` ของ webapi ซึ่งไม่เดาค่าให้ |
| จะแย่ลงไหมหลังแก้ RLS | **ไม่** — ผู้ใช้ที่อ่านแถวตัวเองได้อยู่แล้วจะไม่เข้าเส้นทาง fallback นี้ |
| ควรทำอะไร | แจ้งทีมออกแบบให้เปลี่ยนค่าตั้งต้นเป็นปฏิเสธ · **เป็นรีโปของทีมออกแบบ อยู่นอกขอบเขตรอบนี้** |

## 4. การออกแบบ Policy ใหม่

### 4.1 หลักการ

| ผู้เรียก | ควรอ่านได้ |
|---|---|
| **anon** | **ไม่ได้เลย** |
| authenticated ทั่วไป | **แถวของตัวเองเท่านั้น** |
| `editor` ที่ `approved` | ทุกแถว (ต้องใช้แสดงชื่อผู้เขียนและแดชบอร์ด) |
| `admin` ที่ `approved` | ทุกแถว |

คำสั่ง `UPDATE` / `INSERT` / `DELETE` **ไม่แตะ** — รอบนี้แก้เฉพาะ `SELECT` ที่เป็นต้นเหตุของ R1

### 4.2 ทำไมต้องรวม `editor` ไม่ใช่แค่ `admin`

หน้ารายการเนื้อหาที่ editor เข้าได้ เรียกการอ่าน `full_name`/`email` ของผู้สร้าง ถ้าให้เฉพาะ admin ชื่อผู้เขียนจะหายไปสำหรับ editor

> **ข้อแลกเปลี่ยนที่ต้องรู้** — วิธีนี้ทำให้ `editor` ยังอ่านอีเมลของทุกคนได้ ซึ่งยังกว้างกว่าที่ควรเป็น ทางที่ดีกว่าคือทำ view หรือ RPC ที่คืนเฉพาะ `user_id, full_name` สำหรับแสดงชื่อผู้เขียน แล้วให้ `/admin/users` เป็นทางเดียวที่อ่าน `email` ได้ **แต่ต้องแก้โค้ดหน้าเว็บ ซึ่งเป็นรีโปของทีมออกแบบและอยู่นอกขอบเขตรอบนี้** — บันทึกไว้เป็นงานถัดไป

### 4.3 ⚠ กับดักที่ทำให้ production ล่มได้ — RLS recursion

policy ที่ตรวจสิทธิ์โดย **query ตารางเดียวกัน** จะเกิดการเรียกซ้อนไม่รู้จบ

```sql
-- ห้ามเขียนแบบนี้เด็ดขาด
CREATE POLICY ... ON public.user_profiles FOR SELECT
USING (EXISTS (SELECT 1 FROM public.user_profiles WHERE ...));
--                              ^^^^^^^^^^^^^^^^^ เรียกตัวเองซ้ำ
```

อาการคือ `infinite recursion detected in policy for relation "user_profiles"` และ **ทุกการอ่านตารางนี้จะพังทันที** รวมถึงการล็อกอินเข้าหน้าผู้ดูแลและ M3

วิธีแก้มาตรฐานคือใช้ฟังก์ชัน `SECURITY DEFINER` ซึ่งรันด้วยสิทธิ์เจ้าของฟังก์ชันจึง**ข้าม RLS** ไม่เกิดการเรียกซ้อน

> **ต้องดูผลข้อ 1.1 ก่อน** — ถ้า policy `UPDATE` ที่ใช้อยู่ตอนนี้เขียนแบบอ้างตัวเองแล้วยังทำงานได้ แปลว่าของเดิมใช้กลไกอื่น ต้องดูของจริงก่อนตัดสินใจ

## 5. SQL — เตรียมไว้ในเครื่อง ยังไม่ apply

ไฟล์ที่ควรเก็บ (ยังไม่สร้างจนกว่าจะอนุมัติ)

```
db/migrations/supabase/C1_user_profiles_rls.sql
db/migrations/supabase/C1_user_profiles_rls_rollback.sql
```

> `db/migrations/` ที่มีอยู่เป็นของ PostgreSQL ฝั่งเรา ไม่ใช่ Supabase จึงเสนอให้แยกโฟลเดอร์ย่อยเพื่อไม่ให้สับสน

### 5.1 Migration

```sql
-- C1 — จำกัดการอ่าน public.user_profiles ของ Supabase
-- แก้ความเสี่ยง R1: ตารางนี้อ่านได้โดยทุกคนขณะเก็บ email และ full_name
--
-- แก้เฉพาะ SELECT เท่านั้น · ไม่แตะ INSERT / UPDATE / DELETE
-- ก่อนรัน: ต้องรู้ชื่อ policy เดิมจากข้อ 1.1 แล้วแทนที่ <POLICY_NAME_เดิม>

begin;

-- 0) ยืนยันว่า RLS เปิดอยู่ (ถ้าปิดอยู่ policy ไม่มีผลเลย)
alter table public.user_profiles enable row level security;

-- 1) ฟังก์ชันตรวจสิทธิ์แบบข้าม RLS เพื่อไม่ให้ policy เรียกตัวเองซ้อน
create or replace function public.is_approved_staff()
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select exists (
    select 1
    from public.user_profiles
    where user_id = auth.uid()
      and role in ('admin', 'editor')
      and status = 'approved'
  );
$$;

-- ให้เรียกได้เฉพาะผู้ที่ล็อกอินแล้ว — anon เรียกไม่ได้
revoke all on function public.is_approved_staff() from public, anon;
grant execute on function public.is_approved_staff() to authenticated;

-- 2) ถอด policy เดิมที่เปิดให้ทุกคนอ่าน
--    แทนที่ชื่อด้วยค่าจริงที่ได้จากข้อ 1.1
drop policy if exists "<POLICY_NAME_เดิม>" on public.user_profiles;

-- 3) อ่านแถวของตัวเอง
create policy user_profiles_select_own
  on public.user_profiles
  for select
  to authenticated
  using (auth.uid() = user_id);

-- 4) ผู้ดูแลและผู้แก้ไขที่อนุมัติแล้ว อ่านได้ทุกแถว
create policy user_profiles_select_staff
  on public.user_profiles
  for select
  to authenticated
  using (public.is_approved_staff());

commit;
```

### 5.2 Rollback

```sql
-- คืนสภาพเดิม — ใช้เมื่อพบว่าการจำกัดสิทธิ์ทำให้ระบบส่วนใดพัง
--
-- ⚠ การรัน rollback = เปิดช่องโหว่ R1 กลับมา ให้ใช้เป็นมาตรการชั่วคราวเท่านั้น
--   และต้องวางแผนแก้ใหม่ทันที

begin;

drop policy if exists user_profiles_select_own   on public.user_profiles;
drop policy if exists user_profiles_select_staff on public.user_profiles;

-- คืน policy เดิม — ใช้ชื่อและเงื่อนไขเดิมที่บันทึกไว้จากข้อ 1.1
create policy "<POLICY_NAME_เดิม>"
  on public.user_profiles
  for select
  using (true);

drop function if exists public.is_approved_staff();

commit;
```

> **ก่อน apply ต้องบันทึกผลข้อ 1.1 ไว้ก่อน** — ถ้าไม่รู้ชื่อและเงื่อนไขเดิม จะ rollback กลับไม่ได้

## 7. ความเสี่ยงและ GO / NO-GO

### 7.1 ความเสี่ยงของการแก้

| # | ความเสี่ยง | โอกาส | ผลกระทบ | การลด |
|---|---|---|---|---|
| 1 | **RLS recursion** ทำให้อ่านตารางไม่ได้เลย | กลาง | **สูง** — ล็อกอินเข้าหน้าผู้ดูแลไม่ได้ และ M3 คืน 403 ทุกคำขอ | ใช้ฟังก์ชัน `SECURITY DEFINER` · ทดสอบ X3 ก่อนประกาศสำเร็จ |
| 2 | ลืมรวม `editor` → ชื่อผู้เขียนหายจากรายการเนื้อหา | กลาง | กลาง | ทดสอบ E2 |
| 3 | ชื่อ policy เดิมไม่ตรง → `drop policy` ไม่ทำงาน แล้ว policy เก่ายังอยู่ | กลาง | **สูง** — คิดว่าแก้แล้วแต่ช่องโหว่ยังเปิด | ต้องได้ชื่อจริงจากข้อ 1.1 · ตรวจ A1 หลังแก้ว่าได้ 0 แถวจริง |
| 4 | มีหน้าอื่นที่ยังไม่พบซึ่งอ่านข้ามผู้ใช้ | ต่ำ | กลาง | สำรวจครบ 8 แบบจากไฟล์ที่ deploy จริงแล้ว |
| 5 | rollback แล้วลืมแก้ใหม่ | ต่ำ | **สูง** | บันทึกเป็นงานค้างทันทีที่ rollback |

### 7.2 ความเสี่ยงของการ **ไม่** แก้

| ประเด็น | รายละเอียด |
|---|---|
| ข้อมูลที่เปิดอยู่ | **อีเมลและชื่อจริง** ของผู้ใช้ทุกคนรวมผู้ดูแล |
| ใครเข้าถึงได้ | ใครก็ได้ที่เปิดหน้าเว็บ — anon key อยู่ใน JavaScript ตามธรรมชาติ |
| ต้องใช้ความรู้พิเศษไหม | **ไม่** — เปิด DevTools ก็เห็น |
| เอกสารประเมินไว้ | **ความรุนแรงสูง** และระบุว่า *"เป็นข้อบกพร่องที่มีอยู่ ไม่ใช่สิ่งที่ต้องรักษา"* |

### 7.3 เงื่อนไข GO

| # | เงื่อนไข | สถานะ |
|---|---|---|
| 1 | ได้ผลข้อ 1.1 — รู้ชื่อและเงื่อนไข policy เดิมทุกตัว | **ยังไม่มี** |
| 2 | ยืนยันว่า `SELECT` policy เดิมเป็น `USING (true)` จริง | **ยังไม่ยืนยัน** |
| 3 | รู้ว่า policy `UPDATE` เดิมเขียนอย่างไร (กันชนกับฟังก์ชันใหม่) | **ยังไม่ยืนยัน** |
| 4 | มีช่องทางทดสอบที่ไม่ใช่ production หรือยอมรับว่าทดสอบบนของจริง | **ต้องตัดสินใจ** |
| 5 | มีบัญชีครบ 4 แบบไว้ทดสอบ (anon / user / editor / admin) | **ต้องเตรียม** |
| 6 | ตกลงเวลาที่คนใช้งานน้อย | **ต้องตัดสินใจ** |

### 7.4 NO-GO — หยุดทันทีถ้าเจอ

| อาการ | ทำอะไร |
|---|---|
| `infinite recursion detected in policy` | **rollback ทันที** |

| ชื่อ policy เดิมไม่ตรงกับที่เตรียมไว้ | **หยุด** ปรับ SQL ก่อน อย่ารันต่อ |
| หน้าสาธารณะหน้าใดพัง | **rollback** แล้วหาสาเหตุ |

## 9. ยืนยันขอบเขต

| ข้อห้าม | สถานะ |
