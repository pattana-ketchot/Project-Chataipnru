|---|---|

**เกณฑ์ที่จะใช้ตัดสิน — ไม่ใช่แค่จำนวนข่าวคงที่**

| # | ต้องได้ |

| 1 | `จบรอบ exit=0` ครบ **ทั้ง 3 รอบ** |
| 2 | ทุกรอบอ่านหน้าเว็บต้นทางได้ (มีบรรทัด `อ่านข่าวจากหน้าเว็บได้ N รายการ` และ `N > 0`) |
| 3 | ข่าวล่าสุดในฐานข้อมูลตรงกับข่าวล่าสุดบนเว็บต้นทาง |

| 5 | `detail_url` และ `slug` ไม่ซ้ำ |

> **เหตุที่จำนวนคงที่อย่างเดียวไม่พอ** — รอบแรกที่ทดสอบ จำนวนคงที่ 15 แถวเหมือนกันเป๊ะ
> ทั้งที่งาน **ล้มด้วย `exit=1`** ตั้งแต่รายการแรกและไม่มีข่าวใดถูกเขียนเลย

### 4.3 webapi — ยังรันอยู่แต่ไม่มีใครเรียก

| รายการ | ค่า |
|---|---|
| สถานะ | รันอยู่ `healthy` |
| อ่าน Supabase ด้วย | `VITE_SUPABASE_ANON_KEY` |
| ไฟล์ที่ให้บริการ | `sci-connect-news.js` · `sci-connect-news-detail.js` · `admin/extract-file.js` · `admin/ingest.js` · `admin/sync-sci-news.js` |
| ใครเรียก | **ไม่มี** — หน้าเว็บใหม่ไม่อ้างเส้นทางเหล่านี้แล้ว |
| ทำไมยังเก็บไว้ | **เป็นทางถอยกลับ** ถ้าต้องย้อนหน้าเว็บไปชุดเดิม |

### 4.4 Caddy — เส้นทางที่ยังชี้ไป webapi

| บรรทัด | เส้นทาง | ปลายทาง |
|---|---|---|
| 33–35 | `handle /api/sci-connect-news*` | `webapi:3001` |
| 37–39 | `handle /api/admin/*` | `webapi:3001` |

**ต้องวางไว้ก่อน `handle /api/*`** ตามที่คอมเมนต์ในไฟล์เขียนไว้ · ถ้าลบสองบล็อกนี้ คำขอจะตกไปที่ backend แล้วได้ 404
ตอนนี้**ไม่มีใครเรียกสองเส้นทางนี้** จึงไม่มีผล

### 4.5 cron เก่าใน Supabase

| รายการ | ค่า |
|---|---|
| job | **`sync-sci-news-every-30-min-v2`** (`pg_cron` ในโปรเจกต์ Supabase) |
| ทำงาน | ทุก 30 นาที · เรียก Edge Function `sync-sci-news` |
| เขียนลง | **`public.external_news` ของ Supabase** |
| job รุ่นก่อน | `sync-sci-news-every-30-min` — **ปิดไว้แล้วตั้งแต่งาน C2** |
| สถานะตอนนี้ | **ยังทำงานอยู่** |

**สำคัญ: cron เก่ากับใหม่เขียนคนละฐานข้อมูล แม้ชื่อตารางจะเหมือนกัน**

| | cron เก่า | cron ใหม่ |
|---|---|---|
| เขียนลง | `public.external_news` ของ **Supabase** | `web.external_news` ของ **เซิร์ฟเวอร์เรา** |
| ใครอ่าน | `webapi` (ซึ่งไม่มีใครเรียกแล้ว) | `backend` → หน้าเว็บ |

การกันซ้ำด้วย `detail_url` เป็น unique constraint ในตารางของเราเท่านั้น **มองไม่เห็นแถวใน Supabase**

## 5. แผนถอด Supabase ออก (ขั้น G เป็นต้นไป)

ทำทีละขั้น **หยุดได้ทุกขั้น** และย้อนได้ทุกขั้น

| ลำดับ | ทำอะไร | ย้อนกลับอย่างไร | ความเสี่ยง |
|---|---|---|---|
| **G1** | ปิด cron เก่าใน Supabase | `cron.alter_job(..., active := true)` | ต่ำ — ไม่มีใครอ่านตารางปลายทางแล้ว |
| **G2** | เฝ้าดู 24–48 ชม. ว่าเว็บทำงานปกติ | — | — |
| **G3** | หยุดคอนเทนเนอร์ `webapi` | `docker compose … up -d --no-deps webapi` | ต่ำ — ไม่มีใครเรียก |
| **G4** | ลบสองบล็อก `handle` ใน Caddyfile | คืนไฟล์จากสำรอง แล้ว reload | ต่ำ |
| **G5** | ลบ `VITE_SUPABASE_*` ออกจาก `.env` | คืนจาก `env.before-phase4-2569-10-12` | ต่ำ |
| **G6** | ตัดสินใจเรื่อง 5 ไฟล์กำพร้า | สำรองไว้แล้ว | — |
| **G7** | ลบโปรเจกต์ Supabase | **ย้อนไม่ได้** | **สูง** |

### กฎของขั้น G

| ข้อ | กฎ |
|---|---|
| 1 | **ปิด cron ด้วย `alter_job` ห้าม `unschedule`** — `unschedule` ลบนิยาม job พร้อม header และ secret ทิ้ง ซึ่งเป็นส่วนที่งาน C2 ใช้เวลาแก้นานที่สุด |
| 2 | G7 ทำเป็นข้อสุดท้าย และทำหลัง G1–G6 ผ่านแล้วอย่างน้อยหนึ่งสัปดาห์ |
| 3 | ก่อน G7 ต้องมีสำเนา `auth.users`, ตารางทั้งหมด และไฟล์ Storage ครบ (ไฟล์ครบแล้ว · ตารางได้มาจาก import · `auth.users` 3 แถวย้ายมาแล้ว) |
| 4 | เก็บ `db-backup-2569-10-12.dump` ไว้จนกว่าจะมั่นใจ — **ทดสอบ restore จริงแล้ว 35 ตาราง 26,927 แถว ตรงกันหมด** |
