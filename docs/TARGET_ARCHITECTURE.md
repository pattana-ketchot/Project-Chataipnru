### ทำไมต้องเป็นสาม schema ไม่ใช่ยัดรวมกัน

1. **ไม่แตะของที่ทำงานอยู่** — `public` และ `mko` ไม่ต้องเปลี่ยนแม้คอลัมน์เดียว
   ความเสี่ยงต่อ RAG, crawler, chat จึงเป็นศูนย์
2. **เลี่ยงชื่อชนกันสองคู่** — `courses` และ `user_profiles` มีอยู่แล้วทั้งสองฝั่ง
3. **ถอนกลับง่าย** — `DROP SCHEMA web CASCADE` แล้วจบ ไม่กระทบอะไรเลย
4. `mko` มี **19 FK ชี้เข้า `public`** อยู่แล้ว พิสูจน์ว่าโครงหลาย schema ในฐานเดียวใช้งานได้ดีในโปรเจกต์นี้

## สองสิ่งที่ภาพที่ 2 ยังตอบไม่ได้ และต้องตัดสินใจก่อนลงมือ

### ก. **auth จะอยู่ที่ไหน**

ถ้า Supabase หายไปจากภาพทั้งหมด แปลว่าเลือก **ทางที่ 3** ซึ่งต้องสร้างสิ่งที่ Supabase ให้ฟรีขึ้นมาเองทั้งหมด ตรวจในโค้ดแล้วตอนนี้ FastAPI มี

| สิ่งที่ต้องมีถ้าเป็นเจ้าของ auth เอง | FastAPI ตอนนี้ |
|---|---|
| รีเซ็ตรหัสผ่าน | **0 ไฟล์** |
| ยืนยันอีเมล | **0 ไฟล์** |
| โครงสร้างส่งอีเมล | **0 ไฟล์** |
| ล็อกบัญชีเมื่อใส่รหัสผิดซ้ำ | **0 ไฟล์** |
| rate limit ตอน login | **ไม่มี** — `/auth/login` มีแค่ `Depends(get_db)` |

และ **รหัสผ่านใน Supabase ส่งออกมาไม่ได้** ผู้ใช้ทุกคนต้องตั้งใหม่

### ข. **ไฟล์ที่อัปโหลดจะอยู่ที่ไหน**

`knowledge_articles` ฝั่ง Supabase มีคอลัมน์ `file_name` และ `file_size` ซึ่งบ่งชี้ว่า
ไฟล์จริงอยู่ใน **Supabase Storage** (ยังไม่ยืนยัน 100% — ยังเข้า dashboard ไม่ได้)
ถ้า Supabase หายไป ไฟล์เหล่านั้นต้องมีที่อยู่ใหม่ และต้องแก้ URL ทุกจุดที่อ้างถึง

## ข้อค้นพบที่เปลี่ยนความเข้าใจเรื่อง "ตารางดูแปลก"

ระหว่างคุยกันเรื่องนี้พบว่า **schema ฝั่ง Supabase ไม่ได้ใช้ constraint เลย**
(ที่มา: `docs/database/schema.json` · source `supabase_schema.sql`)

| | Supabase | PostgreSQL ของเรา |
|---|---:|---:|
| ตาราง | 7 | 30 |
| **Foreign key** | **7** | **56** |
| **CHECK constraint** | **2** | **68** |
| UNIQUE | **4** | 7 เฉพาะตารางหลัก |

```
user_profiles.user_id   UUID                       ← ไม่มี FK ไป auth.users
courses.created_by      UUID DEFAULT auth.uid()    ← ไม่มี FK
courses.updated_by      UUID                       ← ไม่มี FK
rag_documents.source_id UUID                       ← ไม่มี FK
```

ความสัมพันธ์มีอยู่จริงในการออกแบบ แต่ **ฐานข้อมูลไม่รู้จักมัน** จึงไม่มีเครื่องมือไหน
วาด ER ให้อัตโนมัติได้ — `docs/database/er_supabase.svg` ที่มีอยู่ต้องเดาจากชื่อคอลัมน์

**นี่คือสาเหตุจริงที่ ER ฝั่งนั้นออกมาบาง ไม่ใช่เพราะ Supabase** และแก้ได้ด้วย SQL ไม่กี่บรรทัด
โดยไม่ต้องย้ายฐานข้อมูล (ทาง 1)

> หมายเหตุ: การเพิ่ม FK กับฐานข้อมูลที่ใช้งานอยู่เป็นการแก้ schema จริง
> ถ้ามีแถวที่ `created_by` ชี้ไปหา user ที่ถูกลบแล้ว คำสั่งจะไม่ผ่าน
> ต้องตรวจแถวกำพร้าก่อน และควรลองบนโปรเจกต์ทดสอบก่อนเสมอ

## ลำดับที่แนะนำ

```
ตอนนี้    เติม FK ที่ Supabase (ทาง 1)      → แก้ปัญหา ER ที่บ่นกันอยู่ · ชั่วโมงเดียว · ไม่แตะโค้ด
ควบคู่    ขอ repo หน้าเว็บ + ขอเป็น member    → ปลดล็อกทาง 2 และ 3 ซึ่งเริ่มไม่ได้ถ้าไม่มี
หลังส่ง   ตัดสินใจว่าจะเดินทาง 2 ต่อไหม       → ตอนนั้นข้อมูลครบแล้วค่อยคิด
```

**ยังไม่เริ่ม migration** จนกว่าจะได้รับอนุมัติจากเจ้าของโปรเจกต์อย่างชัดแจ้ง

## ที่มาของตัวเลขทุกตัวในเอกสารนี้

| ข้อมูล | ตรวจจาก |
|---|---|
| schema, จำนวนแถว, FK, CHECK, index, vector | query `pg_class`/`pg_constraint`/`pg_index`/`pg_attribute` บน production (อ่านอย่างเดียว) |
| ตัวดำเนินการ cosine `<=>` | `backend/app/services/vector_search.py:24,27` |
| สัญญา bge-m3 / 1024 | `pipeline/crawl/approve.py:75-76` |
| Supabase: ตาราง, คอลัมน์, 768 มิติ, RPC, Edge Function | source ใน `webapi/api/**` + bundle ของ SPA + `docs/database/schema.json` |
| Supabase: 7 FK / 2 CHECK / 4 UNIQUE | `supabase_schema.sql` ในรีโป `FoMake/Univercity` |
| ผู้ให้บริการ · shape · ภูมิภาค | cloud-init `cloud-id=oracle` · OCI instance metadata · RDAP ของ IP สาธารณะ |
| FastAPI ไม่มี reset/verify/email/lockout | `grep` ใน `backend/app` — 0 ไฟล์ทั้งสี่เรื่อง |

ยังยืนยันไม่ได้: **RLS policy ของ Supabase** · **จำนวนแถวจริงฝั่ง Supabase** ·
**Storage bucket** — ทั้งสามต้องเข้า Supabase dashboard
